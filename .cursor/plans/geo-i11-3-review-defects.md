### Уточнение D1: причины policy support и решения без пути поля

**Что установлено по callers.** Прямые конструкторы PolicySupportFact, найденные в backend, находятся в тестах и передают uid/state с пустым issues. Однако evaluate_stage уже имеет ветвь передачи непустого support.issues в PolicyProblem. При пустой коллекции для MISSING, FAILED и CYCLE он создаёт собственную причину, используя UID. В failure внешний PolicyProblem.reason выбирает fallback, а вложенные issues доходят до решения. Поэтому сохранение причины и выбор исхода проверяются отдельно. По прямым вызовам установить фактический набор типов внешних причин для restore нельзя.

**Предложение.** Разделить ошибки чтения поля (PolicyTypeError с CheckedPath) и причины операции policy. Для RULE_NO_MATCH вернуть типизированную причину с кодом и стадией BEHAVIOR; для RULE_CONFLICT сохранить стадию и идентификаторы правил с равным приоритетом; для MISSING_SUPPORT, FAILED_SUPPORT и DEPENDENCY_CYCLE сохранить код и support UID. Эти варианты принадлежат dataModel/policy. Пустой путь в policyResolver и псевдопути rules/<id>, supports/<uid> заменить типизированным контекстом. Предлагаемый закрытый union для собственных причин policy состоит из field issue и этих вариантов операции. Возможные внешние причины добавлять в контракт support после проверки producers и readers, включая decode и непрямое создание. Не сужать существующий вход только на основании пустых fixtures.

**Критерий для D2.** Ввести пробу с FAILED support и непустой типизированной причиной: при validate результат UNRESOLVED, причины сохраняют concrete type и контекст. Для той же spec в runtime сравнить исход при наличии и отсутствии fallback по FAILED_SUPPORT. Отдельно проверить RULE_NO_MATCH, конфликт правил и отсутствие support: восстановить решение и сверить код, stage/UID/rule IDs и порядок причин. Для ACCEPTED/PENDING/DISABLED проверить прежнее поведение. Эти пробы предлагаются к реализации; текущий анализ статический.

**№3. Чтение и выбор исхода принадлежат policy, содержимое переданной причины — её производителю.** При отсутствии экземпляра PolicyReader.read уже выбирает UnknownFact. Для FAILED сверить код, конкретный класс, root, segments и message вложенной причины после сериализации решения в обоих состояниях. Для UnknownFact проверить тот же путь отдельно.

**Сверка последствий с принятыми контрактами.** Этот вывод уточняет предварительные предложения о закрытом union и JSON restore выше.

- **№1/2.** Два локальных коллектора принимают только результаты собственных проверок water design. Геометрия вызывается уже после raise_if_any внешнего коллектора. Её ошибки могут пройти к caller отдельно. В scoped D1 singleton admitted применим именно к этим двум коллекторам. Общий PlanBuildFailure остаётся междоменным транспортом C0-9. Для loc, который CheckedPath.from_pydantic_loc не разрешает, требуется отдельная классификация F02 или доказуемая привязка инварианта к полю. Для двух адресуемых loc №1 такой развилки нет. [ERROR-CONTRACTS-1, C0-3/5/9](error-contracts-1.md#L799)
- **№3, владение типом.** PolicyTypeError подходит для отсутствующего binding, где модель и поле известны. У общего UnknownFact есть другие producers: hydrologyPolicyFacts._unknown использует target, nativeFinalWaterQuery — координаты, proceduralSourceAdmission — отсутствие bounds, surfaceCoatingSupport — клетку и канал. PolicyReader.read передаёт уже полученный UnknownFact без преобразования. Сужение UnknownFact.issue до PolicyTypeError либо включение water design в закрытый union общей policy потребует миграции чужих producers и обратной зависимости. Для транзитных *полевых* причин применять C0-9: carrier принимает именованный concrete instance и ревалидирует по его собственной схеме. Для собственных неполевых причин policy использовать отдельные варианты операции рядом с carrier. Их код и контекст определяет policy. Происхождение внешнего FAILED support нельзя выводить из теста. Для регрессии достаточно test-only concrete issue с отличимым enum; привязки к WaterDesignTypeError в общей модели не требуется. [C0-9](error-contracts-1.md#L807) · [Пример внешнего producer](../../backend/app/application/worldData/generators/hydrology/policy/hydrologyPolicyFacts.py)
- **№3, сериализация.** Локальная проба на текущем коде: PolicySupportFact(FAILED) принял непустой test-only concrete field issue и сохранил его класс. model_validate_json(model_dump_json(), strict=True) отверг вложенный dict. Этого требует C0-9. SerializeAsAny сохраняет поля concrete instance при выводе; для обратимого хранения нужен canonical decode по type_id, который собирает вложенный экземпляр до валидации родителя. Вторая проба, encode(ValidatedFieldPath, SURFACE_MANIFEST), дала CanonicalEncodingError «unregistered canonical record/enum type». В D2 проверить замыкание реального payload: сам issue, enum кода, ValidatedFieldPath, ModelIdentity, использованные сегменты, специализацию родителя и allowlist для model identity при холодном чтении. ID 106, 213 (UnknownFact) и 273 (water admission) по отдельности этого не обеспечивают. Проверять encode → cold decode → encode решения с исходными bytes и конкретной причиной. Для support как промежуточного входа достаточно строгой ревалидации экземпляра и проверки односторонней JSON-проекции, пока не установлен собственный persisted boundary. A0-F1 уже согласовал пересоздание данных и обновление manifests в том же срезе.
