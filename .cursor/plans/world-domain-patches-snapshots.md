## 0. Базовая политика runtime/worldEdit

- Один доменный resolver для import/runtime и worldEdit; patches и snapshot
  не вводят своего policy engine, отдельного worldEdit mode/endpoint/pipeline.
- `validate_only=true` — тот же DAG pipeline без публикации pack, commit

- Consumers, unresolved-результат, reason/action и проверки двух режимов
  фиксируются в доменных пунктах плана при приёмке.

  [`docs/tz_logging.md`](../../docs/tz_logging.md), существующий фасад

## 1. Общая архитектура — главное и критическое требование

**Каждый пункт плана, контракт и будущая реализация обязаны соответствовать
этой архитектуре. Нарушение границ ответственности блокирует реализацию
и приёмку шага. Сначала согласуется архитектура, затем определяются
конкретные типы, классы, файлы и реализации.**

Каждый архитектурный пункт принимается мастером отдельно. Для приёмки нужны
определённая ответственность, границы контракта, поведение и проверяемый
результат; перечня классов/папок или общего согласия с направлением недостаточно.
Уточнение требования к пункту не означает приёмку его ещё не описанной архитектуры.

**Критическая проверка каждого класса Patch:** при изменении доменного CRUD
и сохранении публичного контракта модификации Patch совершенно не меняется.
CRUD принадлежит домену; Patch используется для описания модификации.
Проверка обязательна для каждого класса, а не только для базового интерфейса
или одной представительной реализации. Непроверенный класс не принимается.
Если проверка не проходит, это проблема реализации и нарушение критического
архитектурного требования. До устранения дефекта не принимаются затронутый
класс, шаг и план целиком; остальные успешные проверки этот отказ не перекрывают.

**Критический запрет обхода Snapshot:** Patch не записывает мутацию напрямую
в БД или опубликованное состояние, в том числе через вызов существующего
CRUD writer, repository, callback или вложенного сервиса. Подготовка и кэш
не должны изменять authoritative state. Физическое размещение
недостижимых staged blobs/SQL rows разрешено доменной materialization по
вызову DAG через общий staging port: оно не продвигает active heads,
не активирует pack и не означает применения patch. После старта gameplay
опубликованное изменение SQL/pack state допускается только внутри
Snapshot-owned применения подготовленного PatchSet, без самостоятельного
commit домена. До старта gameplay подготовленный bake публикуется через
общую CAS-активацию pack по вызову DAG, без Snapshot (§7.2).
Схема «сначала CRUD сохранил, потом Snapshot записал историю» нарушает
этот gate; version stamp сам по себе её не исправляет.

**Критический запрет оркестрации в Snapshot (мастер, 2026-10-27):**
Snapshot применяет и сохраняет только уже подготовленные изменения.
Применение не является вызовом materialization. Snapshot не инициирует
planning, materialization, bake/refine или достроение отсутствующего
результата — ни напрямую, ни через domain apply/storage, callback или
вложенный сервис. Если Snapshot начинает materialization сам, это перенос
оркестрации из DAG и критический баг. Отсутствующий или несовместимый
подготовленный результат даёт явный отказ; Snapshot не достраивает его.

**Критический запрет самостоятельного сохранения доменом:** домен
подготавливает типизированный результат и patch по внешнему вызову, но
не инициирует сохранение patch, его истории или описанного им изменения.
Домен сам сохраняет patch — критический баг. Доменная реализация
применения изменений к опубликованному runtime SQL/pack состоянию вызывается только Snapshot при применении подготовленного набора;
владение реализацией хранения не даёт домену права инициировать publication
или commit. Staging является отдельным подготовительным IO (§7.2),
не опубликованной записью состояния и не альтернативным apply entry.
Временное удержание результата в patch/PatchSet не является сохранением
patch в authoritative storage и не обходит это ограничение.

**Неизменяемое добавляемое состояние (мастер, 2026-10-27):** изменение
SQL-данных состояния создаёт новые записи/версии, изменение pack — новые
immutable артефакты. Существующие исторические записи и pack не
перезаписываются. Delete доменного объекта отражается новым историческим
изменением/маркером удаления, а не физическим удалением прежнего состояния.
Patch хранит историчность перехода для SQL и pack; Snapshot оборачивает
набор patches и единственный применяет его как согласованное состояние.
Конкретные format/storage/commit механизмы ещё требуют приёмки.

```text
DAG → domain.read(query) → типизированный доменный результат
DAG → domain.patch(change) → подготовленный patch без изменения состояния
Debug API → тот же DAG; DAG → PatchSet → Snapshot → применение и сохранение состояния/истории
```

Контракт чтения принадлежит соответствующему домену. DAG вызывает его
реализацию напрямую. WS не задаёт domain read contracts, не оборачивает
и не маршрутизирует вызовы. Центральный WorldStateService/IWorldStateRead
и обязательный WS-посредник в read/patch цепочке исключены.
Прямой доступ WS к БД запрещён, в том числе через WS storage adapters,
DB-bound context или собственный SQL UOW.

Домен владеет своими данными, контрактами read/patch, правилами изменения,
валидацией и доменной реализацией поведения patch. Подготовка patch не
изменяет сохраняемое состояние. **Применяет patches только Snapshot**:
он вызывает доменную реализацию поведения в своём lifecycle применения.
Доменные правила остаются у домена; самостоятельного входа apply/persist
для DAG/debug API или домена нет. DB/file IO остаётся за storage-портами.

Generator получает подготовленные inputs/актуальный план и возвращает
доменный результат. Он не читает WS/БД, не формирует patches, не собирает
PatchSet, не сохраняет состояние или историю.

Только DAG собирает доменные patches в PatchSet и передаёт его
Snapshot. Debug API вызывает тот же DAG и не собирает собственный PatchSet. Snapshot — единственный владелец применения набора, сохранения
результирующего состояния и общей истории операций. Отдельный общий patcher
как самостоятельный вход применения исключён. Доменные алгоритмы, сбор
набора и запуск materialization не переносятся в Snapshot.

GEN DAG обязателен: production вызывается через DAG; debug API — тонкий
инструмент разработчика, вызывающий тот же граф DAG (своего порядка стадий
не держит). Product
CRUD/import нельзя объявить debug-входом для обхода этой границы.
Существующий Gate: DAG G1–G5 не снимается.
Конкретный связанный **план**, а не только ТЗ —
[GEN-DAG-1](gen-dag-1-post-geo-ws.md). Межстадийное управление (выбор,
порядок, зависимости, scope, planning/materialization) принадлежит DAG.
CRUD и его реализация принадлежат генераторному домену. Patch не заменяет
CRUD и не получает спрятанный pipeline через validate/build_result или
вложенный сервис. Внутренние вычисления одной атомарной доменной операции
допустимы; обёртка над несколькими независимыми стадиями — нет.

## 2. Ответственности и потоки

`read`/`patch` ниже — архитектурные операции, не утверждённые Python signatures.

| Владелец | Ответственность |
|---|---|
| DAG | Когда вызвать read/изменение/materialization; порядок доменных операций; сбор PatchSet |
| Debug API | Тонкий developer entry: вызывает тот же граф DAG; своего порядка стадий/сбора не держит |
| Domain read | Данные и domain-owned результаты, missing/fallback/merged/raw semantics; обращение к своей инфраструктуре |
| Domain change/planning | Реализация write-free create/update/delete: смысл изменения, validation, подготовленный typed результат, зависимости и invalidation; запуск по вызову DAG (в том числе по запросу Debug API через DAG) |
| Domain patch preparation | Формирует frozen typed patch из prepared domain result без изменения опубликованного состояния; сам Patch — только данные |
| DomainSectionHandler | Доменная application-реализация apply/merge; вызывается только Snapshot, не является методом Patch и не инициирует commit |
| Generator/materializer | Pure compute из актуальных prepared inputs; domain output для последующего сохранения |
| Snapshot lifecycle | Единственный владелец применения PatchSet; сохранение результирующего состояния и общей истории; immutable identity/lineage |
| Domain storage (published state) | Реализует добавление новых SQL/pack версий по вызову Snapshot при runtime apply; не публикует состояние и не коммитит набор самостоятельно |
| Domain staging | Доменная materialization по вызову DAG размещает только недостижимые staged blobs/SQL rows через общий staging port; leases, holder handoff и GC принадлежат общему ядру |
| Snapshot storage | Собственное хранение общей snapshot metadata/истории за storage-портом; не реализует SQL/pack запись доменов |

Read не запускает generate/refine. Изменение metadata/planning само по себе
не запускает materialization. Домен определяет актуальность/инвалидацию
зависимых представлений; materialization — отдельный явный запрос.
Snapshot save сохраняет уже имеющиеся результаты, не достраивает мир.

Поток planning/materialization до Snapshot:

```text
DAG → domain planning → prepared typed plan/revision → Patch / PatchSet (кэш)
DAG → domain materialization(готовый plan/revision, scope, LOD) [только по запросу]
    → prepared typed materialization → Patch / PatchSet (кэш)
DAG → Snapshot.apply(подготовленный PatchSet)
    → domain storage по вызову Snapshot → новые версии SQL/pack и история
```

DAG фиксирует порядок и зависимости вызовов; план строит домен. Patch
захватывает результат planning, его inputs/dependencies/revisions и
исторический переход, а не исполняемые стадии. Materialization является
отдельной доменной операцией из готового плана; её результат подготавливается
для последующего сохранения. Snapshot может сохранить metadata/planning
без materialization. Добавление представления другого scope/LOD само по
себе не требует новой semantic revision исходного плана.

Владелец применения закреплён: только Snapshot. Поведенческие гарантии
atomicity/commit закреплены в §8.1; точные порты/backend protocol — §8 шаги 2–3.
Prepared patch нельзя объявить уже применённым,
а запись отдельного домена — атомарным commit всего набора/хода.

### 2.1. Две фазы: домен владеет реализацией, но не инициирует их

Согласовано мастером: **домен реализует подготовку модификации и физическое
сохранение своих данных в SQL/pack. Самостоятельно фазы не инициирует и
не переключает.** Domain CRUD и storage logic не переносятся в Patch,
Snapshot или DAG. Эти две фазы описывают изменение **опубликованного**
runtime-состояния: write-free CRUD preparation не исключает отдельного
staging больших результатов materialization по вызову DAG. Staging сохраняет
только ещё не опубликованные данные; до gameplay pack активирует общий
CAS-механизм, после gameplay PatchSet применяет Snapshot (§7.2).

| Фаза | Кто инициирует | Что реализует домен | Результат |
|---|---|---|---|
| Подготовка | DAG по публичному domain CRUD контракту (включая запрос Debug API через DAG) | Read/validation и расчёт create/update/delete в рамках выбранной операции, без записи состояния | Typed prepared domain result или явный отказ/конфликт |
| Применение/сохранение | Только Snapshot при применении PatchSet | Проверка применимости и добавление подготовленных SQL-версий/pack-артефактов через свой storage контракт | Typed результат записи и references для согласованного состояния/истории |

Create подготавливает новый объект с предусловием отсутствия; update —
переход от исходной версии; delete — историческое логическое удаление.
Конкретные request/result типы принадлежат домену и семантике операции.
Подготовка не вызывает запись автоматически; доменная запись не вызывает
свою подготовку повторно, не запускает соседние стадии и не коммитит весь
PatchSet самостоятельно. Поведение commit/publication принято в §8.1;
его точный storage protocol замораживается до кода по §8 шагам 2–3.

```text
Debug API → DAG (тот же граф, без собственной сборки)
DAG → domain CRUD preparation → prepared domain result
         → domain Patch → PatchSet (возможен временный кэш)
         → Snapshot → domain storage implementation → SQL/pack новые версии
                    → согласованное состояние и общая история
```

Patch принимает подготовленный typed результат и описывает его исторический
переход. Он не вызывает изменяющий CRUD повторно и не содержит repository,
writer callback/SQL-команду или самостоятельный commit. Snapshot вызывает
доменные контракты применения/записи, но не воспроизводит mapping, SQL,
pack layout или бизнес-логику домена. Реализация хранения остаётся целиком
у владельца домена; Snapshot владеет моментом её вызова и согласованностью
набора. Собственная snapshot history storage отделена от domain persistence.

Критическая приёмка для каждого Patch/пути: подготовка не изменяет
опубликованные SQL/pack и active heads; если materialization использует
staging, staged blobs/rows остаются недостижимыми до публикации.
Runtime-применение инициировано Snapshot и делегировано домену; отсутствуют
автоматический переход между фазами, самостоятельный commit и повтор
бизнес-операции. Первичный bake проверяется отдельно как pack activation
без Snapshot (§7.2).

Для каждого класса Patch и каждого пути Snapshot обязательна также проверка
всей вложенной цепочки вызовов:

- planning-only набор сохраняется без единого вызова materializer/bake/refine;
- набор с готовой materialization сохраняет переданный результат без её
  повторного вычисления;
- отсутствующий, stale или несовместимый обязательный результат вызывает
  явный отказ, без planning/materialization fallback внутри Snapshot;
- domain preparation и создание/кэширование patch не сохраняют patch,
  историю или опубликованное состояние и не вызывают применение
  самостоятельно; staging materialization проверяется отдельно по §7.2;
- runtime domain storage опубликованного состояния вызывается только
  в lifecycle применения, инициированном Snapshot; домен не инициирует
  сохранение patch или commit набора. Pregame pack activation — §7.2.

Прямое или косвенное нарушение любого пункта — критический баг реализации;
приёмка класса, соответствующего шага и плана целиком блокируется до
исправления и повторной проверки. Отложить нарушение как технический долг
или скрыть его внутри доменного сервиса нельзя.

## 3. Patch и PatchSet по доменам

**Общий контракт модификации задаёт поведенческие обязанности домена,**
а конкретный Patch — только frozen typed данные изменения (M-1).
Одной оболочки с domain/target/payload недостаточно: домен обязан явно
определить target, предусловия, семантику операции и её результат.
Применение и merge выполняет доменная application-реализация
`DomainSectionHandler` по вызову Snapshot (M-2), а не методы Patch.
Target, доменные операции и payload принадлежат владельцу домена.
Patch не является SQL-строкой, DB row, raw dict или CRUD callback.

### 3.1. Общие вопросы поведения Patch

Приёмка интерфейса требует явного контракта по каждому вопросу ниже.
Точные Python signatures и concrete storage implementations определяются
после архитектуры; поведенческие обязанности не откладываются на этот этап.

| Общий вопрос | Что обязан определить интерфейс / реализовать домен |
|---|---|
| Что изменяется? | Адресат, вид изменения metadata/planning/materialization и затронутый scope; домен сообщает свои данные в согласованной форме |
| К какому состоянию применимо? | Как задаются и проверяются предусловия/ревизии; домен проверяет своё состояние, конфликт выражается явным результатом |
| Как проверяется допустимость? | Граница validation и её side effects; домен проверяет свои правила и возвращает диагностику по общему контракту |
| Кто и когда применяет изменение? | Только Snapshot инициирует runtime-применение; подготовка не пишет опубликованное состояние, доменная реализация выполняется внутри snapshot lifecycle; commit outcome определяется общим протоколом; pregame pack activation — §7.2 |
| Что возвращает применение? | Общие категории результатов и их смысл: изменение, отсутствие изменения, отказ/конфликт; доменный payload и effects сохраняются в typed результате |
| Что происходит при отказе/ошибке? | Какие отказы ожидаемы, как передаётся ошибка, что происходит с уже выполненными effects; домен соблюдает согласованную границу атомарности |
| Что означает повторное применение? | Как определяется повтор/идентичность операции и результат retry; домен реализует согласованную политику без скрытого повторного изменения |
| Каковы зависимости и последствия? | Как сообщаются порядок/зависимости и последствия для planning/materialization; домен определяет содержимое effects, общий механизм не угадывает их |
| Что передаётся snapshot? | Как операция, результат, версии и соответствующие данные/ссылки представляются для общей истории; домен предоставляет свою секцию |

Общие поведенческие правила по этим вопросам приняты в §8.1.
Конкретные domain/operation bindings и типы проходят отдельный freeze;
общая архитектурная приёмка не является приёмкой каждого доменного контракта.
Решения мастера 2026-10-27 (`docs/tz_world_snapshot.md` п. 14–19):
- **Предусловия:** ядро задаёт слот «ожидаемая версия цели»; заполнение —
  ревизии §6 (§8 шаг 5). Несовпадение — явный исход «конфликт», не исключение.
- **Commit:** PatchSet сам не коммитится и не имеет частичного commit секций;
  полноценный commit — только commit Snapshot, набор фиксируется им целиком.
- **Отложено:** контракт результата apply/effects со стороны DAG — до перехода
  DAG на pydantic.
- **История (§3.5):** ссылки на удерживаемые версии, без полных before/after.
- **Кэш (§3.3):** малое — память job, объёмное — staging по lease
  `operation_id`; lifetime = операция.
- **Расширение после старта:** «patches не было» проверяет DAG чтением
  pack + активного overlay; единица — тайл, локация — по footprint;
  гонку закрывает предусловие «цель отсутствует».
Таблица задаёт обязательный охват интерфейса, а не утверждает существование
idempotency/rollback/conflict механизмов. Общие гарантии обязательны всем
доменам; доменная реализация не меняет смысл общего результата молча.
Неприменимое поведение отражается явно в согласованном контракте.
Общий интерфейс не получает DB API, не интерпретирует доменный payload и
не определяет domain read. Сбор PatchSet остаётся только у DAG; Debug API не создаёт альтернативного пути.

Типизация конкретного Patch должна связывать домен, конкретную семантику
модификации, target, inputs, change и result. Интерфейс требует такую
декларацию от каждой реализации. Одного domain tag или пары произвольных
generic inputs/result недостаточно; разные операции внутри одного домена
не становятся взаимозаменяемыми. Существующие domain POJO переиспользуются.
Имена CRUD-методов, их аргументы, DB rows и количество физических записей
не определяют типы/формат Patch.

### 3.1.1. Гранулярность target, частичные дельты и runtime-версии

**Решение мастера 2026-10-30:** система Patch/Snapshot поддерживает
модификации любого объявленного доменом масштаба: от минимальной
изменяемой сущности (стена, блок, семантически адресуемый чанк/часть)
до целого объекта или агрегата (дом, локация и т. п.). Единый для всех
доменов минимальный размер target и обязательный generic field path не
вводятся. Домен владеет typed identity цели, структурой вложенности,
областью воздействия и правилами пересечения целей. Чанк как физическая
единица LOD не превращает семантический Patch в зависимый от LOD формат
(`docs/tz_world_snapshot.md` п. 3).

**Частичная доменная дельта перекрывает только явно затронутую часть
состояния.** Неизменённые части объекта сохраняют прежние значения;
изменение стены не является неявным replace всего дома. Полнообъектная
модификация/replacement допустима, но объявляется как отдельная явная
доменная семантика с её предусловиями. Алгоритм apply/merge определяет
домен, а не общий Snapshot/Patch Store через `dict.update`/last-write-wins
всего payload. Домен также определяет семантику вложенных изменений и
пересечения target (например, операция над домом и над его стеной).

Для runtime-состояния **версия конкретной цели** логически определяется
последним зафиксированным Snapshot активной линии, который изменил эту
цель/область воздействия; для ещё не изменённого содержимого опора —
соответствующая удерживаемая версия исходного pack/состояния.
Snapshot другого тика, не затронувший цель, не меняет её version stamp.
Patch передаёт ожидаемую версию/отсутствие цели, а domain handler при
Snapshot apply сверяет её с актуальным состоянием и пересечением затронутых
целей: несовпадение — явный конфликт. Это ссылка на существующую
immutable snapshot-историю, а не новая независимая система счётчиков
SourceRevision; исходные авторские/source-изменения продолжают пользоваться
своими SourceRevision (§6). Общий CAS `(pack_hash, snapshot_head)` по-прежнему
проверяет атомарную публикацию всего тика независимо от target-level
предусловий. Конкретный тип version stamp и проверка нескольких операций
одного PatchSet — предмет contract freeze, не готовая реализация.

Пример: Snapshot `x1` содержит/удерживает исходное состояние дома с
четырьмя стенами; `x42` несёт операцию разрушения одной стены. Чтение
`as-of x1` восстанавливает четыре стены, `as-of x42` — три; `x42`
не заменяет остальные стены и не переписывает `x1`. Если последующие
snapshots дом не меняли, его runtime stamp остаётся `x42`. Обычное чтение
использует базовый pack + текущий скомпактированный overlay, историческое —
keyframe + дельты, без проигрывания всех тиков на каждом read.

### 3.2. Набор patches

```text
PatchSet
└── sections
    ├── terrain   → terrain patches
    ├── climate   → climate patches
    ├── regions   → region patches
    └── locations → location patches
```

Домены в примере не исчерпывают всю систему. Набор секционирован, не плоский
универсальный payload. Snapshot вызывает domain implementation, не разбирая
чужие доменные поля и не воспроизводя их алгоритмы.
Порядок patches внутри секции определяет домен; междоменные зависимости
и порядок секций задаются явно. Самостоятельной сортировки, hidden retries
или частичных успешных commit общего набора по умолчанию нет.

Patch может описывать сохранение metadata/planning либо результата
materialization. Эти виды изменения различимы в контракте домена;
их нельзя свести к generic upsert клетки или целой DB row.

### 3.3. Временный кэш результатов в PatchSet

Решение мастера: PatchSet может временно кэшировать подготовленные доменные
результаты, включая metadata/planning и результат materialization, для
дальнейшей передачи в Snapshot. Кэш не применяет patches и не изменяет
зафиксированное состояние. **Применение выполняет только Snapshot.**

Результат в кэше связан со своим patch, доменом и исходными inputs/revisions;
его нельзя подменить результатом для другого изменения. Наличие результата
не означает applied/committed outcome. PatchSet — временный носитель до
передачи; authoritative состояние и история фиксируются Snapshot.

Ownership/lifetime, передачу данных/refs, проверку соответствия patch,
поведение при отказе/повторе и освобождение задаёт принятый §8.1.
Малый кэш в памяти не переживает restart; наличие durable staged refs
само по себе не гарантирует resume всей операции. Для resume нужны
сохранённые inputs/refs и контракт операции, замораживаемый в §8 шаге 2.
Transient cache не включается в authoritative snapshot как отдельный store.

### 3.4. Независимость от CRUD — приёмка каждого класса Patch

Для **каждого конкретного класса Patch** в implementation map должны быть
указаны его domain/семантика, публичный контракт модификации, связанные типы
и отдельный сценарий проверки независимости от CRUD.

Проверка выполняется так:

1. Зафиксировать класс Patch, его типы/сериализованный формат и публичный
   контракт доменной модификации, используемый при snapshot apply.
2. Заменить реализацию доменного CRUD с сохранением этого контракта:
   например, изменить storage backend, внутренние методы, batching или
   разложение модификации на физические записи. Сопоставление с новым CRUD
   меняется внутри реализации домена.
3. Применить тот же Patch через Snapshot с прежними публичными входами.
   Проверить наблюдаемую семантику изменения, результаты и отказы по
   согласованному контракту, а не совпадение внутренних CRUD-вызовов.
4. Подтвердить отсутствие изменений кода класса Patch, его декларации типов,
   payload, format version и bindings PatchSet/Snapshot. Для такой замены
   не требуется миграция уже подготовленных/сериализованных patches.

Если изменение CRUD требует правки Patch при сохранённом публичном контракте,
граница ответственности нарушена: класс не принимается до устранения связи.
Это дефект реализации, блокирующий приёмку всего плана. Нельзя закрыть план
с таким дефектом, перенести его в отложенный долг или ослабить проверку ради
приёмки. После исправления проверку затронутого класса выполняют повторно.
Нетипизированный CRUD callback/имя метода в payload не считается развязкой.
Изменение самой семантики публичного контракта — другой случай, требующий
отдельного versioning/compatibility решения; им нельзя оправдывать CRUD coupling.

Evidence должно адресовать каждый класс по имени и сценарию. Общий
contract-test допустим как переиспользуемый механизм, но он должен быть
исполнен для каждого класса; один smoke на домен не заменяет эту проверку.
При этом прослеживается фактическая цепочка вложенных вызовов класса:
типизация и functional pass не оправдывают скрытую межстадийную оркестрацию.
Это дополняет независимость от CRUD; per-node приёмка GEN-DAG-1 остаётся
отдельным обязательным gate будущей DAG-интеграции и этим аудитом не закрывается.
Классы/тесты ещё не созданы: это обязательная будущая приёмка, не выполненный test.

### 3.5. Историчность patch для SQL и pack

Patch должен описывать типизированный исторический переход: identity
изменяемого объекта/части состояния, исходную версию/отсутствие, доменную
модификацию и новую версию/результат. Для materialization сохраняются
удерживаемые ссылки на соответствующие immutable pack-артефакты и их
dependencies. Наличие SQL-данных и pack — разные storage representations
одной истории, а не два независимых механизма изменений.

История должна сохранять различие create/update/delete, исходного отсутствия
и удаления. По принятому решению история перехода удерживает ссылки на
версии (pack либо предыдущие дельты цепочки), а не полные копии
before/after. Одной ссылки на mutable latest недостаточно.
Старая версия должна оставаться доступной для выбранного snapshot;
частичная дельта не должна стирать незатронутые части прежнего состояния
(§3.1.1).

Это требование к данным patch, не право patch писать историю самостоятельно.
PatchSet может держать подготовленные результаты в кэше. Snapshot принимает
набор, проверяет применимость и через storage-контракты добавляет новые SQL
версии/pack-артефакты и фиксирует их совместное состояние/историю. Старый
snapshot и его данные остаются неизменными. Хранение immutable ссылок не
означает обязательного копирования всего pack для каждой операции.

Приёмка каждого класса Patch включает сохранность прежнего SQL/pack
состояния после изменения и наличие достаточной истории перехода.
Прямые UPDATE/DELETE старого состояния, in-place pack rewrite или история,
ссылающаяся только на latest, блокируют приёмку. Возможный отдельный prune/GC
не является доменным delete; его политика хранения согласуется отдельно и
не даёт мутации права потерять удерживаемую историю.

## 4. Snapshot по доменам

```text
Snapshot
├── общие metadata: identity, parent, привязка к операции/ходу, format version
├── состояние по доменам
│   └── <domain>
│       ├── metadata / данные планирования
│       └── имеющаяся materialization или удерживаемые ссылки на неё
└── PatchSet
    └── patch-операции по доменам, приведшие к этому состоянию
```

Это логическая структура; физическое хранение пока не выбрано.
Единая snapshot-история секционирована по доменам; самостоятельные terrain/
climate/region snapshot stores не вводятся. Existing world/player chains
сохраняют свою отдельную предметную семантику; секция домена не новая timeline.
Решение мастера 2026-10-27: изменения world/player одного тика имеют единый
атомарный commit Snapshot. Проверка исходных heads, новые записи обеих цепочек
и продвижение обоих heads входят в одну SQL-транзакцию; конфликт/сбой любой
стороны не публикует ни одну. Правило распространяется на scope migration.
При attach session-домен восстанавливает binding этого игрока из целевого
snapshot с проверкой позиции; при отсутствии binding использует spawn-анкор
целевой ветки. Невалидность даёт явный отказ без публикации; поиск ближайшей
валидной точки требует отдельных правил и не входит в принятую политику.

Домен определяет формат и подготовку/восстановление своей секции.
Snapshot lifecycle сохраняет общую структуру и историю через storage ports.
Он же единственный применяет переданный PatchSet; DAG/domain preparation
не изменяют состояние до этого. Применение создаёт результирующее состояние,
а не переписывает уже зафиксированный snapshot.
Snapshot immutable; изменение создаёт последующее состояние/ветку.
Журнал patches не заменяет authoritative данные состояния при restore:
восстановление не требует неоговорённого replay всей истории.

## 5. Структура исходников по ответственности

Пути ниже — целевая композиция namespaces, не список файлов к созданию.
`<domain>` сопоставляется существующим доменам после inventory, без
дублирования их моделей. Exact class/method/file map — после архитектуры.

```text
backend/app/
├── dataModel/
│   ├── patch/                  общий контракт Patch/PatchSet
│   ├── worldSnapshot/          identity, manifest, domain sections
│   ├── sourceVersioning/       existing design: identity/revision contracts
│   └── <domain>/
│       ├── patch/              доменные изменения
│       └── snapshot/           данные доменной секции
└── application/
    ├── worldSnapshot/          применение PatchSet, состояние и общая история
    └── <domain>/
        ├── read/               доменное чтение
        ├── patch/              подготовка и поведение patch для вызова Snapshot
        └── snapshot/           подготовка/восстановление своей секции
```

Read contract принадлежит dataModel/application ports своего домена,
реализация — application домена. Общего WS read namespace нет.
Storage implementations размещаются по своим существующим слоям, не
переносятся в application только ради приведённого дерева.
Snapshot domain payload не зависит от concrete snapshot storage.

## 6. Версионирование — переиспользование source versioning

Основа — [world-source-versioning](world-source-versioning.md), согласованный
design 2026-10-24. Его реализация ещё не готова; наличие плана не считается
работающим revision store/capture/publication. Второй механизм не вводится.

| Понятие | Роль |
|---|---|
| SourceObjectId | Стабильная identity source-объекта; existing source-versioning design задаёт discriminated union по категориям registry/library/entity, не новую identity на каждую revision |
| SourceRevision | Existing design `seq + content_hash`; семантическое состояние source-объекта |
| Авторский version label | Метка в теле, не identity и не замена revision |
| Planning fingerprint | Фактические effective inputs алгоритма, версии схемы/алгоритма и зависимости планов |
| Snapshot identity/parent | Узел immutable истории и его lineage; не версия source-объекта |
| Runtime target version stamp | Ссылка на последний Snapshot активной линии, изменивший target/затронутую область, либо удерживаемую исходную версию pack; не новая SourceRevision |
| Patch/Snapshot format version | Совместимость формата сериализации; отдельно от semantic revision |

Решение мастера 2026-10-27: общая оболочка Snapshot и каждая доменная секция
имеют собственную format version. Ядро поддерживает чтение старой оболочки,
домен-владелец — своих старых секций через upgrade при чтении. Сохранённая
история не переписывается; старые snapshots обязаны оставаться читаемыми.
Неподдерживаемый формат — явный отказ без пропуска секций, тихой деградации
и подмены latest. Это правило совместимости не меняет semantic revisions.

Обязательное переиспользование:

- В phase 0 черновые правки сохраняют правила source versioning: revision
  accounting ещё не вводится, но прежнее разрешение свободных SQL UPDATE
  не переносится в новый append-only state contract. Представление черновой
  истории требует согласования. В phase 1 семантическое изменение source
  создаёт новую revision независимо от in-flight. Label-only change не
  означает новую semantic revision; новая identity на каждую версию не создаётся.
- Snapshot закрепляет source revision set и удерживает нужные тела.
  Историческое чтение разрешает ссылки as-of/pinned, не по master latest.
  Player accepted set не подменяется latest мастера.
- Capture закрепляет значения и состав коллекций. Операция не переходит
  на latest посередине compute. Snapshot/artifact — долговечный holder;
  GC не удаляет удерживаемые ревизии/материализацию.
- Source revision и planning fingerprint различаются: нерелевантная для
  алгоритма правка не заставляет перестраивать план автоматически.
- Materialization сохраняет dependency stamps частей/планов. Сохранение
  производного результата само по себе не новая semantic source revision.
- Source mutation использует единую source-versioning boundary/ref-integrity
  через владельца домена. Snapshot/PatchSet не подменяют эту проверку.
- Не каждый runtime patch является source mutation: runtime-предусловия
  используют версии затронутых целей из immutable snapshot-истории (§3.1.1),
  а source mutation — SourceRevision. Домен определяет гранулярность,
  пересечения и применимость; механическое сравнение только общего head
  не заменяет проверку target. Общая source-versioning схема не объявляется
  готовой моделью всех runtime-состояний.

Поведение patch preconditions и runtime stamps принято в §8.1;
точные типы проходят freeze в §8 шаге 2, source revision-set binding —
шаг 5 после source-versioning 2–3. Правила capture-finalize, publication, CAS и
retention переиспользуются по смыслу с проверкой совместимости. Прежний
протокол изменения SQL pointer/latest через UPDATE требует пересмотра под
append-only commit; он не является утверждённым механизмом нового плана.
Snapshot должен закрепить согласованный набор SQL/pack версий без перезаписи
старого состояния. Concurrency/head: один CAS-указатель мира `(pack_hash, snapshot_head)`
(решение B-3, `docs/tz_world_snapshot.md` п. 8).
Одного SQL BEGIN для атомарности SQL+files недостаточно.

- ограничения на independent commits и доступность старых write entry points;
- согласованность результирующего состояния, source revisions и snapshot history

этим документом. Код в рамках данного аудита не изменялся.

### 7.2. Первичная materialization: обязательная сверка light_bake/full_bake

**Первый bake — job DAG** с domain materialization через staging и
публикацией pack (решение мастера 2026-10-27; не Snapshot apply). Для SQL и
pack действует append-only contract; bootstrap нельзя завершить прямой
записью мимо staging/публикации. Когда запускать bake (в т.ч. auto bake
мира без pack), решает DAG; `POST pack/bake` — caller того же job; gameplay
без опубликованного базового pack не стартует. Встраивание — GEN-DAG-1;
до него `POST pack/bake` — legacy. **B-2 открыт и блокирует приёмку плана:**
legacy route держит оркестрацию стадий (L0 → C23, finalize/публикация) вне
DAG; план не закрывается, пока bake job не встроен в DAG по GEN-DAG-1.

Сохраняются существующие product contracts (`tz_world_pack_storage.md`
§ Bake modes / Job boundaries и `tz_map_light_bake.md`):

| Режим | Подготовленный результат | Что не включается |
|---|---|---|
| light_bake | Общий L0 compose на named_locations ∪ declared hydro tiles, locations_index и climate coarse; прочие климатические результаты только по existing policy | L2, C23 topology, C11 packing, entry job |
| full_bake | Тот же L0 compose на весь world_bounds со швом мира; затем обязательный C23 plan_topology — второй шаг того же product job | L2, C11/settlement geometry, entry job |

Межстадийный порядок L0 → C23 задаёт DAG по GEN-DAG-1; это не основание
спрятать две стадии в Patch, Snapshot или generator CRUD. Локальные алгоритмы
одной стадии остаются в домене. Partial light pack допустим; вход игрока
не должен получить новую обязательную зависимость от полного full_bake.

При contract freeze проверить следующие границы на основе принятых решений 2026-10-27
(решения под списком имеют приоритет над его первоначальными формулировками):

1. **Исходное состояние:** от какого captured source/revision set строится
   первая materialization; как представлены исходно отсутствующие SQL/pack
   результаты и base snapshot. Наличие исходных world/location metadata не
   означает наличие предыдущей materialization; fake base не создаётся.
2. **Передача между стадиями:** как следующий шаг читает подготовленный L0
   из PatchSet cache/рабочего представления, если он ещё не опубликован.
   Для C23 нельзя предварительно публиковать L0 только ради чтения
   существующим методом. Domain input contract должен быть явным.
3. **Граница публикации:** до gameplay light/full job активирует новую
   immutable версию pack manifest только после обязательных стадий; это не
   Snapshot commit. Product full complete требует C23; промежуточный L0
   нельзя объявить завершённым full_bake. После старта gameplay новые
   результаты материализации фиксируются в Snapshot поверх замороженного pack.
4. **Bulk-результаты:** typed patches/results для batch/scope и immutable
   артефактов; не обязательный отдельный patch/CRUD-вызов на каждую клетку.
   Владение domain storage и per-class проверки независимости сохраняются.
5. **Публикация:** initial bake публикуется через pack activation, а не
   Snapshot. После gameplay изменения и materialization публикует только
   Snapshot; staged SQL rows/blobs недостижимы до соответствующего commit.
   Full после light до gameplay добавляет immutable manifest со ссылками
   на удерживаемые части, не стирая старый pack. Долгая подготовка отделена
   от короткой публикации; source pins и staging lifetime покрывают job.
6. **Приёмка:** first light, first full, light→full, partial light, source edit
   во время bake, отказ после L0/до C23 и между SQL/pack/history шагами,
   retry и отсутствие публикации до pack activation (до gameplay) либо
   Snapshot commit (после gameplay). Предыдущие состояния остаются читаемыми.
   GEN-DAG-1 per-node и Patch per-class gates обязательны.

**Решено мастером 2026-10-27 (п.2, п.4, п.5):** bake поставляет мир одним
замороженным pack; snapshot = patches тиков поверх pack, pack не
перезаписывает. Формулировка п.5 «initial bake … под Snapshot-owned
lifecycle» этим заменена: публикация bake — активация pack, не snapshot.
Staged blobs/SQL rows пишет доменная операция materialization через staging
port; Patch несёт hash-ref; L0 → C23 через «опубликованное + staged refs
job». Норматив — `docs/tz_world_snapshot.md` § «Staged artifacts и точки
публикации» (там же: граница — старт gameplay: до него bake дописывает
один pack, после — вся материализация и правки уходят в snapshot; overlay
без replay тиков; LOD-независимые patches; перепечки нет — только расширение: новые тайлы/локации на wilderness без patches). Новая игра продолжает цепочку world-snapshot. Один активный timeline на мир → один overlay; attach к другой ветке — пересборка overlay от keyframe (DAG). B-3, M-1, M-2,
keyframe, rebase (отвергнут), объём snapshot (dedupe по hash) решены там же
(п. 8–13). Схема `world_snapshots` — `docs/project_data_storage_tz.md`, пороги
keyframe — реализация. Перечисленные product-policy решения приняты;
это не отменяет freeze точных core contracts по §8 шагам 2–3.
End-to-end приёмку дополнительно блокирует B-2.

**Очистка staging при отказе (обязательный lifecycle):** staging SQL rows
с `artifact_id` и blobs не являются частью опубликованной истории. Операция
сохраняет lease по `operation_id`, пока выполняется или может быть
корректно возобновлена; active/resumable lease защищает staged данные от GC.
После подтверждённого терминального отказа/отмены/отклонения, остановки
writers и проверки terminal outcome общий owner освобождает lease; не
опубликованные и более никем не удерживаемые staged rows/blobs становятся
кандидатами на GC. При успешной публикации holder передаётся опубликованному
artifact/snapshot атомарно. `ready_inactive` и другие удерживаемые результаты
не очищаются как обычные сироты до решения об их retention. Recovery сначала
сверяет исход по `operation_id`; одного TTL или факта отсутствия активного
процесса недостаточно для удаления. GC не трогает опубликованную append-only
историю. Это уточнение существующего staging/holder/GC-контракта
`docs/tz_world_snapshot.md` § «Staged artifacts», не новый механизм.

Проверенные несовместимые existing paths: `pack/bake/l0/packMaterializationOrchestrator.py`
вызывает WorldPackWriter, `_persist_bake_relief_grades` и PackBakePublisher;
`pack/bake/finalize/packBakeFinalize.py` сохраняет manifest до repo.update(world);
`pack/io/worldPackWriter.py` пишет по целевым путям, включая os.replace.
Пути относительно application/worldData/. Эти механизмы сейчас не являются
Snapshot-owned append-only publication. Это вход migration inventory, не
разрешение переписать их в текущем документальном шаге или считать проблему решённой.

Согласование этого раздела — prerequisite implementation новых patch/snapshot
контрактов для первичного мира. Locked bake scope и DAG wiring сейчас не меняются.

Эти вопросы нельзя оставить разработчику «решить по месту». Concrete SQL,
DB-модели и имена existing services не заменяют архитектурного решения.

## 8. Последовательность проработки и приёмки

**Контрактная граница и готовность (решение мастера 2026-10-30):**

- **Архитектурный baseline принят.** Владельцы read, domain CRUD,
  planning/materialization, Patch/PatchSet, Snapshot, domain storage и
  staging определены. Это позволяет продолжать самостоятельную
  контрактную проработку и разработку ядра Patch/Snapshot; отсутствие
  целевой реализации GEN-DAG-1 не блокирует эти работы.
- **Не откладываются до GEN-DAG-1 контракты самого ядра.** До реализации
  соответствующих компонентов необходимо согласовать Patch/PatchSet
  (M-1), `DomainSectionHandler`/registry (M-2),
  `Snapshot.apply(PatchSet)`, artifact refs, staging/holder/GC,
  CAS/commit lifecycle, их поведенческие гарантии, ошибки и атомарность.
  Эти независимые от устройства DAG контракты замораживаются по шагам 1–3.
- **До фактической проработки и типизации нод GEN-DAG-1 отложены только
  DAG-интеграционные контракты:** точные входы/выходы нод, типизированный
  execution context, передача/агрегация доменных результатов между нодами,
  привязка этих результатов к формированию PatchSet и DAG-facing
  apply/effects. Не вводить умозрительные DTO и маршрутизацию входных
  данных вместо будущих контрактов реально выделенных нод. Это не
  разрешает переносить чтение, доменное объединение данных или логику
  хранения в DAG.
- **Граница приёмки:** готовность baseline не равна итоговой приёмке
  конкретных контрактов/классов. GEN-DAG-1 интегрируется после
  предусмотренных им gates; end-to-end приёмка Patch/Snapshot и закрытие
  B-2 возможны только после этой интеграции и всех обязательных проверок.

1. Проработать и принять каждый архитектурный пункт §1–6 отдельно, закрывая
   относящиеся к нему вопросы §7; только документы. Открытый вопрос поведения
   интерфейса не переносится в concrete implementation.
2. После приёмки — inventory переиспользуемых domain POJO/ports и contract
   freeze **ядра домена патчей**: Patch/PatchSet (только данные, M-1), порт
   `DomainSectionHandler` и реестр секций (M-2), вход Snapshot
   `apply(PatchSet)`, typed artifact ref, staging port, CAS-указатель мира
   `(pack_hash, snapshot_head)` (B-3); поля, результаты, диагностика, atomicity.
3. Подготовить implementation map: каждый класс → domain/layer → точный файл,
   направления зависимостей, folder composition/counts, existing backend binding.
4. Реализация ядра по слоям (решение мастера 2026-10-27): типы → shared infra
   (content-addressed staging adapter, lease, CAS-указатель мира) → Snapshot
   apply/commit → реестр секций в Container → первый доменный handler. Ядро —
   единственный владелец staging и CAS-указателя; world-source-versioning их
   переиспользует, второй механизм не вводится. Ядро не ждёт source-versioning
   и внешней DAG-интеграции.
5. §6 — привязка ревизий patch/snapshot после контрактов identity/revision
   world-source-versioning (его шаги 2–3).
6. Перевод существующих writer'ов на commit Snapshot / публикацию pack по
   inventory: `MapCellService`, `SettlementPersistService`,
   `ConnectionPersistService`, `region_states`/`StateChangeConsumer`
   (wilderness 9a/10a), write boundary entity-lifecycle L3. Новый прямой
   writer мимо Snapshot противоречит §1 и расширяет долг миграции.
7. Закрытие плана — после устранения B-2 (bake job встроен в DAG); это
   внешняя зависимость, не шаг этого плана.

Каждый implementation шаг — отдельно согласованный, с проверкой критического §1.

DAG wiring/backend-start/коммиты не добавляются этими подшагами автоматически.

### 8.1. Шаг 1 — принятые архитектурные правила (2026-10-30)

Статус: **ПОВЕДЕНЧЕСКИЕ ПРАВИЛА СОГЛАСОВАНЫ МАСТЕРОМ** (2026-10-30,
«Согласен с изменениями» после явного перечисления восьми предложений
и добавления общего домена логирования). Запрос на проверку формулировок
не меняет эти решения. Ниже они зафиксированы как обязательные правила
§1–6 до inventory/contract freeze и implementation map. Python signatures,
новые классы, DDL и DAG-facing DTO этим разделом не утверждаются.
Код не изменён; реализация и её проверки не объявлены принятыми.

**Реестр согласованных решений:**

1. **P-1 — порядок:** DAG передаёт явный порядок и зависимости секций;
   Snapshot только проверяет и исполняет их, неверный набор отклоняет целиком.
2. **P-2 — пересечения:** композиция patches пересекающихся целей требует
   явной доменной семантики; без неё — отказ всего набора.
3. **P-3 — prepared result:** обязательна связь с конкретным patch,
   inputs/revisions/dependencies; отсутствующее или несовместимое не достраивается.
4. **P-4 — исходы:** общий типизированный StrEnum ядра с членами
   COMMITTED / CONFLICT / REJECTED (wire values: committed / conflict /
   rejected); infrastructure failure и неизвестный исход не превращаются
   в успех. Голые str и параллельные доменные enum этих категорий запрещены.
5. **P-5 — retry:** один operation_id связан с одним неизменным запросом;
   terminal outcome возвращается повторно, иное содержимое отклоняется.
6. **P-6 — refs:** kind/format/hash/размер/удержание проверяются до публикации;
   неизвестная секция или невалидный ref отклоняют весь набор.
7. **P-7 — no-op:** фиксация тика не меняет stamp незатронутой цели
   и не разрешает частичный commit секций.
8. **P-8 — source binding:** отсутствие binding означает явную недоступность
   зависящей операции, не фиктивную revision или пропуск предусловий.
9. **L-1 — логирование:** только общий домен/фасад проекта по tz_logging.md;
   домен определяет смысл события, инфраструктура — его доставку.

Развёрнутые правила ниже уточняют P-1…P-8/L-1. Они не ослабляют §1,
§3.4 и действующие ТЗ. При расхождении формулировок требуется исправить
документ до implementation, а не выбирать удобную трактовку в коде.

Норматив шага: `docs/tz_patch_system.md` § «Владелец сбора патчей — только
DAG», `docs/tz_world_snapshot.md` § «Staged artifacts и точки публикации»,
«Правила модели pack + overlay», «Гранулярность модификаций и сохранение
истории»; обязательные границы настоящего плана §1 и §3.4 сохраняются.

#### Приёмка §1 — владельцы и границы вызовов

Baseline не меняется. DAG вызывает domain read и write-free подготовку,
отдельно запрашивает materialization, собирает PatchSet. Pure generator
получает prepared inputs и возвращает результат без IO и patches.
Domain application преобразует prepared result в frozen patch-данные.
Snapshot получает уже собранный набор, вызывает domain handlers и storage
и владеет единым commit. Ни Patch, ни handler, ни repository не инициируют
следующую стадию, Snapshot или самостоятельную публикацию.

Проверяемый результат: трасса вызовов не содержит обратных вызовов из
Snapshot/storage в planning/materialization; подготовка не меняет active
heads или опубликованные SQL/pack. Этот аудит обязателен и для вложенных
сервисов, а не только для публичных методов. WS read/router не вводится.

#### Приёмка §2 — подготовка, проверка и доменное применение

Вход подготовки — доменная операция, явно выбранное исходное состояние
и её typed inputs. Выход — prepared typed result с dependencies и
предусловиями либо явный доменный отказ. Validation не выполняет
сохранение с последующим rollback. `validate_only` не создаёт staging,
lease или commit и использует те же доменные решения/диагностику.

Вход materialization — готовый актуальный план/revision и запрошенный
scope/LOD. Выход — typed result или удерживаемые staged refs. Отсутствующий
план не строится внутри materializer. Staging выполняет application-домен
через общий port; generator/worker IO не получает. Изменение planning
не запускает materialization; domain output явно сообщает invalidation.

При применении handler проверяет собственные предусловия и семантику
переданной секции, формирует её результат и поручает своему storage
добавить версии в Snapshot-owned transaction. Он не пересчитывает
planning/materialization и не вызывает write-операцию подготовки повторно.
Общая инфраструктура не интерпретирует payload и не угадывает effects.
«Формирует результат» здесь означает доменное apply/merge уже подготовленной
дельты, а не создание отсутствующего плана или materialization. Подготовка
и handler возвращают typed диагностику; отказ handler отклоняет весь набор,
не только его секцию.

Проверяемый результат: подготовленное изменение не видно через published
read; после успешного commit виден весь набор; при отказе любого handler
не видна ни одна новая секция. Запись доменных версий без snapshot history
не считается успешным применением.

#### Приёмка §3 — Patch, секции, порядок и конфликты

Каждая доменная операция объявляет свою связку target / expected state /
change / prepared result. Typed target и область воздействия принадлежат
домену; произвольные dict, generic field path, имя CRUD-метода, callback,
repository или файловый путь не являются контрактом модификации.
Patch содержит данные перехода и refs, но не исполняемое поведение.

PatchSet передаёт полный подготовленный набор и явные зависимости секций.
Snapshot проверяет полноту и допустимость указанного порядка, не выбирает
стадии и не сортирует их самостоятельно. Внутри секции порядок и допустимые
композиции определяет домен. Неверный порядок, цикл или отсутствующая
зависимость дают отказ всего набора, без попытки достроить dependency.
Зависимость может быть удовлетворена удерживаемой опубликованной версией
или явно указанным prepared result предшествующей секции этого набора.
Наличие dependency не требует фиктивного patch неизменяемого домена.
Домен объявляет и проверяет содержательную совместимость; Snapshot проверяет
ссылочную полноту и порядок по явным declarations, не разбирая чужой payload.

Предусловие различает ожидаемое отсутствие и удерживаемую версию цели;
удалённая цель не превращается в никогда не существовавшую. Для runtime
используется pack/snapshot provenance по §3.1.1, для source — существующий
контракт SourceRevision после его freeze. Snapshot не вычисляет версии
доменных целей по общему head и не подменяет source revision fingerprint'ом.

Handler проверяет всю секцию относительно согласованного исходного
состояния, включая пересечения target внутри набора. Последовательные
операции над одной целью допустимы только при явно объявленной доменной
семантике композиции; промежуточный prepared result не объявляется
опубликованной версией. Проверка внешних expected versions относится к
исходному состоянию секции; доменная композиция определяет допустимые
переходы между её подготовленными операциями. Нельзя требовать от второй
операции snapshot stamp ещё не опубликованной первой операции.
При отсутствии объявленной семантики композиции отклоняется весь PatchSet.
Межсекционные ограничения объявляются доменами и представлены явной
зависимостью; общий код не выводит их из payload. Проверку пересечения
состояния разных доменов выполняет домен-владелец ограничения через
согласованные domain inputs/read ports; центральный generic overlap engine
в Snapshot не вводится.

Изменение стены сохраняет остальные стены; явный replace агрегата требует
своей операции. Изменение вложенной цели учитывается при проверке
пересекающегося агрегата. Незатрагивающий цель тик не меняет её stamp.
Подготовленный результат другого patch/revision не подходит даже при
совпадении scope. Нет результата или удерживаемого ref — отказ, без generate.

Проверяемый результат: отдельные будущие сценарии для независимых целей,
стена/дом, двух операций одной секции, неверного порядка секций и
несовместимого prepared result. Для каждого concrete Patch обязательна
замена CRUD/backend при неизменных классе, payload, format и bindings
по §3.4. Сейчас эти проверки не выполнены: concrete классов ещё нет.

#### Приёмка §4 — commit, исходы, staging и восстановление

Единица публикации — весь переданный Snapshot набор. Перед записью
проверяются форматы оболочки/секций, зарегистрированные handlers,
связность refs и наличие удержания. Неизвестная секция, неподдерживаемый
формат, отсутствующий или повреждённый artifact отклоняют весь набор.
Проверка ref включает kind, format, hash и размер; доверия одному пути
или факту наличия файла недостаточно. Upgrade старой секции — доменный
read, без перезаписи истории и без materialization.
Результат проверки refs защищён удержанием и immutable storage до commit:
между проверкой и публикацией artifact нельзя удалить или заменить.
Неизвестную секцию/формат нельзя проигнорировать даже при scoped read,
если от неё зависит запрошенное согласованное состояние.

Объёмные blobs/rows уже подготовлены и защищены lease до входа в commit.
Snapshot не создаёт недостающий staged result. В короткой SQL-транзакции
проверяются исходный world CAS `(pack_hash, snapshot_head)` и участвующие
player heads, доменные предусловия; добавляются SQL-версии, история,
snapshot records и ссылки на новый текущий overlay; передаются holders и
фиксируется terminal outcome операции. Продвижение участвующих heads —
в этой же транзакции. Ни domain storage, ни snapshot metadata repository
не делают независимый commit. Старые версии/manifest остаются immutable.
SQL-версии/rows недостижимы из published read до этого commit. Проверки
target выполняются на той же согласованной базе под защитой publication
transaction; предварительная проверка вне неё не заменяет проверку гонки.

Логический CAS не разрешает UPDATE/DELETE исторического состояния.
Его append-only backend binding и защита от конкурирующих successor commits
обязательно фиксируются до реализации в шагах 2–3. Второй указатель
для source-versioning не вводится. До gameplay активация pack проверяет
тем же механизмом, что gameplay не стартовал; после старта pack_hash
цепочки не меняется. Первый snapshot — первый тик, fake base не создаётся.

Принятые категории исходов ядра (не DAG-facing DTO) задаются единым
общим **StrEnum**, принадлежащим dataModel ядра Snapshot:
`COMMITTED = "committed"`, `CONFLICT = "conflict"`,
`REJECTED = "rejected"`. Имя enum и точный файл закрепляются в contract
freeze / implementation map до кода. Поля категории в typed result,
operation outcome и соответствующих logging contracts используют этот
enum, а не голый str, Literal или отдельные доменные копии. Строковое
wire/SQL/JSON-представление разрешается только на границе сериализации
с проверяемым преобразованием в/из enum; неизвестное значение — явный
отказ, без default. Enum не содержит apply/storage/logging поведения.

Conflict — несовпадение head/target precondition;
rejected — недопустимый набор/формат/ref или доменный отказ. Домен явно
сообщает отсутствие изменения; оно не означает публикацию секции раньше
остальных. Если фиксируется тик с no-op, его история не меняет stamp
незатронутой цели. Инфраструктурный сбой не маскируется этими исходами
как успешная операция; неизвестный исход commit сначала восстанавливается.
Причина/действие и WarningError приходят от producer через общий log sink;
consumer не выводит severity по тексту/code и не подставляет default.
Нарушение явно объявленного expected head/target state — conflict;
неподдерживаемая семантика композиции, формат или невалидный набор — rejected.
Если есть несколько причин отказа, producer возвращает их typed diagnostics;
правило выбора основного исхода фиксируется в freeze результата, а не
угадывается consumer. Сбой storage/связи не обозначается доменным rejected.

`operation_id` связан с неизменным содержимым запроса: выбранные исходные
heads, порядок/данные patches, preconditions и prepared refs/dependencies.
Транспортный request_id не задаёт новую модификацию. Точная canonical
encoding/identity fingerprint фиксируется в шаге 2, без второго hash-ядра.
Повтор того же запроса при наличии terminal outcome возвращает его,
не применяя набор снова. Другое содержимое с тем же id отклоняется,
не меняя первоначальные request binding и outcome. Изменение исходной
базы после conflict — новая операция, не retry с тем же id.

При отсутствии terminal outcome повтор не считается уже завершённым:
ядро исключает параллельное применение одного operation_id; DAG явно
запрашивает recovery/resume, если операция возобновима. Недостающие после
restart малые prepared данные не генерируются Snapshot; без подтверждённого
восстановления того же запроса resume недоступен. При потере ответа на
COMMIT recovery сверяет durable outcome до повторной записи или очистки.
Отказ/отмена до commit откатывают весь SQL-набор, а не компенсируют уже
опубликованные доменные изменения. После commit отмена не стирает историю.
Committed outcome сохраняется атомарно с состоянием. Terminal conflict/
rejected после отката доменных записей сохраняются общим operation storage
без публикации domain state и без продвижения heads. Если сохранность
исхода ещё не подтверждена, это infrastructure/recovery ситуация,
а не durable terminal outcome. Точный transaction protocol этой записи
обязателен в шагах 2–3; самостоятельный domain commit запрещён и здесь.

Кэш малых результатов живёт в job/операции; refs объёмных защищены общим
lease. Commit атомарно передаёт удержание опубликованному snapshot/artifact.
После подтверждённого terminal failure/cancellation и остановки writers
общий owner освобождает lease; только неудерживаемые staged данные
допустимы для GC. Неизвестный outcome, resumable job и ready_inactive
не очищаются по TTL. Retry/resume/GC запускает DAG, Snapshot сам их
не планирует; ядро предоставляет операции и гарантии удержания.

Обычный read использует pack + текущий overlay, без replay всех тиков.
Restore выбирает удерживаемые pack/keyframe/deltas; не перезаписывает
SQL-историю, не пересчитывает отсутствующее и не подставляет latest.
При переходе ветки DAG явно запрашивает восстановление overlay, Snapshot
делегирует merge доменам. Обычный commit через handlers добавляет
подготовленные дельты в текущее domain-owned overlay представление и
атомарно публикует его согласованную версию вместе с snapshot. Это
инкрементальный apply, без replay цепочки и без создания keyframe.
Полная компакция/создание keyframe и перестроение overlay при смене ветки —
отдельные явно вызванные DAG операции, вне hot path commit. Их результат
не меняет semantic target stamps и не является новым source change.
Одновременно активна одна линия мира. Keyframe на старте gameplay
не создаёт фиктивный snapshot-тик: начальное состояние задаёт базовый pack
с пустым overlay; точный checkpoint storage freeze не может нарушать
правило «первый snapshot — первый тик».
Attach готовит session-домен по уже принятой политике §4, не Snapshot.

Проверяемый результат: будущие fault tests до/после каждой границы
SQL/refs/history/holder/head; потеря ответа после COMMIT; конкурентные
world/player commits; отказ одной цепочки; отсутствие частичной публикации;
сохранность чтения старого snapshot; запрет GC удерживаемых данных.

#### Приёмка §5 — направления зависимостей

Общие dataModel patch/snapshot контракты не импортируют concrete domain
POJO, application, Container или db. Домен объявляет свои patch/section
типы с использованием общих контрактов; domain application реализует
handler и свои storage ports. Snapshot application зависит на общий порт
handler и snapshot storage, а не на concrete handlers, SQL mapping,
алгоритмы генераторов или domain repositories. Storage adapters зависят
на порты/модели; обратных импортов из dataModel/application в adapters нет.

Только composition root связывает section key с конкретным handler.
Регистрация явная, повтор ключа — ошибка конфигурации, import side effects
запрещены. Handler не получает публичного publish/commit capability.
Snapshot storage хранит общую metadata/историю, не пишет domain SQL за
домен. Общие staging/CAS/holder механизмы находятся вне отдельного
terrain/regions/source-versioning домена и имеют одного владельца.

Проверяемый результат: import/call audit всей цепочки, включая вложенные
storage callbacks; отсутствие SQL/UOW в WS и domain CRUD в Patch.
Exact файлы, существующие ports/POJO и folder counts — шаги 2–3, после
приёмки архитектуры; сейчас новые папки/файлы не добавляются.

#### Приёмка §6 — revisions и граница внешней зависимости

Source identity/revision, runtime target stamp, planning fingerprint и
format version остаются разными понятиями. Операция использует captured
source closure, включая состав коллекций; source/pack refs удерживаются
до передачи holder. Историческое чтение разрешает pinned/as-of, не latest.
Изменение effective inputs инвалидирует соответствующие доменные планы/
представления; unrelated source change не требует новой materialization.
Новая materialization другого LOD сама не создаёт SourceRevision.

Ядро не вводит substitute SourceRevision/store. Точное заполнение source
preconditions, source mutation/ref-integrity и revision-set binding —
отдельный шаг 5 после world-source-versioning 2–3. До него отсутствие
реализованного binding даёт явную недоступность соответствующей операции,
а не фиктивную revision, mutable latest ref или пропуск предусловия.
Это не блокирует независимые типы и инфраструктуру ядра после их freeze.

Проверяемый результат: будущие сценарии pinned read после master edit,
неизменный stamp незатронутой цели, конфликт пересекающегося target,
сохранность удерживаемых source bodies и отказ неподдерживаемого формата.

#### Обязательное уточнение мастера — общий домен логирования (2026-10-30)

Это требование распространяется на всё ядро Patch/Snapshot и его доменных
handlers/storage adapters. SoT маршрутизации, sinks и формата —
`docs/tz_logging.md`; исполнение — существующий `core/loggingConfig.py`.
Смысл событий, reason/action и severity определяет producer соответствующего
домена; общий фасад отвечает за доставку, JSON-формат и маршрутизацию.
Логирование не переносит доменные решения в Snapshot или logging infrastructure.

События проходят через существующий доменный эмиттер, если он уже есть.
Отдельные handlers, форматтеры, файловые writers, print/tee и второй emit
того же события запрещены. Snapshot сообщает собственный lifecycle/outcome,
не повторяет уже записанную доменную причину как новое доменное событие.
Frozen Patch/POJO не эмитят логи и не зависят на logging infrastructure.

До реализации в freeze ядра определить каталог lifecycle/conflict/rejection/
recovery/holder/GC событий, их producer и маршрут через общий фасад;
семантику закрепить в доменных ТЗ, маршруты — в `tz_logging.md`.
Корреляция использует существующий request context и `operation_id`,
а также относящиеся к событию world/timeline/snapshot/section/target refs.
Событие committed эмитится только после подтверждённого commit; неизвестный
исход не логируется как успех. Операционные логи не заменяют durable
operation outcome, snapshot history и восстановление исхода по storage.

`validate_only` возвращает структурированную диагностику без runtime
WarningError emit по `tz_runtime_world_edit_policy.md`; обычное штатное
логирование сохраняется. Приёмка включает проверку маршрутизации и
корреляции, отсутствия дублирующей эмиссии и ложного committed при отказе.

#### Решения freeze, конкретизирующие §8.1

1. **Исходы:** SnapshotApplyOutcomeKind(StrEnum) COMMITTED/CONFLICT/REJECTED;
   SnapshotApplyResult — один frozen record с enum category и проверяемой
   связью committed refs/diagnostics, без bare str/Literal substitute.
2. **Приоритет отказов:** последовательность envelope → immutable operation
   binding/terminal lookup → refs → CAS/heads → domain validation → apply →
   atomic publication. Среди domain validation refusals REJECTED имеет
   приоритет над CONFLICT; ранняя неуспешная общая фаза завершается раньше.
3. **Пустой тик:** явный apply с валидным turn_id/expected heads может
   зафиксировать пустой/no-op snapshot; read не создаёт тика. Неизменённые
   target stamps/section states сохраняются. Empty section запрещена;
   empty tick задаётся sections=(). Это конкретизация P-7, не implicit flush.
4. **Typed dispatch:** generic domain section и handler связываются одним
   concrete type при registration. Core не сериализует subtype как base
   model с потерей полей и не интерпретирует target/change/prepared.
5. **Ref/precondition:** отсутствующая цель, tombstone и удерживаемая
   pack/snapshot version различаются. Prepared dependency проверяется по
   key/fingerprint, не выдаётся за опубликованную SectionStateRef.
6. **Operation lifecycle:** preparation binding фиксируется до staging;
   publication binding — один раз при claim. Один operation kind/ID
   не меняется на другой. Busy и неизвестный COMMIT outcome не являются
   domain conflict/rejection. Terminal retry не повторяет validation/apply.
7. **Artifacts:** общий typed staging mechanism обслуживает BLOB/SQL_ROWS;
   domain backend владеет canonical row mapping, ядро — lease/fence/holder/GC.
   Raw-byte digest общий для existing encoding/tileCodec, не копия алгоритма.
8. **Atomicity:** world/player heads, domain versions/history, overlay refs,
   holders и success outcome публикуются одной Snapshot-owned transaction.
   Refusal записывается common operation storage после rollback; неизвестный
   исход commit сначала восстанавливается, не превращается в refusal.
9. **Logging:** activities и outcome typed; existing facade получает
   target routes world_snapshot/snapshotLifecycle и artifacts/artifactLifecycle.
   ТЗ фиксирует producer/levels/correlation, success только после COMMIT.

`storage/artifacts/blobBackend.py: ContentAddressedBlobBackend` реализует

service и не доменный pack writer. Composition root импортирует его явно.
Обратный импорт application → concrete storage module запрещён.

Ни один новый adapter не наследует mutable BaseRepository для записи
истории и не вызывает transaction_if_needed из domain apply. Storage
scope binder проверяет current asyncio task, database instance,
scope lifetime и разрешённый read/write режим **перед каждым обращением**.
Connection остаётся private внутри db adapter; application handler её
не получает даже через context. Child task, другой Database, закрытый
scope и запись через CommitReadScope дают явный отказ.

SqlitePublicationCommitStore переиспользует GuardedConnection.unit_of_work
и BEGIN IMMEDIATE. Собственный writer gate держится до подтверждённого
COMMIT/ROLLBACK; это один coordinator существующей connection, не второй
SQLite connection или nested UOW. При cancellation/ошибке COMMIT состояние
worker дожидается завершения; если исход не доказан, connection закрывается
для новых операций до recovery. Автоматический ROLLBACK после неизвестного
COMMIT не считается доказательством отказа. Existing Database.transaction_on
не меняется ради legacy callers; новый adapter связывается с его существующей
GuardedConnection, а пути не получают ambient commit capability.

Runtime publication, pregame activation и gameplay-start используют
один WorldPublicationStore и один transaction port. Operation bookkeeping
делает свои короткие transactions без domain state. Read domain adapters
во время validation используют CommitReadScope той же connection; запись
не выходит в bootstrap_conn или отдельный repository auto-commit.

#### 3.4. SQL constraints и точка атомарности

Ниже фиксируется schema contract, не исполняемый DDL этого шага. Имена
таблиц окончательны для implementation; все db row classes синхронизируются
с 0001 и включаются в existing startup validate_schema.

- `world_publications`: publication_id PK, world_uid FK, predecessor_id,
  publication_seq CHECK >=1,
  operation_id, pack_hash, snapshot_head_id, active_timeline_id,
  gameplay_started CHECK 0/1. Composite FK (world_uid, predecessor_id)
  ссылается на тот же мир; UNIQUE(world_uid, publication_id) служит parent key.
  Partial UNIQUE(world_uid) WHERE predecessor_id IS NULL задаёт один root;
  partial UNIQUE(predecessor_id) WHERE predecessor_id IS NOT NULL — один
  successor. CAS читает текущий leaf, сравнивает **все** expected поля,
  вставляет successor; UPDATE указателя/истории нет.
  UNIQUE(world_uid, publication_seq) и index(world_uid, publication_seq DESC)
  обеспечивают current lookup ORDER BY publication_seq DESC LIMIT 1,
  без сканирования всех leaf candidates/проигрывания цепочки.
  Seq = parent.seq+1 (root=1), проверяется guard; это internal append
  position одного pointer, не второй head/SourceRevision/target stamp.
  Первый root без pack/head — explicit infrastructure initialization,
  не запись при read и не fake snapshot. Операции initialization/migration
  доступны только core bootstrap binding, не domain handler.
- `player_publications`: publication_id PK, player_uid FK, predecessor_id,
  publication_seq CHECK >=1,
  player_snapshot_id FK, operation_id. Аналогичные partial UNIQUE на root
  per player и successor; parent FK не позволяет смешать игроков.
  player_uid ссылается на existing character_sheet(character_uid),
  не на несуществующую players. Session audit FK, если задан, — game_sessions(id);
  placement/binding не помещаются в player snapshot payload.
  UNIQUE(player_uid, publication_seq) и DESC index дают current head lookup
  без scan истории; seq — та же internal ordering metadata, не player revision.
  Новый snapshot_ref сравнивается с expected head; смена другой стороны
  тика конфликтует **до** публикации любой стороны.
- `world_snapshots` (existing table уточняется) и `player_snapshots`:
  snapshot_id/player_snapshot_id PK, owner/world/timeline/session fields
  соответствующего chain, turn_id CHECK >=1, parent FK ON DELETE RESTRICT,
  operation_id, format version, created_at, envelope bytes/checksum.
  UNIQUE(operation_id) для world; UNIQUE(operation_id, player_uid) для player.
  Envelope содержит refs/историю секций, не serialized full world dump.
  Обе таблицы и обе publication chains записываются одним CommitScope.
- `publication_operations`: operation_id PK, world_uid, immutable kind и
  preparation_fingerprint. `publication_requests`: operation_id PK/FK,
  immutable publication_fingerprint. Canonical prepared PatchSet **не**
  превращается здесь в отдельный durable cache: после restart для resume
  caller обязан восстановить и передать тот же запрос/inputs.
- `publication_operation_events`: append-only phase/fence events с
  predecessor/event identity и single-successor constraint per operation.
  Index(operation_id, event_seq DESC) разрешает текущую phase/fence без
  replay operation history; такие же per-owner DESC indices — для holders,
  leases и artifact storage events.
  `publication_outcomes`: operation_id PK/FK, outcome bytes/checksum/kind.
  Один ID — один terminal outcome. Success outcome вставляется в transaction
  snapshot/heads/holders. Refusal — после доказанного rollback отдельной
  bookkeeping transaction. Unknown COMMIT — сначала lookup outcome и
  snapshot operation markers; повторного apply наугад нет.
- `artifact_catalog`: artifact_id PK, kind/format/version/hash/bytes/row_count;
  UNIQUE(kind, format_key, format_version, content_hash), CHECK размеров и
  kind-specific row_count. Несогласованный descriptor с тем же identity
  отклоняется, не создаёт второй artifact. Snapshot/held refs разрешаются
  через этот каталог; физические пути не копируются в Patch.
- `artifact_storage_events`: seal/GC events с single-successor ordering
  per artifact. `artifact_holder_events`: append-only acquire/release с
  typed holder identity и single-successor ordering per holder/artifact.
  `artifact_lease_events` и `artifact_writer_claims`: fences, admission,
  acquire/release claims; writers READY/closed/stale fence отклоняются.
  SQL names/table mapping доменных staged rows в эти tables не помещаются.

Исторические rows, catalog identity и publication/outcome events защищаются
от UPDATE/DELETE schema triggers. GC добавляет storage/holder events;
физически удаляет только неподдерживаемые unpublished blobs/domain staged
rows через соответствующий backend под GC guard. Он не удаляет опубликованную
историю или metadata удерживаемого artifact. Op/holder bookkeeping —
append-only projection, не новая source/runtime revision accounting схема.

Проверка родства snapshot/world/player, неизменности pack после gameplay,
монотонности gameplay_started и допустимости переходов обязательна в store
под BEGIN IMMEDIATE; соответствующие FK/UNIQUE/CHECK/BEFORE INSERT guards
не дают обойти её прямой несовместимой вставкой. Parent/owner refs и indices
проверяются schema tests на реальные negative cases. Ни PK, ни SQL BEGIN
по отдельности не объявляются гарантией всей SQL+files atomicity.

Blob storage root задаёт DI как Path(Database.path).parent / artifacts,
один absolute root на database. Backend не принимает пути от Patch.
Path components выводятся из validated content hash и private backend
identity; произвольный UID/format key не используется как относительный
путь. Resolved temp/final/GC paths обязаны оставаться внутри этого root.
Writer пишет private temp artifact своего operation/fence, закрывает,
flush/fsync и проверяет digest; окончательное размещение не перезаписывает
существующий hash path. Seal admission под общим artifact/fence guard;
lease/writer claims защищают temp/final content от GC. Только durable sealed
ref может войти в publication. Files не входят в SQL rollback: при отказе
остаются недостижимыми под lifecycle/retention, без published domain state.
Неизвестный исход, живой/resumable lease и ready_inactive не удаляются.
Canonical SQL_ROWS content включает доменные значения, но не назначаемый
reserve physical artifact_id: его добавляет domain storage binding.
Иначе content hash зависел бы от собственной catalog identity. Проверка
после записи использует тот же domain projection/codec, без нового core
table mapper; одинаковый content разных операций получает тот же ref.

#### Общие правила границы

- Перед SQL write и перед выдачей результата read адаптер явно валидирует
  вход/гидратированные значения существующими контрактами (Pydantic
  model_validate/TypeAdapter с strict/revalidation). Простая аннотация,
  isinstance или from_row этого не заменяет; model_construct/model_copy
  также не являются доказательством валидности instance.
- **U** ниже = существующий EntityUid: строгая непустая opaque string без
  пробелов по краям. Это не UUID parser и не доказательство существования
  записи. **U?** допускает только явный None/SQL NULL; пустая строка,
  sentinel и придуманный UID вместо отсутствия запрещены. Ownership,
  chain identity и достижимость ref проверяются отдельно.
- **H** = RevisionHex; **H?** = он же либо явный None. Формат hash не
  доказывает совпадение bytes, fingerprint binding или content identity.
- **I+** = strict int >= 1; **I0** = strict int >= 0. Не принимать bool,
  float или numeric string на typed write boundary; sequence/fence/turn
  не объявляются FormatVersion или source/runtime revision.
- **B** = typed bool на write, строго integer 0/1 из SQLite на read.
  Проверять raw cell **до** bool_col/from_row: bool(2) или bool('0')
  не должны скрыть повреждение. Затем используется штатный mapper.
- Новые внутренние event_id и artifact_id назначает их owning adapter
  через общий app.ids.deterministicIds.runtime_uid с последующей U-проверкой;
  не вводятся собственный uuid/hash mint или новый UID namespace. Назначенные
  application SnapshotRef/publication refs не переназначаются адаптером.
  Невалидные сохранённые значения дают явную validation/infrastructure
  ошибку; не default, не ложный успех и не новый domain refusal.

Это обязанность нового helper; ContextVar без registry.check недостаточен из-за наследования child task.
- [SqliteOperationStore.read/claim_publication](../../backend/app/db/repositories/sqlite/snapshotCore/operations/operationStore.py) открывают собственный UOW. Их нельзя вызывать внутри artifact UOW. - [DDL guards](../../backend/app/db/migrations/0001_initial.sql): writer acquire требует admitted preparing fence + operation hold; release operation hold требует closed admission и отсутствия claims **всей операции данного fence**. Поэтому отсутствие holders под BEGIN IMMEDIATE исключает admitted writer; отдельный GC live-writer public port не нужен. Claims нельзя освобождать по TTL. SQLite writer lock охватывает physical delete, иначе reserve может вклиниться между live-set check и unlink.
- Storage event root допускает только sealed. Поэтому `mark_deleted` для reserved-but-never-sealed content нельзя реализовать безусловной вставкой gc_deleted. Предлагаемое поведение: после guarded physical delete отсутствие storage events означает no-op; latest gc_deleted также no-op; latest sealed → append gc_deleted. Catalog identity сохраняется; последующий reserve/write/seal создаёт первый sealed либо successor sealed после gc_deleted. Новый DDL не нужен; это явное уточнение port semantics для приёмки.
- Writer chain одна на `(artifact_id, operation_id, fence)`, а не на каждый coroutine. Два одновременных writer одной reservation нельзя считать независимыми claims: второй acquire получает OperationBusyError, не повторно использует чужой claim. Последовательные write и seal append release→acquire в той же цепочке. Разные operations одного content допускаются.
- [ArtifactHolderRef](../../backend/app/dataModel/artifacts/lifecycle/holders.py) требует полный SnapshotRef, а row хранит только snapshot ID. Constructor из preflight не давал владельца разрешения этого ID. Нужна ниже описанная history dependency; нельзя выдавать SQL ID за полный typed ref или добавлять artifact SQL в operation store.

#### Трейсы и порядок владения

1. `TypedArtifactStager.stage → ArtifactStagingService.reserve → leases.assert_writable → catalog.reserve`: предварительная проверка не защищает reserve; reserve повторяет проверку атомарно вместе с hold. Claim защищает весь IO; SQL transaction между acquire/release не удерживается.
2. `ArtifactStagingService.seal → leases.writer → registry.verify → catalog.seal`: отдельный claim после backend.write. Verify не открывает UOW; catalog.seal открывает короткий UOW и проверяет current claim/admission/fence. Cancel между verify и seal даёт отказ seal, затем finally release; никакого ложного sealed success.
3. `ArtifactStagingService.verify → catalog.guard → catalog.is_sealed + holders.is_held → registry.verify`: оба reads используют helper binding. `ArtifactGarbageCollector.collect → catalog.guard → catalog.read + holders.holders → registry.delete → catalog.mark_deleted`: тот же binding до подтверждённого drain physical delete. Child worker BLOB не делает SQL; task scope ему не передаётся. BEGIN IMMEDIATE также исключает конкурирующий reserve/holder acquire с другой connection.
4. `Snapshot/publication owner (будущий) → commits.transaction(operation_id) → holders.handoff(scope, lease, snapshots, retained_refs)`: только explicit bind, без guard/new UOW. Проверить exact current lease, closed/drained writers, sealed transferred refs и существование snapshot refs в caller scope. Приобрести snapshot/retention holds **до** release передаваемых operation holds в той же transaction. Не освобождать непереданные refs; ready_inactive сохраняет retention. Handoff не создаёт snapshot/publication и не вызывает Snapshot. 4C3 проверяет этот путь fixture, не реализует 4D2.
5. `OperationLedger.cancel → leases.cancel`: short UOW читает terminal/evidence и exact fence, закрывает admission; COMMIT; drain вне UOW; новый UOW повторно проверяет fence/terminal/publication facts, отсутствие claims, release exact operation holds + OperationCancelled + terminal event атомарно. Concurrent terminal возвращается как есть. Несовпавший fence — ValueError, ничего не освобождает. Повтор cancel с совпавшим terminal/fence идемпотентен. Не вызывать operations.read внутри UOW; использовать _load, для запрета скрытой publication — existing publication evidence check через record_terminal, rollback при отказе.

Writer finally: release не требует открытого admission/current preparing (cancel уже мог его закрыть), но требует exact acquired chain/fence. Release должен выполняться owner task с защитой от **повторной** cancellation до confirmed transaction outcome. Нельзя просто `shield(repository_call)`: это child task, которому запрещён parent scope. Допустим защищённый отдельный cleanup task с собственным коротким UOW после полного выхода parent UOW, который writer __aexit__ дожидается до конца и затем повторно выбрасывает cancellation. При unknown acquire/release outcome не выполнять blind compensating release; holds сохраняются, connection quarantine наследуется от existing coordinator.

`finish_preparation`: strict unique refs, сравнить полный набор с artifacts.read, все sealed, exact lease, отсутствие writers. В одном UOW закрыть admission и append READY, затем _load вернуть record. Активные writers дают OperationBusyError без частичного закрытия/READY. Cancellation cancel-drain допускает короткие независимые read scopes с cooperative bounded polling (предложение: 50 ms); каждый следующий read заново проверяет persisted state. In-process Event может быть оптимизацией, не источником истины. Отмена самого cancel оставляет closed admission/holds для повторного явного вызова; не эмитирует success.

#### Recovery gate — существенный остаток, не скрывать в реализации

`recover(operation_id)` сначала читает durable terminal и existing historical evidence; terminal возвращает без cleanup/replay. Missing operation — ValueError. PREPARING/READY возвращает подтверждённое наблюдение без повторной materialization, reopen admission или стирания claims. APPLYING/RECOVERY_REQUIRED без terminal может перейти в READY с fence+1 только после доказанного отсутствия живого publication owner, проверки markers и полного sealed/held prepared set. Один BEGIN IMMEDIATE этого **не доказывает**: live caller мог отпустить SQL UOW между claim и publication. Аналогично persisted writer acquire после restart не доказывает смерть filesystem worker; fencing не останавливает уже запущенный _place.

**ОГРАНИЧЕНИЕ ПРИНЯТО МАСТЕРОМ 2026-11-02; НЕ БЛОКИРУЕТ ПРИНЯТЫЙ SCOPE 4C3:** existing IArtifactLeases.recover не принимает owner/quiescence proof, а проверенные SqliteOperationStore/ScopeRegistry не содержат durable process-owner liveness. Для APPLYING/RECOVERY_REQUIRED без terminal `recover` выбрасывает existing OperationBusyError и сохраняет holds/fence; автоматический takeover и принудительное снятие orphan claims в 4C3 запрещены. Cancel ждёт persisted release и отменяем пользователем; не утверждает завершение зависшего writer. Полный crash-resume/takeover gate остаётся **OPEN вне scope 4C3**, требует отдельного freeze owner/quiescence механизма и оценки изменений ports/DDL; предположения «restart означает writers умерли» недостаточно. Исходный preflight обещал recovery без такого доказательства и в этой части заменён принятым ограничением. Эта приёмка не закрывает integration gates и не разрешает 4D2.
