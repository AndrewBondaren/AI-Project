# ID-9 — Конфигурируемые роли LLM: план проработки ТЗ

**Статус:** в работе (проектирование, с 2026-10-30).  
**Источник:** [ID-9 в реестре идей](../../docs/tz_ideas.md#id-9--configurable-llm-roles-intent--npc--background-planner--narrator).  
**Связанные материалы:** [ID-14 — bounded NPC reaction turn](../../docs/tz_ideas.md), [Execution Engine Flow](../../docs/tz_engine_flow.md), [Perception](../../docs/tz_perception.md), [Lazy Simulation](../../docs/tz_lazy_simulation.md).  
**Фаза:** подготовка отдельного доменного ТЗ; реализация, изменение DAG-нод и миграции в этот план пока не входят.  
**Блокер исполнения ID-9:** до завершения и приёмки общей инфраструктурной фазы **DAG-TYPING-1 A1–A3** не уточнять конкретные Pydantic Input/Output-контракты рабочих LLM-нод и не начинать реализацию распределения ролей. Обсуждение принципов и структуры ролей остаётся допустимым.  
**Зависимости:** [DAG-TYPING-1](dag-typing-1.md), [typed node contracts](../../docs/tz_engine_node_context.md), [GEN-DAG-1](gen-dag-1-post-geo-ws.md), [ID-20 — адаптивный контекст Intent](../../docs/tz_ideas.md).

## Цель

Развернуть идею ID-9 в согласованный контракт ролей LLM и план интеграции с существующим движком. После закрытия открытых решений результат оформить отдельным `docs/tz_llm_roles.md`. Этот документ — рабочая программа проектирования, не утверждённое ТЗ реализации.

## Блокер на детализацию контрактов нод и выполнение ID-9 (решение мастера 2026-10-31)

**Обязательный gate: завершить и принять DAG-TYPING-1 A1–A3**, включая общий typed NodeContract/NodeRegistry, проверку зависимостей GraphCompiler, DAGContext/barrier, агрегированное LLM-исполнение/repair и lifecycle. На момент фиксации A1.1–A1.4 и A2.1–A2.3 уже приняты; A2.4–A3 ещё не выполнены.

До закрытия этого gate:

- **Можно:** обсуждать состав ролей (в том числе `TECHNICAL`), логическую декомпозицию функций, model/provider assignment, правила группировки и DSL-политику; фиксировать архитектурные требования без окончательных полей конкретных нод.
- **Нельзя:** утверждать конкретные Pydantic Input/Output POJO, producer/consumer bindings и `NodeContract` рабочих LLM-нод; выполнять их миграцию или реализацию role-aware DAG/агрегации. Отдельное разрешение мастера на код остаётся обязательным даже после закрытия gate.
- **После gate:** инвентаризировать существующие доменные POJO и через владельца конкретных нод (GEN-DAG-1) уточнить Input/Output, Pydantic-состав роли и привязки node → role; только затем согласовать шаги реализации ID-9.

**Без круговой зависимости:** финальный handoff/этап B самого DAG-TYPING-1 требует concrete bindings GEN-DAG-1, поэтому gate для начала **детализации** нод — приёмка общей инфраструктуры **A1–A3**, а не завершение B. Интеграция/переключение production после этого требует собственных согласованных gates GEN-DAG-1 и DAG-TYPING-1 B.

## Исходная формулировка ID-9 (историческая)

Ниже сохранён исходный состав ролей из реестра идей. После решения 2026-10-31 самостоятельная роль `INTENT` в **целевом дизайне** заменена на `TECHNICAL`, а `IntentDetection` является её первой изолированной LLM-нодой. Остальные положения исходной идеи остаются требованиями, пока не согласованы их изменения.

- Минимальный набор функций: **Intent**, **NPC**, **Background Planner / GM**, **Narrator**. Роль задаёт контракт задачи, модель/провайдера, допустимый контекст, права на знания, output schema и validation policy.
- **Intent** возвращает candidate IR для детерминированной проверки, не объявляет результат действия фактом.
- **NPC** получает actor-specific projection; секреты и чужое приватное состояние не должны протекать между акторами.
- **Background Planner / GM** предлагает события вне непосредственной сцены, но не коммитит мир.
- **Narrator** оформляет только разрешённые и видимые игроку результаты сцены; не создаёт новые факты.
- Провайдер/модель настраиваются независимо по ролям, включая local/cloud mix.
- DSL-профиль выбирается детерминированно: exact model → family/type → role default. Профиль может адаптировать инструкцию, но не менять контракт, права или валидацию роли.
- Движок валидирует и коммитит proposals; LLM не является authority. Для интерактивных NPC действует ограниченный reaction beat из ID-14.
- Для replay/debug нужны фактические роль, provider/model и выбранный DSL profile с version/hash.

## Согласованные инварианты (решения мастера 2026-10-30)

Эти требования обязательны для ТЗ ID-9. Они описывают **целевое** поведение, а не утверждение о реализации в текущем DAG. Исключения, точные API и алгоритмы, не перечисленные ниже, остаются открытыми.

| ID | Инвариант |
|---|---|
| **LLMR-01 — роль ≠ модель** | Роль задаёт задачу/контракт и границы знаний, а `provider/model` — назначаемый исполнитель. Одна модель может обслуживать все роли либо каждой роли можно назначить свою. Одинаковая модель не объединяет роли в один запрос. |
| **LLMR-02 — role-first grouping** | Кандидаты на агрегирование сначала разделяются по **роли**, затем по **temperature**. Реальный батч дополнительно требует совместимых фактических provider/model, контекста/permissions, контрактов и зависимостей. Межролевое агрегирование запрещено даже при равных model и temperature. |
| **LLMR-03 — порядок важнее батчинга** | Нельзя агрегировать ноды, если потребителю нужен завершённый Output другой ноды или имеется обязательная последовательность, которую совместный вызов нарушит. `BaseNode.deps` остаётся единственным графом зависимостей. Ролевая стадия/барьер может ограничивать допустимый порядок; температура не переопределяет `deps`. Не вводить второй граф `REQUIRES`. |
| **LLMR-04 — Intent первый и изолированный** | Для игрового сообщения игрока `IntentDetection` — **первый LLM-вызов**, исполняется **отдельно от всех остальных LLM-нод**, независимо от совпадения роли, temperature или модели. Никакой другой LLM-вызов этого хода не запускается до него или параллельно с ним. Необходимые детерминированные Python preconditions/reads могут выполняться раньше. |
| **LLMR-05 — барьер завершения Intent** | Все циклы запроса контекста, validation/repair и формирования окончательного candidate Intent IR завершаются до запуска downstream LLM-ролей. Результат намерения не считается фактом мира. Фоновые процессы без player input не требуют искусственного запуска Intent. |
| **LLMR-06 — нет обязательной Context Analysis LLM** | Никакого принудительного LLM-вызова `ContextAnalysis`/`ContextSnapGatherer` ради каждого Intent и никакого полного предварительного retrieval «на всякий случай». Само наличие роли TECHNICAL не запускает дополнительные ноды. |
| **LLMR-07 — контекстом владеет движок** | Движок формирует разрешённый минимальный вход и выполняет фактические чтения через публичные доменные read-контракты. LLM по своей DSL-инструкции может вернуть **структурированный запрос недостающего контекста**; движок проверяет права, область и необходимость запроса, получает данные и возвращает контекстный патч. LLM не получает прямого произвольного доступа к БД или секретам. |
| **LLMR-08 — адаптивный цикл ограничен** | Контекстный запрос не является финальным IntentResult и не означает успешный outcome. После контекстного патча обработка Intent продолжается в том же логическом исполнении; валидатор также может требовать дополнительный retrieval по политике ID-20. Должны существовать конечный бюджет попыток и явный диагностический выход при неразрешённой неоднозначности; конкретные лимиты пока не утверждены. |
| **LLMR-09 — разные патчи, разная authority** | Контекстный патч дополняет знания вызова; DSL repair patch корректирует инструкции/ответ; доменный World Patch/PatchSet изменяет мир только после собственных проверок и commit. Эти операции нельзя смешивать или превращать запрос контекста в мутацию мира. |
| **LLMR-10 — изоляция акторов** | Для NPC сохраняются actor-specific projections. Даже одинаковые role, temperature и model не разрешают смешивать приватные знания разных NPC в одном физическом LLM-запросе. Role-aware context policy enforced движком, а не только prompt. |
| **LLMR-11 — стабильный контракт** | Смена model/provider или model-specific DSL не меняет смысл роли, разрешения на знания, Output POJO и правила валидации. Выбранные role, model/provider и DSL profile/version/hash должны попадать в execution trace/replay. |
| **LLMR-12 — роль TECHNICAL как состав нод** | `TECHNICAL` является LLM-ролью; `IntentDetection` — её первая изолированная LLM-нода. Список привязанных нод описывается типизированным Pydantic-контрактом; этот список не создаёт второго порядка исполнения и не заменяет `deps`. Остальные технические ноды могут вызываться только по необходимости; их агрегация подчиняется LLMR-02/03/04. |
| **LLMR-13 — физическая агрегация** | Совместимые независимые ноды одной группы выполняются **одним исходным физическим `client.chat()`** с отдельными секциями/Output-схемами, а не несколькими параллельными LLM-вызовами. После общей валидации и необходимых repair-вызовов результаты группы публикуются **атомарно (all-or-none)**; частичные секции недоступны потребителям до завершения группы. Изолированный `IntentDetection` не входит в такой агрегат с другими LLM-нодами. |
| **LLMR-14 — RAG как самостоятельный домен** | Индексы, алгоритмы поиска, ранжирование и проверка релевантности/актуальности событий принадлежат **отдельному домену RAG** с публичными типизированными контрактами. Ни DAG, ни LLM-ноды, ни `ContextSnapGatherer`, ни role router не реализуют RAG. Engine/DAG только управляет исполнением и использует возвращённые доменом данные через разрешённые read-контракты; LLM может запросить дополнительный поиск структурированным `ContextRequest`. Реализация откладывается до приёмки распределения ролей. |
| **LLMR-15 — существующий конфиг, тонкий API, типизированные роли** | Пользователь задаёт назначения provider/model через **тонкий API** по действующим правилам маршрутов (`validate → service → response`), без настройки/оркестрации LLM в route. Конфигурация хранится в **существующем конфигурационном файле**, управляемом `ConfigManager`/`AppSettings`/`SettingsService`, без нового параллельного хранилища. Список ролей и записи настроек — строго типизированный Pydantic-контракт, а не непроверенный свободный `dict`. **Владение доменной семантикой role/model settings ещё требуется решить**; конкретные DTO/поля уточняются после gate DAG-TYPING-1 A1–A3. API не расширяет knowledge permissions. |
| **LLMR-16 — пул моделей NPC** | Для роли `NPC` пользователь задаёт **пул из нескольких моделей/провайдеров**. **Постоянного закрепления модели за конкретным NPC нет**; фактическая модель выбирается из пула для отдельного NPC-вызова до агрегации и фиксируется в trace/replay. Разные фактические provider/model не объединяются в один LLM-запрос даже при совпадении роли/temperature, actor-specific projections не смешиваются. Точная стратегия выбора модели из пула остаётся открытой. |

**Решение о TECHNICAL (2026-10-31):** принят вариант Б: `TECHNICAL` — самостоятельная LLM-роль, `IntentDetection` — её первая изолированная LLM-нода, а не отдельная роль. Роль и нода — разные сущности; состав нод роли задаётся типизированным Pydantic-списком (точная схема ещё проектируется). Classification, Action/Speech Extraction и другие операции допускают отдельные типизированные контракты/ноды, если это обосновано их зависимостями и выходами; не складывать их автоматически в одну «универсальную» Intent-ноду. Логические подзадачи внутри одного Intent-вызова не должны создавать скрытый второй DAG или нарушать isolated-first. Если Classification/Extraction являются частями **первого физического Intent-вызова**, они оформляются как его логические секции/композиция typed-контракта, а не отдельные независимо планируемые LLM-ноды. Если требуется отдельный завершённый Output и DAG lifecycle, это последующая DAG-нода; окончательная декомпозиция ещё открыта.

**Формальный смысл «Intent первый»:** первый **LLM**-вызов интерактивного player turn, не первое действие движка вообще. Обязательная подготовка и gate-логика без LLM остаются допустимыми. Политика явных debug/admin bypass `task_type` должна быть отдельно зафиксирована и не превращаться в скрытое исключение игрового пути.

### Проверяемые сценарии для будущей приёмки

1. Всем ролям назначена одна модель: агрегирование между ролями не происходит; Intent исполняется отдельно и первым.
2. Ролям назначены разные модели: меняется маршрутизация, но не `deps`, смысл Output или права контекста.
3. Две технические LLM-ноды имеют одинаковую температуру: `IntentDetection` не сливается с соседней.
4. Контекст однозначного запроса достаточен: дополнительного Context Analysis/retrieval LLM-вызова нет.
5. Контекст неоднозначен: типизированный запрос → разрешённое чтение движком → контекстный патч → валидированный IntentResult; по исчерпании бюджета — явная диагностика, не бесконечный цикл.
6. Ноды одной роли/температуры имеют зависимость по результату: совместный запрос не допускается; зависимость сохраняется.
7. Два NPC имеют разные приватные данные: контексты не смешиваются при одной модели и температуре.
8. Несколько совместимых независимых нод дают один исходный LLM-вызов с раздельными Output-секциями и атомарной публикацией после проверки всей группы; при ошибке частичные результаты не публикуются.
9. Подзадачи внутри изолированного Intent не создают скрытый scheduler или дополнительный первый LLM-вызов; самостоятельные DAG-ноды исполняются после него согласно `deps`.
10. Для связанной истории DAG/ContextSnap используют только публичный typed API домена RAG, без собственной поисковой реализации или индекса.
11. API получает строгую конфигурацию списка ролей и моделей; неизвестные/недопустимые идентификаторы ролей и непроверенные поля не проходят validation, права контекста не меняются.
12. Роли `NPC` задан пул из двух моделей, без постоянной привязки к персонажам: модель выбирается отдельно для каждого вызова и трассируется; разные provider/model не сливаются в один агрегат, приватные контексты NPC изолированы.

## Шов с текущим и целевым DAG

- Первичный аудит кода: `GraphCompiler` собирает LLM-группы по `temperature`, `LLMAggregateExecutor` выбирает `state.session.llm_provider/model` и выполняет один вызов на группу; `LLMGroupPayloadBuilder` получает доступные на момент сборки `node_results` зависимостей. Role-aware projection отсутствует.
- `context_snap_gatherer` и `intent_detection` сегодня оба LLM-ноды с `temperature=0.2` и попадают в один агрегат, хотя у Intent объявлена зависимость. Её Output не может быть фактически получен от соседней ноды **в том же** исходном запросе. Новые LLMR-03/04/06 требуют пересмотра этой связки, а не обязательной третьей LLM-ноды.
- В текущем `RepairOrchestrator` repair работает в одной conversation; контракт адаптивного context request/patch ещё не введён. Инфраструктуру retrieval следует согласовать с ID-20, не дублируя её в role router.
- `PatchApplier` сейчас фиксирует `pending_patches` в `ExecutionState`; это не готовая доменная транзакция World PatchSet/Snapshot. Не считать текущий путь реализацией LLMR-09.
- В принятом **DAG-TYPING-1** (проверено 2026-10-31) A0, A1.1–A1.4 и A2.1–A2.3 выполнены и приняты, включая обязательные исправления A1.3R/A2.3R; A2.4–A3/B ещё впереди. Целевой контракт сохраняет атомарность temperature-группы. **LLMR-02/03/04/13 меняют будущую политику группировки, но не атомарность публикации.** До реализации необходимо явно синхронизировать/согласовать изменение контрактов DAG-TYPING-1 и `tz_engine_node_context.md`. Не менять их молча и не создавать второй scheduler.
- Первичный аудит ядра DAG выполнен; полная инвентаризация P0 (включая все UI/config call sites и точные миграционные швы) остаётся открытой.

## Порядок реализации: сначала роли, затем контекст Intent (решение 2026-10-31)

**Жёсткая последовательность:** сначала архитектурно завершить, согласовать, реализовать и принять распределение LLM-нод по ролям, role-aware конфигурацию/группировку и isolated-first `IntentDetection`. **Только после этого** отдельным согласованным шагом реализовывать новый сбор контекста и Event Retrieval/RAG. Настоящий план до утверждения допускает описание стыков, но **не разрешает преждевременную реализацию** ContextSnap/RAG или правки рабочих DAG-нод.

Для последующей работы контекстного слоя обозначены три разные ответственности (детали и конкретные Output ещё не утверждены):

1. **ContextSnapGatherer** — подготовка/композиция типизированного фактического контекста движка для Intent. Контекст может включать актуальную сцену, участников, их состояния и связанную историю событий; это не обязательная дополнительная LLM-генерация. Сохранить принцип условных контекстных источников из `project_data_storage_tz.md` (LocalSceneShortContext/CombatContext) и учесть проектную `SceneContextBuilderNode` из `tz_engine_flow.md` для обстановки/объектов/опасностей. Их конкретная декомпозиция ещё не утверждена; не копировать весь мир в общий POJO.
2. **Самостоятельный домен RAG / Event Retrieval** — ограниченный поиск связанных прошлых событий, особенно по смыслу и истории договорённостей. **Вся реализация поиска, индексов, ранжирования, отбора и интерпретации временных/событийных связей принадлежит домену RAG, а не DAG или нодам.** Домен предоставляет публичные типизированные read/search-контракты и соблюдает актуальность, доступность, ветки Snapshot/rollback. DAG/контекстные ноды не содержат RAG-алгоритмов и лишь получают разрешённые данные через доменный интерфейс. Это не отдельная LLM-роль и не обязательный векторный поиск.
3. **IntentDetection** (`TECHNICAL`) — первый изолированный LLM-вызов, который получает исходный подготовленный контекст, может запросить недостающие сведения структурированным `ContextRequest` и продолжить после `ContextPatch` в пределах бюджета/валидации ID-20.

**Открыто для последующей работы:** конкретный Pydantic Input/Output, набор и admission контекстных Python-нод, выбор начального исторического окна, типизированный публичный API домена RAG и его триггеры, typed request/patch protocol, роль текущей LLM-реализации `context_snap_gatherer` в миграции. Не утверждать её переделку в Python до отдельного решения о конкретных нодах/GEN-DAG-1. Эти вопросы **не блокируют сначала выполняемую архитектуру ролей**.

## Граница готовности

План считается готовым к переносу в исполнимое доменное ТЗ, когда **закрыт gate DAG-TYPING-1 A1–A3**, затем закрыты вопросы P1–P5, определены конкретные typed схемы нод и инварианты безопасности, описаны стыки с агрегированными вызовами и есть проверяемые сценарии приёмки. До закрытия gate допустима только концептуальная проработка ролей без concrete NodeContract. Ни одно открытое решение не трактуется как уже одобренная архитектура; разрешение на код выдаётся отдельно.
