# Общий placement всех объектов генератора

Статус 2026-10-20: P0–P2 выполнены. Созданы общие placement POJO, описаны wire/defaults/validate_only и поздние вызовы общего механизма. По последней команде мастера дополнительный обход default-полей и opt-in-флаг удалены; общий JSON resolver возвращён к исходному поведению. Приёмка приведена ниже. Общий spatial resolver P2 реализован. P3 W1–W2: готов водный adapter declared basin/coastline; production wiring и остальные adapters ещё не реализованы.

SoT: [Placement priority](../../docs/tz_map_light_bake.md#placement-priority), [runtime/worldEdit](../../docs/tz_runtime_world_edit_policy.md). Карта связей: [plan-dependency-graph.md](plan-dependency-graph.md).

## Целевая архитектура

`dataModel/placement/` — единый typed контракт намерения, ограничений, зависимостей и результата. `application/worldData/placement/` — общий resolver для всех объектов генератора. Semantic/absolute placement используют один механизм. Domain adapters предоставляют геометрию и ограничения; общий resolver разрешает размещение, не выполняет carve/fill, persist или lifecycle.

Предшественники: существующая runtime/worldEdit основа и домен WorldTopology (HY-11). Утверждён порядок specificity → исходная площадь → UID с соблюдением опор. Общие POJO и wire missing/range зафиксированы в P1; существующее landcover-сравнение не объявляется готовым общим resolver.

**Решено с HY-12 (мастер 2026-10-20, A2+B1):**

- **Позиция resolver'а (B1, уточнено мастером в P1):** после base heightmap + anchors и до Pass 1.4 выполняется общий проход подготовленных мировых объектов на одном snapshot (вода/горы/поселения). Поздние зависимые объекты разрешаются тем же resolver по мере готовности опор, с неизменяемыми ранее принятыми решениями, без пересмотра ранних победителей. Это явно заменяет прежнюю буквальную формулировку «все уровни одним вызовом до 1.4». Контракт P2: «мировой resolve завершён к моменту spec-apply»; domain-local алгоритмы запрещены.
- **Выход adapter'а — доменно-нейтральный resolved-record (A2):** adapter не производит доменный spec. Пример воды: `ResolvedWaterPlacement {footprint_cells, z_water_level, kind, liquid, source_uid}` → доменный маппинг в spec живёт у потребителя (`hydrology/basinSpecFactory.py`), не в placement — resolver/adapter не импортируют bathymetry и прочую доменную физику.

## Шаги

### P0 — инвентарь потребителей

Цель: установить все реальные точки placement и различить размещение, paint precedence и storage merge.

Контракт: перечислить producers, тип входа/выхода, ограничения, опоры, границы операций и текущие defaults. Континенты, районы, водоёмы и другие объекты включаются в инвентарь; отсутствие реализации отмечается явно.
Проверка: для каждого consumer указан путь и адаптация, отдельный список ещё не реализованных объектов.
Done: полный проверяемый migration inventory без объявленной миграции по одному полю.

**P0 выполнен 2026-10-20.** Проверены producers, consumers и границы операций в текущем рабочем дереве, включая незакоммиченные изменения HY-12. Инвентарь и чеклист P3 — в разделе «Инвентарь P0». Код, тесты, fixtures и ТЗ этим шагом не менялись.

### P1 — общий typed контракт

Цель: зафиксировать POJO и ответственность resolver до реализации.
ТЗ: Placement priority; runtime/worldEdit.
Файлы: `docs/tz_map_light_bake.md`, `backend/app/dataModel/placement/`, contract tests, этот план. Используется существующий общий JSON resolver и его validate_only/report/logging, без дополнительного обхода defaults и без смены политики старых POJO.
Контракт: намерение semantic/absolute, identity, footprint, specificity, опоры/ограничения, resolved/unresolved и диагностика; переиспользовать ResolveContext/result/report. Coastline — контракт создания воды. **Решение мастера 2026-10-20:** при отсутствии воды эффективный приоритет `0` независимо от авторского `placement_specificity`, исходное значение в намерении сохраняется; `WarningError` в лог один раз на coastline за проход с UID и причиной. HY-12 шаг 1 описывает bounded footprint и отсутствие воды на pre-carve входе; P1 фиксирует общий typed-вход этого факта и зависимостей. Будущий fill собственного basin intent не становится его опорой. Цикл «сначала вода, чтобы разместить контракт воды» не допускается.
Проверка: ревью контракта; POJO full/patch/missing/null и нарушение обязательных пространственных ограничений.
Done: конкретные сигнатуры и wire-политика описаны в ТЗ; незаданные решения не заменены defaults.

**Решения P1 приняты:** поздние вызовы общего resolver и missing/null specificity → auto подтверждены мастером. Неподтверждённые defaults геометрии/опор/ограничений удалены: adapter явно передаёт данные или явное пустое значение. Priority None и запрет implicit absolute movement остаются schema defaults. По последней команде мастера отдельная missing-default диагностика и opt-in-флаг убраны; применяется прежний общий путь Pydantic-нормализации, INFO wire/resolved и validate_only для мастера.

**P1 выполнен:** `backend/app/dataModel/placement/{common,intent,prepared,batch,result,water}.py`, публичные экспорты и `backend/tests/test_placement_contract.py`. Defaults не создают вымышленную геометрию или constraints. Общий `application/jsonValidation/resolve.py` сохранён без изменений к HEAD; дополнительных обходов default-полей нет. Режим мастера и существующий лог нормализации проверяются через действующие ResolveContext/resolve_result/report_issues. Примеры сверены с declaredRegions.py, regionIdentity.py, worldBundleService.py и профильными тестами. Сигнатуры — `docs/tz_map_light_bake.md` § Placement P1.

### P2 — общий resolver

Цель: реализовать один алгоритм разрешения с доменной топологией.
ТЗ: контракт P1.
Файлы: `backend/app/application/worldData/placement/`, профильные tests.
Контракт: prepared input → deterministic resolve → typed result; без persist, доменной физики и собственного повторного REF-W resolver.
Проверка: перестановка входа, опоры, разные specificity/площади, UID tie, permitted overlap, absolute conflict, full/partial bake, runtime/preview parity.
Done: единый resolver готов для adapters; доменная миграция ещё не объявляется законченной.

**P2 выполнен 2026-10-20:** реализован общий механизм. Публичный `resolve_placements` использует существующую полную wire-валидацию, затем чистый pass: canonical geometry → очередь готовых intent по specificity/исходной площади/UID → проверка candidates/constraints → typed outcomes. Файлы `application/worldData/placement/{geometry,constraints,dependencies,resolver}.py` разделяют геометрию, pair predicates, расписание зависимостей и facade; POJO P1 не расширяются. Вызовы topology — единственный источник мировых соседей/метрики. Конкретизация пространственных предикатов и диагностики до кода — § Placement P2 ТЗ. Runtime пространственные факты логируются без превращения всего запуска в reject; validate_only получает те же факты через существующие sinks, как в regionIdentity. Общий JSON resolver и удалённый обход defaults не меняются. Domain adapters, pipeline wiring и HY-12 materialize остаются P3/профильным трекам.

### P3 — adapters и миграция по инвентарю

Цель: перевести consumers P0 на общий контракт по отдельным атомарным срезам.
ТЗ: контракт P1 и профильные ТЗ каждого consumer.
Файлы: adapters и callers из P0; этот план с явным чеклистом срезов.
Контракт: для HY-12 первым нужен adapter declared basin/coastline; готовность остальных доменов учитывается отдельно. Не удалять локальное paint-сравнение, пока не доказано, что его ответственность покрыта общим контрактом.
Проверка: целевые regression suites каждого среза и проверки P2; отсутствуют локальные копии resolve размещения у мигрированных consumers.
Done: HY-12 может использовать готовый adapter; весь общий трек закрывается только после миграции полного инвентаря.

## Зависимые треки

HY-12 шаг 2 ждёт P1 для данных placement, шаг 3 — P2 и водный adapter P3. Водные системы потребляют результат размещения, но не реализуют placement. Lifecycle независим от геометрии placement. GEO-1 использует этот resolver для designed water; continental/plate-поле требует собственного плана. Никаких DAG-правок, старта backend или коммитов.

### Границы аудита и обозначения

Проверены `backend/app/dataModel/{locations,terrainMasks,hydrology,spatial,topology}/`, `backend/app/application/worldData/{generators,masks,regions,locations,pack}/`, `application/jsonValidation/` и bundle import. Ни один consumer не мигрирован в P0.

### Ещё не реализованные объекты и части контракта

1. **Общий semantic/absolute intent и resolver**: папок `dataModel/placement/` и `application/worldData/placement/` нет. NL coordinates, required positions и river routing — частные входы, не универсальный semantic DSL. Не вводить новый DSL/default через этот инвентарь.
2. **Континенты / continental или plate field**: самостоятельных producers/POJO размещения в проверенных директориях нет. `GeographicSubtype` содержит island, coast, plain и водные/горные подтипы, но не continent/plate; наличие произвольного NL не генератор континента. GEO-1 требует отдельного плана; будущий consumer общего placement остаётся в инвентаре.
3. **Остров как самостоятельный footprint-object**: geographic subtype есть; отдельного island placement producer нет. Sea/coast legacy inference не считать размещением островного объекта.
4. **Водный adapter / ResolvedWaterPlacement / basinSpecFactory** и bounded coastline по новому контракту ещё отсутствуют. `declared_basins` доходит до master input, но `HydrologyGeneratorService.apply` обрабатывает старые coastal sea/ocean/lake/river пути. Closed/water_side/kind/liquid из нового coastline не проходят полным resolved-record до materialize.
5. **Waterfalls / новые водные системы**: в целевых директориях нет placement producer waterfall; это будущий consumer фактов перепада HY-12. `WaterBody` POJO не означает реализованный fill/system placement. Lifecycle и вывод систем учитываются зависимыми треками, не дописываются в P0.
6. **Объектные пещерные системы / ore veins**: вместо них существуют per-cell stubs W13. ТЗ/geometry/identity будущего объекта ещё нужны; их отсутствие нельзя скрыть пометкой «ores/caves мигрированы».

### Вопросы, которые обязан закрыть P1 (не решения P0)

- **Missing/null/range specificity:** у RegionSpecBase и нового DeclaredBasin сейчас nullable None и ge=0; у coastline, mountain, settlement/room общего поля нет. Это существующее состояние, не согласованный default общего intent. Утвердить политику всех producers, сохраняя исходное authored значение и отдельный effective coastline=0.

Исходная площадь topology-aware, до clipping/noise-resolution конфликтов, с определённой семантикой corridor/claim/3D/local frame. Не использовать bbox/module envelope или число sampled cells.

Сохранить embedded shaft-host overlap, shared room walls, road connections, decks и terrain coverage без ложной exclusive collision.

- **Fallback и диагностика:** сохранить distinction valid empty / missing optional / unresolved. Missing xy→0 у `G/coordinates/convert.py::settlement_origin_fine` и `G/terrain/terrainGeneratorService.py::generate_minimal`, legacy mouth/shaft fallback, skip empty lake/anchor не автоматически разрешённые политики нового intent. ### Вопрос 1 — готовность опор и B1

Проверяемые места: `terrain/passes/surfaceTerrainContext.py::prepare_surface_terrain_context` вызывает relief 1.4 до hydro; `hydrology/rivers/resolveDeclaredRiverPath.py::_resolve_mouth` читает готовую воду; `terrain/hills/hillPlacement.py::place_hills` читает region-painted terrain; `structure/layout/layoutEngine.py` размещает комнаты относительно уже подготовленных room instances/стен. Полный инвентарь — W4/W9/H1–H7 выше.

**Предложение для выбора мастером:** один общий resolver и единые правила используются на нескольких границах готовности данных. До 1.4 выполняется согласованный resolve всех подготовленных мировых intent на одном pre-carve snapshot. После подготовки воды/покрытия/планировки разрешаются зависимые intent тем же resolver с явно переданными ранее принятыми решениями и новыми опорами. Поздний вызов не перемещает принятые объекты и не пересчитывает ранних победителей по новым приоритетам. Геометрия/факты передаются отдельно от ResolveContext. Каждый вызов детерминирован и одинаков для runtime/preview, без собственного алгоритма в домене.

Это **изменяет буквальное B1 «все домены одним проходом до 1.4»**; молча применять предложение нельзя. Альтернатива: сохранить B1 буквально и сначала определить, как все поздние опоры/ограничения представлены до 1.4. До выбора не фиксируются batch/session/stage POJO, deferred/retry semantics и окончательная сигнатура prepared input. Это не предложение DAG-ноды или domain-local resolver.

### Вопрос 2 — missing/null placement_specificity

**Предложение для выбора мастером:** в полном authored intent missing/null означает auto, сохраняется `None`; explicit specificity — строго целое ≥0 (bool, дробь и строка числом не считаются). Prepared input обязан иметь явно разрешённое effective значение по утверждённой политике adapter; если политика ещё не определена, результат unresolved с причиной, а не 0 по умолчанию. Patch missing сохраняет прежнее значение, patch null явно возвращает auto. Невалидное значение не превращается в auto.

Альтернатива: мастер утверждает missing/null → 0 в общем контракте. Для неё требуется сохранить authored presence/None отдельно от effective 0. **Уже утверждённое исключение coastline остаётся в обоих вариантах:** pre-carve факт отсутствия воды принудительно даёт effective 0 даже при authored priority >0, с одной диагностикой на UID за проход; будущий собственный fill не является опорой. Неизвестный факт воды не приравнивается к отсутствию воды.

До выбора нельзя вводить `effective_specificity = authored or 0`, применять штатный default произвольного consumer или объявлять nullable поле общим правилом.
