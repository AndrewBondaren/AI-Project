## Целевые контракты и поток данных (2026-10-08)

- **Паки и выбор генератора.** Генератор может выбирать из любого пака,
  инстанцированного в мир (`owner_world_uid` = мир), либо default-пака;
  отдельное назначение одного пака для ферм/района не требуется. Привязок к
  отдельным локациям или генераторам нет; каждый генератор использует
  подходящие ему шаблоны паков мира. Глобальное хранение (`owner=NULL`)
  не равно доступности миру.
- **Владелец и UID.** У шаблона ровно один пак-владелец. UID детерминированно
  вычисляется единой формулой домена `worldData/ids` с учётом пака-владельца и
  локального ключа, без world_uid/world_seed; UID назначается один раз и не
  перезаписывается (ТЗ §2) — «смена идентичности» = новая сущность, не мутация.
  Повторный импорт сохраняет UID; одинаковые локальные имена в разных паках не
  сталкиваются. Принадлежность хранится в каталоге — хэш UID не декодируется.
  Текущий `library_uid(library, system_name)` ещё не учитывает владельца,
  structures используют UUID из JSON. Не вводить локальные формулы в
  импортёрах или генераторах.
- **Единственные точки UID и логов.** UID — только
  `app.application.worldData.ids` по DET-1 (`docs/project_data_storage_tz.md`);
  pack-owned identity расширяет центральный `library_uid`, без отдельных
  builtin/default/pack UID-функций, uuid/hash в адаптерах, импортёрах или
  генераторах. Логи — `app.core.loggingConfig` и существующие доменные
  эмиттеры (`packingLog`, `relief_warning`, `jsonValidation/resolve`) без
  новых logger/sink/formatter; диагностика fallback попадает в доменный sink
  и в generation scope — в транскрипт прогона без повторной эмиссии.
- **Зависимости паков.** Зависимости должны быть явно инстанцированы в тот же
  мир. Инстанцирование родительского пака не инстанцирует зависимость
  автоматически; при инстанцировании проверяется замыкание ссылок на другие
  паки, неполнота диагностируется по политике resolve ниже.
- **Re-instantiate: правки и удалённые члены** (уточнение 2026-10-09).
  Обновление инстанса до
  новой редакции источника перезаписывает локальные правки тел только по
  подтверждению пользователя (preview затрагиваемых членов, ТЗ §2). Члены,
  удалённые автором на уровне движка, исключаются из инстанса при повторном
  инстанцировании, только если не используются миром — не pinned и не
  referenced (ТЗ §1.1); используемый член удерживается с явным статусом
  «удержан по использованию» и диагностируется — удаление источника не
  протягивается в мир деструктивно.
- **Fallback и явный выбор.** Отсутствует значение → доменный default. Явная
  ссылка → указанный шаблон, если разрешима и доступна миру. Неразрешимая
  ссылка (неизвестный UID, недоступный миру owner, missing dependency) →
  доменный default + warning; сохранённая ссылка не переписывается,
  произвольный шаблон из другого пака не подставляется. «Default» —
  доменный контракт: у relief — R21 unresolved-политика. Будущий режим
  мастера — error вместо warning; вне реализации. Ref-поле — три
  состояния (уточнение 2026-10-09, ТЗ §5): `uid` члена библиотеки;
  явный флаг `default` — сохраняемый выбор POJO-контракта домена
  (перечислим, отличим от fallback); отсутствие/битость — WarningError
  + доменное решение, на импорте — ошибка.
- **Ссылки не содержат пак.** В шаблонах сохраняется только ссылка на шаблон,
  без пары `pack → template`. Движок через каталог принадлежности определяет
  единственного владельца и доступность миру. Каталог паков/состава/владения
  явен и сохраняется при импорте — не восстанавливается из диагностического
  `source_file`. Совпадение `local_uid` template-членов не создаёт override
  при чтении: явный `copy`/`replace` относится к записи (ТЗ §0.3).
  Sparse-merge — только для N+1 deferred-фазы; refs по `template_uid`
  приоритетом слоёв не переопределяются.
- **Текущая идентичность до миграции.** Structures: FS stem =
  `StructureTemplate.system_name` = SQL `template_uid` (UUID из JSON).
  Relief: stem = `ReliefTemplate.system_name`, SQL UID — существующий
  доменный helper. Целевая — pack-owned UID по ТЗ §2; переход и обновление
  ссылок — шаг 3.
- **Structures runtime.** canonical FS → attach в SQL → typed catalog →
  генератор. Прямой FS-fallback в `assemble_structure_catalog()` удаляется;
  генераторы получают готовый каталог. Каталог мира = defaults +
  world-owned паки мира (инстансы engine-паков + авторские записи мира,
  ТЗ §1); `list_all()` административной библиотеки в генерацию не отдавать.
  Дочерние structures разрешаются через refs родительских building
  templates — доменный default-слой POJO `canonical_defaults()` либо члены
  world-паков; наличие дочернего UID в SQL не заменяет владение.
  Pack-id в `main_building.structure` не добавляется.
- **Дефолтные canonical-паки.** Явная декларация, без wildcard-сканирования
  domain root: structures — `base`; relief — **пусто** (доменный default =
  POJO-контракты; `smoke_003` — пользовательский пак, доступен миру только
  через инстанцирование). Стандартные plot/building templates — canonical members default-библиотек с UID; defaults параметров — в POJO (A0, 2026-10-14). Пользовательские паки используются миром
  только после явного инстанцирования; наличие файлов/SQL-строк/инстанса
  в другом мире доступности не даёт.
- **Атомарность, кеш, конкурентность attach** — контракты `ensure_canonical`
  в engine-плане; здесь реализуются адаптерами доменов.

## Порядок имплементации (2026-10-09)

```text
B-1 ──┐
A-2 ──┴→ B-2 → B-3 → 4a → 4b → 4c → ┬→ 5a ─┐
(engine)                            └→ 4d ─┴→ 5b → 6 → 7
```

- **B-1 ∥ A-2 первыми** — независимы; контракт шага 2 engine-плана
  (spec-декларация, cache-политика) согласуется до B-2.
- **A-3** (world-scope, engine-план) — сразу после A-2, до B-2: ранняя
  проверка движка на material/terrain до фиксации cache-контракта.
- **B-3 ∥ B-2 частично** — manifests и карта old→new зависят от формулы
  B-1, не от SQL-таблиц.
- **4a → 4b → 4c** — строго последовательно: CRUD → remap →
  re-instantiate; dual-write включён с 4a.
- **5a ∥ 4d после 4c** — каталог и bundle независимы друг от друга.
- **5b — после 5a И 4d обоих:** читателям нужен эффективный каталог (5a),
  а экспорту — секции `library_packs` (4d) — иначе bundle после удаления
  реестров теряет библиотеки мира.
- **5c:** базовый POJO default сохраняется; world/pack override и связанная
  schema отложены в `docs/tz_library_contextual_fallback.md` (2026-10-13).
  Расширение не блокирует 4d/L-5/5b и требует отдельной декомпозиции после ТЗ.
- **6 → 7 — после 5b:** FS-fallback в `assemble_structure_catalog()`
  снимается только когда все читатели на эффективном каталоге.
- `world-bundle-archive-done.md` шаги 1–5 (zip-конверт + `library/` subtree) —
  параллельно шагам 3–4c, закрываются до 4d; его шаг 6 (`pack/` subtree)
  вне критического пути.

### Шаг 2 — SQL-каталог паков, членства и владения — выполнен

- **Цель:** сохранять владельца и состав отдельно от диагностического source_file.
- **ТЗ:** `tz_template_library_packs.md` §3, §6; schema-policy проекта.
- **Файлы:** только `db/migrations/0001_initial.sql`, `db/models/`, repository
  interfaces/sqlite adapters, `core/container.py` wiring; SQL integration tests.
- **Контракт:** три таблицы §3 (packs / members / dependencies — таблицы
  bindings нет: доступность = `owner_world_uid` или default-статус);
  members несёт `source_template_uid` NULL — provenance remap-операции,
  не FK-integrity (решение 2026-10-08, ТЗ §3). PK/FK/unique; уникальность
  локальных имён в пределах владельца, atomic insert-missing, нет replace
  или чужого commit. Bodies + member сохраняются одной транзакцией;
  membership не меняет владельца. Generic mutation-path закрыт:
  `upsert` — raise на всех трёх repo; `save` на member/dependency —
  raise (mutable-полей нет вообще), на `library_packs` — вырожден до
  metadata-update через `__update_exclude__` (`system_name` /
  `owner_world_uid` / `source_pack_uid` иммутабельны). Массовые
  insert-missing идут через
  `app.db.bulkSql` (`executemany_rows`/`iter_batches`, размер пачки —
  только `EXECUTEMANY_BATCH_SIZE`); собственный `executemany`-цикл или
  второй литерал пачки запрещены (`bulk-sql.mdc`).
  Глобальный UNIQUE на `building_templates.system_name` и
  `relief_templates.system_name` снимается явно (ТЗ §3); `get_by_system_name`
  остаётся transitional (deprecated) до шага 5b и при неоднозначности
  (>1 строка) отвечает ошибкой, а не возвращает произвольную строку —
  коллизии возможны с шага 4a, callers мигрируют на UID/эффективный каталог
  в шаге 5b. Хранилище pin-набора мира (пары `library_kind`/`local_uid`) —
  embedded-конфиг мира: JSON-поле строки `worlds`, как существующие
  `*_registry`-колонки, не отдельная таблица каталога; добавляется в этой
  же миграции — шаг 5b пишет туда мигрированные pointer-sets. Форма
  записи — `LibraryPinEntry` POJO (`dataModel/libraryPacks/`); в колонке
  лежат `model_dump`-дикты, `_registry_slice`/bundle-wire — шаги 4d/5b.
  Проверка полноты идёт по canonical UID и membership (ТЗ §6), не по
  непустой таблице — репозитории этого шага дают нужные примитивы, включая
  reverse-lookup `list_dependents` по `required_pack_uid` для
  delete-диагностики (потребитель `idx_library_pack_deps_required`).
  Индекса по `members.source_template_uid` нет: объявленного запроса не
  существует — добавляется в 4c вместе с provenance-resolver, если он
  потребует выборку по источнику (per-pack `list_by_pack` достаточно для
  контракта 4c). Область
  и инвалидирование кеша полноты — единый контракт `ensure_canonical`
  (SoT: ТЗ §6 + spec-декларация шага 2 engine-плана); адаптеры не вводят
  второй кеш-политики, соответствие не откладывается до шагов 6–7.
  Зависимость: spec-декларация `ensure_canonical` (шаг 2 engine-плана)
  согласуется до этого шага — cache-контракт фиксируется здесь по ней,
  а не задним числом. Статус члена «удержан по использованию» (ТЗ §2,
  уточнение 2026-10-09) — **computed по provenance-resolution**:
  только для связанного `creation_kind=pack_copy`: `source_template_uid`
  IS NOT NULL и не резолвится в текущем составе
  source-пака ⇒ «удержан по использованию»; source-пак удалён целиком ⇒
  «source deleted». У независимой `member_copy` отсутствие оригинала
  означает только «источник удалён», не удержание; источник члена не
  обязан принадлежать source-паку владельца. Отдельной колонки статуса
  в members нет (`creation_kind` — факт создания, §3 ТЗ): persisted-флаг был
  бы derived-state с протуханием — pins/referenced/состав источника
  меняются независимо от операции удержания.
- **Проверка:** временная SQLite, schema validation, одинаковые имена разных
  паков, двойное владение, FK, конкурентный attach, rollback/retry, source_file
  preservation. Не трогать пользовательскую БД; recreate выполняет пользователь.
- **Done:** persistence реализует контракт; global autoattach ещё не включён.

  остаются до шага 5b.
- **Контракт:** доступность = владение (ТЗ §1.1, решение 2026-10-08):
  engine user-библиотеки (`owner_world_uid IS NULL`) полностью
  редактируемы — delete безопасен всегда, миры держат инстансы-копии;
  default-паки read-only, единственная мутация — additive canonical
  attach (§6, механика — engine-план + шаги 6–7). FS-импорт пака с
  manifest создаёт engine-библиотеку и сам по себе доступности мирам не
  даёт. World-owned паки (`owner_world_uid` = мир) полностью редактируемы
  в рамках своего мира. Присутствие body без членства не даёт
  доступности миру (ТЗ §1.1, §4). Member-CRUD следует единому контракту
  ТЗ §0.2: проверки перед записью (unique `local_uid` в пределах пака,
  валидность тела, владение, доменные ограничения), частичных применений
  нет; удаление используемого члена — явная политика отказа/разрешения
  зависимостей с диагностикой по контракту адаптера, битые ссылки молча
  не остаются. Missing dependency диагностируется.
  **Переходное состояние до шага 5b:** реестры указателей остаются SoT
  доступности для существующих читателей — pointer-write path
  (`_ensure_registry`/`_ensure_registry_pointer`) сохраняется, members
  пишутся параллельно (transitional dual-write), иначе члены world-owned
  паков невидимы для читателей. Pointer пишется на UID члена

  schema-policy, а каждое тело приходит только через пак с manifest —
  глобальный synthetic/legacy-пак не нужен (решение 2026-10-09).
  Единственный legacy-источник — старые world-bundle файлы: их тела
  получают владельца при импорте мира (шаг 5b), не заранее.
- **Проверка:** CRUD паков и членов, владение и unique `local_uid`,

### Шаг 4b — remap-операции: `instantiate_pack` / `copy_pack` (publish) — выполнен 2026-10-10

- **Цель:** явное инстанцирование engine→world и publish world→engine с
  детерминированным remap UID и refs — snapshot-семантика, правка
  источника не трогает инстансы.
- **ТЗ:** `tz_template_library_packs.md` §1.1, §2 (remap), §4 (операции).
- **Файлы:** pack application service (расширение), remap через
  `worldData/ids` (формула шага 1), member/dep repositories, integration
  tests.
- **Контракт:** `instantiate_pack` = copy+remap пака целиком (частичных
  инстансов нет, ТЗ §1): члены получают новые `template_uid` по
  центральной формуле от нового владельца, `source_template_uid` члена =
  UID члена-источника, `source_pack_uid` инстанса = provenance;
  внутренние refs тел переписываются на новые UID, refs на чужие паки —
  нет; ремапятся и **world-side refs** (pick-policy
  `default_template_uid` и прочие доменные ссылки — перечень фиксируется
  контрактом адаптера). `copy_pack` publish world→engine — тот же remap
  с owner=NULL; исходный world-пак не изменяется. После уточнения 4c
  (2026-10-11) `local_uid` не является идентичностью template-члена:
  одинаковые читаемые атрибуты не дают коллизии или автоматического
  override. Исторический collision-gate реализации 4b снимается в 4c.
  Повторное инстанцирование того же источника в тот же мир =
  обновление инстанса по `source_pack_uid`, не дубль (политика
  перезаписи тел — шаг 4c). Missing dependency диагностируется и не
  инстанцируется автоматически. Dual-write продолжается: pointer пишется
  на UID **instance-member** (world-копии), не на член источника — иначе
  существующие читатели реестров (`layouts_for_world`,
  `load_relief_templates_for_world`) резолвят engine-тело вместо
  world-owned копии и изоляция правок инстанса ломается ещё до шага 5b.
- **Проверка:** remap детерминирован, повторный импорт/инстанс сохраняет
  UID и refs, internal refs переписаны / внешние нет, world-side refs
  ремапнуты, publish не трогает исходник, правка engine-библиотеки не
  трогает инстансы, dependencies не создают инстансов; исторический тест
  отказа по `local_uid` заменяется в 4c проверкой независимых UID одноимённых членов.
- **Done:** instantiate/publish покрыты тестами; re-instantiate и
  member-copy — следующий шаг.

### Шаг 4c — re-instantiate (preview/confirm, hold-by-use) и member-copy — выполнен 2026-10-11

- **Цель:** обновление инстанса до новой редакции источника без
  деструктивности + копирование отдельного члена между паками автора.
- **ТЗ:** `tz_template_library_packs.md` §0.1, §1.1, §2, §4.
- **Файлы:** pack application service (расширение), referenced-set
  resolver (ref-поля доменных адаптеров, ТЗ §1.1), integration tests.
- **Контракт:** re-instantiate — явная операция, требующая
  **подтверждения пользователя** (ТЗ §2, уточнение 2026-10-09):
  двухфазная библиотечная механика preview → явное решение/token — preview-вызов
  возвращает «изменения при обновлении» (diff текущих тел связанных
  `pack_copy` и подготовленного результата по ТЗ §2) и удерживаемых
  членов → повторный вызов с
  явным подтверждением; без него write не выполняется, silently не
  перезаписывается; provenance и pin-набор сохраняются. Авторские
  `authored` и независимые `member_copy` сохраняются; конфликты UID
  с новым составом показываются в preview, совпадения читаемых имён
  конфликтами не являются. Связанные `pack_copy`, удалённые
  автором в новой редакции источника, исключаются из инстанса, только
  если не используются миром — не pinned и не referenced (ТЗ §1.1).
  «Используемый» = pinned ∪ referenced: referenced — computed-множество,
  резолвер считает его по ref-полям адаптеров потребителей (ТЗ §1.2);
  persisted-таблицы referenced нет. До шага 5a выборка идёт по
  membership (`owner_world_uid` мира + default-паки) — тот же состав,
  что даст эффективный каталог; 5a подменяет её фасадом без смены
  семантики.
  Используемый член удерживается в инстансе со статусом «удержан по
  использованию» — computed по provenance (контракт шага 2), колонки в
  members нет; source-пак удалён целиком ⇒ «source deleted». Выборка по
  `source_template_uid` (не per-pack) контрактом не требуется — если
  резолверу понадобится, индекс `idx_library_pack_members_source`
  добавляется в `0001_initial.sql` в этом же шаге (в B-2 его сознательно
  нет: индекс без запроса).
  Member-copy (ТЗ §0.1): независимый новый `template_uid` через
  `app.ids.runtime_uid()` с проверкой уникальности и повтором при
  занятости, `creation_kind=member_copy`,
  provenance на источник, `local_uid` может сохраняться и повторяться
  (не идентичность и не unique-ключ); зависимости проверяются и диагностируются без
  автокопирования; refs в теле не переписываются — внутренние refs
  исходного пака становятся внешними и разрешаются по доступности.
- **Проверка:** preview перечисляет изменения полей при обновлении и
  удерживаемых членов; write без подтверждения не выполняется; член,
  удалённый в источнике и используемый миром (pinned ∪ referenced),
  удерживается, неиспользуемый — удаляется; member-copy независим, с
  provenance и без перезаписи refs.
- **Done:** lifecycle паков полный; bundle-секции и routes — шаг 4d.

#### Утверждённое исправление идентичности template-членов — 2026-10-11

Идентичность — только `template_uid`. Читаемый `local_uid` не является
второй идентичностью, может повторяться внутри пака/мира и не блокирует
копирование. Автопереименование не требуется. Прежний открытый вопрос
выбора занятого ключа закрыт отменой этого ограничения (ТЗ §0.1, §1.1–2).

При реализации 4c необходимо согласованно проверить и исправить:

- UNIQUE(pack_uid, library_kind, local_uid) в `0001_initial.sql`,
  интерфейсы/реализации member-репозиториев и CRUD/collision-gates;
- сопоставление re-instantiate по provenance сохранённых UID, не по имени;
- ремап пака с одноимёнными членами: разные исходные UID не должны
  сводиться в один целевой UID по одинаковому local_uid;
- pins template-членов — по `(library_kind, template_uid)`, с remap
  по uid_map; переход со старого key-based формата требует проверки
  однозначности, без выбора первого одноимённого члена;
- ссылки/lookup template-сущностей — по UID; автоматический override
  default-шаблона по совпадению читаемого имени отменён;
- body-writers и библиотеки: вычисление UID из system_name не должно
  подменять явно назначенный UID копии; обновить соответствующие тесты;
- manifests/bundle и пункты 4d/5a/5b: перенос назначенных UID и pins,
  без восстановления идентичности по local_uid.

Это исправление template-контракта имеет приоритет над прежними
key-based формулировками/проверками завершённых шагов 2–4b и описаниями
4d/5a/5b ниже; их реализация требует указанного аудита. Семантика ключей
deferred N+1-доменов этим решением не меняется. Код/DDL исправлены в шаге 4c.

#### Утверждённый UID полного remap пака — 2026-10-11

- **ТЗ:** `tz_template_library_packs.md` §2; DET-1 в
  `project_data_storage_tz.md`.
- **Правило:** новый UID члена детерминированно получается в центральном
  `app.ids` от **целевого pack_uid + исходного template_uid** в namespace
  библиотечного домена; local_uid/system_name/display_name не участвуют.
  Каноническая сериализация и хэширование — только внутри app.ids;
  API расширяется там, локальные hash/UUID/seed-композиторы запрещены.
- **Применение:** instantiate_pack движок→мир и copy_pack/publish
  мир→движок используют одно правило. UID-map ключуется исходным UID,
  поэтому одноимённые члены не объединяются. Внутренние refs и затронутые
  world-side refs/pins следуют uid_map; provenance указывает на исходник.
- **Повторное обновление:** сохранённые UID связанных членов остаются
  прежними, включая инстансы, созданные старой формулой; matching — по
  provenance. Новая формула применяется только к новым членам. Member-copy
  отдельно использует случайный runtime_uid; импорт переносит сохранённые
  UID без перевычисления. Валидация различает способы создания и не
  проверяет remap UID формулой от local_uid.
- **Файлы реализации:** `app/ids/`, `libraryPacks/remapOps.py`, задача
  re-instantiate, domain body-writers, UID-проверки manifest/bundle,
  `tests/test_deterministic_ids.py`, тесты library-packs 4b/4c.
- **Проверки / Done:** одинаковые входы remap дают одинаковый UID;
  разные source UID с одинаковым local_uid дают разные целевые UID;
  другой target pack даёт другой UID; переименование исходника не
  меняет соответствие; старый инстанс не меняет PK при обновлении;
  новые члены и refs/pins следуют одной uid_map; обе операции полного
  копирования используют центральный API. Реализовано в шаге 4c.

**Проверки реализации уточнений:** независимые копии одного оригинала
имеют разные UID, в том числе при одинаковом local_uid в одном паке;
копирование не требует переименования; pins и ссылки различают такие
копии по UID; full-pack remap не объединяет их; импорт копии сохраняет UID; чужой source-пак у
member-copy не даёт ложного удержания; authored/member-copy переживают
re-instantiate; refs из другого доступного пака/embedded layout
удерживают цель, чужой мир и pointer — нет; технические remap-различия
не создают ложного diff, пользовательские изменения показываются;
preview не пишет и использует ту же подготовку тела, что применение;
confirm с актуальным token применяет показанный план; изменение
значимых входов делает token устаревшим и возвращает новый preview
без записи; confirm без token не пишет; конкурентная запись не может
проскочить между повторной проверкой и применением.
Удаление здания и его структуры не создаёт ложного удержания старой
ссылкой; сохраняемая member-copy удерживает структуру; цикл удаляемых
кандидатов без внешнего использования удаляется; pinned-кандидат
удерживается вместе с цепочкой необходимых кандидатов; preview и
применение получают одинаковое замыкание удержания при тех же входах.

#### Обязательное переиспользование политики библиотек в 4d — 2026-10-12

- **Очередность уточнена пользователем 2026-10-13:** world archive импортирует
  сначала мир, затем его библиотеки в рамках того же архивного пака и общей
  UOW. Copy создаёт новый мир и импортирует библиотеки тем же механизмом
  с согласованным remap. Writer использует world row внутри caller UOW;
  отдельный контекст ещё не созданного мира не требуется. PolicyRequired,
  stale и ошибка откатывают все изменения до ответа, включая world row.
  Обновления через библиотеки и отдельный импорт в мир используют его world
  scope; engine library import не требует мира. Проверить стабильность
  preview/token при повторе copy с новым UID.

- C-5 предоставляет `ArchiveContents.library_packs` и optional
  `write_archive(..., library_packs=...)`: typed manifests и bodies по UID.
  4d использует этот шов; архив не отправляется в name-based FS importer,
  UID-path mapping не реализуется повторно. Guard world-import C-5
  заменяется полноценной общей policy/validation/apply интеграцией только
  после подключения всего library pipeline, без отбрасывания metadata.
- Все решения о записи импортируемых паков и членов проходят через общую
  цепочку `LibraryWriteInspector → LibraryWritePolicy → LibraryWritePlanner
  → LibraryWriteExecutor` и orchestration L-4. Bundle передаёт источник,
  scope и явные решения; собственные правила `copy|replace`, silent upsert
  и обход executor в handlers запрещены.
- Default copy задаёт нового владельца импортируемого мира;
  библиотечные решения проверяет общая policy. Копирование мира не разрешает
  неявный replace библиотечных записей и не подменяет decisions/token.
  Операции carry/attach/mint следуют §4.2, не меняются из-за унификации policy.
- Полный план библиотечной записи готовится до library apply; временная
  world row уже доступна в общей UOW. Используется одна
  карта remap для переносимых паков, членов и межпаковых refs. Формулы UID,
  provenance, remap тел и retention переиспользуются из L-3 и 4b/4c;
  параллельная реализация этих механизмов в bundle запрещена.
- Проверка актуальности и применение библиотечного плана входят в общую
  UOW импорта мира вместе с entity handlers. Executor L-4 должен работать
  в caller UOW без самостоятельного commit; ошибка в любой секции
  откатывает мир, паки, membership и тела целиком. Этот контракт —
  обязательный вход 4d от L-4.
- HTTP сериализует общий preview/decisions/token протокол L-5; библиотечный
  конфликт возвращается как HTTP 409 `status=policy_required`. Первый запрос
  с необходимостью выбора и повторный запрос со stale token не сохраняют
  никаких изменений: временная world row откатывается вместе со всей UOW.
  Используется один library negotiation без второго confirm-механизма.
- Экспорт использует существующие read/adapters и archive codec, не выбирает
  write policy и не изменяет библиотеки. Транспорт C-4 не расширяется этим
  требованием; подключение world-owned библиотек выполняется в 4d.
- **Приёмка/Done дополнительно:** интеграционные проверки подтверждают
  использование общей policy/planner/executor, отсутствие обходных upsert,
  preview/stale без сохранённых изменений, согласованный remap межпаковых refs и rollback
  библиотечных изменений при ошибке entity-секции. Одинаковые библиотечные
  входы и scope дают одинаковые решения через отдельный library-import и
  world bundle. Без этих проверок 4d не закрывается.

    не создаёт — оно уже покрыто инстансом; одинаковый local_uid допустим и не является конфликтом;

    POJO без SQL-строки) → диагностика по §5, pin не создаётся.

  отличается от члена источника, на который мапится pointer, весь этот
  source-пак мигрирует через legacy-маршрут (тела → `legacy`-члены,
  pointer'ы → pins) — instantiate для него не вызывается. Иначе
  instantiate вернул бы исходное тело (silent data loss правок мира),
  одинаковый local_uid не запрещён; основание legacy route — сохранение изменённого тела без silent overwrite. Точка миграции — compatibility import world-row до normalize (SQL hydrate не пишет):
  bundle и fixture-путь по явной карте refs шага 3 (ТЗ §4 legacy-этап);
  отдельной SQL-миграции нет — локальные БД пересоздаются по
  schema-policy.
  Идемпотентна по `source_pack_uid`: инстанс источника уже есть
  (создан dual-write шагов 4a–4c или пришёл манифестом в bundle) →
  пропуск инстанцирования, дописываются только pins. Миграция никогда не
  вызывает write-путь re-instantiate — перезапись тел выполняется
  только по подтверждению пользователя (шаг 4c), вне миграции.
  Поля `context`/`imported_at`/`display_template_name`
  entries не переносятся (`context` выводится из тела, остальное —
  диагностика строки). Потребители `by_system_name` мигрируют на UID либо
  разрешение через эффективный каталог — lookup без владельца после снятия
  UNIQUE неоднозначен (ТЗ §3); перечень call-sites фиксируется в этом шаге.
  При переключении читателей на фасад их собственная unresolved-эмиссия
  (`reject_unresolved`/`REF_W_UNKNOWN` в `layouts_for_world`,
  `load_relief_templates_for_world`, `export_bodies_for_world`)
  снимается — событие одно на границе resolve (ТЗ §7); доменный отказ
  relief сохраняется через `resolve_fallback` адаптера, не через
  дублирующий reject в caller. После переключения всех читателей поля
  реестров, аксессоры и pointer-write path удаляются — transitional
  dual-write шагов 4a–4c снимается.
- **Проверка:** миграция мира даёт pins по всем резолвимым pointer'ам +
  полный инстанс для user-паков с логом расширения каталога; pointer на
  default-член и на член уже присутствующего world-owned пака даёт pin
  без инстанса; изменённое тело гонит весь source-пак через
  legacy-маршрут без instantiate; повторная миграция и dual-write

  caller не читает реестры (source-grep); transitional `get_by_system_name`
