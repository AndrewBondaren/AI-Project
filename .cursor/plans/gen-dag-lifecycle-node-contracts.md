# Lifecycle: локальные ноды варианта А и пакет согласования

2026-11-21. Поручение пользователя: завершить POJO, предложить типизацию секции, точно определить node contracts и выдать владельцам ограниченные задания. Это проектирование до реализации, не code-go. Основной план — entity-lifecycle.md; развитие Б — lifecicle-todo.md.

## Фиксированный scope

IN: готовые typed inputs; четыре pure prepare-операции и pure prepare_section; пять operation leaf; exact generic POJO/evidence/refusal; native секция; Output→Input до существующего PatchSet/apply; декларация atomic boundary и синтетические проверки. OUT: реальные NPC/прочие предметные объекты, их producers/read pipelines/SQL adapters, миграция legacy, production wiring, read_world, физический Delete, settings, bulk API, родитель Б, overlapping chains, engine checkpoint/restart. Отсутствие OUT не блокирует локальную приёмку. Необходимая внутри IN типовая схема не переносится в TODO под видом внешнего producer.

## Node cards — предложение к freeze

### Сведение с первым координатором: representation и coverage

Рекомендация общей сверки 2026-11-21: взять section-level domain_evidence из PrepareLifecycleSection без фильтрации, копирования по patches и изменения порядка. LifecycleSection[P,C](DomainSection[P]) добавляет domain_evidence:tuple[C,...]; C замкнут на synthetic CoverageA|CoverageB. Patch сохраняет только header+prepared. Это минимальная owning representation delta; нормативные declarations и paths должен синхронизировать Lifecycle. Общая приёмка этим не объявляется. Evidence index адресует section.domain_evidence[i]; прежний запрет этого пути был следствием отсутствия поля и должен быть снят после принятия дельты.

Construction recommendation: LifecyclePreparationBinding[Q,P](request_model,prepared_model), nested class constructors выводятся из публичных annotations при construction; section binding содержит request_model/section_contract/closed patch_bindings, section_model только из contract. Plain union PatchAB = A | B | ... на shared admission boundary, без PEP695 TypeAliasType, который actual SectionContract не unwrap. Exact-class mapping не подменяется runtime dispatch по nested kind. Synthetic named classes только tests/support.

Главный remaining IN — semantic coverage, не сохранение одних refs. Snapshot admitted refs/resolved dependencies удостоверяют membership/fingerprint, но не соответствие предметного payload заявленному effect. Producer и проверяющий семантику — owning synthetic domain participant; Lifecycle проверяет отношения effect/typed entity/change/base/evidence, Snapshot только common admission/transaction. Предложение для owning проработки: immutable typed effect witness привязан к exact subject section/patch content и Q; subject owner проверяет соответствие witness собственному payload в своём validate, Lifecycle получает согласованные typed данные для relational checks без foreign вызовов. Все validation должны пройти до любого apply по существующему порядку; не требуется последовательность «subject validate → Lifecycle validate» либо mutable proof-cache. Реализация передачи witness/typed view и неизменность между validation/apply требуют exact capability proposal, не считаются существующим API.

Lifecycle обязан предъявить необходимые поля/источники, subject mock — конкретный producer/verifier Input/Output/Error, Snapshot — ограниченную доставку общего контекста и refs без предметной интерпретации. Нельзя засчитать заявленный witness истинным по class/hash/membership, пропустить проверку source payload или ввести trusted=True. Нельзя требовать новые production domains/SQL. Equal Lifecycle retry не отменяет coverage/subject validation остальных patches и не означает их идемпотентность. Новые публичные стадии/общий context field не вводятся без совместного freeze.

### Повторная сверка C1–C3, 2026-11-21

Owning ответы появились. Exact class→patch construction и отдельный accepted lookup определены концептуально; это больше не отсутствие предложений. Для pure leaf подтверждена допустимость пустого error_types в actual NodeContract; предлагается E=Never, error_types=(), без error_policy/declared domain fault, domain refusals в Output.value. Static typing и runtime negative tests остаются evidence реализации.

Финальное сведение требует одной нормативной формы:

- Construction: PatchSet предлагает LifecyclePreparationBinding(request_model, prepared_model) с выводом nested model classes из public annotations; Lifecycle предлагает отдельные Models с пятью независимо переданными classes. Рекомендация координатора — минимальный двухполевой binding, nested classes извлекать/проверять один раз при construction. Для section — request_model, section_contract, closed tuple patch bindings; section_model брать из contract, не второе конфигурируемое поле. Нужна owning синхронизация, не изменение алгоритмов.
- Lookup: переиспользовать owning Lifecycle AcceptedChangesQuery / AcceptedChangesResultAB и ILifecycleAcceptedChangesReader.lookup_accepted_changes; не создавать параллельные Snapshot AcceptedChangesRequest/read. Current captures возвращаются как closed A/B tuple, accepted lookup отдельно, один borrowed scope.
- Apply refusal: обнаружено реальное несовпадение, не только имена. Lifecycle предлагает LifecycleApplyIssue(FieldPathError) + SectionRefused, evidence mismatch REJECTED; Snapshot — три relation DTO + LifecycleApplyRefused, все CONFLICT. Выбрать один owning контракт Lifecycle и согласовать semantic category/реальные operands со Snapshot; не сохранять два набора. Snapshot proposal evidence_index адресует section evidence, которого owning native section не содержит: это нельзя принимать без точного существующего operand. Отказы preparation и apply остаются разными границами.

Accepted-change order/no-op mapping совпадают: lookup before historical-before checks; equal → без новых history operations; absent → актуальные preconditions; different → conflict; mixed changed только новые refs. Это локальная совместимость, не успех остальных предметных patches и не публикация до commit. Нужен точный evidence→native dependencies trace: если section не хранит domain_evidence, обязательная apply-проверка должна иметь доступ ко всем необходимым данным через объявленные native operands/capabilities, без скрытого producer или trusted flag.

### Результат сверки owning proposals после D1–D7

Проверены entity-lifecycle-local-contracts.md, patch-set-lifecycle-section-typing-proposed.md, snapshot-lifecycle-atomic-boundary.md и actual engine/registration/nodeRegistry.py. Native closed union совместим с предложением PatchSet. Lifecycle exact prepare requests теперь intent/capture/admission, без operation_id; operation_id передаётся producer секции. Это явное уточнение mapping, не использование change_uid как publication identity. Technical generic [T,R] сохраняет T как вид, R как основание; node API использует named closed classes.

Рекомендуемая concrete карта для mock_lifecycle_world: engine.lifecycle.test_a.prepare_create/replacement/end/reactivate и engine.lifecycle.test_b.prepare_create/replacement/end/reactivate (каждый slash здесь обозначает отдельный полный NodeId), плюс engine.lifecycle.prepare_section. Итого девять регистраций, пять logical операций. Причина: registry хранит один contract на NodeId и проверяет exact contract identity; runtime overload по T отсутствует. Все synthetic named contracts/registrations находятся в test-support, production NodeId для несуществующих доменов не создаются. Старые четыре unqualified IDs в таблице ниже — logical обозначения, не одновременно регистрируемые A/B bindings. Итоговая карта остаётся предложением к пользовательскому freeze.

Для каждого X из Create/Replacement/End/Reactivate нужны named InputXA/OutputXA и InputXB/OutputXB на owning generic wrappers; request — exact closed owning request class; success value — exact corresponding named prepared class, плюс LifecycleFieldError/LifecycleLogicError. SectionInputAB.request — concrete PrepareLifecycleSectionAB; SectionOutputAB.value — LifecycleSectionAB | LifecycleSectionRefused. Wrong-T input/output отклоняется; повторного parsing в другой вид нет. Схемы ошибок подготовки предъявлены владельцем; они возвращаются value. Runtime exceptions/cancellation идут existing engine failure transport; новая доменная ошибка ноды не требуется только ради обёртки.

Три технических расхождения IN требуют узкого owning ответа:

1. Lifecycle описывает discrimination по nested intent.operation/entity kind, PatchSet — exact concrete class/канонический RECORD ID. Нормативным выбором wrapper предлагается exact immutable prepared-class→patch-class map; вложенные поля проверяют coherence, но не выбирают runtime public operation. Нужны точная construction signature, output model factory и validation roster, чтобы pure pipeline возвращал named prepared child, ожидаемый node contract. Synthetic classes не должны попасть в production dataModel.
2. Snapshot reader обещает LifecycleCapture с историческим change_uid lookup/completeness; owning LifecycleCapture[T] содержит лишь entity observations/last transitions и явно не обещает полноту истории. Нельзя объявлять эти outputs совместимыми. Владельцам нужен отдельный typed accepted-transition lookup или иной минимальный owning participant read result, не расширяющий pure capture чужими обязанностями. Синтетический fake достаточен; SQL не требуется.
3. Owning LifecycleSectionRefused — отказ pure prepare_section с issue paths его request. Snapshot использует то же имя для apply stale/duplicate conflict, которого нет в pure union. Нельзя конструировать apply diagnostics с фиктивными paths. Нужны exact apply carrier/diagnostic mapping к существующему SectionRefused/H2 и minimal append output; без новой pipeline и без копирования pure refusal. Изменения в общий H2 не предполагаются автоматически.

Локальный PASS: D1–D7, раздельные pure операции, native cardinality и возможность closed mixed section. Общая приёмка exact node/atomic mapping ещё OPEN только по указанным техническим стыкам и final registration freeze; OUT не блокирует. Код не разрешён этим review.

Семейство Lifecycle; все пять — самостоятельные operation leaf без Lifecycle parent. Вызывает существующая prepare_changes; hidden CALL между leaf нет. T означает конкретный вид сущности; замкнутая специализация задаётся composition, а не строковым dispatch в ноде.

## Типизация коллекции — рекомендация координатора

Апдейт 2026-11-21: пользователь принял D1–D7 из итоговой таблицы координатора. D4 — NoDomainMutation запрещён в локальной v1; D7 — порядок участников Replacement не влияет на semantic retry equality, порядок представления сохраняется. D6 — отдельная test-support фикстура `mock_lifecycle_world`, явно названная mock-миром; никаких реальных доменов/production world. Полная фиксация — entity-lifecycle-local-contracts.md. Эти решения больше не OPEN; exact типизация/регистрация/atomic mapping проверяются отдельно.

Раздельные типизированные prepare-вызовы возвращают конкретные prepared records. Общий prepare_section принимает закрытый union разрешённых специализаций и операций. Для проверки использовать два синтетических вида TestEntityA/TestEntityB, не production NPC. Конкретные имена и representation типов выбирает Lifecycle после проверки reuse; не добавлять fictional production entities.

Предлагаемый принцип: каждая native patch-оболочка сохраняет конкретный prepared record и inherited PatchData.header. Конкретная LifecycleSection содержит tuple закрытого union этих patches; один общий owning section key, не по секции на вид. Exact Python declaration/дискриминация/manifest предъявляются PatchSet и Lifecycle: записи должны сохранять вид после decode, не использовать Any, BaseModel, голый UID или открытый generic. Общий алгоритм не ветвится по TestEntityA/TestEntityB. Изменение разрешённого состава — composition/schema review, не модификация DAG-алгоритма. Это рекомендация, не утверждённый mixed-type wire contract.

100 независимых Create одного вида дают 100 prepared records и 100 patches в одной секции. Один Replacement со 100 участниками даёт один patch. При mixed наборе эти правила не меняются; участник не пересекается между переходами. Коллекция сохраняет входной порядок; ordinal — адрес, не зависимость состояний. Отказ не выдаёт частичную секцию. Bulk API не требуется для доказательства этих контрактов.

## Задания владельцам и условия ответа

Lifecycle: предъявить полные схемы четырёх requests/prepared outputs, typed refs/capture/reason/evidence, field/logic/section refusals и invariants; mapping всех полей и reuse existing types. Устранить конфликт «prepared уже native patch» против «native wrapper появляется в prepare_section». Предлагаемая граница: pure prepared record переиспользуется wrapper без копирования payload; один источник header. Дать pure helper ответственность и порядок checks/build, без IO. Proof от предметного mock должен иметь определённый контракт, а не trusted=True или фиктивное отсутствие required данных. Coverage/no-domain-patch конкретизировать на синтетике, не ждать реальных доменов.

PatchSet: проверить exact closed union двух видов, native wrapper/section types и registry/codec compatibility; как одна logical node registration получает closed POJO specialization без dynamic kind dispatch. Выдать точные declarations и synthetic admission/round-trip критерии. Не менять принятое ядро PatchSet, не требовать реальных domain adapters. Новые numeric IDs не назначать без общей сверки.

Snapshot: предъявить ограниченную atomic boundary для готовой Lifecycle section: какие проверки до transaction и внутри, кто проверяет source/base/evidence/duplicate change_uid, где assigned refs, validate/apply/receipt/CAS/commit/unknown. Отличить semantic predicates Lifecycle от Snapshot provenance и PatchSet output admission. Если handler является transaction participant, явно описать разрешённые capability/вложенные вызовы, без автоматического разрешения foreign writer по DI. Нужны typed протокольные обязанности и synthetic fake participant, не production SQL adapter, не перенос H3 Time на Lifecycle. Не переоткрывать принятый C1/C2 или порядок write flow.

Координатор: после owning ответов свести полную node Input/Output/Error карту, exact registration, рекомендации union и общий PASS/OPEN/FAIL только для IN. Ответ каждого владельца обязан назвать: что завершено; точные оставшиеся решения IN; зависимости OUT отдельно. Не выдавать runtime readiness за contract PASS и не возвращать OUT в blockers. Общие решения предъявляются пользователю; код не меняется в этом задании.
