# Динамические водные системы — consumer общего lifecycle

Статус 2026-10-20: отдельный доменный план, реализации нет. SoT: [гидрология — проект контрактов систем](../../docs/tz_terrain_hydrology.md#контракты-домена-динамических-водных-систем--проект), [lifecycle](../../docs/tz_entity_lifecycle.md).

## Границы и зависимости

`dataModel/hydrology/systems/` — участники, соединения, система, snapshot и вход/выход изменений. `application/worldData/hydrology/systems/` — consumer динамической связности. Все соединённые водные объекты образуют одну систему; уровни объектов могут различаться. Иерархия ocean > sea > lake, затем объём; при равенстве нет победителя. Типы участников — существующий GeographicSubtype. Lifecycle замещения общий, placement общий; собственные аналоги не создаются.

**Чистая архитектура, без кода-прецедента (решение мастера 2026-10-20):** домен проектируется по контрактам этого плана и ТЗ, а не по аналогии с существующими system-группировками. `RiverSystemIndex` — declare-time индекс U27, не модель; `relief/gradeVertexSystem` — иная семантика (каталог grade-инстансов), её форма не наследуется.

**Бюджет стоимости (решение мастера 2026-10-20):** система дорогая — consumer обязан быть инкрементальным, не пересчётным. Контракт: вход — snapshot + **change** (не периодический полный пересчёт); merge — union двух множеств членов, O(участники); split — переразметка только затронутой компоненты, ограничена её размером, не миром; выбор primary — иерархия + `V ≈ A_water × Δz` (простое тело, без сканов и интегралов). Полный обход графа воды допустим только при cold-start/first-bake.

**Метаданные ↔ материализация (решение мастера 2026-10-20):** consumer систем — чисто метаданный шаг: меняет membership/primary/уровни-системы и lifecycle-ссылки; **материализация у систем отсутствует** — она выведена из фактов тел (HY-12) и не дублируется. Контракт W-шага без явного указания обеих сторон неполон.

**Взаимодействие инварианта с системами:**

- системное изменение (merge/split/наследование уровня) — только metadata-update; **материализация последствий (границы воды, роли клеток) — событие для доменов-производителей** (HY-12), consumer клетки/z не трогает;
- направление строго двустороннее: producer materialization-факты → `WaterSystemsChange` (вход); consumer → системные записи + lifecycle (выход), без обратной записи в материализованный мир;
- наследование `z_water_level` детьми — метаданное: поле тела обновляется из системы; extent воды по новому уровню довычисляет fill-домен при следующем материализующем проходе, не consumer систем;
- persist одной транзакцией: метаданные систем/lifecycle + факты тел коммитятся вместе (L3/W3) — расщеплённый коммит «системы есть, тела старые» запрещён;
- runtime-изменение (связь добавлена/удалена вне bake) — та же схема: consumer обновляет системы, рематериализация мира — отдельный producer-проход по dirty-региону, не задача W.

Входные данные: водные объекты/контакты после HY-12 fill и river pass; U27 adapter учитывает authored-топологию рек. Domain consumer вычисляет новые параметры, общий lifecycle закрывает предшественников и создаёт преемников; application writer сохраняет их атомарно. Domain consumer не пишет z, не генерирует placement, не выполняет SQL.

## Шаги

### W0 — закрыть контракты связности и измерений

Цель: формализовать доменные входы consumer без скрытых решений.
ТЗ: гидрология § Контракты домена динамических водных систем; lifecycle.
Файлы: `docs/tz_terrain_hydrology.md`, этот план.
Контракт: остаются открыты расчёт объёма/исключение двойного учёта, критерий физического контакта (включая diagonal/подземные связи), участие INLAND_SEA/RIVER в выборе основного объекта. Consumer фиксирует факт разножидкостного union (`liquid` членов различается) — итоговый liquid определяет отдельный домен resolve материалов, вне W. Fate старых систем уже решена и повторно не согласуется.

**Нормализация члена (решение мастера 2026-10-20):** члены разнородны — зеркальные тела имеют уровень/объём, реки — поток. Не опциональные поля на общем члене, а discriminated union по `kind`:

```
WaterSystemMember { member_uid, kind: GeographicSubtype, params }
params = LevelledWater | FlowingWater   # строго по kind, без str-полей

LevelledWater { declared_level, z_water_level, approx_volume }   # ocean/sea/inland_sea/lake
FlowingWater  { /* поток: параметры по контракту рек U27 */ }   # river и протоки
```

Следствия контракта: кандидаты primary — только `LevelledWater`-члены (иерархия ocean>sea>lake → объём); `PHYSICAL_MERGE`-связь допустима только между levelled концами (уровни выравниваются наследованием); `RIVER_LINK`/`FlowingWater`-член зеркальный уровень не получает.

**Наследование уровня — каскад (решение мастера 2026-10-20):** каждый ребёнок union — сам система; `z_water_level` наследуется по цепочке предков `PHYSICAL_MERGE`, не один раз от непосредственного родителя. Nested union (`{A,B}` → S1; `{S1,C}` → S2) → effective уровень A и B = уровень S2 — резолв идёт вверх до верхнего физического предка. Каскад работает **только по физическим рёбрам**: `RIVER_LINK` в цепочку наследования не входит (связность — да, уровень — нет; река соединяет водоёмы на разных высотах). Пересчёт инкрементальный: merge/split трогает только каскад затронутого поддерева, не мир. Прецедент механики — cascade-разрешение контекстов (родительские каналы → fold), не копия значений.

POJO-отражение каскада:

```
LevelledWater { declared_level, z_water_level }   # declared — свой (declared ∩ pour_point);
                                                  # z_water_level — effective после каскада
WaterSystemMember { ..., parent_system_uid }      # ближайший union-предок (цепочка = каскад)
WaterSystem     { system_uid, members, connections, primary_member_uid,
                  z_water_level,                  # уровень системы — источник каскада вниз
                  parent_system_uid | None,       # nested union: S1 может быть членом S2
                  lifecycle }
```

`z_water_level` члена читается только как результат каскада по предкам — локального переопределения «в обход родителя» нет; `declared_level` сохраняется для diagnostics/warnings (declared ≠ inherited → superseded warning).
Проверка: однозначные примеры связной и несвязной воды, равных объёмов, контакта через реку на разных уровнях.
Done: перечисленные вопросы закрыты до реализации алгоритма.

#### Пересыхание и восстановление — принято 2026-10-21

SoT: `tz_terrain_hydrology.md` § «Пересыхание и восстановление водоёма» и `tz_entity_lifecycle.md` § «Доменное состояние и существование сущности».

- W0/W1: явно разделить существующий водный объект с собственными UID/lifecycle, его гидрологическое состояние и текущее членство в действующей системе. Dry-state не кодируется завершением lifecycle или подменой `is_active`. Проекты POJO выше ещё требуют соответствующего уточнения; наличие согласованной семантики не означает готовность моделей.
- Полностью пересохшее озеро сохраняет котловину/authored-данные и identity, но имеет нулевой текущий объём, пустой мокрый footprint и не входит в текущий состав действующей воды. Сохранённое русло/котловина не подтверждает связь. Состояние реки определяется отдельно, без автоматического удаления вслед за озером.
- Изменение состава создаёт систему-преемник даже без разделения оставшейся компоненты. Split обрабатывает только затронутую компоненту; пустая активная система не создаётся. Изменение только объёма/уровня само по себе не перевыпускает UID системы.
- Восстановившееся озеро имеет прежние UID/lifecycle. Восстановление состава/merge создаёт новую систему и новый change, исторический родитель не реактивируется даже при совпавшем составе; ссылки ведут на непосредственных предшественников. Retry прежней операции остаётся идемпотентным.
- W2/W3 приёмка: S0={L1,L2,L3,R} → сухой L2 → одна/несколько систем-преемников → наполнение того же L2 → S2 с исходным составом и новым UID; S0 остаётся исторической. Проверить bridge/non-bridge, сухую/сохранившуюся реку, исчезновение всей воды без пустой системы, сохранность рельефа и участников, атомарность/rollback/fresh read и retry каждого изменения.
- HY-12 поставляет fill/объём/связи, W/L хранит состояние объектов/членство/историю; отсутствие WaterBody в пустом fill не уничтожает durable-объект. Позиционные auto-* не объявляются durable identity истории.

**Шов HY-12/4 реализован 2026-10-21.** Общие `WaterSystemKind`, `UidKind.WATER_SYSTEM/LIFECYCLE_CHANGE`, `app/ids/waterSystemIdentity.py` и producer-факт `PhysicalWaterUnion` созданы. Подробный контракт — `tz_terrain_hydrology` § «Производитель физического union и identity». HY-12 выдаёт фактические parent UID, вложенные физические связи и effective levels в одном результате с клетками. Первый pure bake/preview имеет логическую bootstrap operation; stateful W/L caller обязан передавать новый durable change UID для нового события и тот же UID при retry. Это не готовые WaterSystem/EntityLifecycle consumer/writer. На W0 остаются wet/dry POJO, измерения/двойной учёт, ranks и stateful application-boundary; базовая формула UID/различение видов не открываются повторно.

## Scope

HY-12 даёт физическую воду и её факты; W-трек — связанную динамическую систему. HY-10 отвечает за L0 bands/wire, GEO-1 — designed water/continental field. Эти треки не являются скрытыми задачами W0–W3. Не менять DAG и не коммитить.
