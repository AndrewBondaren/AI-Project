# LOD-A0. Продолжение смены покрытия региона

Первый проверяемый потребитель — `StateChangeConsumer.evaluate`. Регион может оставаться лесом с уже накопленным прогрессом перехода в степь. Здесь можно различить доменный результат, незавершённый процесс и то, что наблюдатель видит на карте. В production метод вызывается при изменении декларации с `elapsed_ticks=0` и календарной меткой аудита. Положительный интервал сейчас передаёт тестовый caller. Автоматический выбор FAR/NEAR для региона отсутствует. [Caller деклараций](../../backend/app/application/worldData/regions/declaredRegionEdit.py#L57) · [Caller с длительностью](../../backend/tests/test_region_state_change.py#L146)

## Выполненный сценарий

На временном файле SQLite применена штатная миграция. Использованы [registry, policy, request и климатический test provider](../../backend/tests/test_region_state_change.py#L34), реальный scorer, writer и новый экземпляр Database после закрытия. Вход постоянен — осадки 0, цель steppe, inertia леса 4, strength 1, общий маркер at=42. Единица опыта — входной tick региона.

1. Контрольный UID обработан одним батчем elapsed=4. Опытный UID в том же мире получил elapsed=2. В БД текущий тип forest, pending_target=steppe, progress=0,5.
2. На границе детализации тот же UID четыре раза спроецирован через overlay_terrain для чтения покрытия. Все четыре результата — forest. Выбран более частый расчёт с шагом 1. При самом переключении writer не вызывается.
3. Соединение закрыто. Через новую Database и новый repository прочитана строка и проверено полное равенство восстановленного RegionState промежуточному. Новый consumer выполнил два вызова elapsed=1.
4. Проверено равенство всех полей итоговых моделей за исключением заведомо разных UID. Итог — steppe, last_eval_tick=4, одна запись перехода и один materialize signal на последнем шаге. Это проверка смены cadence при одинаковых фактах, с чистой функцией проекции. Запуск DAG, фактический L2 read и доставка сигнала не входили в опыт.

Граница обобщения важна для выбора первого примера. Ветка spatial создаёт child UID по seed и начинает нового ребёнка с current_type родителя, без переноса накопленного pending/progress. Родитель при этом только увеличивает last_eval_tick. Если при progress=0,5 передать spatial и два тика, новый ребёнок накопит только 0,5, тогда как whole-region контроль уже перейдёт в степь. Это вывод из [ветвления evaluate](../../backend/app/application/worldData/regions/stateChange/consumer.py#L84). Такой split нельзя считать эквивалентным повышением точности.

## Два наблюдателя

Пусть A и B видят один UID на перекрывающихся участках, A запрашивает частый расчёт, B — редкий. Оба могут читать одну принятую версию. Текущий overlay делает собственный batch read на запрос, поэтому между запросами writer может изменить видимый тип. Два последовательных evaluate с elapsed=2 за один и тот же интервал дадут четыре тика вместо двух. Параллельный read-modify-upsert также допускает потерю прогресса при отсутствии внешней сериализации. Контракт [consumer](../../backend/app/application/worldData/regions/stateChange/consumer.py#L1) возлагает сериализацию на caller. Одна блокировка не распознаёт последовательный повтор интервала.

Критерий C1 для примера — одно вычисление для общего UID, исходной ревизии и интервала, два независимых чтения результата. Уход A может снизить частоту следующих вычислений. Удаление continuation и повтор последнего интервала изменили бы мир. Для stale/retry нужен проверяемый исход до применения effects.

## Согласованный приёмочный сценарий для LOD-C1

Начало отсчёта — T0. В тестовых данных сутки равны 86 400 с, исходный progress равен 0,5, цель — steppe, порог — 1. Симуляция при заданном воздействии даёт скорость 0,1 за сутки. При постоянных входах первый момент достижения порога вычисляется как T0 + (1 − 0,5) / 0,1 суток. В history записывается момент перехода T0 + 5 суток. Оставшиеся трое суток обрабатываются для степи. Если воздействие меняется, расчёт делится в момент изменения.

Будущий тест сравнит три расписания одного процесса на одном исходном мире: FAR одним батчем на восемь суток, NEAR восемью суточными шагами, FAR до конца четвёртых суток и NEAR после смены режима и reopen. При reopen ожидаются лес, цель steppe, progress 0,9 и граница уже обработанного времени T0 + 4 суток. Для каждого расписания ожидаются степь на конец восьмых суток, одна запись перехода с одинаковой датой и одно принятое последствие. Последняя проверка требует T5 и подключения региона к Snapshot.

### Отдельные пограничные тесты к реализации

| Граница | Что проверить |
|---|---|
| Порог внутри шага или точно на его конце | Завершить интервал за 1 нс до расчётного перехода, точно в момент перехода и через 1 нс после. Ожидать соответственно лес, степь, степь. В двух последних случаях дата события одинакова. |
| Общая граница двух шагов | Закончить первый шаг точно на пороге, сменить FAR→NEAR и продолжить. Повторить для NEAR→FAR. Переход учтён ровно один раз. Смена режима и чтение при нулевой длительности сохраняют историю и время. |
| Смена воздействия внутри батча | После трёх суток снизить скорость до нуля при той же цели. На восьмые сутки progress равен 0,8, история пуста. Сравнить с прогоном, разделённым в момент изменения воздействия. |
| Дождь на границе порога | Пусть T — точный момент достижения порога при засухе, а дождь останавливает накопление. При начале дождя в T − 1 нс регион остаётся лесом. При начале дождя ровно в T переход записывается один раз в T, затем применяется дождь. При начале в T + 1 нс дата перехода также T. Для каждого входа сверить историю при FAR, NEAR и reopen. |
| Reopen у границы перехода | Закрыть и открыть мир на последней принятой точке до события и сразу после его принятия. В первом случае продолжение создаёт событие один раз, во втором уже принятое событие читается с прежней датой. |
| Два наблюдателя и повтор операции | Перекрывающиеся области запрашивают один UID и интервал с разной детализацией. Проверить историю и последствия после конфликта и повторной доставки. Уход одного наблюдателя сохраняет continuation. |
| Отказ атомарной записи (T5 + writer региона) | Вызвать сбой до commit и потерю ответа после commit. После reopen в первом случае видна полностью исходная публикация, во втором — полностью принятая. Повтор с тем же operation_id приводит к одному принятому переходу. |

Это задание на отдельные исполняемые тесты. Прогон A0 выше проверял legacy ticks с постоянной меткой at=42. Согласованное правило Regions: метка события — первая представимая точка Time на достигнутом пороге или после его пересечения. Например, 100,4 нс от начала секунды дают метку 101 нс, а ровно 100 нс сохраняются. Округление выполняется один раз для метки события. Принятые границы TimeInterval остаются точными. При совпадении меток применяется согласованный порядок из LOD-плана. ## Вопросы на решение LOD-C1

**Решение владельца о длительности.** Длительность перехода леса в степь в мировом времени динамически рассчитывает симуляция региона. Даже при постоянных условиях момент завершения следует из начального состояния и хода процесса. Четыре тика в опыте выше — свойство выбранных тестовых данных. Критерий для C1: при одинаковом исходном состоянии и одинаковой истории воздействий сравнить метку завершения по согласованному правилу и принятый результат для разных расписаний вычисления, включая смену детализации и reopen.

- **DAG/settings.** Где объединяются требования двух observers и кто владеет правом обработать конкретный интервал? Как читатель получает принятую ревизию? Для [LS-T1–T9](../../docs/tz_lazy_simulation.md) остаются открыты EventBus, радиусы, cadence, NPC batch/unfold, дальние события, freeze клеток, overlap NPC и wiring климата. Значения этих политик из примера региона не следуют.
- **Time, настройки World и Regions.** T4 читает точку принятой публикации. Для следующего шага caller задаёт длительность в секундах и наносекундах, а `prepare_advance` вычисляет интервал от base.point и возвращает предложение. Принятым конец интервала становится после commit. World владеет календарными настройками `hours_per_day`, `calendars`, `selected`, `epochs`. Они определяют календарное представление точки. Частоту вызовов выбирает LOD/DAG. Владелец Regions должен решить, как выразить скорость перехода и inertia в единицах точной длительности, как мигрировать `last_eval_tick` и какую точку записать в history при пересечении порога. Если он сохраняет дискретный шаг, ему же нужно определить длительность шага и перенос остатка после reopen. Миграция явно отложена в Time-плане. [Prepare](../../backend/app/application/time/changes/advancePipelineOpenPipeline.py#L16) · [WorldTimeSettings](../../backend/app/dataModel/world/settings/timeSettings.py#L13) · [Граница миграции](./time-domain.md#L742)
- **Регионы.** Допустима ли смена только cadence при неизменных фактах? При пространственном split/merge кто переносит progress, историю, fingerprint и границы дочерних scope, и когда возвращать unsupported?
- **Snapshot/T5.** Передача целевой публикации уже реализована. При ожидаемой P и назначенном snapshot S сервис создаёт Q, передаёт обработчикам секций один `SnapshotApplyContext` с P, S, Q и общим `CommitScope`, затем выполняет `compare_append(scope, P, Q)`. Конфликт прерывает применение. T5 должен подключить запись часов к этому пути и подтвердить rollback и retry с тем же operation_id. Вопрос владельцу Snapshot — какой зарегистрированный handler и какие state/history refs обеспечат чтение continuation региона именно для Q после reopen или для исторической S? Вопрос Regions — какие данные перехода и какие последствия `MaterializeSignal` writer передаст в ту же операцию? Сейчас upsert по world/region использует `transaction_if_needed`, а сигнал возвращается caller. Такая запись сама по себе не даёт истории по публикациям или гарантии доставки сигнала. Миграция writer регионов отдельно перечислена в Snapshot-плане. [Контекст](../../backend/app/application/worldSnapshot/contracts/context.py#L22) · [Назначение Q, apply и CAS](../../backend/app/application/worldSnapshot/service/worldSnapshotService.py#L100) · [Writer региона](../../backend/app/db/repositories/sqlite/regionStateRepository.py) · [План миграции](./world-domain-patches-snapshots.md#L820)
- **Spatial/Physics.** Каким публичным bounded read подтверждать покрытие на общей ревизии? Для водного потребителя нужны отдельные PH-LOD/PH-HANDOFF transform, баланс и допустимая погрешность. Проверка региона не устанавливает эквивалентность AGG/LOCAL воды. [Spatial](./spatial-distribution-domain.md) · [Physics](./physics-spatial-dynamics.md)
