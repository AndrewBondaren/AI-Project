# GEO · WATER_KIND_MISMATCH · scoped D1

**Статус — D1 согласован 5 ноября 2026 года.** Приняты три решения:

1. Hydrology / Water Input владеет WaterKindMismatchIssue с source_uid, authored_kind и physical_kind. На стыке доменов эта причина возникает в materialize_water: физический класс уже вычислен, а решение сохранить authored kind и назначить FALLBACK принимает Hydrology.
2. Checked path указывает на поле результата WaterBody.kind. Исходный объект идентифицирует source_uid.
3. Граница D2 — публикация и строгий round-trip fine-water envelope через SURFACE_MANIFEST. Совместимость open-water source v1 остаётся отдельным решением владельца storage. ERROR-CONTRACTS владеет контрактом checked path и переносом конкретной причины, владелец surface codec согласует wire ID до публикации.

Основание — [диагностика discover](geo-i11-3-discover-diagnosis.md) и [отчёт I11.3](geo-i11-3-d2-verification.md). В адресном запуске прошли пять сценариев (ранний отказ, admission коллекторов, FAILED support, cap геометрии и cap плит). В полном discover на d01cf073 зарегистрированы 245 errors и один failure на 892 теста. Из 61 записи с барьером в water_issue ровно 58 приходятся на mismatch. Это число записей, включая ошибки setup. Две WATER_TERRAIN_UNRESOLVED и одна WATER_CANNOT_HOLD принадлежат отдельным ERROR-ветвям.

## Откуда берётся факт

В [первом репро](../../backend/tests/geo1/fine_water/test_fill.py) два объявленных BasinSpec с UID a и b занимают соседние квадраты 6×6 при y=2…7, x=2…7 и 8…13. Оба задают LAKE, дно −5, уровень 0. fill передаёт specs и принятую placement в WaterBodyPlanner.fill_fine. FineWaterPublicationJob.publish проверяет refs и footprints и вызывает FineWaterJob.fill. Тот применяет carve к scratch и передаёт diagnostics.append в assemble_water_bodies.

[water_sources](../../backend/app/application/worldData/generators/hydrology/water/waterSources.py) сортирует declarations по source_uid и выставляет authored=True. После resolve уровней assembler вызывает [materialize_water](../../backend/app/application/worldData/generators/hydrology/water/waterMaterialize.py). Labelled fill даёт owner-index клетки, component_fills объединяет соприкасающуюся воду. Классификатор получает None для authored каждой компоненты, чтобы независимо вычислить physical kind. Общая компонента крупнейшая на default_water_level=0, поэтому physical kind равен OCEAN. В цикле authored доступны пары (a, LAKE, OCEAN) и (b, LAKE, OCEAN). UID здесь — sources[i].spec.source_uid. Для authored он же станет water_body_uid, location_uid и declared_basin_uid. Вычисленный по anchor auto_uid используется для remap естественных источников. Отдельный UID «физического океана» причину не идентифицирует.

Декларация определяет kind каждого authored тела, физический контакт определяет общий уровень и union. Поэтому kinds_by_source[i] получает spec.kind: в результате остаются два тела LAKE с lake-ролями их мокрых клеток, union с участниками a и b и mapping по исходным UID. Именно materialize_water в ветви authored и spec.kind != kind передаёт FALLBACK. Сегодня water_issue пытается собрать базовый FieldPathError из строкового кода и tuple, конструктор прерывает поток до callback.

## Согласованный контракт

Проверены ближайшие типы. BasinKind уже выражает обе классификации. WaterPreparationCode.KIND_MISMATCH сравнивает geographic subtype с подготовленным kind в placement adapter. WaterDesignTypeError выражает ошибку подготовки; WaterSourceIssueCode описывает frame, revision и пригодность фактов canonical source. RiverRouteDiagnostic относится к маршрутам рек. Ни один из них не переносит эту пару BasinKind и authored UID как причину продолжения materialize. PlanDiagnostic уже переносит конкретный FieldPathError и отдельно disposition.

Предлагается один конкретный Hydrology WaterKindMismatchIssue(FieldPathError[HydrologyMaterializationCode]) с единственным членом enum WATER_KIND_MISMATCH и таким же wire value. Обязательные поля — source_uid: EntityUid, authored_kind: BasinKind, physical_kind: BasinKind и унаследованные code, path, message. Оба kind различны. Текст сообщает о сохранении authored kind и может выводить UID, машинное сравнение опирается на поля. Disposition принадлежит producer, внешняя пара для этой ветви всегда FALLBACK.

Путь указывает на поле **результата** WaterBody.kind, в котором сохранено authored значение. BasinSpec — frozen dataclass, тогда как CheckedPath.root принимает BaseModel. WaterBody уже является POJO Hydrology с полем BasinKind и входит в SURFACE_MANIFEST. Фабрика причины получает source_uid и оба kind прямо из цикла и связывает поле через CheckedPath.from_pydantic_loc(WaterBody, ("kind",)). При отсутствии поля построение завершается ошибкой. Контракт path — ValidatedFieldPath с root ModelIdentity.of(WaterBody), одним FieldSegment того же owner и name="kind", projection() == ("kind",). Валидировать этот точный путь и неравенство kind также при восстановлении. UID хранится как контекст объекта отдельно от пути.

## Транспорт и критерии D2

1. Вынести доставку уже построенной причины в waterDiagnostics, сохранив действующие маршруты. Для mismatch строить конкретную причину прямо из аргументов producer. Остальные коды за пределами среза. С emit проверить один PlanDiagnostic на каждого несовпадающего authored owner данной компоненты и отсутствие повторной записи в ctx или лог. При совпадении kind либо естественном owner этот код отсутствует. Сравнить исходные UID, оба enum, checked path и disposition, включая вход с обратным порядком specs.
2. Проверить обе стороны общего assembler. WaterBodyJob._materialize и FineWaterJob.fill передают diagnostics.append; HydrologyGeneratorService.apply вызывает assembler без callback. Без emit validate_only и collect_only доставляют конкретный issue через report_issues в ctx.errors; обычный runtime вызывает log_issues единожды на факт. Проверять именно тип и поля аргумента доставки и отсутствие второго маршрута. Fill продолжается с authored результатом. На fine-пути только disposition ERROR становится PlanBuildFailure; FALLBACK доходит через дедупликацию в PlanBuildResult.diagnostics.
3. Surface codec — явные уникальные стабильные bindings для конкретной записи и enum в SURFACE_MANIFEST, проверка существующих bindings BasinKind и path. На PlanDiagnostic проверить strict decode и decode_bounded, точный type(issue), enum-типы и значения, UID, root/segment, message и FALLBACK, затем побайтный re-encode, также после cold restore со штатным manifest. Отрицательные случаи — чужой корень, чужое поле, равные kinds, неизвестный код или wire ID. Строковой dump причины не удовлетворяет этому критерию.
4. Реальный fill_fine должен опубликовать PlanEnvelope[FineWaterResult] с обеими диагностиками, телами LAKE, union и mapping. Проверить refs входных PRE_WATER_SURFACE и WATER_PLACEMENT и output_fingerprint(payload, dependencies, diagnostics, SURFACE_MANIFEST), strict round-trip envelope и FineWaterPublicationJob.admit_result на том же ref. Удаление причины при сохранении ref должно провалить проверку fingerprint. [Execution](../../backend/app/application/worldData/generators/hydrology/water/planning/fine/execution.py) · [Publication](../../backend/app/application/worldData/generators/hydrology/water/planning/fine/publication.py)
5. Отдельная граница — [open-water source v1](../../backend/app/application/worldData/generators/hydrology/encoding/sourceSchema.py). Таблица пар уже содержит mismatch/FALLBACK, однако admission требует exact FieldPathError, plain tuple path и str code и сначала проверяет lock closure. Это самостоятельный storage handoff из GEO. Владелец codec должен определить версию/совместимость до выпуска нового wire-типа. Критерий fine-water использует SURFACE_MANIFEST; молчаливое расширение или перегенерация source-v1 lock в D2 исключены.
