# SR-02 — переход потерянного RUNNING stage к явному recovery CALL

2026-11-26. **PROPOSED, plan-only** для сверки DAG-координатором и решения пользователя. Этот файл не разрешает реализацию, не назначает NodeId/финальный workflow и не меняет owning API Artifacts. Основания: [stage recovery contract](artifacts-stage-recovery-contract.md) § «Предлагаемая DAG-цепочка и outcomes», SR-02; [identity transport plan](dag-artifacts-identity-transport.md) §§ 5–7; `.cursor/rules/dag-generator-interface.mdc`. Направление A (Artifacts владеет stage-attempt authority) используется как предпосылка предложения, пока общий контракт остаётся OPEN.

## 1. AS-IS и запрет на повтор

`InvocationCoordinator.__init__` сейчас переводит каждый `RUNNING` в `READY`; `DAGExecutor._schedule_invocations` затем вызывает `begin` и запускает child. Для отдельного эффектного stage это может повторить запись без решения Artifacts. `InvocationGraph.join_complete` принимает только `SUCCEEDED/FAILED/CANCELLED`; `InvocationCoordinator.event` выдаёт `CallRuntimeFailure` лишь после `FAILED` без объявленного Error. Поэтому простая замена `RUNNING` на `FAILED` тоже неверна: неизвестный исход stage не является установленным runtime failure, а parent не получает отдельного типизированного сигнала. `CheckpointCodec.restore` проверяет registry и payload; `ActiveCheckpoint.resume` выполняется под существующим claim, `OwnedExecution.save` делает revision CAS. Эти механизмы сохраняются.

## 2. Public граница Engine (предлагается)

| Контракт | Точное предложение | Владелец и смысл |
|---|---|---|
| `NodeContract.interrupted_call: InterruptedCallPolicy = RETRY` в `application/engine/contracts/nodeContract.py` | Именованный enum `RETRY` / `REPORT_UNKNOWN`; default сохраняет обычные RUNNING→READY. Policy задаётся при регистрации target, не выбирается runtime по типу Artifacts и не меняется между рестартами. | Engine владеет состоянием вызова, домен решает, какой leaf требует owning recovery. Не является permission на stage retry. |
| `RegisteredContract.interrupted_call` в `dataModel/engine/dag/invocations/record.py` | Сериализуемая часть registry fingerprint; mismatch с `NodeContract` даёт `RestoreFailure` до CALL. Старый checkpoint без поля имеет явный legacy `RETRY` только для контрактов с таким же policy; для `REPORT_UNKNOWN` требуется новая checkpoint/contract version. | Engine checkpoint compatibility, без эвристики по имени ноды. |
| `InvocationStatus.OUTCOME_UNKNOWN` | Joinable состояние только child с `caller_invocation_id`, `caller_step`, `call_key` и policy `REPORT_UNKNOWN`; `terminal=None`, `error_index=None`. Исходный `attempt_counter`, `plan_revision`, input и caller bindings сохраняются. Root/обычный DAG dependency без CALL не получает это состояние: несовместимая регистрация/graph отклоняется. | Engine фиксирует отсутствие достоверного результата, не изображает domain outcome. |
| `CallOutcomeUnknown(lost_attempt: ExecutionIdentity)` в `application/engine/contracts/invocation/resumeEvent.py` | Отдельный вариант `CallResult`; `CallResults.get(key,target)` возвращает его с проверкой прежнего target и address. Это не `CallFailure`, `CallRuntimeFailure`, `CallCancelled` и не Artifacts Error. `lost_attempt` адресует child attempt без ссылки на несуществующую диагностику; доменные binding/generation в event не копируются. | Engine уведомляет parent о доказанной потере ответа без заявления о stage success/failure. |

`NodeContract` и `RegisteredContract` не принимают callback восстановления и не содержат Artifacts service/DTO. `CallTarget` сохраняет Input/Output/Error и версию; `CallOutcomeUnknown` добавляется в общий union результатов без изменения целевого Output/Error. Для stage recovery DAG parent уже должен иметь в своём типизированном continuation (из ранее допущенного stage input) точные `StageBinding` и потерянную `generation`; `lost_attempt` одного недостаточно. Owning Artifacts определяет и валидирует `StageRecoveryInput(binding,generation)`, `StageAttemptResult` и его Error. Если continuation не может сохранить эти значения через checkpoint, stage target нельзя регистрировать с `REPORT_UNKNOWN` до изменения принятого parent контракта.

Регистрация `REPORT_UNKNOWN` для effectful stage требует `retry_policy=None`: `InvocationCoordinator.finish` сейчас применяет declared-error `retry_policy` и может перевести stage в `READY` без `Allowed`. Это отдельная проверка `NodeContract`/`GraphCompiler`; policy не может скрываться за callback. Declared `ArtifactInputError`/lease refusal остаются типизированными исходами parent, но не разрешают повторить эффектный stage. Новая stage попытка возможна только с новым owning `StageAttemptPermit` из `Allowed`, проверенным Artifacts admission; Engine не выводит Allowed из error code. Для recovery/begin leaf default `RETRY` допустим лишь после owning доказательства идемпотентности exact request по SR-04; без него такая регистрация и восстановление RUNNING не принимаются.

## 3. Единственный owner и порядок перехода

1. `ExecutionRecovery.resume` получает существующий fenced claim и сохраняет действующий renew/drain/release loop. `ActiveCheckpoint.resume` компилирует прежний plan, проверяет header/session/registry и восстанавливает graph через согласованный `CheckpointCodec` из identity-плана. Никакой domain service здесь не вызывается.
2. До `PassExecution.run` и до выбора `ready` один `InvocationCoordinator.reconcile_interrupted()` просматривает сохранённые `RUNNING` в стабильном порядке invocation id. Нынешнюю безусловную мутацию `RUNNING→READY` из `InvocationCoordinator.__init__` нужно убрать; constructor только проверяет binding. Для default `RETRY` явный reconcile применяет прежний `READY` без изменения обычного retry. Для объявленного `REPORT_UNKNOWN` проверяет child address, caller WAITING_CALLS на том же `caller_step`, registered target/policy, отсутствие terminal/error и валидность checkpoint; затем ставит `OUTCOME_UNKNOWN`. Невыполненная проверка даёт `RestoreFailure`, не fallback `READY`/`FAILED`.
3. Если есть переходы, `ActiveCheckpoint` вызывает **существующий** `OwnedExecution.save` под тем же claim: один checkpoint/revision CAS публикует все изменения до исполнения любого parent/child. CAS/owner loss означает отказ от этого graph и отсутствие dependent CALL. Повторная загрузка уже `OUTCOME_UNKNOWN` идемпотентна. Не создаются новый executor, второй owner loop или отдельное хранилище объектов.
4. `InvocationGraph.join_complete` считает `OUTCOME_UNKNOWN` завершением ожидания для соответствующего CALL group, но не успешным output dependency. `InvocationCoordinator.ready` после завершения всех siblings переводит parent `WAITING_CALLS→READY` и увеличивает `step_index` ровно один раз; это сохраняется обычным checkpoint перед start. Неизвестный child не входит в runnable set. Обычные `SUCCEEDED/FAILED/CANCELLED` siblings и `CallGroup` сохраняют прежний порядок и ключи.
5. При resume parent `InvocationCoordinator.event` формирует `ReturnedCall(original call_key, original target, CallOutcomeUnknown(lost_attempt))`. Доставка события **at least once**: crash после вызова `parent.resume`, но до durable `accept` может вызвать тот же resume повторно. Parent из сохранённого continuation и `lost_attempt` строит детерминированные recovery `call_key`, exact `StageRecoveryInput(binding,generation)` и следующий continuation-state `WAIT_RECOVER`; `InvocationCoordinator.accept` сверяет `key/target/input/state` с существующим dispatch, сохраняет caller link до запуска child и дедуплицирует **один логический recovery CALL** по `(parent invocation, parent step, call_key)`. После сохранённого accept parent ждёт recovery child и не получает старое unknown event снова. Engine не обещает ровно один физический вызов `StageAttemptService.recover`: RUNNING recovery child может повториться после crash только при доказанной owning идемпотентности exact request.
6. Recovery node одним public вызовом `StageAttemptService.recover` возвращает owning `Allowed | Confirmed | Refused | Unresolved` или объявленный Error. Только parent после `Allowed` вправе сформировать новый stage CALL с новым owning permit; `Confirmed` использует подтверждённый `ArtifactRef` без stage; `Refused/Unresolved` не вызывают stage. Это ветвление DAG parent по typed result, без прямого междоменного service call и без фальшивого `CallSuccess` старого child. Конкретные NodeId, ключи нового CALL и финальный graph остаются за отдельной приёмкой DAG.

Parent continuation различает `WAIT_STAGE(binding,generation,lost_attempt?)` и `WAIT_RECOVER(binding,generation,recovery_call_key)` (точные POJO/имена — отдельный DAG contract). Повтор `begin`/`recover` с тем же binding/generation должен вернуть тот же owning logical decision или явно определённый результат replay; потеря ACK после выдачи новой generation не должна выдать следующую. Это внешний критерий SR-04, не Engine механизм. Бесконечной recovery-of-recovery цепи нет: recover leaf не получает `REPORT_UNKNOWN`. Если SR-04 не доказывает безопасный `RETRY` recover/begin, регистрация всего маршрута остаётся OPEN; parent не фабрикует `Unresolved` вместо Artifacts и Engine не переключается на произвольный новый recovery CALL.

Переход `RUNNING→OUTCOME_UNKNOWN` выполняется **только после восстановления checkpoint под claim**. Свежий `RUNNING` текущего owner не помечается unknown; cancellation/stop обрабатываются действующим порядком до dependent CALL. Конфликт revision или смена owner останавливает работу без запуска parent. `OwnedExecution._checkpoint` и child cancellation CAS сохраняют нынешнюю атомарность; повторный reader восстанавливает уже записанный status и тот же `ExecutionIdentity` потерянной попытки.

## 4. Матрица исходов и replay

| Durable child при restore | Engine действие до scheduling | Parent и следующий CALL |
|---|---|---|
| `READY` до side effect | Обычный выбор `ready/begin` по контракту | Нет unknown event. |
| `RUNNING`, policy `RETRY` | Существующее `READY`; ordinary retry/replay не меняется | Обычный terminal result после выполнения. |
| `RUNNING`, policy `REPORT_UNKNOWN`, parent WAITING_CALLS | CAS `OUTCOME_UNKNOWN`; stage **не** запускается | После join — `CallOutcomeUnknown`, затем только объявленный recovery CALL. |
| `OUTCOME_UNKNOWN` после повторного restart | Никакого нового перехода/child stage | Восстановить parent continuation и тот же unknown event либо уже сохранённый recovery CALL; replay не создаёт второй call_key. |
| Recovery/begin child `RUNNING` после потери ACK | Default `RETRY` только после owning SR-04 exact-request idempotency; иначе регистрация такого маршрута не принята | Тот же логический call_key/input; физическое повторное выполнение может произойти, новая generation без owning основания запрещена. |
| `SUCCEEDED` с terminal, включая потерю ACK после его checkpoint | Никакой recovery stage | Обычный `CallSuccess`; parent не повторяет stage. |
| `FAILED` с объявленным Error / runtime fault | Сохранить исходную категорию: `CallFailure` / `CallRuntimeFailure`, diagnostic и error payload; не переклассифицировать в unknown. | Effectful stage parent не повторяет stage. Для runtime failure/`UnknownCommitOutcome`, пойманного runner после возможного эффекта, parent строит тот же owning recovery CALL из continuation либо прекращает маршрут, если binding/generation недоступны. Declared typed Error трактует owning contract; никакой auto retry stage. |
| `CANCELLED`, stop intent или owner loss до CAS | Действующий cancellation/stop/owner отказ | Нет нового dependent CALL после прекращения владения. |
| `RUNNING` с policy `REPORT_UNKNOWN`, но caller/continuation/registry несовместимы | `RestoreFailure` до scheduling | Никакого stage/recovery CALL. |

Потеря ACK после physical seal, но до child terminal checkpoint остаётся неизвестным Engine результатом. Только owning `recover` может ответить `Confirmed`; Engine не читает storage и не повышает child status до `SUCCEEDED`. Потеря ACK после checkpoint `SUCCEEDED` даёт обычный replay success. Если одновременно есть sibling WAIT_INPUT, join ждёт его штатного исхода; `InputWaitCoordinator.validate/waiting` должен учитывать новый joinable status без ложного `waiting_for_input` и без отмены чужого wait.

`FAILED` сам по себе не доказывает отсутствие доменных эффектов. `CallRuntimeFailure` сохраняет эту категорию, а stage parent по своему объявленному contract выбирает owning recover для потенциально эффектного отказа; Engine не инспектирует Python exception и не превращает его в `StageRecoveryUnresolved`. Если runner потерял различие `UnknownCommitOutcome` и другой runtime fault, потребуется отдельно согласованная owning typed Error/diagnostic mapping до обещания полного recovery; SR-02 не закрывает этот внешний дефект молча. На любом таком OPEN пути допустим fail/stop без новой stage попытки.

## 5. Class inventory и критерии отказа плана

| Класс/модуль | Роль, допустимые зависимости/эффект | Проверяемый критерий; отказ при нарушении |
|---|---|---|
| `NodeContract`, `RegisteredContract` | Public policy + versioned registry; только типы/проверка конфигурации, без service. | Default ordinary RETRY и persisted fingerprint; `REPORT_UNKNOWN` stage требует `retry_policy=None`; отказ при выборе по имени stage, domain callback, auto retry или silent legacy upgrade. |
| `GraphCompiler` / `ExecutionPlan` | Регистрационная проверка, что `REPORT_UNKNOWN` относится к CALL child с объявленным resumable parent и не используется как output dependency вне CALL. | Отказ до исполнения при root-only/orphan target и при downstream dependency, которой нужен отсутствующий output. |
| `InvocationRecord`, `InvocationGraph` | State/address/caller binding и join; данные checkpoint, не domain verdict. | Unknown только для объявленного CALL child; отказ при success-like terminal, runnable unknown или потерянном call_key. |
| `CallOutcomeUnknown`, `CallResults` | Public typed event parent; проверяют target/address, без новых полей Artifacts. | Отказ при преобразовании unknown в runtime/typed failure или обходе target check. |
| `CheckpointCodec` | Валидация registry/status/continuation и wire restore; без решения о retry. | Reject несовместимой версии и orphan unknown до исполнения; отказ при восстановлении domain output по equality/guess. |
| `InvocationCoordinator` | Один graph transition, join, event, CALL admission/replay. | Ни один `REPORT_UNKNOWN RUNNING` не становится READY; unknown не запускается; at-least-once event и durable dedup одного logical CALL по key/target/input/state; declared-error retry stage не обходит owning Allowed. Отказ при domain branch внутри coordinator. |
| `ActiveCheckpoint` | В существующем owner вызывает reconcile и один save до PassExecution. | CAS перед dependent CALL; отказ при втором claim/worker либо transition после start. |
| `DAGExecutor` | Существующий scheduler и start CAS; direct-entry использует тот же reconcile под своим claim. | Ни stage, ни parent не стартуют до durable transition; отказ при прямом вызове recovery service. |
| `OwnedExecution` | Existing checkpoint/renew/CAS и conflict handling; API не расширяется. | Отказ при отдельном recovery store, втором owner loop или loss без drain. |
| `ExecutionRecovery`, `PassExecution` | Existing owner и утверждённый порядок pass/cancellation/replan; orchestration без domain checks. | Отказ при прямом Artifacts call, смене порядка или общем запрете ordinary replan/retry. |
| `InputWaitCoordinator` | Validation/wait state при mixed CALL/WAIT. | Отказ при ошибочном join, исчезнувшем pending wait или запуске parent до всех siblings. |
| Stage parent/resumable node (точный класс/NodeId OPEN) | Единственный DAG выбор recovery CALL и последующих outcome branches; зависит от declared CallTargets, typed continuation и owning POJO, без storage. | Отказ при повторном stage до `Allowed`, неверном binding/generation или прямом domain-to-domain вызове. |
| Artifacts begin/recover/stage leaf nodes (точные NodeId OPEN) | Один public Artifacts call на node, domain validation/error unchanged. | Отказ при issuance/authority logic в DAG, двух public calls в leaf или синтетическом Confirmed. |

`ExecutionAdmission`, `SessionFrame`, `ExecutionSnapshotService` и codec identity-плана могут потребовать wire/mapping cutover из §§5–7 identity-плана, но SR-02 не назначает им новый owner или sidecar. Перед кодом проверить весь serializer inventory и отсутствие двойного декодирования producer. Никаких changes в `application/engine/nodes/` этот пакет сам не разрешает.

## 6. Что требует приёмки до реализации

1. DAG-координатор сверяет `REPORT_UNKNOWN` и `CallOutcomeUnknown` с полным registered parent→stage→recover→stage/terminal графом, включая конкретные CallTargets, тип parent continuation и Output→Input mapping. Пользователь утверждает policy/API delta и порядок; этот файл не назначает ноды вместо него.
2. Artifacts утверждает `StageRecoveryInput`/`StageAttemptResult` и StageBinding/generation persistence из SR-03/04/05, включая exact-request idempotency begin/recover после потреблённого permit, выданной generation и потерянного ACK. Без этого parent не может построить безопасный owning recover CALL, и SR-02 остаётся OPEN.
3. Доказать на actual public `DAGEngine.run/resume` и direct-entry: crash после start до terminal, crash после доставки unknown event до accept, crash после durable recovery dispatch, crash после выдачи generation до ACK, crash после seal до ACK, crash после terminal checkpoint, runtime FAILED после возможного эффекта, concurrent cancel/claim loss, mixed CallGroup/WAIT_INPUT, replay одного key, default ordinary retry/replan. Assert: ноль повторов stage до `Allowed`, один **логический** recovery CALL на сохранённый step (физические вызовы допускаются только owning idempotency), no fake child success, exact typed outcome, прежняя error category и monotonic revision/CAS. Fixture stage spy не доказывает real artifact write.

**Статус SR-02: предложена конкретная Engine/DAG transition schema; приёмка OPEN.** Она зависит от согласования public Engine delta и owning SR-03/04/05, не является реализацией и не закрывает production Artifacts route.
