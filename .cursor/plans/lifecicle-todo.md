# Lifecycle: развитие оркестрации — вариант Б

2026-11-21. Отдельный техдолг развития по поручению пользователя. Статус: TODO, вне текущего скоупа варианта А. Имя файла lifecicle-todo.md сохранено по запросу пользователя. Основной план: [entity-lifecycle.md](entity-lifecycle.md).

## Цель и условие запуска

При появлении сценария, которому нужна повторно используемая подготовка нескольких Lifecycle-команд, спроектировать orchestration node prepare_lifecycle_changes. Она вызывает существующие operation leaf варианта А, не создаёт второй набор доменных методов и не дублирует их алгоритмы. Создание этого плана не запускает реализацию.

Оба маршрута могут сосуществовать под prepare_changes:

```text
prepare_changes
  ├─ А: выбранные prepare_lifecycle_* leaf → prepare_lifecycle_section
  └─ Б: prepare_lifecycle_changes
          → те же prepare_lifecycle_* leaf → prepare_lifecycle_section

успех выбранного маршрута → LifecycleSection → assemble_patch_set → apply_snapshot
```

Маршрут выбирается по явному контракту сценария. Для одного набора изменений выполняется только А или Б. Общий parent выбирает маршрут, Б управляет дочерними CALL, leaf вызывают публичные методы, Lifecycle выполняет доменные проверки. Нельзя запускать А и Б для повторной подготовки одной секции или переносить доменные алгоритмы в любой parent.

## Предложение контрактов — не принято как exact API

- PrepareLifecycleChangesInput: operation_id, expected_world, непустой упорядоченный набор конкретно типизированных команд и domain_evidence. Exact fields/closed union требуют проработки без дублирующих источников identity/base.
- PrepareLifecycleChangesOutput: LifecycleSection либо типизированный отказ подготовки с указанием команды/стадии. Успешная секция совместима с маршрутом А; exact общий error mapping остаётся OPEN.
- Родитель не получает методы/callbacks как данные и не выполняет скрытые storage reads или commit.

## Что согласовать перед включением Б

1. Реальное требование повторного использования и явный сценарий выбора А/Б; допустим синтетический контрактный пример до подключения предметных доменов.
2. Полные Input/Output/Error, закрытый union команд, family/parent/NodeId и engine continuation/correlation contracts.
3. Порядок CALL, перенос готовых результатов, политика нескольких отказов и прекращение зависимых вызовов; параллельность не предполагается автоматически.
4. Проверка общей базы и непересечения участников остаётся у Lifecycle. DAG не сливает кандидаты и не создаёт поддельные captures.
5. Поведение cancellation/runtime faults, отсутствие частичной секции и двойного добавления в PatchSet, сохранение operation identity.
6. Контрактные тесты с моками: прямой маршрут А и Б дают совместимые результаты для одинакового допустимого намерения; ошибки сохраняют причины; отказ не запускает зависимый section/apply путь.
7. Координаторская сверка всей цепочки, обязательные критерии DAG и решение пользователя до активации маршрута.

Б сам по себе не разрешает пересекающиеся переходы. Такое расширение ведётся отдельно в [entity-lifecycle-overlapping-transitions.md](entity-lifecycle-overlapping-transitions.md); ordinal не задаёт порядок состояний. Техдолг Б не блокирует локальное завершение контрактов варианта А.
