# DAG-TYPING-1 — общесистемная типизация engine DAG

**Статус:** DRAFT — самостоятельный **план реализации** общесистемной типизации DAG. Принципы Input/Output и DAGContext утверждены 2026-10-30; перечисленные ниже вопросы остаются открытыми. **Сначала согласуются и реализуются архитектурные изменения инфраструктуры, только затем мигрируются ноды.** Документ не разрешает изменять код без отдельного согласования с мастером.
**Область:** весь существующий engine DAG — Python-ноды, LLM-ноды, NodeRegistry, DAGContext, execution runtime, replan/resume/repair и диагностика. **Не часть GEN-DAG-1:** интеграция генератора с DAG остаётся самостоятельной задачей; порядок выполнения двух планов и точки стыка не назначены автоматически.
**Нормативные документы:** `docs/tz_engine_node_context.md` (подробные решения и ответственность), `.cursor/rules/engine-nodes.mdc`, `.cursor/rules/contract-creation.mdc`, `.cursor/rules/dataModel-no-hardcode.mdc`, `.cursor/rules/type-kind-str-fields.mdc`, `docs/tz_json_validation.md`. Для стыка генератора: `.cursor/plans/gen-dag-1-post-geo-ws.md`.

## Цель и граница

Типизировать входы и выходы **каждой** ноды и обмен опубликованными результатами между нодами без превращения DAG в доменный resolver, новую POJO-инфраструктуру или владельца CRUD. Изменение состава/порядка DAG не должно требовать изменения реализации доменных операций при сохранении их публичных контрактов.

Граф зависимостей по исполнению уже определён через `BaseNode.deps` и `GraphCompiler`; второй механизм `REQUIRES` не вводить. Текущие `NodeResult.data: Any`, `ExecutionState.node_results: dict[str, object]` и `shared_context: dict` — legacy, а не образец целевой архитектуры.

**Существующий параллелизм — обязательный инвариант:** `GraphCompiler` строит топологические уровни; `DAGExecutor._run_level()` запускает независимые Python-ноды одного уровня одновременно через `asyncio.gather(..., return_exceptions=True)` и ожидает завершения уровня перед следующим. LLM-ноды исполняются агрегированными группами по temperature; это другая семантика, её не подменять отдельными одновременными вызовами. Типизация не вправе последовательно выполнять все ноды, вводить глобальную блокировку, ломать уровни/фазы, replan/gate или вызывать повторные LLM-запросы без отдельного согласования.

## Принятые архитектурные решения (2026-10-30)

1. **Контракты каждой ноды:** обязательные, статически объявленные **Input и Output POJO** по действующим правилам `dataModel`/Pydantic. Нода формирует конкретный Input самостоятельно; Output возвращается непосредственно как значение заявленного POJO. `NodeResult(data: Any)` не сохранять ради обёртки без дополнительной подтверждённой семантики.
2. **Семантическое переиспользование POJO:** если публичный read/CRUD домена возвращает подходящий POJO, нода может напрямую использовать его в Input/Output. Если нужно несколько объектов — объявить собственный композиционный POJO с типизированными полями доменных POJO. Отдельный контракт ноды допустим при иной семантике; не модифицировать доменный POJO лишь ради формы DAG и не дублировать его поля, defaults и нормализацию.
3. **Получение данных:** нода явно вызывает публичные доменные read-контракты и может читать типизированные Output завершённых зависимостей. Объявление поля Input POJO **не** запускает автоматический поиск/CRUD по его типу. Домены владеют read/missing/fallback; каждая стадия читает согласованное исходное состояние. Snapshot не решает, какие поля отдать ноде.
4. **Выполнение:** DAG выбирает операции, зависимости, условия и порядок; нода делегирует вызов публичному API нужного домена. Алгоритмы и CRUD принадлежат домену. Нельзя скрывать за нодой несколько самостоятельных операций мира с собственным внешним жизненным циклом; внутренние вычислительные шаги одной доменной операции остаются у домена.
5. **Контекст результатов:** логический `DAGContext` — разреженный каталог опубликованных типизированных Output по производителям, а не копия мира и не гигантский `TerrainContext`/`SceneContext`. Input короткоживущий по умолчанию. Малый Output может храниться непосредственно; крупный — содержать типизированные доменные ссылки, если это предусмотрено самим контрактом. Не копировать подтверждённо неизменяемые, включая вложенные данные, payload между уровнями DAG. **Параллельные ноды одного уровня не должны видеть частично сформированные результаты друг друга**; конкретный механизм публикации/барьера — открытый вопрос. Правила идентичности/времени жизни Output пока не утверждены.
6. **Валидация:** переиспользовать POJO/Pydantic, строгие `RegistryKey`/enum и существующие ограничения. `NodeRegistry` должен связывать ноду с её типами Input/Output, не копируя Pydantic-схемы. LLM JSON — транспортная форма, в контекст публикуется только валидированный Output POJO. Не дублировать механизмы `jsonValidation` и каскада там, где их семантика не применима.
7. **Runtime и эффекты:** статусы, ошибки, replan, repair, cancellation и trace — ответственность execution runtime, не обязательные поля каждого Output. Output не обязан быть Patch/PatchSet. Сбор PatchSet — ответственность DAG в пределах отдельно согласованных контрактов, применение/история — Snapshot; прямые persist-записи из нод не вводить.

Подробное объяснение и границы ответственности — в `docs/tz_engine_node_context.md`. **Принятые пункты не являются разрешением немедленно мигрировать работающий код.**

## Открытые вопросы типизации (2026-10-30)

**Статус:** решения **не приняты**. Ни один пункт ниже не отменяет уже согласованные POJO Input/Output, композицию доменных POJO, `BaseNode.deps`, разреженный `DAGContext` и границы DAG/domain/PatchSet/Snapshot. Выбор конкретных механизмов — при подготовке соответствующих шагов DAG-TYPING-1, с согласованием мастера до реализации.

### Архитектурные вопросы

1. **Идентичность Output при повторном исполнении.** Как различать результаты одной ноды при повторном запуске, нескольких pass, `replan` и `resume`? Какой именно Output должен видеть потребитель, если прежний результат уже опубликован, а нода выполнена вновь? Как исключить чтение устаревшего результата? Не считать текущий ключ `node_id` достаточным ответом без проверки сценариев.
2. **Доступность Output зависимостей.** Как потребитель получает типизированный Output, если нода-производитель пропущена условием, не была выполнена, завершилась ошибкой или была остановлена gate/replan? Как различать зависимость только по порядку и фактическое потребление данных, не вводя второй реестр вместо `deps`? Отсутствующий Output зависимости — вопрос исполнения DAG; доменные missing/fallback остаются в домене.
3. **Жизненный цикл опубликованных Output.** Какие POJO/ссылки удерживаются в памяти, когда допускается освобождение, что необходимо для `replan`/`resume`/диагностики и как их безопасно восстанавливать? Не фиксировать автоматическое удаление после последнего потребителя, пока не установлены правила повторного исполнения; не копировать крупные payload ради trace/snapshot уровня.

4. **Параллельная публикация Output и согласованность чтения.** Как ноды одного топологического уровня публикуют POJO без гонок в общих `node_results`/`node_status`/trace, что доступно им во время параллельного выполнения и когда результаты уровня становятся видны зависимым нодам? Нужна ли публикация по завершении каждой ноды или согласованный барьер уровня? Решение не должно превращать `asyncio.gather` в последовательный запуск; отдельно сохранить существующую агрегированную семантику LLM-групп и gate/replan.

### Вопросы механизма и миграции (на этапе реализации)

5. **Типобезопасный доступ через DAGContext/NodeRegistry.** Как привязать производителя к классу объявленного Output POJO и предоставить статически проверяемое получение результата без повторного объявления схемы и без дополнительного `REQUIRES`? Где обнаруживать несовместимые контракты и как проверять Python/LLM-группы? Использовать существующую POJO/Pydantic-инфраструктуру, не создавать отдельный DAG-валидатор полей.
6. **Переход от свободного ExecutionState.** Как заменить `node_results`, `shared_context`, `NodeResult(data: Any)` и типизировать `node_status`, `node_errors`, `ExecutionTrace`, `ExecutionLevelSnapshot` без нарушения repair, replan, cancellation и resume? Как сохранять результат LLM именно как валидированный Output POJO, а не raw JSON/`dict`?

**Отложено по ранее принятой границе:** конкретный состав результатов доменных операций и правила их агрегации в PatchSet согласовать при реализации соответствующей интеграции GEN-DAG-1; не считать их заранее определёнными этим разделом.

## Порядок реализации: сначала архитектурная инфраструктура, потом ноды

**Жёсткая последовательность:** запрещено начинать массовую миграцию нод до индивидуальной приёмки архитектурных изменений ядра (A1–A3). Для каждого шага — отдельно зафиксированные контракт, обратная совместимость, проверки и подтверждение мастера. При обнаружении новой архитектурной дыры остановить соответствующий шаг и согласовать решение, не маскировать временными `Any`/`dict`-адаптерами.

### Фаза A — архитектурные изменения (до миграции нод)

- **A0 — инвентаризация и закрытие архитектурных вопросов.** Прочитать и картировать существующие `BaseNode`/`deps`, `GraphCompiler`, `ExecutionPlan`, `DAGExecutor`, `NodeRegistry`, Python/LLM executors, `ExecutionState`, repair, `SessionSnapshot`, трассировку и диагностику. В явном виде согласовать 4 архитектурных вопроса выше: идентичность Output, доступность результатов, lifetime/resume и параллельную публикацию. Нельзя использовать только имена нод как доказательство поведения.
- **A1 — каркас типизированных контрактов нод.** После A0 определить POJO-binding ноды к Input/Output в `NodeRegistry`, минимальный typed-call контракт для Python и LLM и место валидации через существующую Pydantic-инфраструктуру. Обеспечить поддержку старых нод без навязывания им изменения до фазы B. В отдельной карте зафиксировать прямое переиспользование доменных POJO, композицию и потребление Output зависимостей.
- **A2 — архитектура DAGContext и параллельной публикации.** Внедрить согласованный способ типобезопасного чтения/публикации результатов, работающий с `asyncio.gather` независимых Python-нод одного уровня. Установить правила согласованного read view: входы нод формируются из завершённых доступных Output и доменных read-контрактов, без чтения незавершённого Output соседа. Ограничить общий mutable state, обеспечить корректную обработку одновременных успехов, ошибок, отмены и gate/replan; не блокировать весь DAG ради типизации. Сохранить уровни, фазы, группировку LLM и текущий порядок управления исполнением.
- **A3 — runtime/lifecycle/compatibility.** После A2 определить разделение типизированных результатов и статусов/ошибок, ссылки и время жизни крупных Output, сохранение/восстановление при replan/resume и диагностические снимки без копий больших payload. Предусмотреть временный совместимый путь для legacy `NodeResult`/`node_results`/`shared_context` до миграции их потребителей. Проверить вложенную неизменяемость POJO: одного `frozen=True` недостаточно для доказательства неизменяемости mutable вложений.

### Фаза B — последовательная миграция потребителей после принятой фазы A

- **B1 — Python-ноды по согласованной карте.** Переводить ноды небольшими проверяемыми группами на объявленные POJO Input/Output и публичные доменные read/CRUD-контракты; не переносить доменную реализацию или межоперационную оркестрацию в ноды. Для каждой ноды проверить deps и чтение Output, в том числе при параллельном выполнении соседей.
- **B2 — LLM-ноды и агрегированные группы.** Переход от `contract_json`/raw JSON к опубликованным валидированным Output POJO без изменения семантики одного LLM-вызова на temperature-группу, ошибок, repair и payload зависимостей. При необходимости обосновать и согласовать адаптацию существующих LLM-валидаторов вместо дублирования схем.
- **B3 — ExecutionState, replan/resume, trace и удаление legacy.** Мигрировать конкретных потребителей `NodeResult`, `node_results`, `shared_context`, snapshot/trace, `ResponseResolver` и cancellation; убрать совместимые пути только после подтверждённой замены всех usages. Не менять жизненный цикл генерации/публикации мира или правила PatchSet/Snapshot как побочный эффект типизации.

### Приёмка параллелизма (обязательна для A2 и повторно после B)

- Две независимые Python-ноды одного уровня **фактически перекрываются по времени**, а не исполняются последовательно после внедрения типизации.
- Ноды следующего уровня получают только согласованные завершённые типизированные результаты зависимостей; нет чтения чужого частичного Output или mutable-состояния другой ноды.
- Одновременные success/fail/cancel и gate/replan сохраняют предусмотренное управление и диагностику без гонок и потери Output/ошибок.
- LLM temperature-группы по-прежнему используют предусмотренное агрегированное исполнение и repair, без случайного раздробления на независимые вызовы.
- Диагностические snapshots и resume не нарушают согласованность результатов параллельного уровня, не дублируют тяжёлые payload и не возвращают устаревшее значение как актуальное.

## Критерии архитектурной приёмки

- Все ноды охвачены картой POJO Input/Output или имеют явно согласованный этап миграции; Python и LLM не расходятся по типу публикуемого результата.
- Реиспользованные доменные POJO не скопированы и не изменены ради DAG; ограничения полей остаются в существующем SoT.
- Никакой второй системы `REQUIRES`, каскада/field-policy, автоподбора read API по типам POJO либо неявного доменного pipeline в подготовке Input.
- При каждом типизированном чтении Output проверяемы производитель, объявленный контракт, актуальность и доступность результата; поведение при replan/resume/skip/fail явно определено перед реализацией.
- Параллельное исполнение Python-нод одного уровня и агрегированные LLM-группы сохранены и подтверждены проверками фактического поведения, включая конкурирующие записи результата/статуса/trace.
- Согласован жизненный цикл больших результатов без копирования payload и без неограниченного удержания данных.
- Работающий repair/LLM aggregation, cancellation, диагностика и текущие пути исполнения имеют проверяемую стратегию миграции.
- Архитектурная типизация не меняет ответственность DAG/domain/Snapshot и не диктует новый порядок реализации `GEN-DAG-1`; интеграционные PatchSet-контракты согласуются в соответствующем плане.

## Отношение к GEN-DAG-1

`GEN-DAG-1` владеет подключением самостоятельных операций генератора к существующему DAG и интеграцией PatchSet/Snapshot. `DAG-TYPING-1` владеет **общесистемными** контрактами нод и инфраструктурой обмена Output. Ни один план не должен реализовывать ответственность второго «заодно». Их совместимость и порядок внедрения определяются отдельным согласованием, а не фактом упоминания ссылки.
