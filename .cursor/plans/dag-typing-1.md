# DAG-TYPING-1 — общесистемная типизация engine DAG

**Статус:** DRAFT — самостоятельный **план реализации** общесистемной типизации DAG. Принципы Input/Output, DAGContext и решения исполнения ниже согласованы 2026-10-30 до подготовки ТЗ. **Сначала согласуются и реализуются архитектурные изменения инфраструктуры, только затем мигрируются ноды.** Документ не разрешает изменять код без отдельного согласования с мастером.
**Область:** весь существующий engine DAG — Python-ноды, LLM-ноды, NodeRegistry, DAGContext, execution runtime, replan/resume/repair и диагностика. **Не часть GEN-DAG-1:** интеграция генератора с DAG остаётся самостоятельной задачей; граница работ и зависимость точки переключения явно заданы в пункте 8 и разделе «Стык планов без совместимого слоя».
**Нормативные документы:** `docs/tz_engine_node_context.md` (подробные решения и ответственность), `.cursor/rules/engine-nodes.mdc`, `.cursor/rules/contract-creation.mdc`, `.cursor/rules/dataModel-no-hardcode.mdc`, `.cursor/rules/type-kind-str-fields.mdc`, `docs/tz_json_validation.md`. Для стыка генератора: `.cursor/plans/gen-dag-1-post-geo-ws.md`.

## Цель и граница

### Готовность плана по правилам агента (проверка 2026-10-30)

**Архитектурные решения согласованы; план ещё не готов к реализации A1–B3.** Подготовка ТЗ/карты реализации в A0 не разрешает писать код по неполным карточкам шагов. До реализации дополнить этот же план перечисленными ниже артефактами; решения исполнения заново не выбирать.

- `code-gates.mdc` § «Гейт 2/3»: для каждого нового/изменяемого класса нужна полная карта «ответственность → домен → слой → точный файл → producers/consumers → допустимые импорты». Текущие групповые пути `execution/`, `repair/`, «расположение выбрано в ТЗ» не заменяют эту карту. До кода окончательные пути и сигнатуры должны быть перенесены из подготовки ТЗ в план.
- A1–A3/B1–B3 пока являются фазами. Детализировать их в атомарные шаги внутри согласованного scope; для каждого указать цель, конкретный раздел ТЗ, файлы, контракт/сигнатуры, точную команду проверки с ожидаемым результатом и Done. Сообщить пользователю о детализации шагов до реализации; один шаг → краткий отчёт → подтверждение → следующий шаг. Сейчас воспроизводимые команды и карточки каждого шага отсутствуют.
- До A1 синхронизировать `docs/tz_engine_node_context.md` §§2–5 с принятыми решениями и дать каждому шагу ссылку на конкретный раздел. Согласованный план задаёт содержание обновления ТЗ, но не заменяет требование иметь актуальное ТЗ перед кодом.
- `folder-composition.mdc`: текущие непосредственные файлы — `backend/app/application/engine` 4, `nodes` 6, `nodes/pojo` 7, `graphs` 2, `dag` 5, `execution` 3, `repair` 5 (пути относительно engine), `backend/app/application/cancellation` 6. Итоговые количества неизвестны до карты файлов; зафиксировать их до реализации, включая служебные файлы. WARN для папок с >5 файлами сообщён пользователю. Не добавлять 11-й файл; необходимую композицию и обновление импортов включить в план до добавлений.
- `class-size-limit.mdc`: для каждого затрагиваемого orchestrator/planner/facade требуется карта владельцев операций и проверка фактической ответственности перед приёмкой шага. Это относится как минимум к `DAGExecutor`, `LLMExecutionEngine`, `GraphCompiler`, `NodeRunner`, `LLMAggregateExecutor` и затронутому repair. В execution-отчёте шага кратко фиксировать проверенные компоненты и результат; доменная работа в оркестраторе блокирует Done независимо от тестов и размера класса. Проверить порог 300 строк и композицию по ответственности.
- Для подробной диагностики использовать `docs/tz_logging.md` §§ «Инварианты», «Каталог консьюмеров», «Маршрут»: общий `loggingConfig` и зарегистрированный sink. До реализации определить в ТЗ и плане точные domain/service, путь sink и владельца событий; новый независимый logger/router не вводить. Сейчас конкретный sink DAG-диагностики не определён.

Размещение плана, разделение DAG/domain/Snapshot, single-writer, параллельный data flow, переиспользование POJO и граница удаления генераторных legacy-нод соответствуют согласованному направлению. Настоящая проверка — проверка готовности документа, не приёмка кода. Планировка/L0/L2, SQL-схема и HTTP в этом плане не меняются; соответствующие предметные требования остаются за интеграционными планами.

Типизировать входы и выходы **каждой** ноды и обмен опубликованными результатами между нодами без превращения DAG в доменный resolver, новую POJO-инфраструктуру или владельца CRUD. Изменение состава/порядка DAG не должно требовать изменения реализации доменных операций при сохранении их публичных контрактов.

Граф зависимостей по исполнению уже определён через `BaseNode.deps` и `GraphCompiler`; второй механизм `REQUIRES` не вводить. Текущие `NodeResult.data: Any`, `ExecutionState.node_results: dict[str, object]` и `shared_context: dict` — legacy, а не образец целевой архитектуры.

**Существующий параллелизм — обязательный инвариант:** `GraphCompiler` строит топологические уровни; `DAGExecutor._run_level()` запускает независимые Python-ноды одного уровня одновременно через `asyncio.gather(..., return_exceptions=True)` и ожидает завершения уровня перед следующим. LLM-ноды исполняются агрегированными группами по temperature; это другая семантика, её не подменять отдельными одновременными вызовами. Типизация не вправе последовательно выполнять все ноды, вводить глобальную блокировку, ломать уровни/фазы, replan/gate или вызывать повторные LLM-запросы без отдельного согласования.

## Принятые архитектурные решения (2026-10-30)

1. **Контракты каждой ноды:** обязательные, статически объявленные **Input и Output POJO** по действующим правилам `dataModel`/Pydantic. Нода формирует конкретный Input самостоятельно; Output возвращается непосредственно как значение заявленного POJO. `NodeResult(data: Any)` не сохранять ради обёртки без дополнительной подтверждённой семантики.
2. **Семантическое переиспользование POJO:** если публичный read/CRUD домена возвращает подходящий POJO, нода может напрямую использовать его в Input/Output. Если нужно несколько объектов — объявить собственный композиционный POJO с типизированными полями доменных POJO. Отдельный контракт ноды допустим при иной семантике; не модифицировать доменный POJO лишь ради формы DAG и не дублировать его поля, defaults и нормализацию.
3. **Получение данных:** нода явно вызывает публичные доменные read-контракты и может читать типизированные Output завершённых зависимостей. Объявление поля Input POJO **не** запускает автоматический поиск/CRUD по его типу. Домены владеют read/missing/fallback; каждая стадия читает согласованное исходное состояние. Snapshot не решает, какие поля отдать ноде.
4. **Выполнение:** DAG выбирает операции, зависимости, условия и порядок; нода делегирует вызов публичному API нужного домена. Алгоритмы и CRUD принадлежат домену. Нельзя скрывать за нодой несколько самостоятельных операций мира с собственным внешним жизненным циклом; внутренние вычислительные шаги одной доменной операции остаются у домена.
5. **Контекст результатов:** логический `DAGContext` — разреженный каталог опубликованных типизированных Output по производителям, а не копия мира и не гигантский `TerrainContext`/`SceneContext`. Input короткоживущий по умолчанию. Малый Output может храниться непосредственно; крупный — содержать типизированные доменные ссылки, если это предусмотрено самим контрактом. Не копировать подтверждённо неизменяемые, включая вложенные данные, payload между уровнями DAG. **Параллельные ноды одного уровня не должны видеть частично сформированные результаты друг друга**; применяется барьерная публикация уровня и правила идентичности/времени жизни из раздела согласованных решений ниже.
6. **Валидация:** переиспользовать POJO/Pydantic, строгие `RegistryKey`/enum и существующие ограничения. `NodeRegistry` должен связывать ноду с её типами Input/Output, не копируя Pydantic-схемы. LLM JSON — транспортная форма, в контекст публикуется только валидированный Output POJO. Не дублировать механизмы `jsonValidation` и каскада там, где их семантика не применима.
7. **Runtime и эффекты:** статусы, ошибки, replan, repair, cancellation и trace — ответственность execution runtime, не обязательные поля каждого Output. Output не обязан быть Patch/PatchSet. Сбор PatchSet — ответственность DAG в пределах отдельно согласованных контрактов, применение/история — Snapshot; прямые persist-записи из нод не вводить.

Подробное объяснение и границы ответственности — в `docs/tz_engine_node_context.md`. До синхронизации этого ТЗ в A0 согласованные решения исполнения и дополнительные уточнения настоящего плана являются источником принятых решений; старые пометки ТЗ «открытый вопрос» не разрешают выбирать их заново. **Принятые пункты не являются разрешением немедленно мигрировать работающий код.**

## Согласованные решения исполнения (2026-10-30)

**Статус: согласовано пользователем до подготовки ТЗ.** A0 сверяет реализацию с этими решениями и составляет карту изменений. Агент не выбирает архитектуру заново при написании ТЗ. При обнаружении несовместимости он описывает конкретное противоречие и возвращает изменение решения на согласование в этот план. Детализация сигнатур и размещения типов не должна менять приведённую семантику.

1. **Идентичность.** Результат адресуется `execution_id + node_id + attempt`; resume сохраняет `execution_id`, повторное исполнение получает новый `attempt`. Ревизия плана хранится отдельно. Каталог различает исторический результат и актуальный результат; наличия записи по `node_id` недостаточно для reuse. После фиксации координатором исхода попытки её запись закрывается; повторная или поздняя публикация запрещена. Локальное завершение задачи ещё не является закрытием записи: координатор фиксирует её исход на барьере, в том числе при штатной отмене уровня.
2. **Доступность и типы.** На начало уровня формируется read-only представление опубликованных результатов. Нода заранее явно объявляет, от какого производителя какой контракт Output ей требуется и является ли чтение обязательным. Объявления связываются с Input/Output через NodeRegistry без копирования POJO-схем; производитель должен присутствовать в `deps`. До исполнения проверяются существование производителя, совместимость объявленных контрактов и соответствие `deps`; runtime дополнительно проверяет доступность и актуальность результата. Чтение необъявленного производителя/контракта запрещено. `deps` остаётся единственным графом исполнения; объявления контрактов уточняют данные на его связях, а не создают независимый реестр порядка. Обязательное чтение при отсутствии результата завершает подготовку Input ошибкой runtime; необязательное явно возвращает отсутствие. Несовпадение типов всегда является ошибкой. Доменные missing/fallback остаются в домене. Статический API сохраняет конкретный тип POJO; динамические идентификаторы дополнительно проверяются runtime. Схемы остаются в POJO/Pydantic.
3. **Параллелизм.** Независимые Python-ноды уровня одновременно исполняются через `asyncio.gather`. Задача возвращает локальный исход исполнения; каталог, статусы и trace обновляет координатор. Output публикуются на барьере после завершения задач уровня. Соседи не читают Output друг друга даже после раннего завершения. Исполнение доменных операций, I/O и LLM не удерживает общую блокировку. Локальный runtime-исход не заменяет публичный Output обёрткой `NodeResult(data: Any)`.
4. **Ошибки, отмена, gate.** При ошибке Python-ноды соседи завершаются; успешные Output сохраняются, следующий уровень не запускается. При отмене запуска незавершённые задачи отменяются и ожидаются, завершённые валидные результаты сохраняются для resume. Отмена не является успехом. Gate обрабатывается после барьера: следующий уровень и LLM не запускаются, управление возвращается для replan. Несколько gate-сигналов уровня — ошибка конфликта независимо от порядка завершения; ошибка уровня не маскируется replan. Остановка на границе уровня при gate — согласованное изменение текущей проверки после всей pre-LLM-фазы.
5. **Инвалидация.** Runtime записывает версии Output, реально прочитанные в рамках заранее объявленных требований при подготовке Input, включая отсутствие необязательного результата. Учёт чтений дополняет явные объявления ноды и не выводит её контракты автоматически из исполнения. Это метаданные исполнения, не второй граф зависимостей. Изменение прочитанной версии инвалидирует потребителя и транзитивных потребителей его результата; зависимость только по порядку сама по себе не инвалидирует данные. Для доменных чтений reuse допускается лишь при подтверждённой актуальности исходного состояния; без гарантии домена нода исполняется заново. `_should_skip()` и `skip_on_replan` не обходят проверку актуальности.
6. **LLM-группа.** Temperature-группа остаётся единицей исполнения и публикации: один исходный запрос и существующий repair, затем публикация всех валидированных Output целиком. Output соседа внутри этого же запроса недоступен как завершённый результат при подготовке Input. Требование такого чтения — несовместимый контракт, а не повод скрыто дробить запрос. При resume полностью актуальная группа переиспользуется; незавершённая или инвалидированная исполняется целиком.
7. **Lifetime/resume.** Каталог содержит неизменяемые, включая вложения, Output либо предусмотренные доменным контрактом ссылки. Trace содержит идентификаторы результатов и диагностику без тяжёлых payload. Данные удерживаются, пока нужны активному исполнению или сохранённому resume-снимку; история попыток сама по себе не удерживает payload. Resume восстанавливает актуальность, управляющее состояние и ещё не применённые эффекты, а не только `node_results`. Прямые persist-записи из нод не вводятся; состав доменных PatchSet остаётся за соответствующей интеграцией.
8. **Удаление legacy-нод — ответственность GEN-DAG-1.** Замена и удаление legacy-нод генератора, их регистраций и обходных путей выполняются в `.cursor/plans/gen-dag-1-post-geo-ws.md`. DAG-TYPING-1 не переписывает эти ноды ради последующего удаления: он задаёт общие Input/Output, каталог результатов и runtime, мигрирует сохраняемых общесистемных потребителей. Новые генераторные ноды в GEN-DAG-1 используют эти контракты. Адаптеры legacy/typed и смешанный режим исполнения не вводятся. Удаление инфраструктурных `NodeResult`, свободных `node_results`/`shared_context` остаётся в DAG-TYPING-1 после устранения всех usages, включая генераторные в GEN-DAG-1. Решение не разрешает удалять пользовательские данные или сохранённые snapshots.

**Стык планов без совместимого слоя:** фазу A проверять на типизированных тестовых нодах. DAG-TYPING-1 готовит инфраструктуру и переход сохраняемых потребителей; GEN-DAG-1 заменяет и удаляет legacy-ноды генератора. Полное включение typed runtime и удаление старых каналов возможно после готовности обеих частей и проверки отсутствия legacy-потребителей. Это зависимость точки переключения, а не требование завершить весь GEN-DAG-1 до начала инфраструктурной фазы A. В A0 перечислить конкретные интеграционные работы обоих планов; не возвращать удаление генераторных нод в scope типизации.

### Дополнительные согласованные уточнения (2026-10-30)

- **Согласованность доменных чтений.** Подготовка Input использует согласованную доменную ревизию или snapshot через публичные read-контракты. Read-only DAGContext фиксирует Output, но сам по себе не фиксирует состояние БД. Если домен не поддерживает согласованное чтение, соответствующая интеграция не принимается до появления подходящего публичного доменного read-контракта. Блокер явно указывается в карте A0 и ТЗ соответствующей интеграции; одной фиксации ограничения недостаточно для разрешения несогласованного чтения; повторное исполнение ноды не считается решением проблемы согласованности. Не вводить скрытый persist или глобальную блокировку DAG для компенсации ограничения.
- **Момент инвалидации.** При назначении новой попытки старый Output сразу исключается из актуальных; тогда же инвалидируются результаты, потребившие его, по правилам пункта 5. Ошибка или отмена новой попытки не возвращает старый Output в актуальные. Историческая запись может оставаться в диагностике без доступности через обычное чтение каталога.
- **Версии resume-снимков.** Снимок хранит версию формата и версии контрактов сохранённых данных. Перед восстановлением проверяется совместимость с текущими контрактами. Несовместимость завершается явной диагностической ошибкой без автоматической миграции и скрытого повторного запуска; исходный снимок не удаляется. Конкретные поля и представление версий описываются в ТЗ A3 с сохранением этого поведения.
- **Граница гарантий восстановления.** DAG-TYPING-1 гарантирует resume после штатной отмены, при которой runtime дождался задач и успешно сохранил снимок. Восстановление после падения процесса и недублирующее применение эффектов требуют отдельного согласованного контракта хранения/применения PatchSet/Snapshot. Сохранение Output не является доказательством этих гарантий. Конкретная реализация устойчивости к падению и дедупликации эффектов не входит в общую типизацию автоматически.

- **Отмена отдельной Python-ноды.** Если отменена одна задача, а весь запуск не отменён, координатор дожидается соседей, сохраняет их успешные валидные Output на барьере и останавливает выполнение перед следующим уровнем с исходом «отмена». Отменённая нода не публикует успешный Output; gate не разрешает продолжение после такой отмены. Сопутствующие ошибки и gate-сигналы сохраняются в диагностике, а не теряются из-за итогового исхода.
- **Подробная диагностика отмены.** Структурированные события и trace должны позволять восстановить причину и последствия: `execution_id`, ревизию плана/pass, фазу и уровень, `node_id` и `attempt`, время запроса/наблюдения отмены и завершения, источник и причину отмены (если неизвестны — явно «неизвестно»). Записывать объявленные требования ноды: производитель, ожидаемый контракт и обязательность; отдельно — реально прочитанные версии/отсутствие и состояние доступности. На барьере фиксировать исход каждой соседней задачи, идентификаторы сохранённых Output, ошибки/gate-сигналы, решение остановить дальнейшее исполнение и факт/ошибку сохранения resume-снимка, если оно выполнялось. Не записывать тяжёлые payload/Input целиком и не хранить их в trace ради диагностики. Владельцем итоговой записи остаётся координатор; сообщения параллельных задач коррелируются по идентификаторам, а не по порядку строк логов.
- **Недействительная доменная ссылка при resume.** Если объект по сохранённой ссылке отсутствует или недоступен для корректного восстановления, resume завершается явной ошибкой с идентификатором ссылки, производителем, попыткой и причиной. Не подставлять пустой результат, не запускать генерацию автоматически и не выдавать устаревший результат как актуальный.

Эти уточнения обязательны при детализации A0 и реализации A2/A3. Проверки включают недоступность старого Output после неуспешного перезапуска, отказ при несовместимых версиях снимка/недействительных доменных ссылках, восстановление после штатной отмены и отмену отдельной ноды с проверкой полноты коррелируемой диагностики. Отдельно проверять запрет необъявленных чтений и несовместимых контрактов зависимостей. Вопрос объединения записей legacy-нод снят: смешанный режим не вводится, замена и удаление генераторных нод принадлежат GEN-DAG-1.

### Практики, применимые к выбранной архитектуре

- **Управляемое время жизни задач:** координатор владеет задачами уровня, ожидает их завершения и очистки при отмене. `CancelledError` не подавляется как обычная ошибка. Сохраняем `gather(return_exceptions=True)`: автоматическая замена на `TaskGroup` изменила бы выбранную политику завершения соседей при ошибке. Основание: [Python asyncio](https://docs.python.org/3/library/asyncio-task.html).
- **Реальная неизменяемость опубликованных данных:** `frozen=True` не делает вложенный `dict` неизменяемым. При инвентаризации проверять весь граф вложений; не считать read-only внешнюю оболочку достаточной для безопасного разделения payload. Основание: [Pydantic — faux immutability](https://docs.pydantic.dev/latest/concepts/models/#faux-immutability).
- **Повторное использование записанного результата:** восстановление завершённой актуальной LLM-группы не выполняет новый запрос. Это применение принципа сохранения результатов недетерминированных операций, а не внедрение Temporal или полного event sourcing. Основание: [Temporal Workflows](https://docs.temporal.io/workflows).

**Согласованная граница ответственности за эффекты:** идемпотентность применения после resume требует контракта PatchSet/Snapshot. Идентификатор логического эффекта должен переживать retry; `attempt` результата не подходит в качестве единственного ключа дедупликации. Конкретный ключ и атомарность применения согласуются в соответствующей интеграции, а не выбираются этим планом за GEN-DAG-1. Основание: [Temporal — Activity definition](https://docs.temporal.io/activity-definition). Гарантия exactly-once для внешнего LLM-запроса при потере ответа здесь не заявляется.

## Порядок реализации: сначала архитектурная инфраструктура, потом ноды

**Жёсткая последовательность:** запрещено начинать массовую миграцию нод до индивидуальной приёмки архитектурных изменений ядра (A1–A3). Для каждого шага — отдельно зафиксированные контракт, состав замены и удаления, проверки и подтверждение мастера. При обнаружении новой архитектурной дыры остановить соответствующий шаг и согласовать решение, не маскировать временными `Any`/`dict`-адаптерами.

### Фаза A — архитектурные изменения (до миграции нод)

- **A0 — инвентаризация и карта реализации согласованных решений.** Прочитать и картировать существующие `BaseNode`/`deps`, `GraphCompiler`, `ExecutionPlan`, `DAGExecutor`, `NodeRegistry`, Python/LLM executors, `ExecutionState`, repair, `SessionSnapshot`, трассировку и диагностику. Сверить код с восемью согласованными решениями и всеми дополнительными согласованными уточнениями выше. Результат шага — карта конкретных изменений, детализация API и таблица сценариев с ожидаемыми Output, статусами, действиями replan/resume и судьбой соседних задач. Архитектурные решения уже приняты в плане; A0 не является этапом их выбора. Нельзя использовать только имена нод как доказательство поведения.
- **A1 — каркас типизированных контрактов нод.** После A0 определить POJO-binding ноды к Input/Output в `NodeRegistry`, минимальный typed-call контракт для Python и LLM и место валидации через существующую Pydantic-инфраструктуру. Новый путь регистрации требует Input/Output для каждой ноды; legacy-поддержку не добавлять. До фазы B проверять инфраструктуру на типизированных тестовых нодах. В отдельной карте зафиксировать прямое переиспользование доменных POJO, композицию и потребление Output зависимостей.
- **A2 — архитектура DAGContext и параллельной публикации.** Внедрить согласованный способ типобезопасного чтения/публикации результатов, работающий с `asyncio.gather` независимых Python-нод одного уровня. Реализовать согласованные в плане правила read view: входы нод формируются из завершённых доступных Output и доменных read-контрактов, без чтения незавершённого Output соседа. Ограничить общий mutable state, обеспечить корректную обработку одновременных успехов, ошибок, отмены и gate/replan; не блокировать весь DAG ради типизации. Сохранить уровни, фазы и группировку LLM; управление исполнять по согласованным решениям, включая остановку при gate на границе уровня вместо завершения всей фазы. Не принимать A2 без работающего учёта актуальности и runtime-метаданных, необходимого для безопасной публикации; эти зависимости нельзя оставлять заглушками до A3.
- **A3 — runtime/lifecycle.** Завершить реализацию и интеграционную проверку согласованных в плане контрактов: разделения типизированных результатов и статусов/ошибок, ссылок и времени жизни крупных Output, инвалидации потребителей, сохранения/восстановления при replan/resume и диагностических снимков без копий больших payload. Проверить lifecycle нового runtime на типизированных нодах; совместимый путь для legacy не создавать. Проверить вложенную неизменяемость POJO: одного `frozen=True` недостаточно для доказательства неизменяемости mutable вложений. Новое архитектурное решение возвращается на согласование в план до изменения ТЗ, а не принимается задним числом после реализации A2.

### Фаза B — последовательная миграция потребителей после принятой фазы A

- **B1 — Python-ноды по согласованной карте.** Переводить сохраняемые ноды небольшими проверяемыми группами; legacy-ноды генератора на замену/удаление передать в GEN-DAG-1. Сохраняемые ноды переводить на объявленные POJO Input/Output и публичные доменные read/CRUD-контракты; не переносить доменную реализацию или межоперационную оркестрацию в ноды. Для каждой ноды проверить deps и чтение Output, в том числе при параллельном выполнении соседей.
- **B2 — LLM-ноды и агрегированные группы.** Переход от `contract_json`/raw JSON к опубликованным валидированным Output POJO без изменения семантики одного LLM-вызова на temperature-группу, ошибок, repair и payload зависимостей. При необходимости обосновать и согласовать адаптацию существующих LLM-валидаторов вместо дублирования схем.
- **B3 — ExecutionState, replan/resume, trace и удаление старых каналов.** Мигрировать конкретных потребителей `NodeResult`, `node_results`, `shared_context`, snapshot/trace, `ResponseResolver` и cancellation; удалить старые общесистемные каналы после замены всех usages; удаление legacy-нод генератора и их регистраций выполняется в GEN-DAG-1. Не менять жизненный цикл генерации/публикации мира или правила PatchSet/Snapshot как побочный эффект типизации.

**Как описывать параллелизм:** ТЗ A2 должно содержать последовательность для уровня из нескольких нод: какие данные читаются до запуска и во время работы, какие объекты локальны задаче, кто обновляет каталог/статусы/trace, где находятся точки `await`, когда публикуются результаты и как завершаются оставшиеся задачи при отмене или replan. Сохранить конкурентный запуск независимых Python-нод через существующий `gather`; не держать общую блокировку на время доменных вызовов, I/O или LLM-запроса. Если для публикации нужна синхронизация, описать её границы и обосновать, что она не сериализует исполнение нод. Для LLM отдельно описать агрегированную группу и её repair; не переносить на неё механически алгоритм отдельных Python-задач.

**Условие готовности к реализации шага:** агент может по ТЗ определить, какие компоненты и методы изменить, какие данные передать, в каком порядке выполнить действия и какие исходы опубликовать. Если для этого всё ещё приходится самостоятельно выбирать идентичность Output, политику инвалидации или параллельной публикации, ТЗ не соответствует согласованному плану либо обнаружено новое противоречие, требующее согласования изменения плана. Нельзя компенсировать отсутствующее решение расширением списка тестов.

### Приёмка параллелизма (обязательна для A2 и повторно после B)

- Две независимые Python-ноды одного уровня **фактически перекрываются по времени**, а не исполняются последовательно после внедрения типизации.
- Ноды следующего уровня получают только согласованные завершённые типизированные результаты зависимостей; нет чтения чужого частичного Output или mutable-состояния другой ноды.
- Одновременные success/fail/cancel и gate/replan сохраняют предусмотренное управление и диагностику без гонок и потери Output/ошибок.
- LLM temperature-группы по-прежнему используют предусмотренное агрегированное исполнение и repair, без случайного раздробления на независимые вызовы.
- Диагностические snapshots и resume не нарушают согласованность результатов параллельного уровня, не дублируют тяжёлые payload и не возвращают устаревшее значение как актуальное.

**Проверяемые сценарии:**

- Подтвердить перекрытие двух независимых Python-нод через управляемые события/барьер: обе входят в исполнение до разрешения завершиться любой из них. Ограниченный timeout обнаруживает последовательный запуск; одной проверки наличия `gather` или сравнения длительности недостаточно. Проверить уровень из нескольких типизированных нод.
- Управляемо поменять порядок завершения соседей; проверить согласованный read view и публикацию Output/статусов/trace по согласованному контракту. До разрешённой точки публикации результат недоступен потребителям; частичная или вложенная mutable-структура не доступна через API каталога.
- Проверить success+fail, success+cancel, отмену всего уровня и конкурирующие gate/replan-сигналы. Проверять не только исключение, но и отсутствие бесконтрольных задач, согласованную судьбу успешных Output и невозможность поздней публикации из устаревшего запуска. `CancelledError` должен учитываться как отмена, а не успешное завершение.
- Проверить повторное исполнение производителя в цепочке и разветвлённом DAG, включая завершённых потребителей, независимую ветку и resume после частичного уровня. Ожидаемое переиспользование/инвалидация следует согласованным решениям плана; устаревшие результаты не выдаются как актуальные.
- Для LLM-групп проверить число агрегированных запросов, repair и восстановление частично завершённой группы по принятому контракту. Актуальная завершённая группа не вызывает LLM повторно. Незавершённая или инвалидированная группа выполняется целиком согласно пункту 6; это явно разрешённое повторное исполнение. Дробление группы и дополнительные запросы из-за преобразования типов запрещены; существующий repair сохраняется.

### Приёмка статической типизации (A1/A2 и после миграции B)

- Зафиксировать используемый type checker, конфигурацию и воспроизводимую команду проверки. Корректные объявления Input/Output и чтение результата производителя проходят проверку с сохранением конкретного типа POJO.
- Добавить отрицательные примеры: возврат несовместимого Output, передача неверного Input, присваивание прочитанного Output несовместимому типу. Type checker должен обнаруживать ошибки без опоры только на runtime-валидацию Pydantic.
- Для динамического выбора производителя отдельно описать границу runtime-проверки регистрации/контракта; не обещать статическую проверку произвольного строкового идентификатора. Типизированные потребители не должны обходить контракт через `Any` или непроверенные `cast`.

## Критерии архитектурной приёмки

- При завершении плана все оставшиеся ноды имеют POJO Input/Output; legacy-ноды генератора и их регистрации удалены в GEN-DAG-1, общесистемные старые пути исполнения и usages каналов удалены в DAG-TYPING-1. Нет адаптеров legacy/typed и смешанного режима. Python и LLM не расходятся по типу публикуемого результата.
- Реиспользованные доменные POJO не скопированы и не изменены ради DAG; ограничения полей остаются в существующем SoT.
- Никакой второй системы `REQUIRES`, каскада/field-policy, автоподбора read API по типам POJO либо неявного доменного pipeline в подготовке Input.
- При каждом типизированном чтении Output проверяемы производитель, объявленный контракт, актуальность и доступность результата; поведение при replan/resume/skip/fail явно определено перед реализацией.
- Параллельное исполнение Python-нод одного уровня и агрегированные LLM-группы сохранены и подтверждены проверками фактического поведения, включая конкурирующие записи результата/статуса/trace.
- Согласован жизненный цикл больших результатов без копирования payload и без неограниченного удержания данных.
- Работающий repair/LLM aggregation, cancellation, диагностика и текущие пути исполнения имеют проверяемую стратегию миграции.
- Архитектурная типизация не меняет ответственность DAG/domain/Snapshot. Единственная заданная здесь межплановая зависимость — готовность нужных частей обоих планов до полного переключения runtime; интеграционные PatchSet-контракты согласуются в соответствующем плане.

## Отношение к GEN-DAG-1

`GEN-DAG-1` владеет подключением самостоятельных операций генератора к существующему DAG и интеграцией PatchSet/Snapshot. `DAG-TYPING-1` владеет **общесистемными** контрактами нод и инфраструктурой обмена Output. Ни один план не должен реализовывать ответственность второго «заодно». GEN-DAG-1 также владеет заменой и удалением legacy-нод генератора. Точка полного переключения на typed runtime требует готовности общих контрактов и устранения legacy-потребителей обоими планами; инфраструктурная фаза A не зависит от завершения всего GEN-DAG-1.
