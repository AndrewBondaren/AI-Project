# Cache — публичные контракты данных и настроек

Владелец — домен Cache. Домен передаёт в GEN-DAG принятые контракты. Текущий статус OPEN. [Норматив Cache PC-0](../../docs/tz_terrain_generation.md#surface-planningcache--норматив-pc-0-2026-10-23)

**Cache V1 / AS-IS — binding передаёт caller.** Конкретный владелец — `app.application.cache.service.cacheService.CacheService`. Действующие синхронные методы: `get[T](binding: CacheBinding[T], key: CacheKey[T]) -> CacheLookup[T]`, `put[T](binding: CacheBinding[T], entry: CacheEntry[T]) -> CacheAdmission`, `evict[T](binding: CacheBinding[T], key: CacheKey[T]) -> None`. У get два результата: CacheHit с точными key/value и CacheMiss. Put добавляет либо заменяет запись по тому же ключу; STORED и SKIPPED_OVERSIZE штатны. Evict удаляет точный ключ. Для пути чтения/заполнения нужны get/put. CacheFailure имеет причины CONTRACT_MISMATCH, INVALID_PAYLOAD, BACKEND_FAILURE; конвертация ошибки в miss нарушает контракт. Источники: [норматив общего sync API](../../docs/tz_terrain_generation.md), [ключ](../../backend/app/dataModel/cache/identity/cacheKey.py), [entry и admission](../../backend/app/dataModel/cache/contracts/cacheEntry.py), [lookup](../../backend/app/dataModel/cache/contracts/cacheLookup.py), [реализация CacheService](../../backend/app/application/cache/service/cacheService.py).

**Ограничение архитектурной границы.** В целевом контракте composition root регистрирует binding внутри Cache. DAG передаёт ключ или запись. По потоку данных передаются только POJO ключа, записи и результата; registry, codec, worker, storage guard и backend не являются выходами доменных операций. В V1 get/put вызывает codec.validate; put также вызывает retained_bytes. Для Pack предусмотреть чистый codec bytes, для планов проверить каждый зарегистрированный envelope binding. Допускаются локальная проверка immutable schema и расчёт размера. Callback, выполняющий расчёт плана, проверку pin, чтение хранилища, повтор или обращение к другому домену, блокирует перенос такого binding. [Методы CachePayloadCodec](../../backend/app/application/cache/contracts/cacheBackend.py) · [Pack: точные входы и результаты](../../docs/tz_world_pack_storage.md#контракты-чтения-manifest-через-cache--проект-для-приёмки-владельцами)

### Область действия настроек Cache

**Решение пользователя.** У каждого экземпляра RAM-кэша одна эффективная `CachePolicy`. Публичные операции создания, чтения, обновления и удаления настроек относятся к политике конкретного экземпляра. Все его namespace делят `max_retained_bytes` и очередь LRU; `max_entry_bytes` ограничивает стоимость одной записи. Если Planning и Pack используют разные экземпляры, у каждого свой бюджет и своя очередь. Размещение Planning и Pack в одном или разных экземплярах остаётся отдельным решением о ресурсах.

**Адресация согласована.** При композиции контейнер привязывает целевой `CacheSettingsService` к конкретному экземпляру Cache. Все четыре операции настроек используют эту привязку, без параметра `cache_id`. При двух независимых кэшах каждому соответствует своя привязка сервиса настроек. Решение относится к одному контейнеру. В V1 `create_app()` сохраняет созданный Container в app.state; WorldDataWiring под RLock однократно создаёт planning backend и сервис для этого контейнера. Реестр CacheBinding внутри Cache по-прежнему нужен для выбора кодека по contract.id и проверки schema_version. Выбор общего экземпляра или двух независимых экземпляров для Planning и manifest Pack остаётся за решением о ресурсах. [Создание приложения](../../backend/app/core/app.py) · [DI Planning](../../backend/app/core/container/worldData.py) · [ТЗ Pack](../../docs/tz_world_pack_storage.md#manifest-cache-reader)

**Действующая политика.** Требование к реализации: одно авторитетное состояние политики на экземпляр. Settings.read возвращает действующую immutable CachePolicy этого состояния; admission и LRU используют её же. В V1 CacheService и MemoryCache хранят отдельные ссылки _policy, а planning_resources() кэширует стартовую конфигурацию. Последняя задаёт начальные значения; чтение настроек после runtime update должно отражать применённое изменение. [CacheService](../../backend/app/application/cache/service/cacheService.py) · [MemoryCache](../../backend/app/application/cache/backends/memoryCache.py) · [Поля и ограничения CachePolicy](../../backend/app/dataModel/cache/policy/cachePolicy.py)

| Контракт до freeze | Что требуется согласовать и проверить |
|---|---|
| OPEN — атомарное применение | Create принимает решение о наличии ключа, admission, вставке и вытеснении по одной эффективной политике в порядке, согласованном с settings.update. На гонке create/update допустим результат любого из двух последовательных порядков. Смешение старого max_entry_bytes с новым бюджетом и частичное применение недопустимы. Определить судьбу существующих записей отдельно при снижении max_entry_bytes и max_retained_bytes, порядок LRU и момент, с которого новый лимит гарантирован. Проверить read сразу после update, retained_bytes и доступность записей после снижения лимитов; независимый Cache B сохраняет свои настройки при изменении A. |
| OPEN — жизненный цикл | Зафиксировать, где и на какой срок сохраняется runtime update, что загрузит новый контейнер после рестарта, предусмотрена ли доставка изменений другим процессам и какой положительный ограниченный режим останется после удаления настроек. CRUD адресует один экземпляр; любое внешнее хранение или распространение требует отдельного явного контракта. Проверить delete с последующей операцией Cache, новый процесс и два независимых контейнера. |

**Приёмка линеаризуемости.** Указать единственную точку применения новой CachePolicy для экземпляра. Наблюдаемые результаты create, settings.update и settings.read, состав записей, порядок LRU и retained_bytes должны соответствовать последовательному исполнению с учётом реального порядка завершившихся вызовов. Решение о лимитах и эффекты вставки/вытеснения относятся к одной эффективной политике. Расхождение политики сервиса и backend в любом наблюдаемом состоянии означает отказ. На управляемых барьерах воспроизвести оба порядка гонки; после успешного update выполнить отдельные read и create. До прогона задать ожидаемую судьбу уже удерживаемой записи при снижении только max_entry_bytes и порядок вытеснения при снижении только max_retained_bytes. Проверить также одновременное снижение обоих лимитов. [Текущая проверка размера](../../backend/app/application/cache/service/cacheService.py) · [Текущее изменение LRU и счётчика](../../backend/app/application/cache/backends/memoryCache.py)

**Приёмка жизненного цикла.** В контракте указать источник и порядок выбора эффективной политики для каждого сценария: первый запуск из начальной конфигурации; рестарт после runtime update (как учитывается сохранённая версия, если предусмотрена персистентность); delete и последующий рестарт (какая явно заданная политика по умолчанию вступает в силу и откуда загружается). Для каждого сценария задать различимые лимиты у возможных источников, проверить settings.read и реальное решение create на граничном размере. Указать поведение другого процесса. Успешный delete оставляет экземпляр с валидной ограниченной CachePolicy; при отсутствии допустимого источника запуск либо переход должен завершиться отказом до работы без политики. [Обязательная CachePolicy в PlanningRuntimeSettings](../../backend/app/dataModel/planning/policy/planningRuntimeSettings.py) · [Валидация лимитов](../../backend/app/dataModel/cache/policy/cachePolicy.py)

Сигнатуры CRUD настроек, их POJO и ошибки остаются OPEN до согласования этих условий.

### Публичное чтение записи Cache

Целевой синхронный метод `CacheService.get[T](self, key: CacheKey[T]) -> CacheLookup[T]`. Cache разрешает binding по id и версии. При успешном чтении возвращается существующий `CacheHit[T](status=HIT, entry: CacheEntry[T])` с точным ключом и валидированным значением либо `CacheMiss(status=MISS)`, если запись для допустимого ключа отсутствует. Ошибка контракта, повреждённое значение и сбой backend дают `CacheFailure(error: CacheError)` с operation=GET и соответствующей причиной. Эффект hit в MemoryCache — обновление позиции записи в LRU. Выбор дальнейшего действия принадлежит DAG. [Вход](../../backend/app/dataModel/cache/identity/cacheKey.py) · [Модели результата](../../backend/app/dataModel/cache/contracts/cacheLookup.py) · [Проверки V1](../../backend/app/application/cache/service/cacheService.py)

Приёмка: проверить hit на точный ключ, miss после вытеснения, отказ до backend для неизвестной версии, ошибку на записи с чужим ключом или недопустимым значением и отдельный backend failure. Ни один отказ не возвращает MISS и не запускает вычисление внутри Cache.

### Публичная запись Cache после переноса

Целевой публичный метод `CacheService.create[T](entry: CacheEntry[T]) -> CacheAdmission` вызывается DAG после MISS и успешного вычисления. Целевые варианты CacheAdmission: STORED, ALREADY_PRESENT, SKIPPED_OVERSIZE. Публичного put после переноса нет.

**Порядок create.** До изменения Cache разрешить точный namespace/version и валидировать полные key и value. Далее backend под одной блокировкой проверяет наличие ключа, сравнивает занятое значение либо проверяет текущий лимит и вставляет отсутствующую запись. Решение о лимите и изменение политики синхронизированы со вставкой. Раздельные публичные get и put не обеспечивают эту атомарность. Лимит относится к стоимости удержания целой записи по CachePolicy.

| Условие | Наблюдаемый исход |
|---|---|
| Неверный контракт или недопустимое значение | Типизированная ошибка до мутации. |
| Ключ занят, валидированные значения полностью эквивалентны | ALREADY_PRESENT, в том числе если прежняя запись всё ещё присутствует после снижения лимита. |
| Ключ занят, значения различаются | CacheFailure с operation=CREATE, reason=CONTRACT_MISMATCH и issue.code=KEY_OCCUPIED_DIFFERENT_VALUE. Прежняя запись сохраняется независимо от её размера. |
| Ключ свободен, стоимость превышает действующий max_entry_bytes | SKIPPED_OVERSIZE; ни вставки, ни вытеснения. |
| Ключ свободен, стоимость в пределах лимита | STORED после атомарной вставки и требуемого LRU-вытеснения. |

**Эквивалентность принадлежит binding.** Для bytes manifest Pack сравниваются все байты. Для PlanEnvelope[T] сравнение охватывает полный ref (включая key и output_fingerprint), dependencies, payload и diagnostics с контрактным порядком элементов. Допускается точное сравнение полных канонических bytes при доказанном однозначном кодировании каждого из этих полей, либо эквивалентный чистый компаратор полных валидированных значений. Ни совпадение ссылки на объект, ни равенство ключа или одного fingerprint доказательством не являются. До допуска binding проверить независимо созданные равные значения и отличие в каждом смысловом поле. [PlanEnvelope](../../backend/app/dataModel/planning/contracts/planEnvelope.py) · [Codec binding](../../backend/app/application/cache/contracts/cacheBackend.py)

**Политика замены — свойство семантики ключа.** В V1 CacheEntry и CacheService требуют глубокой неизменности принятого значения, но MemoryCache.put заменяет значение занятого ключа. CacheBinding содержит contract и codec; переключателя политики замены в коде нет. В целевом срезе для каждого описанного контракта действует правило: один занятый ключ допускает только полное эквивалентное значение. Для manifest Pack ключ адресует полный ArtifactRef; для planning envelope ключ вычисляется из PlanKey входов, а равенство результата обеспечивается требованием детерминизма. Различные результаты одного расчётного ключа должны обнаруживаться. В проверенных production-регистрациях Cache потребность в замене значения под тем же ключом не установлена. Это граница текущего среза; вводить второй режим или поле политики только ради CRUD оснований нет. [Тип binding](../../backend/app/application/cache/contracts/cacheBackend.py) · [Регистрации Planning](../../backend/app/application/worldData/planning/composition/planProviders.py) · [PreparedNaturalTerrain](../../backend/app/application/worldData/planning/composition/natural/preparedTerrain.py) · [Формула ключа](../../backend/app/application/planning/service/planFingerprints.py)

**Проект публичного update.** `CacheService.update[T](entry: CacheEntry[T]) -> CacheUpdateResult`. Предлагаемый модуль `backend/app/dataModel/cache/contracts/cacheUpdateResult.py`: immutable POJO `CacheUpdateResult(outcome: CacheUpdateOutcome)`, строгий enum `NOT_FOUND="not_found"`, `UNCHANGED="unchanged"`. Сначала проверить контракт и вход по общим правилам. Затем под одной блокировкой backend установить наличие точного ключа и сравнить полные валидированные значения по правилам binding. Для отсутствующего ключа (в том числе после LRU) вернуть NOT_FOUND без создания; при эквивалентности — UNCHANGED. При отличии вернуть ошибку через исключение CacheFailure с operation=UPDATE, reason=CONTRACT_MISMATCH, issue.code=KEY_OCCUPIED_DIFFERENT_VALUE; существующая запись сохраняется. Проверить все три исхода и гонку с вытеснением. Это проект метода, POJO и ошибки; в V1 они отсутствуют.

**Конкурентная приёмка.** При достаточном бюджете запустить два create под барьером. Для A/A ровно один STORED и один ALREADY_PRESENT; для A/B один STORED и один типизированный конфликт, читается значение победителя. Повторить гонку MISS → compute → create с заполнением ключа между MISS и create. Снизить лимит между MISS и create: для свободного ключа проверить SKIPPED_OVERSIZE, для всё ещё занятого — равенство либо конфликт раньше лимита. После create(K,A) и отказа create(K,B) проверить отказ update(K,B) и неизменность A. Отдельно проверить отсутствие дублирующего вычисления через [single-flight runtime DAG](../../docs/tz_world_generation_dag.md#single-flight-при-переносе-planningservice): уникальная вставка сама по себе допускает два вызова evaluate.

После миграции всех вызывающих мест удалить публичный V1 `CacheService.put`, включая aliases, overloads, fallback и тестовые обходы. Проверка приёмки: положительный сценарий MISS проходит через create; среди публичных методов и обращений к CacheService отсутствует put. Внутренний backend-примитив `MemoryCache.put` может остаться только с подтверждённым целевым caller и соблюдением атомарной семантики create/update. [V1 API](../../backend/app/application/cache/service/cacheService.py) · [Backend](../../backend/app/application/cache/backends/memoryCache.py)

### Публичное удаление записи Cache

Единственный публичный метод CRUD-удаления записи — синхронный `CacheService.evict[T](self, key: CacheKey[T]) -> CacheEvictResult`. DAG передаёт точный ключ. Cache сам разрешает binding по namespace и версии. Вход — [CacheKey](../../backend/app/dataModel/cache/identity/cacheKey.py). Целевой модуль результата — `backend/app/dataModel/cache/contracts/cacheEvictResult.py`: строгий immutable POJO `CacheEvictResult` с единственным обязательным полем `outcome: CacheEvictOutcome`. Значения enum — `EVICTED="evicted"` и `NOT_FOUND="not_found"`.

Backend определяет исход, удаляет запись и корректирует счётчик занятых байтов под одной блокировкой. EVICTED означает, что именно этот вызов удалил запись и вычел её стоимость. NOT_FOUND означает, что на момент операции ключ отсутствовал; счётчик сохраняется. Это штатный исход повторного удаления или удаления после LRU. Неизвестный namespace либо несовместимая версия дают CacheFailure с reason=CONTRACT_MISMATCH и operation=EVICT до обращения к backend. Сбой backend даёт BACKEND_FAILURE с operation=EVICT. Для Pack эффект ограничен копией в RAM: pin, artifact holders и публикация сохраняют своё состояние. [Действующий метод V1](../../backend/app/application/cache/service/cacheService.py) · [Блокировка и учёт в backend](../../backend/app/application/cache/backends/memoryCache.py)

Приёмка через публичный метод: два одновременных evict существующего K дают ровно один EVICTED и один NOT_FOUND. Размер записи вычтен ровно один раз, стоимость остальных записей сохранена. После LRU ожидается NOT_FOUND; при ошибке версии backend не вызван. После evict manifest действующий pin по-прежнему позволяет загрузить его из artifact storage.

### Обязательная приёмка удаления Cache V1

V1 здесь означает API Cache с явным binding и прежний путь get_or_build → Cache. После переноса всех callers предъявить инвентарь использований в application, DI, workers, debug, scripts и tests, diff удаления и проверки через публичный API. В итоговом коде отсутствуют мёртвые V1-методы, импорты, регистрации, adapters, прежние overload/fallback и дублирующие маршруты чтения/записи. Для каждого сохранённого общего компонента (включая CacheBinding, codec и RAM backend) показать действующий целевой caller. При наличии хотя бы одного остаточного или параллельного пути приёмка отклоняется. Проверить hit, miss, ошибочную версию до backend и единственную запись результата через DAG. Метки `LEGACY REMOVE(CACHE-V1-BINDING)` снять вместе с переходом, после проверки каждого места. ### Открытые замечания Cache

#### Публичная ошибка Cache для DAG

Согласован транспорт через исключение `CacheFailure`. Целевая сигнатура в `application/cache/service/cacheService.py`: `CacheFailure(error: CacheError)`; публичное поле `error: CacheError`. DAG читает `exc.error.reason`. Обычное завершение `get` возвращает только CacheHit или CacheMiss. Отказ любой из трёх категорий прерывает операцию; переход к вычислению по miss допускается только при действительном CacheMiss.

**Схема для реализации.** Модуль владельца — `backend/app/dataModel/cache/contracts/cacheError.py`. Определить в нём строгий immutable POJO `CacheError` и следующие типы. `CacheFailureReason` перенести из service с сохранением трёх существующих строковых значений и единственного объявления enum. `CacheOperation` описывает методы этого среза: GET=`get`, CREATE=`create`, UPDATE=`update`, EVICT=`evict`.

| Поле CacheError | Тип | Обязательность и смысл |
|---|---|---|
| reason | CacheFailureReason | Обязательно. CONTRACT_MISMATCH=`contract_mismatch`, INVALID_PAYLOAD=`invalid_payload`, BACKEND_FAILURE=`backend_failure`. |
| operation | CacheOperation | Обязательно. Имя вызванного публичного метода. |
| message | StrictStr | Обязательное непустое сообщение, пригодное для диагностики. Решения caller определяются enum reason. Exception, traceback, содержимое payload и произвольный текст backend в POJO не включаются; техническую причину сохраняет цепочка исключений. |
| issues | tuple[CacheFieldIssue \| CacheContractIssue, ...] | По умолчанию пустой кортеж. CacheFieldIssue — конкретный FieldPathError[CacheIssueCode] с code, проверенным path и message. CacheContractIssue — POJO с code: CacheIssueCode и message: StrictStr для отказа по целому контракту или записи, без фиктивного пути. Оба типа и enum объявляются в том же модуле, что CacheError. |

**Причина и код детали.** CacheFailureReason задаёт категорию; CacheIssueCode уточняет событие. При CONTRACT_MISMATCH различать UNKNOWN_NAMESPACE, SCHEMA_VERSION_MISMATCH, KEY_OCCUPIED_DIFFERENT_VALUE и прочий CONTRACT_VIOLATION. Для конфликта значений обязателен CacheContractIssue с кодом KEY_OCCUPIED_DIFFERENT_VALUE. При INVALID_PAYLOAD допустим код INVALID_VALUE; путь указывается только для реального поля. При BACKEND_FAILURE issues всегда пуст. Проверять допустимую пару reason/code. [Правила диагностики F01/F02/F05](./error-contracts-1.md)

**Приёмка реализации.** Через публичный get предъявить hit, miss и три независимых отказа: неизвестная версия до вызова backend, повреждённое значение в hit и исключение backend. Для каждого отказа проверить класс CacheFailure и точные поля error, отсутствие возврата CacheMiss и отсутствие запуска вычисления. Проверить round-trip CacheError с реальным полевым issue и с пустым issues; отклонить BACKEND_FAILURE с полем, недопустимые пары reason/code и синтетический путь. Для create/update/evict проверить operation при сбое backend; SKIPPED_OVERSIZE остаётся штатным результатом create.
