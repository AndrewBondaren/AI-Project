# Cache — публичные контракты данных

## Шаг 1. Архитектурная приёмка Cache

Это первый обязательный шаг, до правок кода. Владелец — Cache. Зафиксировать границы двух экземпляров RAM-кэша, четыре публичных CRUD-метода, модели входа/результата/ошибки, ответственность и критерий отказа каждого класса, а также полный список V1 callers. Проверить вложенные вызовы для каждого зарегистрированного кодека: только локальные проверки и оценка значения; выбор следующей операции, запуск provider, обращение в Pack или обратный вызов DAG отклоняют архитектуру. Владелец ветвления hit/miss — DAG. Runtime отвечает за single-flight. Pack отвечает за проверку pin. Публичный CRUD настроек исключён решением пользователя. [Критерии архитектуры](../rules/dag-generator-interface.mdc#обязательная-приёмка-плана-любого-домена) · [Правило CRUD](../rules/dag-generator-interface.mdc#конкретность-публичного-crud-контракта)

**Шаг 1 — архитектура предъявлена, согласование OPEN.** Контракт реестра bindings согласован. На согласовании остаются источник конфигурации Pack, внутренний атомарный порт и сравнение canonical bytes, семантика LRU при идемпотентной записи и POJO результата create. При архитектурной приёмке сверяются границы классов, инварианты и критерии проверки; исполнение тестов относится к последующим шагам. Доменная приёмка отделена от приёмки маршрута: конкретные DAG-ноды пользователь проектирует совместно с агентом. [Граница Planning](./generator-public-surface-planning.md#публичный-вход-вычисления-и-передача-результата-в-dag) · [Внешние зависимости нод](./gen-dag-1-post-geo-ws.md#зависимости-нод-от-публичных-контрактов)

### Уточнения шага 1 по ревью (проект для приёмки, 2026-11-10)

**Реестр bindings Cache — архитектурное решение принято пользователем 2026-11-10.** Переиспользовать существующий `CacheBinding[T](contract, codec)`. В V1 composition передаёт binding в registered plan contract, PlanRegistry.register отклоняет повтор одного cache id, PlanningService передаёт binding в CacheService при каждом get/put. Существующий CacheContractRegistry описывает только метаданные и также требует уникальный id. В целевом пути composition один раз собирает полный набор bindings экземпляра Cache и передаёт его внутреннему реестру. [Регистрация V1](../../backend/app/application/planning/providers/planRegistry.py) · [Пара contract/codec](../../backend/app/application/cache/contracts/cacheBackend.py) · [Модель метаданных](../../backend/app/dataModel/cache/contracts/cacheContract.py)

- **Класс и создание.** Целевой `CacheBindingRegistry` — `backend/app/application/cache/service/cacheBindingRegistry.py`. Конструктор получает набор зарегистрированных bindings с разными типами payload, валидирует полные metadata и строит индекс по CacheContractId. Один id допускает одну версию в пределах экземпляра. Дубликат id, включая другую версию или повтор того же binding, — ValueError при композиции; частично собранный сервис не публикуется. После создания состав фиксирован. Planning и Pack получают отдельные реестры со своими bindings. Регистрация planning providers и проверка dependency slots остаются у Planning.
- **Чтение.** Внутренний синхронный метод `resolve[T](self, contract: CacheContract[T]) -> CacheBinding[T]` получает строго проверенный `key.contract`, находит запись по id и сравнивает schema_version. Разрешается эквивалентный восстановленный ключ. Возвращается только зарегистрированная пара, кодек из запроса не принимается. Результат проходит дальнейшую runtime-валидацию конкретного payload через зарегистрированный codec. Гетерогенный индекс и восстановление generic-типа инкапсулированы в реестре; публичным callers не нужен cast.
- **Отказы.** При неизвестном id или неверной версии resolve выдаёт внутренний `CacheBindingResolutionError(code: CacheIssueCode)` со значением UNKNOWN_NAMESPACE или SCHEMA_VERSION_MISMATCH. CacheService, которому известна фактическая CRUD-операция, формирует публичный CacheFailure с reason=CONTRACT_MISMATCH до вызова backend. Реестр не читает storage, не вызывает codec/provider и не владеет execution. [V1-проверка ключа и binding](../../backend/app/application/cache/service/cacheService.py)
- **Критерий приёмки.** Проверить повтор id, восстановленный ключ, обе ошибки разрешения и ноль обращений к backend при отказе. Передача ключа Pack в Planning Cache отклоняется. Проверить типизированное разрешение на двух различных payload и отсутствие возможности подменить codec через внешний запрос. Требование V1 о тождестве объекта handle в PlanRegistry.check относится к executable provider; Cache разрешает сериализуемое описание по id и версии.

**Источник второй политики.** Предлагается секция TOML `[world_pack.manifest_cache]` → обязательное поле `manifest_cache: CachePolicy` строгого immutable POJO `WorldPackCacheSettings` в `backend/app/dataModel/worldPack/bake/worldPackCacheSettings.py` → `AppSettings.world_pack`. При загрузке ConfigManager._to_flat передаёт секцию в валидатор, _to_nested сохраняет её при round-trip; AppSettings.update выполняет ту же типизированную проверку. До переключения V1 отсутствие секции допустимо для сценариев без manifest V2. При сборке V2 отсутствие секции или обязательных бюджетов блокирует подключение manifest Cache с диагностикой пути; некорректная явно переданная секция отклоняется при загрузке. На V2-only старте проверить до начала обслуживания. В `backend/app/core/container/packs.py` предложена фабрика `PacksWiring.pack_manifest_cache_service()`, однократно под lock создающая пару MemoryCache/CacheService на контейнер из world_pack.manifest_cache. Не брать бюджет Planning или произвольный default. Приёмка: разные заданные лимиты, повторный и конкурентный вызовы фабрики, валидный config round-trip, отсутствие секции и неверные лимиты; ошибка не оставляет частично зарегистрированный экземпляр. [Загрузка в create_app](../../backend/app/core/app.py) · [Сериализация TOML](../../backend/app/core/configManager.py) · [AppSettings](../../backend/app/core/appSettings.py) · [Pack DI](../../backend/app/core/container/packs.py)

**Атомарный порт (предложение).** В `application/cache/contracts/cacheBackend.py` целевой CacheBackend сохраняет get и получает методы `create[T](entry: CacheEntry[T], codec: CachePayloadCodec[T], cost: int) -> CacheAdmission`, `update[T](entry: CacheEntry[T], codec: CachePayloadCodec[T]) -> CacheUpdateOutcome`, `evict[T](key: CacheKey[T]) -> CacheEvictOutcome`. Это внутренний порт. CacheService разрешает binding, валидирует immutable entry и передаёт cost по существующей формуле max(codec.retained_bytes(value), retained_entry_bytes(entry)); размер не даёт раннего SKIPPED_OVERSIZE. MemoryCache под одной блокировкой определяет присутствие по точному адресу; при занятом ключе сравнивает полные `codec.encode(existing) == codec.encode(incoming)`. Сравнение выполняется до мутации и без вызова get, который меняет порядок LRU. Выбран canonical encode; дополнительный comparator в контракт не вводится. Для пустого ключа create под той же блокировкой применяет лимиты, вытесняет и вставляет. Для update/evict там же определяется точный исход. При разных значениях backend сообщает внутренний `CacheValueConflict`; CacheService формирует CONTRACT_MISMATCH с правильной operation и KEY_OCCUPIED_DIFFERENT_VALUE. Ошибка валидации/кодирования — INVALID_PAYLOAD; отдельный backend fault — BACKEND_FAILURE. Проверить эти различия до общего перехвата технических исключений. CacheService упаковывает внутренние enum в публичные POJO. [Текущий backend port и codec](../../backend/app/application/cache/contracts/cacheBackend.py) · [Текущая реализация LRU](../../backend/app/application/cache/backends/memoryCache.py)

**LRU для идемпотентной записи (выбранный вариант для приёмки).** ALREADY_PRESENT и UNCHANGED сохраняют значение, стоимость и позицию записи. Конфликт также сохраняет LRU. Успешный get освежает позицию. В двух отдельных прогонах заполнить A, затем B (бюджет на две записи), выполнить create(A, A-value) либо update(A, A-value), затем вставить C: вытесняется A. В контрольном прогоне после get(A) вытесняется B.

**Инвентарь binding и вложенные вызовы.** В текущем production-пути WorldDataWiring.surface_planning → register_world_plan_providers восемь CacheContract с id `surface.envelope.pc.<slot>`. Для каждого зарегистрирован `SurfaceEnvelopeCodec(PlanEnvelope[тип ниже], SURFACE_MANIFEST)`. [Точка сборки](../../backend/app/core/container/worldData.py) · [Регистрации](../../backend/app/application/worldData/planning/composition/planProviders.py) · [Версии](../../backend/app/dataModel/surfacePlanning/surfacePlanBindings.py)

У всех восьми validate проходит через validate_immutable, строгую TypeAdapter-валидацию конкретного envelope и canonical encode; encode валидирует и кодирует, decode декодирует и повторяет validate, retained_bytes считает граф объектов. В этих методах нет вызова provider, DAG или Pack. Отдельная фабрика register_natural_terrain объявляет terrain.envelope.prepared_natural v1 с тем же codec и PreparedNaturalTerrain; её вызов в backend/app не найден. GEO-декларации сами по себе не доказывают production-регистрацию. Для каждого допускаемого binding нужны fixture полного payload, доказательство однозначности canonical bytes и проверка вложенных валидаторов; статический разбор общего codec этих тестов не заменяет. [Codec](../../backend/app/application/worldData/planning/encoding/surfaceEnvelopeCodec.py) · [Отдельная фабрика](../../backend/app/application/worldData/planning/composition/natural/preparedTerrain.py)

**Manifest Pack.** Предложен `ManifestBytesCodec` в `application/cache/contracts/manifestBytesCodec.py`: validate(value: object) → bytes принимает ровно bytes; encode(value: bytes) → bytes и decode(encoded: bytes) → bytes сохраняют все байты без нормализации; retained_bytes(value: bytes) → int возвращает len(value), а сервис дополнительно учитывает стоимость entry. Проверка digest, pin, seal, world_uid и формата остаётся в Pack. На hit DAG передаёт entry на доменную проверку; для Planning проверяются ref.key, dependencies и output fingerprint. На miss существующая цепочка PlanRegistry.build → registration adapter → provider.build остаётся AS-IS; допустимый прямой публичный вход конкретного домена и его согласование с пользователем OPEN в GEN-SURFACE-PLAN. [Проверка envelope](../../backend/app/application/planning/providers/planProvider.py) · [Callback](../../backend/app/application/planning/providers/planRegistry.py) · [Открытый доменный вход](./generator-public-surface-planning.md#публичный-вход-вычисления-и-передача-результата-в-dag)

Владелец — домен Cache. Домен передаёт в GEN-DAG принятые контракты. Текущий статус OPEN. [Норматив Cache PC-0](../../docs/tz_terrain_generation.md#surface-planningcache--норматив-pc-0-2026-10-23)

**Cache V1 / AS-IS — binding передаёт caller.** Конкретный владелец — `app.application.cache.service.cacheService.CacheService`. Действующие синхронные методы: `get[T](binding: CacheBinding[T], key: CacheKey[T]) -> CacheLookup[T]`, `put[T](binding: CacheBinding[T], entry: CacheEntry[T]) -> CacheAdmission`, `evict[T](binding: CacheBinding[T], key: CacheKey[T]) -> None`. У get два результата: CacheHit с точными key/value и CacheMiss. Put добавляет либо заменяет запись по тому же ключу; STORED и SKIPPED_OVERSIZE штатны. Evict удаляет точный ключ. Для пути чтения/заполнения нужны get/put. CacheFailure имеет причины CONTRACT_MISMATCH, INVALID_PAYLOAD, BACKEND_FAILURE; конвертация ошибки в miss нарушает контракт. Источники: [норматив общего sync API](../../docs/tz_terrain_generation.md), [ключ](../../backend/app/dataModel/cache/identity/cacheKey.py), [entry и admission](../../backend/app/dataModel/cache/contracts/cacheEntry.py), [lookup](../../backend/app/dataModel/cache/contracts/cacheLookup.py), [реализация CacheService](../../backend/app/application/cache/service/cacheService.py).

**Ограничение архитектурной границы.** В целевом контракте composition root регистрирует binding внутри Cache. DAG передаёт ключ или запись. По потоку данных передаются только POJO ключа, записи и результата; registry, codec, worker, storage guard и backend не являются выходами доменных операций. В V1 get/put вызывает codec.validate; put также вызывает retained_bytes. Для Pack предусмотреть чистый codec bytes, для планов проверить каждый зарегистрированный envelope binding. Допускаются локальная проверка immutable schema и расчёт размера. Callback, выполняющий расчёт плана, проверку pin, чтение хранилища, повтор или обращение к другому домену, блокирует перенос такого binding. ### Конфигурация экземпляра Cache

По решению пользователя от 2026-11-10 публичный CRUD Cache относится только к записям. Контейнер при создании экземпляра передаёт обязательную валидную immutable CachePolicy в сервис и backend; она действует до пересоздания экземпляра. Новый экземпляр получает политику из своей стартовой конфигурации. CacheSettingsService, runtime-переопределения и их распространение между процессами исключены из плана. Каждый экземпляр ведёт собственный учёт памяти и LRU по всем своим namespace. Контейнер создаёт два отдельных экземпляра Cache: один для планов Planning, второй для проверенных bytes manifest World Pack V2. У каждого своя пара CacheService/MemoryCache, стартовая CachePolicy, счётчик retained_bytes и очередь LRU. Приёмка: заполнить оба кэша, вызвать вытеснение в одном и проверить, что записи и retained_bytes второго сохранились; повторить в обратную сторону. Конкретные значения бюджетов задаются конфигурацией. [DI Planning](../../backend/app/core/container/worldData.py) · [CachePolicy](../../backend/app/dataModel/cache/policy/cachePolicy.py)

### Публичное чтение записи Cache

Целевой синхронный метод `CacheService.get[T](self, key: CacheKey[T]) -> CacheLookup[T]`. Cache разрешает binding по id и версии. При успешном чтении возвращается существующий `CacheHit[T](status=HIT, entry: CacheEntry[T])` с точным ключом и валидированным значением либо `CacheMiss(status=MISS)`, если запись для допустимого ключа отсутствует. Ошибка контракта, повреждённое значение и сбой backend дают `CacheFailure(error: CacheError)` с operation=GET и соответствующей причиной. Эффект hit в MemoryCache — обновление позиции записи в LRU. Выбор дальнейшего действия принадлежит DAG. [Вход](../../backend/app/dataModel/cache/identity/cacheKey.py) · [Модели результата](../../backend/app/dataModel/cache/contracts/cacheLookup.py) · [Проверки V1](../../backend/app/application/cache/service/cacheService.py)

Приёмка: проверить hit на точный ключ, miss после вытеснения, отказ до backend для неизвестной версии, ошибку на записи с чужим ключом или недопустимым значением и отдельный backend failure. Ни один отказ не возвращает MISS и не запускает вычисление внутри Cache.

### Публичная запись Cache после переноса

После MISS и успешного вычисления DAG вызывает create. Согласованы три исхода: STORED, ALREADY_PRESENT, SKIPPED_OVERSIZE. В V1 CacheAdmission — enum с двумя значениями. Для выполнения правила об именованном POJO результата на шаг 1 предложено `CacheService.create[T](self, entry: CacheEntry[T]) -> CacheCreateResult`, где строгая immutable модель `CacheCreateResult(outcome: CacheAdmission)` размещается в `dataModel/cache/contracts/cacheCreateResult.py`, а enum в `dataModel/cache/contracts/cacheEntry.py` дополняется ALREADY_PRESENT. Ошибка — общий CacheFailure(error: CacheError). Форма POJO требует согласования; поведение трёх исходов сохраняется. [Действующие модели записи и admission](../../backend/app/dataModel/cache/contracts/cacheEntry.py)

**Порядок create.** До изменения Cache разрешить точный namespace/version и валидировать полные key и value. Далее backend под одной блокировкой проверяет наличие ключа, сравнивает занятое значение либо проверяет текущий лимит и вставляет отсутствующую запись. Проверка бюджета экземпляра и изменение LRU образуют одну атомарную операцию вставки. Раздельные публичные get и put не обеспечивают эту атомарность. Лимит относится к стоимости удержания целой записи по CachePolicy.

| Условие | Наблюдаемый исход |
|---|---|
| Неверный контракт или недопустимое значение | Типизированная ошибка до мутации. |
| Ключ занят, валидированные значения полностью эквивалентны | ALREADY_PRESENT. |
| Ключ занят, значения различаются | CacheFailure с operation=CREATE, reason=CONTRACT_MISMATCH и issue.code=KEY_OCCUPIED_DIFFERENT_VALUE. Прежняя запись сохраняется независимо от её размера. |
| Ключ свободен, стоимость превышает действующий max_entry_bytes | SKIPPED_OVERSIZE; ни вставки, ни вытеснения. |
| Ключ свободен, стоимость в пределах лимита | STORED после атомарной вставки и требуемого LRU-вытеснения. |

**Эквивалентность принадлежит binding.** Для bytes manifest Pack сравниваются все байты. Для PlanEnvelope[T] сравнение охватывает полный ref (включая key и output_fingerprint), dependencies, payload и diagnostics с контрактным порядком элементов. Backend сравнивает полные канонические bytes средствами codec под блокировкой. Для допуска binding требуется однозначное кодирование всех перечисленных полей. Ни совпадение ссылки на объект, ни равенство ключа или одного fingerprint доказательством не являются. До допуска binding проверить независимо созданные равные значения и отличие в каждом смысловом поле. [PlanEnvelope](../../backend/app/dataModel/planning/contracts/planEnvelope.py) · [Codec binding](../../backend/app/application/cache/contracts/cacheBackend.py)

**Политика замены — свойство семантики ключа.** В V1 CacheEntry и CacheService требуют глубокой неизменности принятого значения, но MemoryCache.put заменяет значение занятого ключа. CacheBinding содержит contract и codec; переключателя политики замены в коде нет. В целевом срезе для каждого описанного контракта действует правило: один занятый ключ допускает только полное эквивалентное значение. Для manifest Pack ключ адресует полный ArtifactRef; для planning envelope ключ вычисляется из PlanKey входов, а равенство результата обеспечивается требованием детерминизма. Различные результаты одного расчётного ключа должны обнаруживаться. В проверенных production-регистрациях Cache потребность в замене значения под тем же ключом не установлена. Это граница текущего среза; вводить второй режим или поле политики только ради CRUD оснований нет. [Тип binding](../../backend/app/application/cache/contracts/cacheBackend.py) · [Регистрации Planning](../../backend/app/application/worldData/planning/composition/planProviders.py) · [PreparedNaturalTerrain](../../backend/app/application/worldData/planning/composition/natural/preparedTerrain.py) · [Формула ключа](../../backend/app/application/planning/service/planFingerprints.py)

**Проект публичного update.** `CacheService.update[T](entry: CacheEntry[T]) -> CacheUpdateResult`. Предлагаемый модуль `backend/app/dataModel/cache/contracts/cacheUpdateResult.py`: immutable POJO `CacheUpdateResult(outcome: CacheUpdateOutcome)`, строгий enum `NOT_FOUND="not_found"`, `UNCHANGED="unchanged"`. Сначала проверить контракт и вход по общим правилам. Затем под одной блокировкой backend установить наличие точного ключа и сравнить полные валидированные значения по правилам binding. Для отсутствующего ключа (в том числе после LRU) вернуть NOT_FOUND без создания; при эквивалентности — UNCHANGED. При отличии вернуть ошибку через исключение CacheFailure с operation=UPDATE, reason=CONTRACT_MISMATCH, issue.code=KEY_OCCUPIED_DIFFERENT_VALUE; существующая запись сохраняется. Проверить все три исхода и гонку с вытеснением. Это проект метода, POJO и ошибки; в V1 они отсутствуют.

**Конкурентная приёмка.** При достаточном бюджете запустить два create под барьером. Для A/A ровно один STORED и один ALREADY_PRESENT; для A/B один STORED и один типизированный конфликт, читается значение победителя. Повторить гонку MISS → compute → create с заполнением ключа между MISS и create. Для свободного ключа проверить границы стоимости записи при фиксированной политике экземпляра. После create(K,A) и отказа create(K,B) проверить отказ update(K,B) и неизменность A. Отдельно проверить отсутствие дублирующего вычисления через [single-flight runtime DAG](../../docs/tz_world_generation_dag.md#single-flight-при-переносе-planningservice): уникальная вставка сама по себе допускает два вызова evaluate.

После миграции всех вызывающих мест удалить публичный V1 `CacheService.put`, включая aliases, overloads, fallback и тестовые обходы. Проверка приёмки: положительный сценарий MISS проходит через create; среди публичных методов и обращений к CacheService отсутствует put. Внутренний backend-примитив `MemoryCache.put` может остаться только с подтверждённым целевым caller и соблюдением атомарной семантики create/update. [V1 API](../../backend/app/application/cache/service/cacheService.py) · [Backend](../../backend/app/application/cache/backends/memoryCache.py)

### Публичное удаление записи Cache

Единственный публичный метод CRUD-удаления записи — синхронный `CacheService.evict[T](self, key: CacheKey[T]) -> CacheEvictResult`. DAG передаёт точный ключ. Cache сам разрешает binding по namespace и версии. Вход — [CacheKey](../../backend/app/dataModel/cache/identity/cacheKey.py). Целевой модуль результата — `backend/app/dataModel/cache/contracts/cacheEvictResult.py`: строгий immutable POJO `CacheEvictResult` с единственным обязательным полем `outcome: CacheEvictOutcome`. Значения enum — `EVICTED="evicted"` и `NOT_FOUND="not_found"`.

Backend определяет исход, удаляет запись и корректирует счётчик занятых байтов под одной блокировкой. EVICTED означает, что именно этот вызов удалил запись и вычел её стоимость. NOT_FOUND означает, что на момент операции ключ отсутствовал; счётчик сохраняется. Это штатный исход повторного удаления или удаления после LRU. Неизвестный namespace либо несовместимая версия дают CacheFailure с reason=CONTRACT_MISMATCH и operation=EVICT до обращения к backend. Сбой backend даёт BACKEND_FAILURE с operation=EVICT. Для Pack эффект ограничен копией в RAM: pin, artifact holders и публикация сохраняют своё состояние. [Действующий метод V1](../../backend/app/application/cache/service/cacheService.py) · [Блокировка и учёт в backend](../../backend/app/application/cache/backends/memoryCache.py)

Приёмка через публичный метод: два одновременных evict существующего K дают ровно один EVICTED и один NOT_FOUND. Размер записи вычтен ровно один раз, стоимость остальных записей сохранена. После LRU ожидается NOT_FOUND; при ошибке версии backend не вызван. После evict manifest действующий pin по-прежнему позволяет загрузить его из artifact storage.

### Обязательная приёмка удаления Cache V1

V1 здесь означает API Cache с явным binding и прежний путь get_or_build → Cache. После переноса всех callers предъявить инвентарь использований в application, DI, workers, debug, scripts и tests, diff удаления и проверки через публичный API. В итоговом коде отсутствуют мёртвые V1-методы, импорты, регистрации, adapters, прежние overload/fallback и дублирующие маршруты чтения/записи. Для каждого сохранённого общего компонента (включая CacheBinding, codec и RAM backend) показать действующий целевой caller. При наличии хотя бы одного остаточного или параллельного пути приёмка отклоняется. Проверить hit, miss, ошибочную версию до backend и единственную запись результата через DAG. Метки `LEGACY REMOVE(CACHE-V1-BINDING)` снять вместе с переходом, после проверки каждого места. ### Открытые замечания Cache

#### Публичная ошибка Cache для DAG

Согласован транспорт через исключение `CacheFailure`. Целевая сигнатура в `application/cache/service/cacheService.py`: `CacheFailure(error: CacheError)`; публичное поле `error: CacheError`. DAG читает `exc.error.reason`. Обычное завершение `get` возвращает только CacheHit или CacheMiss. Отказ любой из трёх категорий прерывает операцию; переход к вычислению по miss допускается только при действительном CacheMiss.

**Схема для реализации.** Модуль владельца — `backend/app/dataModel/cache/contracts/cacheError.py`. Определить в нём строгий immutable POJO `CacheError` и следующие типы. `CacheFailureReason` перенести из service с сохранением трёх существующих строковых значений и единственного объявления enum. `CacheOperation` описывает методы этого среза: GET=`get`, CREATE=`create`, UPDATE=`update`, EVICT=`evict`.

| Поле CacheError | Тип | Обязательность и смысл |
|---|---|---|
| reason | CacheFailureReason | Обязательно. CONTRACT_MISMATCH=`contract_mismatch`, INVALID_PAYLOAD=`invalid_payload`, BACKEND_FAILURE=`backend_failure`. |
| operation | CacheOperation | Обязательно. Имя вызванного публичного метода. |
| message | StrictStr | Обязательное непустое сообщение, пригодное для диагностики. Решения caller определяются enum reason. Exception, traceback, содержимое payload и произвольный текст backend в POJO не включаются; техническую причину сохраняет цепочка исключений. |
| issues | tuple[CacheFieldIssue \| CacheContractIssue, ...] | По умолчанию пустой кортеж. CacheFieldIssue — конкретный FieldPathError[CacheIssueCode] с code, проверенным path и message. CacheContractIssue — POJO с code: CacheIssueCode и message: StrictStr для отказа по целому контракту или записи, без фиктивного пути. Оба типа и enum объявляются в том же модуле, что CacheError. |

**Причина и код детали.** CacheFailureReason задаёт категорию; CacheIssueCode уточняет событие. При CONTRACT_MISMATCH различать UNKNOWN_NAMESPACE, SCHEMA_VERSION_MISMATCH, KEY_OCCUPIED_DIFFERENT_VALUE и прочий CONTRACT_VIOLATION. Для конфликта значений обязателен CacheContractIssue с кодом KEY_OCCUPIED_DIFFERENT_VALUE. При INVALID_PAYLOAD допустим код INVALID_VALUE; путь указывается только для реального поля. При BACKEND_FAILURE issues всегда пуст. Проверять допустимую пару reason/code. [Правила диагностики F01/F02/F05](./error-contracts-1.md)

**Приёмка реализации.** Через публичный get предъявить hit, miss и три независимых отказа: неизвестная версия до вызова backend, повреждённое значение в hit и исключение backend. Для каждого отказа проверить класс CacheFailure и точные поля error, отсутствие возврата CacheMiss и отсутствие запуска вычисления. Проверить round-trip CacheError с реальным полевым issue и с пустым issues; отклонить BACKEND_FAILURE с полем, недопустимые пары reason/code и синтетический путь. Для create/update/evict проверить operation при сбое backend; SKIPPED_OVERSIZE остаётся штатным результатом create.
