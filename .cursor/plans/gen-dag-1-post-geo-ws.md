# GEN-DAG-1 — Передача оркестрации генерации в engine DAG (после GEO-1 и WS)

**Статус:** DRAFT / DEFERRED. Только фиксация архитектурного намерения; не разрешение на имплементацию.
**Входные gates:** завершён и принят GEO-1; завершён и принят WS (общие patch/snapshot контракты); отдельное согласование с мастером перед изменениями DAG.
**Связанные SoT:** `geo-1-designed-water.md`, `docs/tz_world_generation_dag.md`, `docs/tz_engine_flow.md`, `.cursor/rules/dag-generator-interface.mdc`, актуальные WS-планы/контракты. При конфликте со старыми правилами persist/bake — сначала сверить и согласовать SoT, не молча менять их.

## Цель

Устранить собственный «DAG внутри генератора»: управление **тем, какие стадии, когда, в каком порядке и в каком scope выполнять**, принадлежит существующему engine DAG. Это **не изменение роли DAG**, а подключение генераторных операций к уже принадлежащей DAG оркестрации.

Генератор отвечает на вопрос **как вычислить/построить результат конкретной доменной операции**. Он не владеет глобальной очередью стадий, не принимает решения о запуске соседних доменов и не обходит DAG для изменения production-состояния.

Одинаковая архитектурная граница применяется к:
- первоначальному сотворению мира (bootstrap/bake);
- lazy-планированию и материализации;
- локальному изменению (пример: ведро воды → лужа);
- региональному/глобальному изменению (пример: потоп);
- другим действиям игрока и фоновой симуляции, затрагивающим мир.

Масштаб сам по себе не диктует обязательный набор доменов: DAG выбирает необходимые операции по контрактным зависимостям и последствиям, не по захардкоженному сценарию «лужа/потоп».

## Разделение ответственности

- **Engine DAG:** выбор операций и стадий (включая planning vs materialization), их порядка/зависимостей, scope, условий запуска, повторного исполнения и сборки PatchSet из результатов по WS-контракту. DAG решает **что/когда/как организовать исполнение**, но не реализует доменные алгоритмы.
- **Генераторы и домены:** чистые, переиспользуемые операции с явными входами/выходами; доменные расчёты, алгоритмы и локальная композиция внутри атомарной операции. Не владеют общей последовательностью чужих стадий и не пишут production-патчи в обход DAG.
- **Patcher / WS:** применение собранных изменений и история/snapshot по собственным контрактам. Не подменять WS отдельным generator-specific patch store.

**Граница ноды:** не превращать каждый helper, цикл, chunk или внутренний шаг алгоритма в DAG node. Выносить самостоятельные операции с внешними зависимостями и управляемым жизненным циклом; сохранять внутреннюю алгоритмическую композицию в домене. Размер класса сам по себе не критерий границы.

## План работ (после gates)

1. **Аудит текущих контрактов и исполнения.** Прочитать актуальный код DAG, GEO-1 planning/materialization, bake callers, debug HTTP и WS. Составить таблицу существующих оркестраторов: какие вызовы — межстадийная оркестрация, какие — внутренняя доменная работа; зафиксировать несовместимые legacy-контракты. Никаких догадок о нодах по названиям.
2. **Контрактная карта DAG ↔ операции.** Для каждой переносимой операции зафиксировать входы, результаты, deps, scope, planning/materialization, idempotency/retry/cancel и жизненный цикл кеша; определить границу атомарности. Утвердить с мастером до кода.
3. **Вынести межстадийное управление.** DAG выбирает и вызывает отдельные операции; generator APIs остаются стабильными и не получают знаний о DAG/ExecutionState. Не переносить доменные алгоритмы в DAG. Не создавать второй глобальный pipeline в bake или generator.
4. **Интегрировать WS.** Генераторные результаты → доменные патчи → сборка PatchSet под управлением DAG → применение через patcher → snapshot/history по WS. Сверить bootstrap/bulk bake и runtime paths с принятыми WS-контрактами, не придумывать обходы.
5. **Сохранить debug/test paths.** Debug API может вызывать те же доменные интерфейсы для изолированной диагностики, но не становится альтернативным production-оркестратором и не подменяет DAG.
6. **Приёмка.** Проверить как минимум bootstrap мира, lazy materialization, локальную лужу и региональный потоп (последние — сценарии проверки маршрутизации, не требование реализовать физику воды в этом плане); корректность deps/scope, отсутствие лишнего глобального bake, детерминизм, повторные вызовы, failure/retry и WS consistency. Тесты должны различать выбор операций DAG и правильность доменных вычислений.

## Жёсткие запреты / out of scope

- Не менять engine DAG до отдельного разрешения мастера и прохождения GEO-1 + WS gates.
- Не создавать новый DAG/оркестратор внутри генератора вместо использования существующего.
- Не дублировать вычисления в DAG, не смешивать planning/materialization, не писать в состояние мира мимо согласованного WS пути.
- Не переписывать GEO-1, WS или алгоритмы гидрологии «заодно»; при обнаружении пробела контракта — отдельное решение.
- Этот документ не утверждает готовность или конкретную номенклатуру будущих DAG-нод.

## Definition of Done

- Единственный production-владелец межстадийной оркестрации генерации/изменений — engine DAG.
- Генераторные домены отвечают за «как», DAG — за выбор и порядок операций, WS — за применение/историю состояния по контракту.
- Первичная генерация, локальные и региональные изменения используют один принцип оркестрации без отдельного generator-DAG.
- Контракты и регрессионные проверки приняты мастером.
