# DAGEngine — распределение реализации по доменам

Предложение для согласования. Область — весь [DAGEngine](../../backend/app/application/engine/runtime/dagEngine.py), включая поведение до F4. Контракты поведения заданы в [ТЗ engine §§7–10](../../docs/tz_engine_node_context.md) и [плане durable invocation, включая F2–F4](./dag-invocations-bake-admission.md).

## Публичная граница

Сохранить конструктор и сигнатуры run, resume, accept_input, resume_input, cancel_waiting_child, cancel_execution. DAGEngine связывает зависимости и передаёт команды владельцам. resume_input задаёт порядок accept → resume с валидацией запроса до первой записи. Второй публичный движок и общая база с полями прежнего фасада не нужны. Новые компоненты получают только свои зависимости. Их конструкторы не принимают DAGEngine.

Прямые импорты runtime-фасада в backend найдены в [pass tests](../../backend/tests/dag_typing/lifecycle/test_passes.py), [invocation tests](../../backend/tests/dag_typing/invocations/test_world_calls.py) и в typing fixtures [valid](../../backend/tests/dag_typing/typing/valid.py), [invalid](../../backend/tests/dag_typing/typing/invalid.py). Проверки взаимодействия через [input tests](../../backend/tests/dag_typing/invocations/test_input_wait.py) используют тот же engine через fixture. Пробы, патчащие приватные поля фасада, подключать к исходному binding/executor fixture.

## Границы и направление вызовов

Пути TARGET ниже даны от `backend/app/application/engine`. Шаги выполняются в порядке зависимостей: сначала операции, затем их вызывающие компоненты, последним — admission. Точки входа фасада, их generic-типы, значения по умолчанию и исключения зафиксированы [действующими сигнатурами](../../backend/app/application/engine/runtime/dagEngine.py). Новых wire POJO, enum, версий checkpoint и схем SQL не требуется. Изменения F5, production bindings и снятие pins за границей плана.

В конечной композиции DAGEngine передаёт run/resume в ExecutionAdmission, команды ввода и отмены — в ExecutionInteraction. Admission вызывает SessionRecovery, ExecutionRecovery и PassExecution. ExecutionRecovery владеет claim и вызывает восстановление активного графа либо завершение stop intent. Восстановление активного графа передаёт готовые state и plan в PassExecution. Компоненты не импортируют DAGEngine и не получают ссылку на него. Существующие DAGExecutor, LifecycleBinding, ExecutionSnapshotService, InputWaitCoordinator и оба store сохраняют свои контракты.

## Последовательность переноса и приёмка

Для каждого шага ниже указаны исходные операции [DAGEngine](../../backend/app/application/engine/runtime/dagEngine.py), их caller, целевая замена и критерий удаления. Команды выполняются из `backend`. Нормативные источники — [ТЗ engine](../../docs/tz_engine_node_context.md), [контракты durable invocations и F1–F4](./dag-invocations-bake-admission.md) и [разделы Pack о CLOSED](./spatial-distribution-domain.md). Для каждого шага ожидается успешный выход указанной команды.

**1. Общий заголовок и terminal replay.** ТЗ §9.3, F4. В `runtime/invocations/recovery/checkpointHeader.py` вынести функцию `read_header(saved: Checkpoint, execution_id: ExecutionId, settings: InvocationOptions, max_passes: int, requested_task: TaskType | None) -> tuple[InvocationGraph, SessionFrame]`. Её вызывают обе ветви _restore_durable. Проверять execution, session, revision, interaction owner и соответствие исходному task; сохранить правило для старого checkpoint. В соседнем `terminalReplay.py` функция `terminal_result[O: BaseModel](saved: Checkpoint, execution_id: ExecutionId, response_type: type[O]) -> ResolveResult[O] | Failed` проверяет финальную revision и декодирует outcome. Checksum проверяет SQLiteExecutionStore.load. Сохранить PermissionError для чужого owner и RestoreFailure для несовместимого checkpoint/ответа. Удалить обе локальные функции после переключения всех вызовов, включая чтение победителя после конфликта. Проверка: `python -m unittest tests.dag_typing.invocations.test_world_calls`. Done — одинаковый результат после reopen при действующей lease, 0 claim/compile/restore/open, отказ при чужой identity, доступе и повреждении.

**2. Подтверждение CLOSED.** ТЗ §9.3, F4 и Pack F3. Разделить владельцев операции: [ExecutionPins](../../backend/app/db/repositories/sqlite/worldPack/executionPins.py) выполняет физические close и read_closed, а recovery-клиент отвечает за получение подтверждения после потери ответа. TARGET `runtime/invocations/recovery/closeConfirmation.py`, функция `async confirm_closed(pack: PackCloser, intent: ExecutionStopIntent) -> CloseReceipt`. Единственный caller — ветвь ExecutionStopping. Использовать две существующие сигнатуры [PackCloser](../../backend/app/application/engine/contracts/invocation/executionStore.py); дополнительных требований к реализациям порта нет. Сначала read_closed(intent); при отсутствии вызвать close(intent) и снова read_closed(intent). После UnknownCommitOutcome/OSError перечитать по тому же intent; если receipt отсутствует, распространить исходную ошибку. Пустое чтение после успешного close даёт RestoreFailure. При подтверждении только [ExecutionStore.finalize](../../backend/app/db/repositories/sqlite/dagExecutions/executionStore.py) проверяет совпадение receipt с актуальным intent и CAS полномочий; соответствующий контракт действует и в памяти. Удалить протокол обмена с Pack из drive_to_final; heartbeat охватывает весь await. Проверка: `python -m unittest tests.dag_typing.invocations.test_world_calls tests.dag_typing.invocations.test_execution_stop_intent tests.spatial_pack.test_execution_pins`. Done — нет finalized после пустого/чужого receipt или потери полномочий, после commit возвращается победитель, holds сохраняются.

**3. Команды взаимодействия.** ТЗ §§8, 9.3, durable WAIT_INPUT и F2. TARGET `runtime/invocations/interaction/executionInteraction.py`, ExecutionInteraction получает текущие invocation settings и LifecycleBinding. Методы accept_input, cancel_waiting_child и cancel_execution повторяют параметры и результаты одноимённых публичных методов engine. _interaction_settings и _interaction_graph становятся внутренними операциями этого владельца; используемую recovery-путём проверку отмены предоставить через `cancelled_diagnostic(execution_id: ExecutionId, saved: Checkpoint) -> str | None` с прежней проверкой доступа. [InputWaitCoordinator.accept](../../backend/app/application/engine/runtime/invocations/inputWaitCoordinator.py) по-прежнему валидирует и принимает payload. Владельцы записи — действующие store и OwnedExecution. Переключить три метода фасада и ветку OwnershipConflict; resume_input по-прежнему валидирует параметры до accept и вызывает resume после receipt. Проверка: `python -m unittest tests.dag_typing.invocations.test_input_wait`. Done — конфликты owner, revision и отмены, а также повторная доставка дают прежние результаты.

**4. Сессия и отмена до переноса цикла pass.** ТЗ §§9.1–9.3, 10. TARGET `runtime/dag/lifecycle/sessionRecovery.py`, SessionRecovery получает snapshots, registry, snapshot store, binding, emit и clock. `async restore(execution_id: ExecutionId, max_passes: int) -> tuple[ExecutionState, ExecutionPlan]` обслуживает memory resume. Проверить cursor, общий бюджет и revision; при ошибке после создания state освободить его до выхода, сохранить прежние исключения и RESTORE_FAILED. `async save_cancelled(state: ExecutionState, durable: OwnedExecution | None) -> None` обслуживает ветку отмены цикла. Сохранить drain отмены перед snapshot, при отзыве claim исключить перезапись отменённого execution, отличать SNAPSHOT_FAILED от SNAPSHOT_SAVED. Capture, encode, restore и decode остаются у [ExecutionSnapshotService](../../backend/app/application/engine/runtime/dag/lifecycle/executionSnapshotService.py). Переключить resume и обработчик отмены _drive, удалить _lifecycle_event из фасада. Проверка: `python -m unittest tests.dag_typing.lifecycle.test_passes tests.dag_typing.invocations.test_input_wait`. Done — ошибка restore/save сохраняет прежний snapshot; отмена и ошибка освобождают state; исходный CancelledError распространяется после успешного сохранения.

**5. Исполнение pass.** ТЗ §§7.2, 8, 9.3. TARGET `runtime/dag/lifecycle/passExecution.py`, PassExecution.run получает параметры и возвращает результат действующего _drive, включая опциональный OwnedExecution. Владельцы фаз — DAGExecutor, переходов и эффектов — LifecycleBinding, разрешения ответа — ResponseResolver, invalidation — каталог state. PassExecution задаёт порядок и вызывает SessionRecovery.save_cancelled из шага 4. Передача state в run означает передачу владения: его finally выполняет release на всех путях. Переключить fresh, memory resume и drive_claimed; удалить _drive и _prepare_reuse из DAGEngine. Проверка: `python -m unittest tests.dag_typing.lifecycle.test_passes tests.dag_typing.invocations.test_world_calls`. Done — прежние бюджет pass, reuse, порядок effects/response и release; resume со стадии RESPONSE не повторяет effects.

**6. Durable recovery, включая обычный незавершённый execution.** ТЗ §§9.2–9.3, F2/F4. TARGET `runtime/invocations/recovery/executionRecovery.py`, ExecutionRecovery.resume имеет параметры и результат действующего _restore_durable. Метод сначала читает store, проверяет finalized до claim, затем владеет claim, renew, отменой и drain задачи, release и чтением победителя при гонке. При stop intent подтверждает его действующим claim, вызывает confirm_closed, затем finalize и terminal_result. При отсутствии PackCloser сохраняется граница ExecutionStopping. Store остаётся единственным writer.

Для обычного исполнения TARGET `runtime/invocations/recovery/activeCheckpoint.py`, ActiveCheckpoint.resume принимает `saved: Checkpoint, header: InvocationGraph, frame: SessionFrame, claim: Claim, settings: InvocationOptions, max_passes: int, options: LLMExecutionOptions, confirmed: Mapping[str, DomainRevision] | None, cancellation: CancellationRequest | None` и возвращает `ExecutionResult[O]` асинхронно. Caller — ExecutionRecovery после повторной загрузки под claim и проверки заголовка. Сюда переносится остаток drive_claimed: compile по cursor, CheckpointCodec.restore, revision/root check, правила старого initial_task, обработка failure/cancellation/wait/response. Только продолжающийся pass декодирует session и передаёт state, plan и OwnedExecution в PassExecution.run. До передачи за release при ошибке отвечает создатель state, после передачи — PassExecution. Владельцы результата, lease и state различны; ActiveCheckpoint не запрашивает второй claim. Удалить _restore_durable со всеми вложенными callbacks после переключения run/resume. Проверка: `python -m unittest tests.dag_typing.invocations.test_world_calls tests.dag_typing.invocations.test_input_wait tests.dag_typing.invocations.test_execution_stop_intent`. Done — обычный restart продолжает работу, stop и finalized обходят рабочий restore, у старого owner нет права записи.

**7. Admission и итоговый фасад.** ТЗ §9.3. TARGET `runtime/dag/lifecycle/executionAdmission.py`, ExecutionAdmission.run и resume повторяют параметры и результаты публичных run/resume. Компонент создаётся один раз на экземпляр engine, владеет набором активных ExecutionId и снимает допуск в finally. Fresh admission выполняет preflight compile, затем создаёт state; при durable create освобождает временный state и передаёт управление ExecutionRecovery. Memory resume получает пару state/plan из SessionRecovery и передаёт владение PassExecution. До передачи при исключении освобождает state текущий владелец. Удалить _enter и подготовку исполнения из фасада. Проверка: `python -m unittest tests.dag_typing.lifecycle.test_passes tests.dag_typing.invocations.test_world_calls`. Done — конкурентный вход под одним ID отклонён; preflight failure не создаёт execution; total pass budget и повторный terminal run сохраняют семантику.

## Порядок сдачи

Каждый шаг — отдельный diff с переключением callers из предыдущего раздела. Ручные правки вносить только через apply_patch. После каждого шага показать diff, включая новые файлы, результат команды и принадлежность перенесённых операций. Остановиться до «ок» пользователя. Последующий шаг использует уже принятую реализацию предшественника.

Проверить [правило композиции](../rules/folder-composition.mdc): runtime/invocations сейчас содержит 8 непосредственных файлов, после переноса — 8; recovery и interaction получают отдельные подпапки. В runtime/dag/lifecycle число файлов меняется с 1 до 4. Проверить размер и обязанности каждого нового класса, включая вложенные функции. На входе DAGEngine содержит 479 строк при лимите 300. При промежуточном превышении фиксировать остаток по незакрытым зонам; после переноса фасад и каждый владелец укладываются в 300 строк. Фасад не знает wire, retry, CAS, правил snapshot и исполнения фаз.

После шага 7 выполнить полную DAG-команду и положительный Pyright из [отчёта F4](./sp-p2w-f4-verification.md), отдельно `python -m unittest tests.spatial_pack.test_execution_pins`. Проверить типизацию новых файлов и импорт DAGEngine через прежний путь, обновить ссылки проверок на фактических владельцев. Приёмка требует успешных проверок и сверки кода каждого оркестратора с этой картой.
