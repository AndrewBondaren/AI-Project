# Runtime и worldEdit — общая политика разрешения и диагностики

**Статус (2026-10-08):** базовое требование к последующим планам. Реализованы общая основа, два пилотных поля и read-only import preview (E0–E5). В E6 мигрированы 578 legacy-default полей и общий resolver; оставшиеся consumer/ref boundaries перечислены в плане. Соответствие всего существующего кода не утверждается.

## Назначение

Миграция полей E6: declared defaults/default_factory применяются только при
отсутствии; nullable null и штатные auto-сентинелы сохраняются. Ошибка типа,
enum, ограничения или model invariant отвергает объект/коллекцию целиком.
Полный объект проходит исходные Pydantic validators, включая поддерживаемые
wire aliases; нельзя обходить их предварительной подстановкой defaults.
Patch сохраняет отсутствие и явно переданный null, затем проверяется полное
состояние после merge. Invalid repair validators и фильтрация ошибочных строк
на read adapters удаляются. Каноническое дополнение отсутствующих библиотечных
записей остаётся штатным отдельным контрактом. Scope и приёмка — E6 плана.

Один доменный resolver и одинаковые ограничения для runtime и редактора мира. Режим исполнения определяет обработку результата и представление диагностики, но не меняет геометрию, приоритеты или критерии допустимости.

## Выбор политики через импорт (решение мастера 2026-10-08)

- Контекст пользовательского сценария определяет frontend. Backend не выводит worldEdit/runtime из факта create, import, load, роли пользователя или содержимого JSON.
- Импорт имеет необязательный API-флаг включения валидационной политики. Без флага дополнительная политика не задана: обычный импорт/загрузка для игры. Это не означает отключение обязательного разбора wire и проверок целостности.
- Для проверки создаваемого/редактируемого мира frontend вызывает **тот же импорт** с флагом; не создаётся отдельный backend worldEdit-mode, endpoint валидации или второй алгоритм проверки.
- API-контракт (утверждён 2026-10-08): `POST /worlds/import` и `POST /worlds/import?validate_only=true`. Необязательный boolean-флаг `validate_only`: отсутствие/false — обычный импорт; true — проверка и разрешение с диагностикой для frontend, **без применения изменений**. Ранее предложенное имя validate не является целевым API-контрактом.
- Флаг — контекст конкретного запроса. В одном общем месте входа он разрешается в typed context; далее import service → handlers → resolver получают этот контекст, без повторной интерпретации флага, локального угадывания и сброса во вложенных вызовах. В world JSON/SQL/snapshot как постоянное свойство мира не сохраняется.
- Обычный вызов использует runtime-поведение: доменное авторазрешение либо WarningError без error defaults. Валидационный вызов использует те же правила и возвращает структурированную диагностику frontend для авторского сценария.
- `validate_only=true` не пишет в БД и Pack, не сохраняет remap/version allocation и не запускает изменяющие мир задачи. Разрешены чтение, вычисления в памяти и штатная диагностика. Это проверочный путь того же pipeline, не write с последующим rollback: rollback не отменяет файловые/очередные side effects. Для проверки текущих данных мира используются read-only зависимости/индексы; candidate IDs и изменения остаются неперсистентными.
- После проверки/исправлений frontend отправляет обычный импорт без флага. Он заново выполняет те же проверки по актуальным входам и состоянию; успешная проверка не является reservation или разрешением пропустить повторную проверку. Существующая транзакционная семантика обычного bundle import сохраняется, частичный persist этим контрактом не вводится.
- Дальнейшие упоминания runtime/worldEdit в этом ТЗ обозначают пользовательские сценарии и обработку диагностики, а не обязательный backend enum `mode: runtime | worldEdit`. Создание, редактирование и draft UI не требуют отдельной backend-сессии policy.

## Одно место разрешения политики, контракты конкретных полей

**Утверждено мастером:** выбор политики централизован, дальнейшее применение автоматически учитывает характеристики каждого поля. Это не одна одинаковая реакция на любые данные.

```text
API flag → единое разрешение request context
    → общий policy resolver
        + typed контракт поля/модели
        + входное значение и path
        + результаты доменных проверок
    → resolved/unresolved результат + диагностика
```

- SoT характеристик поля — существующие typed модели dataModel и их field annotations/metadata (включая WireFieldPolicy), а не параллельный словарь в route, import handler или генераторе. Текущая опора — application/jsonValidation/resolve.py и ResolveContext; при реализации расширяется/пересматривается существующий механизм, не создаётся второй движок.
- Контракт поля различает отсутствие, null, пустое значение, неправильный тип, нарушение диапазона/enum, неразрешённую ссылку и доменный конфликт. Допустимость, обязательность и штатный default определяет конкретная модель; эти состояния нельзя автоматически приравнивать друг к другу.
- Общий resolver использует тип, ограничения, field policy, reference contract и reason/action поля вместе с request context. Результат и ошибка привязаны к точному field path и schema/object identity. Существующее DefaultOnWire не разрешает автоматически подменять ошибку default в новой политике.
- Ошибки, специфичные полю/домену, имеют свои reason/code и параметры диагностики. Общий механизм выбирает обработку результата и каналы по policy; он не заменяет разные ошибки общим сообщением «невалидно».
- Межполевые, reference и пространственные проверки остаются typed правилами модели/домена. Они отдают структурированный результат в тот же механизм обработки, с путями участвующих полей/UID; не создают локальную политику ошибок и не сводятся искусственно к одному полю.
- Во вложенных моделях, списках и handlers наследуется уже разрешённый контекст; меняются path/локальные данные, а не policy. Запрещены локальные if validate/IMPORT/RUNTIME, выбирающие собственный fallback/reject/log вместо общего механизма. Проверка доменных условий при этом не запрещается.
- Диагностическое поле context/policy, если присутствует, описывает уже разрешённое решение общего входа; consumer не должен восстанавливать политику из его строкового значения.

## Общий контракт

### Default только при отсутствии: эталон POJO (утверждено 2026-10-08)

Целевой общий маркер — `DefaultWhenMissing[T]`: штатный schema default применяется только при отсутствии поля. Невалидное переданное значение не заменяется default. Маркер определяется один раз в общих field annotations; отдельные обработчики на каждое поле не добавляются.

Эталон — `ForestsCategoryPolicy.forest_min_rainfall` из `backend/app/dataModel/terrainMasks/worldTerrainMasks.py`:

```python
# As is: существующая annotationPolicy объединяет missing и invalid.
forest_min_rainfall: DefaultOnWire[int] = Field(default=45, ge=0)

# Target: одна строка POJO; тип, default и ограничение остаются в модели.
forest_min_rainfall: DefaultWhenMissing[int] = Field(default=45, ge=0)
```

Ожидаемое поведение при полном описании объекта одинаково для обычного и валидационного вызова:

- Поле отсутствует → `45` (штатный default, не ошибка).
- Передано `60` → `60`.
- Передано `-1` → ошибка диапазона, без подстановки `45`.
- Передано `"abc"` → ошибка типа, без подстановки `45`.
- Передано `null` → ошибка, поскольку `None` не входит в тип этого поля; не считать null отсутствием.

Для partial update отсутствующее поле означает «не изменять», а не заполнение default. Допустимые преобразования типов определяются typed schema и согласованным wire-контрактом, не угадываются policy; эталон не вводит неявно strict parsing для всех полей.

Общий resolver делегирует стандартную проверку типу/ограничениям Pydantic; не дублирует `ge=0` и default=45 в application-коде. Ошибки преобразуются в общий report с исходными type/code, path и context; доменные проверки дополняют report. Реакция централизована: runtime — WarningError в существующем sink, validation — структурированная диагностика frontend. Валидационный report не исключает обычное штатное логирование, но отдельный emit из каждого POJO запрещён.

При ошибке модель/зависимая операция явно неразрешена. Нельзя возвращать некорректную POJO как валидную, подставлять default через повторную сборку/пропуск поля или использовать `model_construct` для обхода ошибки. Это не общий запрет model_construct в проекте: запрещено выдавать им невалидные данные за разрешённые на мигрируемом пути. Валидный пустой результат, missing optional и unresolved — разные состояния. Область отказа и продолжение независимых объектов определяются контрактом потребителя.

Контекст остаётся служебным request-контекстом (validation flag, partial/path/schema identity по необходимости); registry, DB-сессия, геометрия и logger не превращаются в его универсальное содержимое. Report и зависимости доменных resolver передаются отдельно. POJO хранит поля, metadata и локальные инварианты; межобъектные правила — в доменных resolver; обработка диагностики — в общей политике.

Это целевая миграция `annotationPolicy` и `jsonValidation/resolve`, а не утверждение о выполненной замене текущего `DefaultOnWire`. Каждый consumer мигрируется по явному списку; код и SQL этим документом не меняются.

### Совместимость с каскадом

Нормы [tz_cascade_context.md](./tz_cascade_context.md) о штатном None-наследовании и declared terminal default сохраняются. Nullable каскадный source сохраняет default=None; wire default не подставляется в каждое звено и не перекрывает наследование. EmptyLink обозначает намеренно пустой уровень, а не ошибку подготовки source.

Нужно различать валидное значение, штатное отсутствие/допустимый None и unresolved. Невалидный authored source не превращается в None/EmptyLink/пропущенное поле ради наследования родителя или terminal default. Source resolution и membership checks предшествуют передаче объекта в каскад; при ошибке зависимая операция возвращает unresolved через общий механизм. ResolveContext не объединяется с LocationContext; error sentinel не добавляется в доменные поля для обхода типов.

Приёмка общей основы требует двух пробных подключений из [плана](../.cursor/plans/runtime-world-edit-policy.md): обычного forest_min_rainfall и каскадного RoomDef.economic_tier. Для каскада обязательны authored override, None-наследование, штатный terminal default, невалидный source без скрытого наследования, сохранение provenance/ancestor snapshots и одинаковое доменное решение при обоих API-сценариях. Массовая миграция выполняется после этой приёмки и повторного прогона существующих тестов.

Reference membership требует индекса, подготовленного из допустимых данных мира. Ошибка самого реестра — не unknown-ref и не повод взять canonical registry. Partial validation должна сохранять patch intent; проверка полного состояния выполняется после согласованного merge. Продолжение анализа независимых объектов не означает разрешение частичного persist: validate_only не сохраняет ничего, обычный импорт сохраняет свою bundle transaction/rollback семантику. Конкретный порядок gates определён планом; подключение API требует приёмки общей основы и проверки отсутствия write side effects.

Применяется ко всем новым и пересматриваемым планам, затрагивающим разрешение данных, ссылок, размещение и генерацию мира. Wilderness — один потребитель общей политики.

1. Доменные правила и resolver едины. Runtime/worldEdit не реализуют два разных алгоритма разрешения одних входов.
2. Resolver возвращает результат и структурированную диагностику. Неразрешённый результат отличается от валидного пустого результата и не выдаётся за успех.
3. Разрешённое доменным контрактом авторазрешение выполняется детерминированно; исходные авторские данные не переписываются молча.
4. Если разрешение невозможно, runtime фиксирует WarningError в существующем доменном логе, без подстановки default вместо ошибочного объекта/ссылки/геометрии/значения. Зависимая операция не потребляет выдуманный результат; независимая работа может продолжаться. План обязан определить границу зависимой операции и представление неполноты.
5. WorldEdit использует ту же диагностику и показывает автору исходную проблему и результат авторазрешения. Неразрешённые данные не объявляются успешно разрешёнными/применёнными. Исправление авторских данных требует явного действия. Сохранение draft, транзакционные границы и блокирование publish описываются конкретным планом.
6. Default при штатном отсутствии необязательного поля допустим только как явная норма typed schema. Он не является оправданием замены невалидного или неразрешимого значения. Новые fallback при ошибке запрещены; исключение требует явного решения мастера и изменения этой политики.
7. Ошибки transport/wire, инфраструктуры и программирования не превращаются в WarningError ради подавления исключения. Обязательный разбор wire и проверка целостности действуют при обоих значениях флага; доменная строгая диагностика не включается автоматически только из-за операции import.
8. Диагностика содержит стабильный reason/code, контекст валидационного флага, domain, world_uid, object/ref UID и path при наличии, причину и действие; для конфликтов — участвующие UID. Используются существующие фасад и sinks из [tz_logging.md](./tz_logging.md), без второго logger/отдельного sink ради новой политики.

WarningError — семантика доменной диагностики, не утверждение о существующем exception-классе или logging level. Конкретный общий typed API должен быть определён до миграции потребителей.

## Утверждено: runtime размещения

- Сначала выполняется детерминированное разрешение конкуренции: placement_specificity по убыванию, площадь исходного footprint по убыванию, UID по возрастанию. Зависимости опор и обязательные пространственные ограничения сохраняются. Геометрические подробности — [контракт placement](./tz_map_light_bake.md#placement-priority); общая политика не зависит от реализации L0.
- Оставшийся неразрешимый конфликт диагностируется как **WarningError в логе**, без подстановки default-объекта, default-геометрии, default-координат или default-ссылки.
- WarningError описывает доменную диагностику runtime; это требование не утверждает наличие одноимённого Python exception или отдельного logging level в текущем коде.
- Неразмещённый объект не выдаётся за успешно размещённый. Его исходное описание сохраняется; resolver возвращает явно неразрешённый результат с причиной. Доменные ограничения нельзя обходить для продолжения генерации.
- Приоритетное авторазрешение не является default/fallback. Допустим только результат, удовлетворяющий заданным ограничениям; абсолютные координаты не изменяются без явного разрешения.
- Диагностика содержит world_uid, object_uid, конфликтующие UID, код/причину ограничения, режим и принятое действие. Порядок входных записей, bake-тайлов и выполнения задач не влияет на решение.
- Ошибка размещения сама по себе не превращается в runtime exception/HTTP reject всего запуска. Некорректный wire и технические ошибки исполнения — отдельные контракты, не маскируются под конфликт размещения.

## Применение в worldEdit

- Frontend редактора вызывает тот же импорт с валидационным флагом и показывает возвращённые конфликты и результат авторазрешения автору. Backend worldEdit-mode/отдельный validation pipeline не вводится.
- Неразрешённые изменения не применяются молча, исправления не записываются вместо авторских данных без явного действия.
- Сохранение draft и UI действия могут определяться отдельными планами редактора, но вызов validate_only ничего не сохраняет. Данный контракт не вводит HTTP-коды или новый transport reject-path; response DTO/status проверки фиксируются до реализации API.

## Обязательный раздел последующих планов

В начале каждого применимого плана размещается раздел «Базовая политика runtime/worldEdit» со ссылкой на этот документ. Он должен определить:

- затронутые resolver/consumers и их текущее соответствие политике;
- штатное авторазрешение и его детерминизм;
- неразрешимый результат, границу зависимой операции и поведение независимой работы;
- reason/code и существующий log sink; последствия в runtime и представление в worldEdit;
- отсутствие скрытых defaults и изменений авторских данных;
- проверки одинаковых входов в двух режимах, разрешённого конфликта, неразрешимого случая и отсутствия ошибочного fallback.
- используемые typed field/model contracts, специфичные reason codes, наследование context/path и отсутствие локального выбора политики в consumers.

Если компонент уже использует общий механизм, план ссылается на него и добавляет доменные правила. Если механизма нет или существующий потребитель противоречит контракту, обязательный первый этап — общая основа/явная зависимость на [runtime-world-edit-policy.md](../.cursor/plans/runtime-world-edit-policy.md), а не локальная копия policy. Неприменимость отдельных пунктов объясняется кратко; универсальный placement priority не переносится на домены без пространственной конкуренции.

## Границы и согласование существующих политик

Общий механизм диагностики должен быть отделён от доменных правил и transport. Import — операция, worldEdit — контекст frontend, runtime — обычный сценарий игры, включая импорт/загрузку. Существующий `ResolveMode.IMPORT`, жёстко выбранный write-facade, не является целевым способом выбора пользовательской политики: его consumers требуют аудита и согласования с API-флагом.

В существующих ТЗ присутствуют прежние domain-specific error defaults: [JSON validation](./tz_json_validation.md), [world bundle](./tz_world_bundle.md), [logging](./tz_logging.md). Для новых/пересматриваемых планов базовым требованием является настоящий контракт. Старые fallback при ошибке требуют инвентаризации и явно запланированной миграции; наличие старой нормы не разрешает добавлять новые error defaults. Штатные schema defaults при отсутствии поля не отменяются. Массовая миграция и изменение кода не выполняются правкой этого ТЗ.

Общие diagnostic/result API и WarningError в resolve sink реализованы для pilots; следующие consumers подключаются через ту же основу. Не создавать локальную альтернативную политику только для wilderness.

## Технический контракт реализации (2026-10-08)

`DefaultWhenMissing[T]` хранит только wire metadata; default/constraints остаются в Pydantic Field. Existing `resolve_model` сохраняет успешный return type; при неразрешённом новом контракте бросает `UnresolvedModelError`, содержащий структурированные FieldPathError, и никогда не возвращает unchecked POJO. `resolve_result` представляет этот исход как typed result. Partial resolve возвращает typed patch со supplied fields, а полная POJO проверяется после merge. Runtime логирует WarningError в существующем resolve sink; validation собирает те же facts. Legacy DefaultOnWire явно сохраняет прежнюю семантику до миграции.

Membership использует отдельную зависимость resolver — существующий WorldRegistryIndex с lookup по классу RegistryKey target, не поле context/POJO. Недоступный индекс для явно проверяемой ссылки — отдельная ошибка, а не пустой реестр/канон. Room source строит lookup только из проверенного исходного tier registry.

Import application entry создаёт один request context из validate_only. До transaction/remap выполняется общий preflight: world normalization и checks, connection normalization, подготовка entity/library bodies и domain refs на incoming world. Handlers используют те же prepare/check методы при обычном импорте. Preview не вызывает import_section, repositories, Pack writer, version allocation/remap или tasks. Обычный импорт повторяет preflight при каждом запросе и сохраняет bundle transaction/rollback.

HTTP: `POST /worlds/import?validate_only=true` возвращает 200 с `{validate_only: true, valid: boolean, issues: [{loc, msg, code, schema_id?}]}` для завершённой проверки. Нечитаемый upload/неверный request остаётся HTTP 422. Инфраструктурные ошибки не превращаются в valid=false. Обычный ответ импорта и 207 rollback сохраняются.

`ResolveContext.for_import(validate_only=...)` — единственное место выбора request policy. `validate_only` наследуется children; ResolveReport владеет диагностикой, reference index передаётся отдельно. Существующий ResolveMode сохранён для совместимости wire interpretation: оба bundle-сценария используют IMPORT, поэтому legacy enum/strict проверки не меняют решение между preview/apply. Он не определяет пользовательский сценарий. Новые facts централизованно логируются только без validate_only; preview отдаёт их в ответе.

`resolve_patch` возвращает mapping только supplied полей, а не неполную POJO. WorldService объединяет JSON blob patch с текущим миром и повторяет полную проверку до update. Supplied registry collections являются полными заменами. После миграции полей fieldwise construct/row skip и invalid defaults удалены из общего resolver. Deprecated DefaultOnWire/DefaultEnumOnWire exports означают ту же DefaultWhenMissing policy. ResolveMode не выбирает решение поля. Общий engine не имеет legacy error-default ветки.

Все девять handlers поддерживают read-only preflight и используют те же consumer prepare/check функции, что обычная запись. Preflight обнаруживает wire/domain failures до transaction; ordinary вызов в таком случае отвечает 422. Ошибки записи сохраняют atomic rollback/207. Preview не гарантирует успешный будущий commit и не резервирует идентификаторы: текущие данные/ограничения хранения повторно проверяются при применении.

Приёмка реализации: 196 tests, OK; все восемь import/export fixtures, включая переименованный `world_test_002`. Typecheck cascade и frontend build прошли. Defaults применяются без изменения authored field presence: модельные ограничения вроде `count`/`count_range` не получают ложное явно заданное поле. Результаты и оставшийся scope E6 — в [плане](../.cursor/plans/runtime-world-edit-policy.md#проверки-реализации).

## Миграция полей E6

Перечень и границы — [runtime_policy_field_migration.md](./runtime_policy_field_migration.md).
556 полей dataModel и 22 поля bundle DTO используют missing-only default. Полный
resolve делегирует исходной Pydantic-модели; patch переиспользует compiled field
schemas с field validators без default factories отсутствующих полей. Межполевые
инварианты проверяются на полном состоянии после merge. Partial patch не является POJO.

SQL NULL ненастроенной scalar-колонки означает отсутствие; JSON mapping сохраняет
явно переданный null для проверки nullable. Реестры World хранят list metadata;
NULL/исторический пустой map hydrate в пустой list, остальные malformed значения
не исправляются. SQL schema не меняется. Типы/ограничения/defaults остаются в dataModel.
Каноническое дополнение отсутствующих библиотечных записей и явно разрешённые
доменные blank pin/template sentinels сохраняются; они не являются error defaults.

Room/opening/height/stem invalid repair удалены. Ошибочная строка отклоняет реестр
целиком; битая attachment-ссылка останавливает уровень через общую диагностику.
Остальные cascade membership и доменные repair/placement/material boundaries
не объявлены закрытыми; остаток E6 указан в плане.
