# Паки библиотек шаблонов и canonical defaults

**Статус:** целевой контракт, согласован 2026-10-08; существующая реализация ещё
не хранит паки и их подключения отдельно. Не относится к terrain/map pack-файлам.

## 1. Доступность и использование

Пак — именованный набор шаблонов; каждый шаблон имеет ровно один пак-владелец.
Глобальная SQL-библиотека хранит тела независимо от миров. Мир не привязывается
к engine-паку по ссылке: использование пака миром = **явное инстанцирование** —
копия пака становится world-owned экземпляром этого мира. Инстанцирование
распространяется на весь мир, не на отдельную локацию или генератор.
Генераторы выбирают подходящие им шаблоны из всех инстансов мира по
существующим доменным условиям.

Defaults движка явно перечислены доменными canonical-spec и доступны без
ручного импорта. Любой автоматический импорт пака вне этих деклараций — баг.
Пользовательский пак движка используется миром только после явного
инстанцирования (bundle либо более поздняя операция). Наличие файлов,
SQL-строк или инстанса в другом мире не даёт доступности этому миру.

Эффективный каталог мира = объявленные defaults + world-owned паки мира
(инстансы engine-паков + авторские записи мира). Административный `list_all()`
глобальной SQL-библиотеки не является каталогом генерации. Pick-policy и
фильтры домена применяются поверх эффективного каталога; отсутствие
per-template pointer не исключает шаблон world-owned инстанса.

### 1.1 Политика библиотек (единственная, 2026-10-08)

**Библиотеки движка** (`owner_world_uid IS NULL`):

- **Default** — декларируемые движком паки для resolve дефолтов; read-only,
  единственная мутация — additive canonical attach (§6).
- **User** — создаются и **полностью редактируются** на уровне движка;
  импортируются в миры как инстансы. Правка user-библиотеки не затрагивает
  уже созданные инстансы миров — snapshot-семантика; обновление мира до
  новой редакции — явное повторное инстанцирование.

**Библиотеки мира** (`owner_world_uid` = мир):

- Обязательные зависимости мира; создаются только инстанцированием из
  библиотек движка (`instantiate_pack`) либо авторством записей мира.
- Полностью редактируемы в рамках своего мира — изменяется только экземпляр.
- Поставляются в bundle вместе с миром (self-contained export, §4).
- Могут быть явно экспортированы в библиотеку движка — publish
  (`copy_pack` world→engine, тот же remap-механизм §2).

Доступность = владение: член доступен миру, если его пак default либо
`owner_world_uid` равен миру. Отдельной таблицы/операции «подключения» нет.
CRUD библиотеки движка никогда не ломает миры: изоляция построена на копии,
не на запрете правок.

`local_uid` — системный ключ, ось идентичности: обязан быть уникален в
эффективном каталоге мира внутри домена. `display_name` — другая ось
(человекочитаемое наименование), в разрешении ссылок и идентичности не
участвует и может повторяться свободно. Коллизия `local_uid` между разными
world-паками одного мира отвергается при инстанцировании (пере-импорт того
же источника = обновление инстанса, не коллизия); world-pack может
осознанно **переопределять** default-запись по тому же `local_uid` —
это не коллизия, а приоритет слоя.

Приоритет эффективного каталога: `defaults < world packs`. Ссылки по
`local_uid` разрешаются по этому порядку; для каталожных N+1-записей
сохраняется field-level merge — member может быть sparse-override поверх
default-записи с тем же `local_uid`.

Целевой охват: pack-модель — целевая для всех каталожных N+1-доменов
(terrain, material, economic_tier, race, perk и пр.). Embedded-конфиг мира
(скаляры, настройки) — не библиотека. Миграция существующих N+1-доменов —
отдельная фаза после template-доменов, per-domain.

## 2. UID и владение

UID формируются исключительно инфраструктурой `app.application.worldData.ids`
по [DET-1](./project_data_storage_tz.md). Новых builtin/pack UID-функций вне неё
нет; импортёры, POJO и генераторы не хэшируют и не конкатенируют входы формулы.

Центральный `LibraryKind` расширяется видами `LIBRARY_PACKS` и
`STRUCTURE_TEMPLATES`. Пак получает UID существующим вызовом
`library_uid(LibraryKind.LIBRARY_PACKS, system_name)`: `system_name` пака —
устойчивый глобальный ключ автора, например `engine.structures.base`.
Имя FS-папки — локальный `pack_name`, а не глобальная идентичность пака.

Для шаблонов центральный API расширяется до
`library_uid(library, system_name, *, pack_uid=None)`: в pack-owned пути
`system_name` означает локальный ключ шаблона, `pack_uid` обязателен на уровне
адаптера пака. Центральный helper сериализует домен, владельца и локальный ключ
однозначно и детерминированно с существующим UUID5/hash-ядром. Legacy-вызов без
владельца остаётся только для ещё не мигрированных доменов; он не используется
новыми pack-owned импортёрами. UID не зависит от мира, seed, display name,
версии, абсолютного пути или порядка импорта.

Один локальный ключ в одном домене/паке = один UID. Одинаковые ключи в разных
паках различны; повторный импорт сохраняет UID. Владение хранится в каталоге,
а не декодируется из UID. Изменение владельца/локального ключа меняет идентичность;
обычная правка тела или display name её не меняет.

`copy_pack` / `instantiate_pack` — доменная remap-операция адаптера, не
SQL-copy: новый владелец → новый `pack_uid`; члены получают новые UID по
той же центральной формуле; ссылки внутри тел на членов **того же** пака
переписываются на новые UID, refs на чужие паки и внешние тела не трогаются;
`dependencies` копируются. Инстанцирование engine→world = copy с
`owner_world_uid` мира + `source_pack_uid` исходника (диагностика
происхождения); при этом ремапятся и **world-side refs** на членов пака
(pick-policy `default_template_uid` и прочие доменные ссылки — перечень
фиксируется контрактом адаптера). Повторное инстанцирование того же
источника в тот же world-пак обновляет членов, UID сохраняются, refs мира
остаются валидными; локальные правки инстанса перезаписываются — операция
явная. Publish world→engine — тот же copy с owner=NULL.

Structures сохраняют wire-контракт `system_name == template_uid` (UUID),
локальный ключ для формулы находится в описании состава пака. У building/relief
локальный ключ соответствует `system_name` тела. Stem файла по-прежнему совпадает
с `system_name` тела. UID структуры, записанный в JSON, проверяется против формулы.

## 3. Каталог и SQL

Целевой storage-контракт:

- `library_packs`: `pack_uid` (PK), `system_name` (UNIQUE), `pack_name`,
  `display_name`, `version`, `owner_world_uid` (NULL → worlds FK),
  `source_pack_uid` (NULL → packs FK, диагностика инстанцирования).
  Non-null `owner_world_uid` = библиотека мира (§1.1): mutable, каскадно
  умирает с миром. Default-статус определяется доверенной декларацией
  движка по UID; пользовательский manifest не может назначить себе этот статус.
- `library_pack_members`: `template_uid` (PK), `pack_uid` (FK → packs),
  `library_kind`, `local_uid`; UNIQUE (`pack_uid`, `library_kind`, `local_uid`).
  Одна строка фиксирует единственного владельца; ссылку на чужой шаблон нельзя
  записывать как своё членство. Тела остаются в доменных SQL-таблицах.
  Наименование члена — `display_name` тела (единая ось `display_*`); на member
  не денормализуется, листинг каталога читает его из тела.
- `library_pack_dependencies`: PK (`pack_uid`, `required_pack_uid`), владелец
  `pack_uid` — FK. `required_pack_uid` допускает ещё не импортированный пак:
  неполнота диагностируется, а не блокирует runtime import по текущей политике.
- Таблицы bindings нет: доступность мира = владение паком (`owner_world_uid`)
  либо default-статус. Удаление world-пака каскадом с миром; удаление
  engine-пака безопасно всегда — миры держат инстансы-копии.

Доменные `system_name` не должны оставаться глобально UNIQUE в таблицах
building/relief после перехода: уникальность локального ключа задаётся владельцем
в каталоге. `get_by_system_name` без контекста пака не разрешает неоднозначность;
потребители переходят на UID либо запрос с явным владельцем.

Тело и членство сохраняются атомарно и проверяются доменным адаптером
(полиморфный `library_kind` не заменяет проверку наличия тела). Смена владельца
через upsert запрещена. `source_file` остаётся диагностическим происхождением,
не ключом пака, не признаком подключения или default-статуса.
SQL-schema изменяется только в `0001_initial.sql` с синхронизацией dataclass;
локальная БД пересоздаётся по действующей schema-policy.

## 4. Manifest, импорт и bundle

Typed manifest пака содержит `pack_uid`, `system_name`, `pack_name`,
`display_name`, `version`, `dependencies` (список UID паков), `members`.
Каждый member содержит `library_kind`, `local_uid`, `template_uid` и,
для FS-импорта, `source_file` относительно соответствующего domain root.
UID проверяются центральным helper; дубликаты/несовпадение владельца/формулы —
ошибка контракта импорта. Путь не выходит из domain root; домены не смешиваются.
Один логический пак может иметь членов разных доменов, сохраняя отдельные FS-roots.
FS manifest хранится отдельно от JSON-тел как `pack.manifest.json` в папке пака;
сканер никогда не интерпретирует его как тело шаблона.

Bundle расширяется секциями `library_packs` (manifests — и engine user-паки
с `owner_world_uid=NULL`, и инстансы мира с `owner_world_uid` импортируемого
world), `structure_templates` (тела дочерней геометрии) и прочими доменными
body-секциями. Секции bindings нет: доступность мира следует из владения —
global manifest импортирует пак в библиотеку движка, не давая доступности
миру; доступность даёт только world-owned manifest/инстанс.

Import: проверить весь wire/UID/владение → создать world → manifests → все
доменные тела + membership → проверка зависимостей и диагностика.
Все операции выполняются в существующей транзакции bundle, без промежуточных
commit. Битые body/manifest отвергаются обычной валидацией; fallback не позволяет
принимать повреждённый JSON или подделанное владение.

Операции жизненного цикла (тонкие API → pack application service):
engine scope — полный CRUD user-библиотек (delete безопасен всегда: миры
держат инстансы-копии); defaults read-only. World scope — `instantiate_pack`
(engine→world инстанс, remap §2), повторное инстанцирование (обновление
инстанса, перезаписывает локальные правки пака — явная операция),
`copy_pack` publish world→engine, правка членов world-пака. World-owned тела
путешествуют в bundle как обычные manifests/members с owner мира.

Self-contained export включает world-owned manifests и их тела/состав
целиком, `source_pack_uid` provenance и зависимости. Объявление зависимости
не создаёт инстанс; отсутствующая зависимость остаётся диагностируемой
неполнотой. Refs в телах остаются только template UID, без пары
pack → template. World remap не меняет pack/template UID engine-библиотеки;
world-owned UID стабильны по формуле от владельца мира.
Defaults доступны из деклараций движка; pack identity пользовательского контента
при переносе сохраняется и не превращается в default.

Legacy fixtures/bundle переводятся отдельным явным этапом: карта старых/новых
UID применяется ко всем refs, manifests/bindings добавляются явно. Не угадывать
пак по `source_file`, не присваивать всем импортируемым телам default-пак.

## 5. Разрешение ссылок и fallback

Движок получает только UID из ссылки, находит тело и единственного пак-владельца
в каталоге, проверяет доступность (пак — default либо `owner_world_uid` равен
миру) и применимость шаблона к генератору.
Зависимости требуют явного инстанцирования в мир; транзитивного
автоинстанцирования нет. Циклы зависимостей обходятся с visited-set; проверка
не создаёт инстансов.

Отсутствует настройка/значение → доменный default. Разрешимая явная ссылка →
конкретный указанный шаблон. Неизвестный UID, недоступный миру владелец или
missing dependency → соответствующий default + warning log; сохранённая ссылка
остаётся исходной. Нельзя подменять её произвольным пользовательским кандидатом.
Если default домена — существующее soft-fallback поведение (например relief R21),
используется этот POJO/доменный контракт, без новых литералов в движке.
Этот режим касается template refs; правила REF-W остальных реестров не меняются.

Будущий режим мастера использует те же диагностические причины, но выдаёт
конкретную ошибку вместо warning/default. Реализация режима мастера вне scope.

## 6. Canonical attach и жизненный цикл

`world_wire_overlay` остаётся чистым merge исходных wire-полей перед resolver.
`global_fill_missing` загружает/валидирует весь явно объявленный default-источник,
затем атомарно добавляет отсутствующие UID и membership; существующие тела и
`source_file`, включая override default UID, не заменяются. Ручной update —
отдельная явная политика, владение при этом неизменно.

Все публичные global read-пути обеспечивают доступность defaults перед чтением;
это не меняет world ownership/pick-policy. Runtime hydrate мира использует
эффективный каталог §1 и не обходит его через прямой FS-loader или общий SQL list.
FS root: env → repo-relative fallback, без зависимости от cwd.

Полнота проверяется по canonical UID и membership, не по непустой таблице.
Удалённый default восстанавливается при следующей проверке; новые default UID
подключаются после проверки источника. Положительный бессрочный кеш полноты
не используется; допускается кеш провалидированного источника с инвалидированием
при изменении manifest/файлов, но наличие строк проверяется заново.
Canonical attach — единственная мутация read-only default-паков: engine может
добавлять отсутствующих членов, но только insert-missing, никогда replace
существующей строки.
Конкурентные attach сериализуются в контексте БД/библиотеки; SQL-conflict не
заменяет существующую строку. Ошибка записи откатывает весь attach; ошибка до
записи не оставляет строк. В чужой транзакции adapter использует существующий
transaction/savepoint-контракт, не делает скрытый commit или вложенный BEGIN.

Стартовый default structures — объявленный `base`, родительские builtin plots
тоже должны иметь явное canonical-членство. Для relief наличие `smoke_003` не
делает пак дефолтным: до подключения relief-spec фиксируется отдельный явный
список default-паков, без массового сканирования пользовательского FS-контента.

## 7. Логирование

Единственный фасад — `app.core.loggingConfig`, правила L1–L8
[tz_logging](./tz_logging.md). Использовать существующие доменные эмиттеры:
settlement `packingLog`, relief `relief_warning`, policy resolve — существующий
`jsonValidation/resolve`. При необходимости расширяется их типизированный
контракт событий, без новых параллельных log-функций/handlers/форматтеров.

Причины: unknown template, owner pack unavailable to world, missing dependency,
default applied. Диагностика несёт world UID, generator/domain, requested template
UID, owner/dependency pack UID (если известны), reference path, причину и выбранный
default. Одно событие эмитируется один раз на границе resolve; callers его не
дублируют. Штатный facade направляет запись в доменный JSON sink, generation
scope копирует её в существующий transcript. Warning не теряется из-за нового
logger вне allowlist. Кеши не подавляют необходимые предупреждения другого мира.

## 8. Проверяемые инварианты

- Пак вне default-spec не автоимпортируется; SQL одного мира не протекает в другой.
- Правка/удаление engine user-библиотеки не меняет инстансы миров (snapshot);
  правка world-инстанса видна только его миру; copy/instantiate/publish remap
  детерминирован — внутренние refs переписаны на новые UID, внешние — нет.
- Явное инстанцирование всего пака делает его подходящие шаблоны доступными
  генераторам мира.
- UID стабилен при повторном импорте; локальные имена разных владельцев не сталкиваются.
- Один владелец, template-only refs и явные зависимости сохраняются при round-trip.
- Missing ref/dependency → default + одно warning через штатный sink, исходный ref сохранён.
- Canonical attach сохраняет user override, атомарен, выдерживает конкурентный вызов,
  rollback/retry, частичную библиотеку и восстановление удалённого default.
- Cwd/env-root не меняют владельца/UID; FS-fallback не маскирует отсутствующий SQL attach.
