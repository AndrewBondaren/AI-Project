**Статус:** целевой контракт, согласован 2026-10-08, уточнён 2026-10-14 (A0).
Реализованы хранение/CRUD паков, полный remap, re-instantiate preview/confirm
и независимое member-copy, effective catalog 5a, bundle/routes 4d/L-5.
Разделение plot/building и снятие registries 5b ещё не реализованы.
Не относится к terrain/map pack-файлам.

**Домены plot/building/structure:** [актуальный контракт A0](tz_domain_template_libraries.md).
Plot имеет собственный шаблон с building templates внутри; building содержит

правило «builtin plots вне SQL/member-каталога», не требует превращать
каждый вложенный building body в голую UID-ссылку.

## 0. Граница ответственности и универсальность библиотек

Библиотеки отвечают на вопрос **«что доступно для создания/генерации»**: определения сущностей, их свойства, ограничения и связи. Генераторы и другие доменные потребители отвечают на вопрос **«как создавать и использовать»** эти определения: алгоритмы, размещение, материализацию и исполнение механик. Библиотечные параметры могут влиять на выбор алгоритма, но сама библиотечная инфраструктура не реализует доменную логику генерации.

Pack-механизм — **общая инфраструктура авторского контента всего движка**, не частный механизм геометрического генератора. Он должен быть пригоден для последующего подключения шаблонов NPC, рас, предметов, материалов, флоры, фауны и других доменов без отдельной системы владения и распространения библиотек для каждого. Общими остаются идентичность и происхождение, владение и изоляция миров, копирование/remap ссылок, импорт/экспорт, публикация, обновление и проверка контрактов. Состав тел, алгоритмы создания, механики и правила выбора определяет **адаптер конкретного домена**; универсальный pack-слой не должен диктовать им общую предметную модель.

Canonical defaults и общий resolver — отдельная ответственность: определяют значения при допустимом отсутствии полей, наследование и проверку параметров, не заменяя библиотечные определения или доменные алгоритмы. Разрешение параметров и валидация должны быть согласованы между runtime и импортом/редактированием.

«Некорректное» разделяется по типу и контуру (уточнение 2026-10-09):

- **Некорректное имя поля** (неизвестный wire-ключ): validation — ошибка;
  runtime — WarningError через доменный sink, ключ отбрасывается, работа
  продолжается. Детект unknown-ключей — обязанность слоя resolve
  (сравнение wire-ключей с полями модели), а не `extra` POJO: целевой
  режим един для всех wire-моделей и не требует `extra="forbid"`.
  Доменный контракт слоя — [`tz_json_validation.md` § Unknown wire
  keys](./tz_json_validation.md#unknown-wire-keys).
- **Агрегация ошибок валидации:** отчёт собирает ошибки всех полей и
  секций за один проход — возвращается полный список `FieldPathError`,
  не первая ошибка.
- **Корректное имя, ошибочное значение**: validation (импорт/редактирование)
  — всегда ошибка, fallback не применяется; runtime (генерация/resolve) —
  WarningError-запись через штатный доменный sink (§7) и доменное решение:
  fallback там, где контракт домена его объявляет (подавляющее большинство
  случаев — §5), отказ операции для полностью невалидного. Подмены молча
  нет ни в одном контуре.

**Шаблон не равен экземпляру мира.** Например, библиотека NPC может описывать исходный архетип и параметры создания, но созданный NPC имеет собственный UID, состояние, память, биографию и отношения, изменяемые симуляцией. Правка библиотечного шаблона сама по себе не должна молча перезаписывать существующих NPC; политика применения изменений к уже созданным экземплярам относится к отдельному доменному контракту. Аналогично шаблон здания не тождественен построенному зданию.

Это архитектурная граница для будущих доменов, **не требование реализовать все перечисленные домены в текущей фазе**. Их интеграция проводится поэтапно.

### 0.1 Практическая цель: повторное использование и копирование контента

Паки нужны не только для изоляции миров и будущей платформенности, но и для **удобной повседневной работы автора**: повторного использования, вариаций, переноса и редактирования содержимого без ручного пересоздания определений и исправления ссылок. Это относится **ко всем видам паков и их членов**, а не только к шаблонам зданий/рельефа: к N+1-каталогам материалов, рас, характеристик и другим подключаемым доменам. Общие операции не должны быть жёстко привязаны к понятию «шаблон»; доменный адаптер определяет тип и допустимые зависимости члена.

Целевые пользовательские сценарии:

- **Копирование отдельного члена библиотеки** в указанный целевой пак (в том же мире, между доступными автору паками либо при явной публикации в движок): независимая запись с новым UID, сохраняющая происхождение, без изменения оригинала. Автор может изменить копию и создать вариант определения. Перед копированием проверяются уникальность нового UID, владение и допустимость ссылок; совпадение читаемых атрибутов не блокирует копирование.
- **Копирование пака целиком**: независимый пак и копии всех членов с remap UID и внутренних ссылок по §2; оригинал остаётся неизменным. Операция должна работать для поддерживаемых видов паков, а не только для template-доменов.
- **Инстанцирование engine→world**, **явная публикация world→engine** и **повторное инстанцирование с preview/подтверждением** используют общие правила владения, происхождения и remap из §1–4, а не отдельные несогласованные механизмы для каждого домена.
- **Повторное использование**: автор собирает каталоги определений и переносит их в новые миры, не воспроизводя вручную состав и связи. Копирование не создаёт автоматическую синхронизацию: изменения источника не переписывают копии без явной операции.

**Контракт копирования члена (решение 2026-10-09):** операция разрешена как составная над базовым CRUD (§0.2), при соблюдении общих контрактов:

- Целевой пак выбирает автор из паков, доступных ему для записи; перенос члена между scope (мир↔движок) идёт существующими операциями пака целиком (`copy_pack`/publish, инстанцирование), а не member-copy.
- Копия — самостоятельный новый член с **новым `template_uid` через `app.ids.runtime_uid()`** (уточнение 2026-10-11), с проверкой уникальности и повторным вызовом при занятости UID. Полученный UID сохраняется один раз; повторные чтения, правки и перенос существующей записи его не пересчитывают. Владелец копии — целевой пак, единственный (§1); `creation_kind=member_copy`, `source_template_uid` указывает на непосредственный оригинал. Происхождение целевого пака не меняется. Dangling provenance допустим (§3); оригинал не изменяется.
- `local_uid` — локальный ключ, не отображаемое имя и не идентичность члена; копия может сохранять его независимо от наличия членов с тем же ключом. Совпадение не требует автоматического переименования; выбор `copy`/`replace` выполняется общим протоколом §0.3 (уточнение 2026-10-11).
- Зависимости члена проверяются на разрешимость в целевом каталоге и диагностируются; автоматического рекурсивного копирования зависимостей нет.
- Ссылки внутри копируемого тела не переписываются: внутренние refs на членов исходного пака становятся внешними refs исходного пака и разрешаются по правилам доступности (§5).

**Идентичность template-членов (решение 2026-10-11):** определяется
только `template_uid`. Читаемый `local_uid` не является второй
идентичностью и не имеет unique-ограничения ни внутри пака, ни внутри
эффективного каталога мира. Предыдущий отказ по занятому читаемому
ключу отменён. Ссылки на конкретные template-сущности — по UID;
при реализации необходим аудит всех прежних key-based потребителей.

### 0.2 Единый CRUD-контракт библиотечной инфраструктуры

**Архитектурный инвариант:** каждый подключаемый библиотечный домен использует единый базовый контракт CRUD для паков и их членов; новый домен не должен создавать отдельную инфраструктуру хранения, копирования и редактирования с нуля. Общая инфраструктура управляет идентичностью, владением, атомарностью, проверками и ссылочной целостностью; доменный адаптер отвечает за модель тела, доменные ограничения, валидацию и допустимые последствия операций.

- **CRUD паков:** create/read/update/delete метаданных и состава с учётом scope, прав на изменение и зависимостей. Default-паки остаются read-only с исключением additive canonical attach (§6).
- **CRUD членов:** create/read/update/delete записей любого поддерживаемого `library_kind` в рамках паков. Изменение тела или отображаемого имени не меняет UID; смена идентичности оформляется созданием новой записи, а не переписыванием первичного ключа (§2).
- **Проверки перед записью:** уникальность ключей, валидность тела, владение, допустимость ссылок и ограничения домена; недопустимые изменения не применяются частично. Удаление используемых записей не должно оставлять незамеченные битые ссылки: необходима явная политика отказа/разрешения зависимостей с диагностикой, определяемая контрактом операции и адаптера.
- **Составные операции:** копирование члена/пака, `instantiate_pack`, `copy_pack` (publish), повторное инстанцирование и import/export строятся поверх согласованных базовых операций, UID/remap и валидации; они не должны обходить ограничения CRUD или молча менять существующие экземпляры мира.

Этот пункт определяет **целевую общую границу ответственности**, а не утверждает, что CRUD всех доменов уже реализован. Точные API, транзакционные границы, политика удаления и обработка зависимостей уточняются до реализации без изменения правил владения и provenance из настоящего ТЗ.

### 0.3 Единый механизм политики записи (решение 2026-10-11)

Пользовательские операции записи паков и members библиотек мира и движка
используют один механизм выбора политики. Он охватывает импорт, перенос,
копирование, публикацию и повторное инстанцирование. Тип источника (FS,
архив, SQL), домен и область владения не вводят отдельные протоколы выбора.
Ограничения владения и переходов scope из §0.1/§1 сохраняются.

**Обнаружение совпадений:** у пака — существующий `pack_uid` или занятая
целевая идентичность, вычисленная центральным UID-контрактом; у member —
существующий целевой `template_uid` либо совпадение
`(целевой pack_uid, library_kind, local_uid)`. Совпавшие `local_uid` в других
паках не создают конфликт. `display_name` не участвует. Все совпавшие members
возвращаются списком; неоднозначность нельзя разрешать первым результатом.
Связанные members при повторном инстанцировании сопоставляются по provenance
(§2), а не по `local_uid`; совпадения ключей не сливают их идентичности.

**Единый двухэтапный протокол:**

1. Фронт отправляет исходный запрос без политики. Бэкенд читает и валидирует
   источник и целевое состояние, проверяет доступ и собирает совпадения.
2. При совпадениях возвращается результат `policy_required`: цели с их UID,
   допустимые действия и причины ограничений, preview последствий и токен
   актуальности. Записей и частичного импорта до выбора нет. Если совпадений
   нет и операция допустима, исходный запрос может выполняться сразу.
3. Фронт повторяет запрос с явной политикой `copy` либо `replace`, выбранными
   целевыми UID и полученным токеном. Для пакета объектов решения задаются
   по каждому совпадению; неявной политики по умолчанию нет.
4. Бэкенд заново читает источник и цель и проверяет актуальность выбора.
   Устаревший preview возвращается с обновлёнными фактами без записи.
   Проверка состояния и применение согласованного плана выполняются в одной
   транзакционной границе; конкурентная запись не обходит проверку.

**Семантика политик:**

Wire-контракт выбора: `decisions[]` содержит `item_key`, `policy`, для
`replace` — `target_uid`, для `copy` пака — новый `copy_system_name`.
Последний является ключом новой идентичности, не отображаемым именем;
UID вычисляется через существующий `app.ids.library_uid`. Занятый ключ
нельзя перезаписать политикой `copy`; бэкенд проверяет его отдельно.
Копия member не принимает `copy_system_name` и сохраняет локальный ключ.
Preview token связан с проверенным состоянием и предложенными вариантами;
выбор клиента проверяется против этих фактов при повторном запросе.

- `copy` создаёт независимую идентичность и сохраняет существующую сущность.
  Для member — новый UID и допустимое сохранение `local_uid`; для пака —
  новый UID пака и новые UID членов, remap внутренних ссылок (§2).
  Независимая копия пака не обязана переиспользовать занятую идентичность
  инстанса/публикации: подготовка новой идентичности выполняется общим
  центральным UID-контрактом, без локальных формул.
- `replace` сохраняет UID и владельца выбранной цели, заменяет её содержимое
  целиком после валидации. Ссылки на UID цели остаются действительными.
  Для пака preview явно описывает сопоставление members, добавления,
  замены, удаления/удержание, dependencies и remap. Исчезнувшие используемые
  members не удаляются молча: сохраняется контракт pinned ∪ referenced (§2).
  При замене сохраняется lineage цели (`source_pack_uid`,
  `source_template_uid`, `creation_kind`): это происхождение идентичности,
  а не история редакций тела. Независимая member-копия остаётся
  `member_copy`, даже если тело заменено содержимым pack-copy. Источник
  новой редакции не присваивается immutable provenance цели.

Недопустимость замены default-пака, чужого владельца либо невалидного тела
не обходится политикой клиента. Явное редактирование по UID использует ту же
проверку разрешений и план замены; при однозначно заданной цели отдельный
выбор копирования не требуется. Внутренний canonical attach (§6) остаётся
служебным insert-missing: пользовательский `replace` не открывает замену
default-паков. Валидация импорта (§0) не подменяется fallback.

**Архитектурная граница:** чтение состояния, чистое решение политики,
построение плана и атомарное применение — отдельные ответственности.
Единственный общий компонент политики принимает факты и явный выбор,
возвращает решение без I/O и side effects. Планировщики паков/members
реализуют состав действий, доменные адаптеры — валидацию тел и работу со
ссылками. Routes, импортёры, адаптеры и репозитории не выбирают `copy`/`replace`
самостоятельно. Генерация и эффективный каталог (§1/§5) только читают
результат записи и не заменяют членов автоматически по `local_uid`.

## 1. Доступность и использование

Пак — именованный набор шаблонов; каждый шаблон имеет ровно один пак-владелец.
Глобальная SQL-библиотека хранит тела независимо от миров. Мир не привязывается
к engine-паку по ссылке: использование пака миром = **явное инстанцирование** —
копия пака становится world-owned экземпляром этого мира. Инстанцирование
распространяется на весь мир, не на отдельную локацию или генератор и всегда
копирует состав пака целиком — частичных инстансов не существует; автор мира
выбирает нужные члены и их свойства поверх полного набора (включая будущий
conditional/random pick по конкретному паку).
Генераторы выбирают подходящие им шаблоны из всех инстансов мира по
существующим доменным условиям.

Defaults движка явно перечислены доменными canonical-spec и доступны без
ручного импорта. Любой автоматический импорт пака вне этих деклараций — баг.
Пользовательский пак движка используется миром только после явного
инстанцирования (bundle либо более поздняя операция). Наличие файлов,
SQL-строк или инстанса в другом мире не даёт доступности этому миру.

Эффективный каталог мира = объявленные defaults + world-owned паки мира
(инстансы engine-паков + авторские записи мира). Административный `list_all()`
глобальной SQL-библиотеки не является каталогом генерации. Pick-policy и
фильтры домена применяются поверх эффективного каталога; отсутствие
per-template pointer не исключает шаблон world-owned инстанса.

### 1.1 Политика библиотек (единственная, 2026-10-08)

**Библиотеки движка** (`owner_world_uid IS NULL`):

- **Default** — декларируемые движком паки для resolve дефолтов; read-only,
  единственная мутация — additive canonical attach (§6).
- **User** — создаются и **полностью редактируются** на уровне движка;
  импортируются в миры как инстансы. Правка user-библиотеки не затрагивает
  уже созданные инстансы миров — snapshot-семантика; обновление мира до
  новой редакции — явное повторное инстанцирование.

**Библиотеки мира** (`owner_world_uid` = мир):

- Обязательные зависимости мира; создаются только инстанцированием из
  библиотек движка (`instantiate_pack`) либо авторством записей мира.
- Полностью редактируемы в рамках своего мира — изменяется только экземпляр.
- Мир хранит **pin-набор** автора — пары (`library_kind`, `template_uid`)
  как embedded-конфиг мира (не членство и не библиотека): маркер
  «напрямую выбрано/используется», чисто информационный для ориентации
  автора, без семантики генерации и влияния на pick-кандидатов. Привязка
  по UID конкретного template-члена; при remap pin переносится по той
  же uid_map, что и остальные ссылки. «Используется» = pinned ∪
  **referenced** — член называется ссылками потребителей (тела членов,
  pick-политики, specs по `template_uid` или ключу; доменный адаптер
  объявляет свои ref-поля, движок вычисляет множество referenced по
  эффективному каталогу при запросе и не хранит его). Подсветка «не
  используется» — член без pin и без referenced (напр. material-запись,
  не упомянутая ни одним телом).
- Поставляются в bundle вместе с миром (self-contained export, §4).
- Могут быть явно экспортированы в библиотеку движка — publish
  (`copy_pack` world→engine, тот же remap-механизм §2).

Доступность = владение: член доступен миру, если его пак default либо
`owner_world_uid` равен миру. Отдельной таблицы/операции «подключения» нет.
CRUD библиотеки движка никогда не ломает миры: изоляция построена на копии,
не на запрете правок.

У template-члена идентичность — `template_uid`; `local_uid` и
`display_name` — читаемые атрибуты и могут повторяться. Совпадение имени
не означает одну сущность, не блокирует копирование/инстанцирование и
не даёт основания для слияния или перезаписи. Повторное инстанцирование
сопоставляет связанные `pack_copy` по provenance, не по читаемому ключу.

Для deferred каталожных N+1-доменов приоритет: `defaults < world packs`. Ссылки по
`local_uid` разрешаются по этому порядку; для каталожных N+1-записей
сохраняется field-level merge — member может быть sparse-override поверх
default-записи с тем же `local_uid`. Эти правила ключей N+1 не задают
идентичность template-членов. Совпадение `local_uid` template-члена с
default-шаблоном не создаёт override; автоматическое whole-body
замещение по имени отменено. Refs по `template_uid` адресуют
конкретного члена и приоритетом слоёв не переопределяются (§5).

Целевой охват: pack-модель — целевая для всех каталожных N+1-доменов
(terrain, material, economic_tier, race, perk и пр.). Embedded-конфиг мира
(скаляры, настройки) — не библиотека. Миграция существующих N+1-доменов —
отдельная фаза после template-доменов, per-domain.

### 1.2 Вычисление использования членов (решение 2026-10-11)

Единый resolver в `libraryPacks/` строит computed-индекс
«целевой член → потребители и пути ref-полей». Доменные адаптеры и
извлечение ссылок находятся в **`libraryPacks/domainAdapters/`**, каждый
домен в своём модуле. Адаптер потребителя объявляет ссылки своего тела
и world-конфига; общая инфраструктура не знает имён доменных полей.
Описание ссылки содержит целевой домен, UID либо системный ключ,
источник (член или конфиг мира) и путь поля для диагностики.

В текущей реализации покрываются building-ссылки `main_building.structure`,
`secondary_buildings[].structure`, embedded layouts мира и relief policy.
Целевой контракт A0 дополнительно покрывает plot recipe UID refs/keys
plot_counts/plot_priority и NamedLocation.system_template_uid /
system_structure_template_uid. Вложенные полные тела сканируются рекурсивно
через объявленные поля домена; наличие вложенного body не означает отдельный
member. Ссылки созданных локаций учитываются usage/deletion/retention.
Сканируются только объявленные ref-поля, не произвольные UUID в JSON.

Каталог выборки — defaults + паки данного мира, до шага 5a через
membership-репозитории, после него через фасад эффективного каталога
без смены семантики. UID адресует конкретного доступного члена; системный
ключ разрешается по приоритету слоёв только для доменов с key-based
контрактом (§1.1); конкретные template-члены адресуются по UID, без
lookup по повторяющемуся local_uid. Тела чужих миров и недоступных
engine-паков не участвуют. Битые ссылки возвращаются с диагностикой.

Индекс строится один раз на операцию и используется preview/удержанием,
проверкой удаления и диагностикой member-copy. Pins учитываются отдельно;
provenance, объявления dependencies и registry pointers сами по себе не
означают использование члена. Persisted-таблицы `referenced` нет.
Расширение usage-индекса 2026-10-11 само по себе не меняло генераторы.
Проводка перечисленных A0 refs и переход читателей выполняются отдельными
кодовыми шагами; остальные библиотечные домены подключаются позже.

## 2. UID и владение

UID формируются исключительно инфраструктурой `app.ids`
по [DET-1](./project_data_storage_tz.md). Новых builtin/pack UID-функций вне неё
нет; импортёры, POJO и генераторы не хэшируют и не конкатенируют входы формулы.

Фактический путь после переноса пакета — **`app.ids`**. Для независимой
авторской member-copy используется существующий `runtime_uid()` (§0.1),
а не локальная формула или прямой вызов UUID API. Детерминированный
`library_uid()` сохраняется для обычного создания и FS-импорта;
для remap пака целиком центральный API расширяется по правилу ниже.
UID с `creation_kind=member_copy` проверяется на формат,
уникальность и согласованность тела/членства, но не на равенство формуле
`library_uid(kind, local_uid, pack_uid=...)`. Импорт существующей копии
сохраняет её записанный UID; не создаёт новый при каждом чтении/импорте.

Центральный `LibraryKind` расширяется видами `LIBRARY_PACKS` и
`STRUCTURE_TEMPLATES`. Пак получает UID существующим вызовом
`library_uid(LibraryKind.LIBRARY_PACKS, system_name)`: `system_name` пака —
устойчивый глобальный ключ автора, например `engine.structures.base`.
Имя FS-папки — локальный `pack_name`, а не глобальная идентичность пака.

Для шаблонов центральный API расширяется до
`library_uid(library, system_name, *, pack_uid=None)`: в pack-owned пути
`system_name` означает локальный ключ шаблона, `pack_uid` обязателен на уровне
адаптера пака. Центральный helper сериализует домен, владельца и локальный ключ
однозначно и детерминированно с существующим UUID5/hash-ядром. Canonical-форма
(решение 2026-10-09): owner-less — `"{library}|{system_name}"` (прежняя,
bit-compatible); pack-owned — владелец в root-слоте формы DET-1,
`"{pack_uid}|{library}|local_uid={system_name}"`; разделитель `|` во входах
отвергается — сериализация остаётся однозначной. Legacy-вызов без
владельца остаётся только для ещё не мигрированных доменов; он не используется
новыми pack-owned импортёрами. UID не зависит от мира, seed, display name,
версии, абсолютного пути или порядка импорта.

Для детерминированного пути один локальный ключ в одном домене/паке = один
UID. Независимая member-copy использует назначенный UID по §0.1; это
исключение из формулы; unique-ограничения читаемых атрибутов template-членов
не устанавливаются. Одинаковые
ключи в разных паках в детерминированном пути различны; повторный импорт
сохраняет UID. Владение хранится в каталоге,
а не декодируется из UID. Смена владельца через копирование создаёт новую
сущность; правка читаемых атрибутов существующей строки не меняет её UID.
Детерминированная формула служит созданию/повторному FS-импорту, а не
доказательством идентичности независимых копий по имени. Remap обязан
различать исходные UID, даже если их читаемые атрибуты совпадают; сведение
нескольких исходных членов в один целевой UID недопустимо.

**UID при полном копировании/remap пака (решение 2026-10-11).**
Для нового члена целевого пака UID вычисляется детерминированно
центральной инфраструктурой **`app.ids` от целевого `pack_uid` и
исходного `template_uid`**, в namespace соответствующего библиотечного
домена. `local_uid`, `system_name` и `display_name` не являются входами
идентичности полного remap. Центральный API отвечает за каноническую
сериализацию и хэширование; consumers не составляют seed-строк и не
вызывают hash/UUID API самостоятельно.

Правило едино для `instantiate_pack` (движок → мир) и `copy_pack` /
publish (мир → движок). Карта строится как «исходный template_uid →
целевой template_uid»: разные исходные члены, включая одноимённые
независимые копии, сохраняются разными сущностями. Одинаковые целевой
пак, исходный UID и домен дают тот же целевой UID; другой целевой пак
даёт другую идентичность. По этой карте переписываются внутренние
ссылки и затронутые world-side refs/pins; provenance сохраняет
непосредственный исходный UID.

При re-instantiate уже существующие связанные члены сохраняют записанные
UID и сопоставляются по provenance; новую формулу нельзя применять для
перезаписи PK существующих строк, включая ранее созданные инстансы.
Для добавленных членов применяется правило полного remap выше.
Независимая member-copy остаётся отдельной операцией с новым случайным
UID через `app.ids.runtime_uid()` (§0.1). Импорт существующих записей
сохраняет их UID; проверка учитывает способ создания и прежние инстансы,
не требует равенства нового remap UID формуле от local_uid.

UID — назначенный один раз первичный ключ строки, а не значение,
перевычисляемое при правках: ни импорт, ни экспорт, ни remap, ни обновление
источника не перезаписывают `pack_uid`/`template_uid` существующей строки —
иначе теряется связь по внешним ключам. «Смена идентичности» — это новая
сущность с новой строкой и новым uid, не мутация uid на месте; новый uid
возникает только при появлении новой сущности (создание, импорт,
remap-копия) как её internal key. Детерминизм формулы служит стабильности
повторного импорта и проверке записанного uid, а не перезаписи.
UID не является версией:
правка тела, `version`, `display_name` и `dependencies` не меняют ни
`pack_uid`, ни `template_uid` — включая UID engine-библиотеки, поэтому
`source_pack_uid` инстанса остаётся валидным после обновления источника и
именно по нему определяется «тот же источник» при повторном инстанцировании.
Внешние ключи происхождения (`source_pack_uid`, `source_template_uid`)
immutable: их назначает только remap-операция (создание строки инстанса
или перезапись члена источником при повторном инстанцировании); правки
тел, переименования и bump `version` их не меняют.

`copy_pack` / `instantiate_pack` — доменная remap-операция адаптера, не
SQL-copy: новый владелец → новый `pack_uid`; члены получают новые UID по
центральному правилу «целевой pack_uid + исходный template_uid» выше
и сохраняют `source_template_uid` — UID члена
источника (provenance, §3); ссылки внутри тел на членов **того же** пака
переписываются на новые UID, refs на чужие паки и внешние тела не трогаются;
`dependencies` копируются. Инстанцирование engine→world = copy с
`owner_world_uid` мира + `source_pack_uid` исходника (диагностика
происхождения); при этом ремапятся и **world-side refs** на членов пака
(pick-policy `default_template_uid` и прочие доменные ссылки — перечень
фиксируется контрактом адаптера). Повторное инстанцирование того же
источника в тот же world-пак обновляет связанные `pack_copy`, UID
сохраняются, refs мира остаются валидными; отличающиеся **тела** этих
членов перезаписываются — операция явная: показывает «изменения при
обновлении» (preview текущего и подготовленного результирующего тела) и
выполняется только по подтверждению пользователя; решение остаётся за
пользователем — предупредить, не блокировать навсегда и не перезаписывать
silently (уточнение 2026-10-09); provenance-ключи сохраняются, pin-набор
мира (§1.1) лежит вне членства и remap не затрагивается. Авторские
`authored` и независимые `member_copy` сохраняются и не включаются в
перезапись/удаление как остаток источника; конфликт нового состава с их
UID показывается в preview; совпадение читаемых имён не конфликт.
Связанные `pack_copy`, удалённые
автором в новой редакции источника, исключаются из инстанса, только если
не используются миром — не входят в pin-набор и referenced (§1.1);
используемый член удерживается в инстансе с явным маркером «удержан по
использованию» — статус члена в каталоге/листинге, dangling
`source_template_uid` при этом допустим (§3) — и перечисляется в
preview; удаление на уровне движка не протягивается в мир деструктивно
(уточнение 2026-10-09). Publish world→engine — тот же copy с owner=NULL.

**Единый механизм инстанцирования (уточнение 2026-10-13).**
Compatibility-вход `instantiate_pack(confirm, preview_token)` и вход
`instantiate_pack_negotiated(decisions, preview_token)` используют общую
проверку допустимости источника и общее выполнение write-запроса через
`LibraryWriteService`. Источник — только non-default engine-пак;
проверка предшествует поиску существующего инстанса и запуску writer.
Правила допуска и запуск записи не дублируются в двух методах фасада.
Общий механизм возвращает `WriteResult | PolicyRequired` после штатного
преобразования отказа в доменную ошибку; подготовка legacy-подтверждения
и адаптация результата остаются ответственностью соответствующего входа.
Compatibility-вход сохраняет `ReinstantiatePreview` для повторного
инстанцирования, negotiated-вход — `PolicyRequired` для согласования и
`PackRemapResult` после применения. Первый успешный compatibility-вызов
также возвращает `PackRemapResult`. Семантика token/stale, UID/remap,
provenance, проверки POJO и атомарность определяются существующими §0.3/§2.

Итог архитектурного ревью `ea09865f`: фасад с делегированием допустим;
различия wire-идентичности structures и building/relief ниже — требования
доменных контрактов. Подготовка источника авторской записи не заменяет
POJO-валидацию: общий pipeline вызывает доменный `prepare_body` и
`resolve_model`, использующий схему и валидаторы POJO. Передача явных
зависимостей вместо целого сервиса и вынос интерпретации идентичности в
адаптер остаются рекомендациями, не обязательными работами этого уточнения.
План реализации: [library-instantiate-dedup.md](../.cursor/plans/library-instantiate-dedup.md).

**Подготовка и сравнение тел для preview (решение 2026-10-11).**
Доменный адаптер без записи готовит актуальное тело источника:
подставляет сохранённый UID члена инстанса, ремапит внутренние ссылки
на сохранённые UID членов инстанса и приводит сравниваемые тела к
одинаковому доменному представлению. UID существующих членов не
восстанавливаются пересчётом формулы. Общий механизм diff сравнивает
подготовленные тела без знания доменных полей; задача re-instantiate
собирает preview и применяет подтверждённые изменения в транзакции.
Подготовка результирующего тела общая для preview и записи.

Preview показывает поле, текущее значение и значение после обновления,
включая пользовательские поля вроде `display_name`. `source_file`
хранится отдельно от `row.data`, остаётся диагностикой и в diff тела
не участвует; timestamps строк и registry pointers также не входят в
сравнение тел. Без baseline нельзя отличить авторскую правку инстанса
от изменения источника, поэтому различия не называются доказанными
«локальными правками». Сохранение baseline и трёхсторонний merge в 4c
не вводятся. Самостоятельные `authored` и `member_copy` в перезапись
не входят.

**Подтверждение конкретного preview (решение 2026-10-11).** Первый
вызов возвращает preview и `preview_token` — fingerprint плана изменений
и значимых входов. Повторный вызов передаёт этот token и явное
подтверждение; одного `confirm=True` для записи недостаточно.

В fingerprint входят состав и тела источника/инстанса, provenance и
`creation_kind`, pins и ссылки, определяющие удержание, зависимости и
ключи каталога, влияющие на конфликты. При подтверждении сервис повторно
читает значимые данные и строит план тем же механизмом. Если fingerprint
изменился, write не выполняется: возвращаются актуальный preview и
новый token для повторного явного подтверждения.

Адаптеры готовят доменные данные, задача re-instantiate собирает план,
общий механизм fingerprint не содержит доменных правил. Повторная
проверка token и применение выполняются в одной транзакции с защитой
от конкурентной записи: изменение значимых входов между проверкой и
записью недопустимо. Preview и token пересчитываются без отдельной
persisted-таблицы или сессии подтверждения; отмена ничего не пишет.

**Использование при обновлении (решение 2026-10-11).** Hold-by-use
вычисляется по результирующему каталогу, а не только по состоянию до
обновления. Задача re-instantiate без записи готовит новый состав
связанных `pack_copy`, сохраняя `authored`, `member_copy`, остальные
паки мира и defaults. Связанные члены, удалённые из источника,
становятся кандидатами на удаление; их собственные ссылки изначально
не являются основанием для удержания.

Сначала удерживаются кандидаты, названные pins, конфигом мира или
телами сохраняемых членов результирующего каталога. Затем по ссылкам
удержанных членов удерживаются необходимые им кандидаты; обход
повторяется до прекращения изменений. Оставшиеся кандидаты удаляются.
Цикл ссылок только между кандидатами без использования извне и без
pins не удерживает их. Ссылка из удаляемого старого тела, отсутствующая
в подготовленном новом теле, также не удерживает цель. Ссылка из
сохраняемой независимой копии удерживает цель на общих основаниях.

Resolver (§1.2) извлекает и разрешает ссылки; задача re-instantiate
вычисляет замыкание удерживаемых кандидатов по графу. Адаптеры
потребителей не принимают решения об удалении. Окончательный состав
и причины удержания показываются в preview и входят в проверку
`preview_token` вместе со значимыми входами. Вычисление не пишет в БД.

Structures сохраняют wire-контракт `system_name == template_uid` (UUID),
локальный ключ для формулы находится в описании состава пака. У building/relief
читаемый атрибут соответствует `system_name` тела. FS stem по-прежнему
совпадает с `system_name` тела для обычного FS-импорта. UID структуры из
JSON проверяется против формулы в детерминированном пути; для назначенных
UID независимых копий действует исключение выше. Формат переноса
одноимённых копий не должен использовать читаемое имя как уникальный
идентификатор тела.

## 3. Каталог и SQL

Целевой storage-контракт:

- `library_packs`: `pack_uid` (PK), `system_name` (UNIQUE), `pack_name`,
  `display_name`, `version`, `owner_world_uid` (NULL → worlds FK),
  `source_pack_uid` (NULL; provenance-ключ remap-операции, не
  FK-integrity — как у `required_pack_uid` / `source_template_uid`:
  пак-источник может быть удалён, dangling читается как статус
  «source deleted»; enforced FK блокировал бы удаление engine-пака,
  которое по этому разделу всегда безопасно).
  Non-null `owner_world_uid` = библиотека мира (§1.1): mutable, каскадно
  умирает с миром. Default-статус определяется доверенной декларацией
  движка по UID; пользовательский manifest не может назначить себе этот статус.
- `library_pack_members`: `template_uid` (PK), `pack_uid` (FK → packs),
  `library_kind`, `local_uid`, `source_template_uid` (NULL),
  `creation_kind` (`authored` | `pack_copy` | `member_copy`).
  Единственная идентичность члена — PK `template_uid`; прежний UNIQUE
  (`pack_uid`, `library_kind`, `local_uid`) отменён для template-членов.
  Одна строка фиксирует единственного владельца; ссылку на чужой шаблон нельзя
  записывать как своё членство. Тела остаются в доменных SQL-таблицах.
  Наименование члена — `display_name` тела (единая ось `display_*`); на member
  не денормализуется, листинг каталога читает его из тела.
  `source_template_uid` — UID члена-источника, из которого этот член
  отремаплен (§2); NULL у авторских членов и членов паков, созданных в своём
  scope без копирования. `creation_kind` фиксирует способ создания данной
  записи: `authored` — авторство/обычный FS-импорт, `pack_copy` — копирование
  или инстанцирование пака целиком, `member_copy` — независимая копия члена.
  Это persisted-факт создания, а не вычисляемый статус использования.
  `source_template_uid` — provenance-ключ, не FK-integrity: источник может быть удалён,
  dangling допустим как у `required_pack_uid`. Пока обе стороны живы,
  для `pack_copy` значение указывает на члена пака `source_pack_uid`
  владельца — несоответствие диагностируется, но хранение не блокируется.
  Для `member_copy` непосредственный оригинал может принадлежать другому
  паку; совпадение с `source_pack_uid` владельца не требуется. Повторное
  инстанцирование сохраняет связь; хранимый ключ сохраняет факт
  происхождения и когда выводимая по `local_uid` связь недоступна —
  источник удалён или его локальный ключ переименован (что по §2 меняет
  идентичность члена).
  Статусы вычисляются при запросе, отдельной колонки статуса нет:
  у связанного `pack_copy` исчезновение source-члена при сохранённом
  source-паке означает «удержан по использованию», удаление source-пака —
  «source deleted». У `member_copy` исчезновение непосредственного
  оригинала означает только «источник удалён»: независимая копия
  сохраняется и не считается удержанной re-instantiate.
- `library_pack_dependencies`: PK (`pack_uid`, `required_pack_uid`), владелец
  `pack_uid` — FK. `required_pack_uid` допускает ещё не импортированный пак:
  неполнота диагностируется, а не блокирует runtime import по текущей политике.
- Таблицы bindings нет: доступность мира = владение паком (`owner_world_uid`)
  либо default-статус. Удаление world-пака каскадом с миром; удаление
  engine-пака безопасно всегда — миры держат инстансы-копии.

Доменные `system_name` не являются identity и не должны быть глобально UNIQUE
в plot/building/relief. Local_uid может повторяться даже внутри пака согласно
уточнению §0.1/1.1/2; уникальность member обеспечивается PK template_uid.
`get_by_system_name` без контекста не разрешает неоднозначность;
member-level lookup удалён (B7) — идентичность члена только `template_uid`.
`get_by_system_name` остаётся только на pack-репозитории: `system_name` пака —
глобально уникальная идентичность, не member identity.

Тело и членство сохраняются атомарно и проверяются доменным адаптером
(полиморфный `library_kind` не заменяет проверку наличия тела). Смена владельца
через upsert запрещена. `source_file` остаётся диагностическим происхождением,
не ключом пака, не признаком подключения или default-статуса.
SQL-schema изменяется только в `0001_initial.sql` с синхронизацией dataclass;
локальная БД пересоздаётся по действующей schema-policy.

## 4. Manifest, импорт и bundle

Typed manifest пака содержит `pack_uid`, `system_name`, `pack_name`,
`display_name`, `version`, `dependencies` (список UID паков), `members` и
необязательный `defaults` в archive DTO сохранён как транспортное поле
отложенного расширения, а не действующее назначение fallback пака.
**Решение пользователя 2026-10-13:** fallback, объявляемый manifest пака,
вынесен в [отдельное ТЗ расширения](tz_library_contextual_fallback.md).
Он не входит в 4d/L-5 и не требует реализации SQL-хранения в этих этапах.
Базовая парадигма — дефолты POJO и объявленные дефолтные библиотеки движка.
Каждый member содержит `library_kind`, `local_uid`, `template_uid` и,
для FS-импорта, `source_file` относительно соответствующего domain root.
`source_pack_uid` пака и `source_template_uid` членов присутствуют только в
bundle-манифестах скопированных паков — их назначает remap-операция,
автор FS-манифеста происхождение не объявляет.
Bundle-member дополнительно переносит `creation_kind`; для независимых
`member_copy` переносится назначенный UID по исключению §2, без его
перевычисления. FS-авторство не позволяет подделать этот режим.
UID проверяются центральным helper с учётом исключения §2;
дубликаты/несовпадение владельца/формулы в детерминированном пути —
ошибка контракта импорта. Путь не выходит из domain root; домены не смешиваются.
Один логический пак может иметь членов разных доменов, сохраняя отдельные FS-roots.
FS manifest хранится отдельно от JSON-тел как `pack.manifest.json` в папке пака;
сканер никогда не интерпретирует его как тело шаблона.
Минимальная единица импорта — пак с `pack.manifest.json`: lone-файлы `*.json`
в корне domain root не импортируются — у шаблона обязан быть пак-владелец и
локальный ключ из manifest (решение 2026-10-08).

World bundle расширяется секцией `library_packs` (только world-owned
manifests — инстансы и авторские паки с `owner_world_uid` импортируемого
мира). Flat body-секции (`plot_templates`, `building_templates`,
`structure_templates`, `relief_templates`) — только compatibility input,
потребляемый `import_libraries` в world-owned `legacy` pack (B7);
современный экспорт тел идёт `library/`-subtree архива §4.2, а не секциями.
Engine user-паки (`owner_world_uid=NULL`) в world bundle не
входят: перенос библиотеки движка идёт отдельным архивом
`kind:"library_pack"` (§4.2) либо явным publish (§4.1); импорт мира никогда
не пишет глобальный каталог (уточнение 2026-10-09). Секции bindings нет:
доступность мира следует из владения; доступность даёт только world-owned
manifest/инстанс.

Import: проверить весь wire/UID/владение → создать world → manifests → все
доменные тела + membership → проверка зависимостей и диагностика.
Все операции выполняются в существующей транзакции bundle, без промежуточных
commit. Битые body/manifest отвергаются обычной валидацией; fallback не позволяет
принимать повреждённый JSON или подделанное владение.

Операции жизненного цикла (тонкие API → pack application service):
engine scope — полный CRUD user-библиотек (delete безопасен всегда: миры
держат инстансы-копии); defaults read-only. World scope — `instantiate_pack`
(engine→world инстанс, remap §2), повторное инстанцирование (обновление
связанных `pack_copy` инстанса — явная операция с preview
изменений при обновлении (§2) и обязательным подтверждением
пользователя; без подтверждения write не выполняется; члены, удалённые в
источнике, удерживаются, если используются миром — §2),
`copy_pack` publish world→engine, правка членов world-пака. World-owned тела
путешествуют в bundle как обычные manifests/members с owner мира.

Self-contained export включает world-owned manifests и их тела/состав
целиком, `source_pack_uid` provenance и зависимости. Объявление зависимости
не создаёт инстанс; отсутствующая зависимость остаётся диагностируемой
неполнотой. Refs в телах остаются только template UID, без пары
pack → template. World remap не меняет pack/template UID engine-библиотеки;
world-owned UID стабильны по формуле от владельца мира.
Defaults доступны из деклараций движка; pack identity пользовательского контента
при переносе сохраняется и не превращается в default.

Legacy fixtures/bundle переводятся отдельным явным этапом: карта старых/новых
UID применяется ко всем refs, manifests/bindings добавляются явно. Не угадывать
пак по `source_file`, не присваивать всем импортируемым телам default-пак.

### 4.1 Разделение импорта мира и публикации библиотек

**Статус: актуализировано пользователем 2026-10-13.**

- Импорт world bundle должен восстанавливать библиотеки мира как **world-owned** зависимости импортируемого мира, не публикуя их автоматически в глобальные пользовательские библиотеки движка (`owner_world_uid IS NULL`).
- Перенос выбранной библиотеки (или нескольких библиотек) из мира в каталог движка должен быть **отдельной явной операцией** (`copy_pack` / publish world→engine), с собственным подтверждением и проверками. Импорт чужого мира не должен изменять глобальный пользовательский каталог побочным эффектом.
- При явной публикации выполняется remap UID пака, членов и внутренних ссылок; происхождение сохраняется в `source_pack_uid` и `source_template_uid`. Исходный world-owned пак не изменяется.
- Импорт целого мира по умолчанию создаёт независимую копию с согласованным
  remap `world_uid`, entity UID, UID world-owned паков, членов, pins и всех
  затронутых ссылок. Это default операции, а не только реакция на коллизию.
  Совпадение исходного world_uid не требует отдельного выбора update/copy;
  исходный мир не изменяется. Обновления существующего мира выполняются через
  библиотеки и действующую политику патчей. Full-world update не входит в
  обязательный контракт 4d/L-5.
- В одном архивном импорте сначала создаётся мир, затем импортируются его
  библиотеки в общей UOW. Library policy/decisions/token остаются общими;
  default copy мира не разрешает неявный replace библиотек. PolicyRequired,
  stale и ошибка откатывают все изменения, включая временную world row,
  до формирования ответа. Engine library import не требует мира.
- Различие форматов зафиксировано в §4: world bundle несёт только world-owned manifests; engine-библиотеки переносятся отдельным архивом `kind:"library_pack"` (§4.2), не секциями world bundle.

### 4.2 Формат архива (zip-конверт)

**Статус: контракт и уточнения C-1 согласованы мастером 2026-10-11;
модель манифеста и codec реализуются следующими шагами.**

Экспорт/импорт мира и library-паков — один zip-архив с файловой
структурой, читаемой мастером стандартным архиватором (решение
2026-10-09). Архив — транспортный конверт над моделью секций §4;
handlers и модель `dict {section_key: payload}` не меняются, codec —
тонкая граница сериализации.

- **Контейнер:** zip (расширение `.wpack`), ZIP64. JSON-секции —
  DEFLATED; `*.zst` и уже-сжатые блобы — STORED. Порядок entries
  детерминирован, переменных метаданных нет — хеш архива
  воспроизводим.
- **Структура архива мира** (`kind:"world"`):

```text
{name}.wpack
  bundle.manifest.json        # метаданные упаковки — не доменные данные
  skeleton/
    world.json                # world row + реестры + pin-набор
    states.json
    locations.json
    connection_nodes.json
    connection_edges.json
    {section_key}.json        # transitional: плоские body-секции —
                              # до переезда world-owned тел в library/;
                              # pack-owned тела плоскими не дублируются
  library/                    # библиотеки мира — self-contained
    {domain_root}/
      {pack_uid}/
        pack.manifest.json    # схема §4: members, deps, provenance
        {template_uid}.json   # тела членов, идентичность — UID
  pack/                       # запечённый World Pack — только уровень full:
                              # verbatim зеркало pack_root; layout SoT —
                              # WorldPackPaths, здесь не перечисляется;
                              # debug `*.grade_rays.json` не входят
```

- **`bundle.manifest.json`:** `kind`, `format_version`, `source`,
  индекс `section key → path`. Доменные настройки живут в секционных
  файлах, манифест их не дублирует.
- **Версия и индекс:** первая версия — целое `format_version: 1`;
  неизвестная версия отвергается до чтения доменных секций. Поле
  `sections` — объект `{section_key: relative_path}`. Для плоских секций
  разрешены только пары из явной таблицы `SECTION_PATHS` в
  `dataModel/worldBundle/`; все девять текущих ключей
  `BundleSection.SKELETON` получают пути `skeleton/{section_key}.json`.
  Это явные девять пар, не правило для произвольных новых ключей.
  `world` обязателен в world-архиве; остальные секции могут отсутствовать
  согласно уровню/содержимому. Каждый объявленный файл существует;
  секционный файл без записи в индексе, два ключа на один путь и
  неизвестная пара key/path отвергаются. `library/` и `pack/` — отдельные
  файловые subtree, не произвольные секционные JSON-файлы; их mapping
  задаётся отдельно при добавлении соответствующего subtree.
- **`source` — владелец-источник:** `{kind:"world", world_uid,
  world_name, exporter, exported_at, content_hash?}`; по
  `source.world_uid` импорт проверяет исходного владельца и строит remap
  независимой копии по §4.1; это не разрешение обновлять существующий мир.
  Per-pack provenance (`source_pack_uid`/`source_template_uid`)
  остаётся в `pack.manifest.json`.
- **Согласованность источника:** `source.kind` совпадает с корневым
  `kind`; для world-архива `source.world_uid` совпадает с UID в
  `skeleton/world.json` до remap. Расхождение — reject, иначе source
  metadata и импорт могли бы использовать разных владельцев.
  `world_name` — подпись источника, не отдельная настройка мира.
  Для `kind:"library_pack"` источник — `{kind:"library_pack", pack_uid,
  exporter, exported_at, content_hash?}`; `pack_uid` совпадает с
  `pack.manifest.json`. Один такой архив переносит один логический пак,
  включая его отдельные domain roots. Зависимости не означают, что в
  архив автоматически включаются другие паки.
- **Воспроизводимость:** одинаковые payloads и одинаковый корневой
  manifest дают одинаковый архив в рамках одной версии codec.
  `exported_at` — явное время операции экспорта (UTC ISO 8601), задаваемое
  один раз вызывающим слоем; codec не добавляет текущее время ни в JSON,
  ни в ZIP metadata. Новая операция с другим `exported_at` закономерно
  имеет другой хеш архива. Writer фиксирует ZIP metadata, сортирует пути
  и детерминированно сериализует JSON; порядок массивов сохраняется.
  `source.content_hash` optional: в версии 1 writer его не формирует,
  reader не использует его как разрешение записи или token negotiation. Это не хеш
  архива, содержащего само поле; алгоритм дедупликации — отдельное
  расширение формата.
- **Уровни экспорта:** `registry` → manifest + `skeleton/world.json`;
  `skeleton` → + `skeleton/*` + `library/`; `full` → + `pack/`.
  `full` на мире без запечённого pack — явная ошибка уровня.
- **Архивный layout по UID (согласовано 2026-10-12):** папка пака —
  `pack_uid`, имя body-файла — `template_uid.json`; `pack_name`,
  `system_name` и `local_uid` остаются метаданными, не компонентами пути.
  Одноимённые паки и члены с разными UID не конфликтуют и не переименовываются.
  Авторский FS-layout `{domain_root}/{pack_name}/{system_name}.json`
  сохраняется; его name/formula-gates не применяются к архивам копий.
  `source_file` — диагностическое происхождение, не адрес body внутри
  архива; может отсутствовать в архивном member. UID не вычисляется
  из имён при чтении конверта.
- **`library/` subtree сохраняет разделение доменов** (`template-pack-layout`):
  тела членов лежат внутри папки своего пака; плоские body-секции §4 для
  pack-owned тел в архиве **не дублируются** — секция `library_packs`
  разворачивается в subtree. Тело вне папки пака — ошибка структуры
  (аналог lone files).
  Один логический пак разных доменов несёт одинаковый полный manifest
  в каждой из своих domain-root/UID папок. Manifest объявляет весь состав;
  необходимы все объявленные domain roots и тела. Точный allowlist файлов
  выводится из проверенных manifests и фиксированного mapping
  `library_kind → domain_root`, не из произвольных entries ZIP.
  В этом domain layout пак без членов отвергается явно: корень домена
  определяется объявленным составом, а не угадывается по имени.
  Domain roots v1: `building_templates`, `structures_templates`,
  `relief_templates`, `race_templates`, `perk_templates`.
  Manifest сохраняет provenance, creation_kind, defaults и дополнительные
  метаданные без потери; тела — JSON objects без нормализации/remap codec.
  Формулы UID, доступ/владение и доменная валидность проверяются в 4d
  общей политикой библиотек. Одна body UID не может принадлежать двум
  пакетам; pack-owned тела не дублируются в плоских body-секциях.
- **Строгость входа:** неизвестные файлы, битый zip, отсутствующий или
  невалидный manifest — reject до разбора секций. Секция ↔ path — явная
  таблица, не вывод из имени файла.
  Пути — относительные POSIX-пути внутри архива: абсолютные пути,
  `..`, обратные слеши, дубликаты entries и symlink entries отвергаются.
  Необязательные ZIP directory entries допускаются только для родителей
  разрешённых файлов; неизвестная пустая папка не расширяет allowlist.
  Ошибка структуры не должна приводить к частичной записи в SQL или
  pack-каталог. Проверка структуры предшествует доменному resolver;
  UID/владение/тела затем проверяются существующим import pipeline.
- **World archive несёт только world-owned manifests** (§4.1); engine
  library-пак экспортируется тем же контейнером с `kind:"library_pack"`,
  корень = domain layout (`pack.manifest.json` + member-файлы).
  Корневой `bundle.manifest.json` обязателен и для library-пака;
  его `sections` пуст, `skeleton/` и `pack/` отсутствуют, тела лежат по
  `{domain_root}/{pack_uid}/{template_uid}.json` (без `library/`).
  Сокращённый layout без domain root допустим только для отдельного
  upload API, явно привязанного к домену (`template-pack-layout`);
  универсальный `.wpack` такого внешнего контекста не требует.
- **UID при импорте архива — carry / attach / mint** (решение
  2026-10-09). Три операции над идентичностью, не смешиваются: **carry**
  — uid тянется из источника без изменений (повторный импорт того же
  объекта = тот же uid); **attach** — uid перевычисляется по центральной
  формуле §2 при смене владельца (новый `pack_uid`, member
  `template_uid` от нового владельца, `source_*` фиксирует исходные);
  **mint** — новый uid по uid_map ремапа мира. По артефактам:
  при default copy целого мира `world_uid` и entity uids — mint;
  world-owned `pack_uid` / `template_uid` членов — attach
  (владелец сменился ⇒ идентичность новая,
  исходный в provenance); refs в телах и world-side refs переписываются
  по общей карте всех переносимых world-owned членов; зависимости между
  переносимыми паками также следуют карте pack UID. Ссылки на UID вне
  карты сохраняются. Правило §2 «чужие паки не трогаются» относится к
  операции над одним паком; copy целого мира переносит все его паки;
  pin-набор template-членов по UID переписывается по той же uid_map;
  `pack/` subtree — uid-поля `manifest.json`/`locations_index.json` и
  имена `locations/l.{uid}.*` переписываются по тому же uid_map, тела
  блобов verbatim (хеши тел валидны, `content_hash` манифеста
  пересчитывается), `terrain_pack_path` сбрасывается на pack_root
  импортированного мира. Для первичного переноса `kind:"library_pack"`
  без коллизий — carry: UID пака и членов из архива сохраняются в engine scope.
  Повторный импорт не разрешает silent update: коллизии проходят общую policy §0.3.
  REPLACE сохраняет identity выбранной цели; COPY получает новую identity
  и remap через общий planner. Attach/mint выполняет application pipeline,
  не codec; instantiate/publish следуют §2.
  Условие verbatim для `pack/` при copy требует проверки wire-форматов
  zst-payloads на шаге C-6: если remapped UID хранятся внутри блобов,
  потребуется переупаковка и пересчёт их хешей. До этой проверки
  побайтное сохранение блобов при copy не считается доказанным.
- **Legacy:** flat-JSON bundle остаётся допустимым входом импорта
  (transitional read, карта старых/новых UID — §4 legacy-этап); запись —
  только архив.

## 5. Разрешение ссылок и fallback

Движок получает только UID из ссылки, находит тело и единственного пак-владельца
в каталоге, проверяет доступность (пак — default либо `owner_world_uid` равен
миру) и применимость шаблона к генератору.
Зависимости требуют явного инстанцирования в мир; транзитивного
автоинстанцирования нет. Циклы зависимостей обходятся с visited-set; проверка
не создаёт инстансов.

Отсутствует настройка/значение → доменный default. Разрешимая явная ссылка →
конкретный указанный шаблон. Неизвестный UID, недоступный миру владелец или
missing dependency → соответствующий default + warning log; сохранённая ссылка
остаётся исходной. Нельзя подменять её произвольным пользовательским кандидатом.
«Default» — существующий доменный контракт, без новых литералов в движке:
домены с подстановкой используют свой POJO-default; relief — R21
unresolved-политику (пустые candidates / недоступный UID → `reject_unresolved`,
подстановка другого шаблона запрещена).
Это runtime-контур §0: WarningError через доменный sink + доменное
решение — fallback там, где контракт домена его объявляет (исходная
ссылка сохраняется), отказ для полностью невалидного; на контуре
валидации/импорта ошибочное значение — всегда ошибка (§0), fallback не
применяется.

Ref-поле различает три состояния (уточнение 2026-10-09):

- **uid** — явная ссылка на член библиотеки; единственный владелец
  находится через каталог принадлежности (§2).
- **default** — явный флаг «доменный default»: выбор POJO-контракта
  `canonical_defaults()` домена — детерминированный fallback без
  библиотеки. Это сохраняемое значение, отличимое от неявного fallback:
  потребители дефолта перечислимы в диагностике, при удалении/изменении
  POJO-контракта их список известен. Флаг допустим только на ref-полях,
  для которых домен декларирует default-слой; wire-форма маркера — по
  spec домена.
- **пусто / битое** — неявное состояние (`fallback`): обрабатывается по
  правилу выше — runtime WarningError + доменное решение; validation /
  импорт — ошибка.

Уточнение 2026-10-15 — граница снапшота (missing body): член каталога
без тела, с невалидным телом или с висячей declared-ссылкой исключается
на read-границе (`TemplateSnapshotLoader`) с одной диагностикой через
`report_issues` (sink `jsonValidation/resolve`) — планировка видит
замкнутый граф. Runtime не подставляет произвольного кандидата: домен с
объявленным default-слоем применяет свой POJO-default, без него
(relief, R21) — reject. Не pack-домены (race/perk) политику не наследуют.

Этот режим касается template refs; правила REF-W остальных реестров не меняются.

Будущий режим мастера использует те же диагностические причины, но выдаёт
конкретную ошибку вместо warning/default. Реализация режима мастера вне scope.

### 5.1 Default-слой structures: POJO; override отложен

**Актуализация пользователем 2026-10-13:** manifest-defined fallback пака
оставлен расширением для [отдельного ТЗ](tz_library_contextual_fallback.md).
Описанная ниже прежняя цепочка `world → pack → POJO` сохранена как история
предложения и не является действующим требованием реализации. Автоматически
вводить world override, pack defaults в SQL и выбор первого пака нельзя.
Дефолты POJO и дефолтные библиотеки движка остаются базовым контрактом.
Наличие подходящего члена в паке не гарантирует покрытия всех случаев:
расширению нужны правила выбора контекста, пригодности и дальнейшего
доменного fallback/отказа. 4d/L-5 от реализации расширения не зависят.

Домен `structure_templates` получает default-слой для fallback-ветки §5
(unknown UID / owner unavailable / missing dependency / member без body /
пустой ref / явный `default`-маркер). До этого решения домен контракта не
объявлял — исход был отказ (`GenerationError` в planner/area assembler).

**База — POJO.** `StructureTemplate.canonical_defaults()` — валидное тело с
**объявленными комнатами**, не пустая оболочка: один уровень `z_offset=0`
с одной обязательной комнатой. Strict-поля комнаты/уровня (`room_id`,
`display_name`, `room_type`, `is_public`/`is_forbidden`/`required`, `size`)
объявляются canonical-константами в модуле POJO (прецедент —
`WorldRoomTypeRegistry._CANONICAL_ENTRIES`): `room_type` — ключ из
canonical `WorldRoomTypeRegistry` (`common_hall`), `size` — preset
`RoomSize` (без литеральных диапазонов), `purpose` — лист `house`,
`entry_point` объявлен. Все остальные поля — Field-defaults моделей
(`RoomDef`/`LevelDef`/`StructureTemplate`: высоты, двери, `attach_wall`,
`passage_type`…). `system_name` — детерминированный UUID из центрального
`ids` (model A). Это доменный POJO-контракт fallback-тела: без
SQL-строки, без pack-членства, без FS; тело проходит те же валидаторы, что
любой шаблон (`validate_room_ids`, `RoomDef._conditional_fields`).

**Прежнее предложение, отложено:** `world → pack → POJO`, первый найденный:

1. **Мир** — `worlds.structure_defaults.default_template_uid` (POJO
   `WorldStructureDefaults`, `canonical_defaults()` = пусто). Это
   template ref: разрешается через эффективный каталог мира по §1.1
   (членство + доступность); сам ref **не** проходит fallback — битый
   override = обычная диагностика §5 с причиной и переход к следующему
   уровню, подстановка другого кандидата запрещена. Пишется как scoped
   world-column (см. `world-scoped-column-write.md`).
2. **Пак** — `defaults.structure_templates` манифеста (§4) пака, входящего
   в membership мира. Приоритет внутри уровня: world-owned паки выше
   default-паков; при нескольких объявлениях в одном ярусе — детерминированный
   выбор sort by `pack_uid` + одна warning-запись (причина
   `default_conflict`, перечень pack UID). Объявление пака вне membership
   не участвует. Объявление хранится в SQL-каталоге паков вместе с
   членством (export/bundle/instantiate переносят его; remap §2
   переписывает `local_uid` не требуется — он локален для пака).
3. **POJO** — `StructureTemplate.canonical_defaults()`.

Выбранный default попадает в `selected_default` диагностики как
`{source}:{uid}` (`world:` / `pack:` / `pojo:`); событие одно, на границе
resolve (§7). Сохранённая ссылка не переписывается ни на одном уровне.

Не меняется: relief остаётся на R21 (reject, без default-слоя тел),
building/plot применяют собственные POJO-defaults параметров; их стандартные
шаблоны — members объявленных default-библиотек по A0. Отложенный contextual
override не делает чужой пак доступным и не меняет trusted default status.

## 6. Canonical attach и жизненный цикл

`world_wire_overlay` остаётся чистым merge исходных wire-полей перед resolver.
`global_fill_missing` загружает/валидирует весь явно объявленный default-источник,
затем атомарно добавляет отсутствующие UID и membership; существующие тела и
`source_file`, включая override default UID, не заменяются. Ручной update —
отдельная явная политика, владение при этом неизменно.

Все публичные global read-пути обеспечивают доступность defaults перед чтением;
это не меняет world ownership/pick-policy. Runtime hydrate мира использует
эффективный каталог §1 и не обходит его через прямой FS-loader или общий SQL list.
FS root: env → repo-relative fallback, без зависимости от cwd.

Полнота проверяется по canonical UID и membership, не по непустой таблице.
Удалённый default восстанавливается при следующей проверке; новые default UID
подключаются после проверки источника. Положительный бессрочный кеш полноты
не используется; допускается кеш провалидированного источника с инвалидированием
при изменении manifest/файлов, но наличие строк проверяется заново.
Canonical attach — единственная мутация read-only default-паков: engine может
добавлять отсутствующих членов, но только insert-missing, никогда replace
существующей строки.
Конкурентные attach сериализуются в контексте БД/библиотеки; SQL-conflict не
заменяет существующую строку. Ошибка записи откатывает весь attach; ошибка до
записи не оставляет строк. В чужой транзакции adapter использует существующий
transaction/savepoint-контракт, не делает скрытый commit или вложенный BEGIN.

Стартовый default-**пак** structures — объявленный `base` (каталог
кандидатов); default-**тело** для fallback одной ссылки — POJO
`StructureTemplate.canonical_defaults()`. Override world → pack из прежнего
§5.1 отложен в отдельное расширение, не часть текущего lifecycle.
Стандартные plot/building templates хранятся как canonical members
объявленных default-библиотек ([A0 §3–4](tz_domain_template_libraries.md)).
Canonical source задаёт стандартные тела; POJO задаёт defaults параметров;
SQL хранит подготовленные записи. Старое исключение 2026-10-09 «plots вне
SQL/pack membership» отменено 2026-10-14. Явный выбор — обычный template_uid,
без специального default/drawing_key selector. У relief объявленный
список default-паков пуст (решение 2026-10-08): `smoke_003` и любые FS-паки
остаются пользовательскими и доступны миру только через явное инстанцирование;
доменный default relief — существующие POJO-контракты (`canonical_defaults`
policy, registry, скаляры), тел шаблонов в defaults нет. Массового
сканирования пользовательского FS-контента нет ни в одном домене.

## 7. Логирование

Единственный фасад — `app.core.loggingConfig`, правила L1–L8
[tz_logging](./tz_logging.md). Использовать существующие доменные эмиттеры:
settlement `packingLog`, relief `relief_warning`, policy resolve — существующий
`jsonValidation/resolve`. При необходимости расширяется их типизированный
контракт событий, без новых параллельных log-функций/handlers/форматтеров.

Причины: unknown template, owner pack unavailable to world, missing dependency,
body missing, default applied, default conflict (§5.1). Диагностика несёт world UID, generator/domain, requested template
UID, owner/dependency pack UID (если известны), reference path, причину и выбранный
default. Одно событие эмитируется один раз на границе resolve; callers его не
дублируют. Штатный facade направляет запись в доменный JSON sink, generation
scope копирует её в существующий transcript. Warning не теряется из-за нового
logger вне allowlist. Кеши не подавляют необходимые предупреждения другого мира.

## 8. Проверяемые инварианты

- Пак вне default-spec не автоимпортируется; SQL одного мира не протекает в другой.
- Правка/удаление engine user-библиотеки не меняет инстансы миров (snapshot);
  правка world-инстанса видна только его миру; copy/instantiate/publish remap
  детерминирован — внутренние refs переписаны на новые UID, внешние — нет.
- Явное инстанцирование всего пака делает его подходящие шаблоны доступными
  генераторам мира.
- UID стабилен при повторном импорте; локальные имена разных владельцев не сталкиваются.
- Один владелец, template-only refs и явные зависимости сохраняются при round-trip.
- Повторное инстанцирование не перезаписывает локальные правки тел без явного
  подтверждения пользователя; preview перечисляет затрагиваемых членов.
- Член, удалённый в источнике и используемый миром (pinned ∪ referenced),
  удерживается в инстансе при повторном инстанцировании с явным статусом
  «удержан по использованию»; неиспользуемый удаляется.
- Missing ref/dependency → default + одно warning через штатный sink, исходный ref сохранён.
- Canonical attach сохраняет user override, атомарен, выдерживает конкурентный вызов,
  rollback/retry, частичную библиотеку и восстановление удалённого default.
- Cwd/env-root не меняют владельца/UID; FS-fallback не маскирует отсутствующий SQL attach.
