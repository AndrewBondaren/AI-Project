## 0. Зачем

Мир должен меняться после создания: механики (Politics, Economy, Construction,
War, natural processes, действия игрока) порождают структурные изменения —
новая дорога, разрушенное здание, деградировавший район. Этот документ
фиксирует контракт нижнего API для таких изменений: **как мутация проходит
от решения механики до состояния мира**, без привязки к конкретной механике.

Генератор отвечает за структуру мира: он знает, как корректно создать и
изменить принадлежащую ему структуру. Ему говорят «создать дорогу» — он не
выясняет, хватило ли городу денег и кто издал указ. Его вопрос: **можно ли
структурно сделать изменение и как корректно встроить его в существующий
мир**. Почему произошёл `DELETE district` — экономика, война, пожар, приказ —
генератору знать необязательно.

**Не путать:** «generator CRUD» — продуктовое имя контракта. Реализация —
**mutation layer** (единственная точка фиксации); генераторы остаются pure,
persist — у persist-делегатов (`layer-boundaries`).

---

## 1. Термины

- **Чертёж (blueprint)** — всё, что мир знает о себе на уровне сущностей и
  состояний: topology (`named_locations`, `connection_edges`, `transitions`,
  `connection_nodes`, …) + state-объекты (`location_states`, `cell_states`,
  feature-объекты). Единая семантическая правда мира.
- **Проекция (materialization)** — физическое представление чертежа:
  `map_cells`, zst-кадры, bake. Derived-данные, перевыводимы из чертежа.
- **Мутация (mutation)** — запись изменения в чертёж. Единственный способ
  изменить мир после создания.
- **Scope / footprint** — область влияния мутации: набор entity uid +
  геометрические bounds затронутых клеток. Обязательное поле мутации.
- **Журнал (journal)** — persisted история мутаций. Существует для отката
  и экспорта; **не** участвует в вычислении текущего состояния.
- **Mutation layer** — единственная точка фиксации изменений в store.
- **Derived write** — запись проекции генерацией/materialize
  (перевыводимо из base + текущего чертежа). Не мутация.
- **Dirty scope** — область проекции, инвалидированная мутацией чертежа;
  перевыводится materialize.

## 2. Базовая модель состояния

```text
state = base(seed + authored) + applied_mutations
```

| | **Base** | **Mutation** |
|---|---|---|
| Происхождение | `origin=authored` (JSON-импорт мастера), `origin=generated` (seed-генерация) | `origin=runtime` |
| Свойство | воспроизводимо: импорт детерминирован, генерация — из `world_seed` | невоспроизводимо: результат механик, seed не выдаст |
| uid | uuid5 — перевычислим (DET-1) | uuid4 — живёт только в instance |
| Журнал | не пишется — base и есть точка отсчёта | обязателен |
| Откат | нет «патча ноль»; сброс = новый instance из pack | rollbackable |

**Дискриминатор base/mutation уже существует** — `origin ∈ {authored,
generated, runtime}` и сплит uid-схем в DET-1. Модель мутаций обобщает это
решение на весь store, новой оси не вводит.

**Генезис — не мутация.** Журнал начинается после границы base. Rollback
никогда не пересекает genesis по определению: «отменить создание мира» —
не rollback, а создание нового instance.

### 2.1 Чертёж не знает автора

Topology-строка, созданная импортом, seed-генерацией или runtime-механикой,
для materialize — один и тот же вход. `origin` — provenance-тег, не ветка
логики. Authored-чертёж и runtime-изменённый чертёж структурно не различаются;
LOD не создаёт «чертёж второго сорта».

**Следствие — схема topology = поверхность мутаций.** Механика выражает
только то, что чертёж умеет хранить. «Дорога построена на 73%» — не topology;
`edge under_construction, progress=0.73` — topology. Каждый новый тип
изменения начинается с вопроса «в чём это выражено на чертеже», а не
«какие клетки поменять».

## 3. Один процесс записи

**Инвариант:** клетки пишет только materialization; мутации пишут только
чертёж. Второго пути записи в проекцию нет — иначе расхождение неизбежно.

```text
Intent / Decision (механика, действие игрока, инструмент мастера)
    ↓
DAG-патч — intent, потребитель объектов: ссылки на uid, поля;
           не знает про журнал, клетки, footprint
    ↓
Mutation layer — единственная точка фиксации:
    resolve объектов → footprint (entity set + cell bounds)
    before-image / inverse
    валидация инвариантов (≥1 main_entrance, связность, стороны перехода…)
    typed mutation → journal
    write-through в store (rows + state) через persist-делегатов
    ↓
dirty scopes → re-materialize(scope) → cells
```

- Ни один путь не пишет состояние мира мимо mutation layer: ни repo.execute
  из ноды, ни debug-route, ни инструмент мастера.
- Persist-сервисы (`MapCellService`, `ConnectionPersistService`,
  `SettlementPersistService`) — **write-делегаты внутри** mutation layer,
  не альтернативный путь.
- Генератор — источник знания «как структурно встроить»: его вызывает
  mutation layer для вычисления дельты чертежа; пишет только mutation layer.

**Гранулярность журнала = commit-пакет**, не sub-op: ход может породить N
intent'ов — пишется одна запись с объединённым scope и одной причиной.
Откат — по записи, не по половине действия.

## 4. Мутация = правка чертежа в любом регионе

Мутация в развёрнутый и неразвёрнутый регион — **один и тот же процесс**:
правка чертежа → dirty scope → проекция перевыводится. Разницы нет:

| Регион | Что происходит |
|---|---|
| Не развёрнут (lazy) | мутация пишется в чертёж; materialize позже прочитает уже актуальное состояние — отдельная «дельта проекции» не нужна |
| Развёрнут | те же записи в чертёж + footprint становится dirty scope → re-materialize |

### 4.1 Правила границы lazy

1. **Materialize всегда читает текущую topology** — включая journaled
   topology-мутации. Дорога, построенная механикой в far-зоне до развёртки,
   материализуется сразу «построенной».
2. **Cell-level мутация не может целиться в неразвёрнутый регион** —
   клеток нет. «Кратер в far-зоне» обязан существовать как объект чертежа
   (feature/событие); materialize отрендерит его при развёртке.
   Симметрично: entity-мутация неразвёрнутого региона валидна — это
   topology-дельта.

### 4.2 Два вида мутаций по цели

| Вид | Цель | Пример |
|---|---|---|
| **Entity mutation** | адресуемая сущность (transition, node, building, edge) | сломать дверь: transition → `breach`/inactive → re-materialize проёма |
| **Feature/region** | blueprint-объект с явными bounds | воронка от взрыва: terrain feature + `Transition(breach)` если соединила пространства |

Сырой «region patch» в клетки не существует: excavation — это feature
чертежа (`patch_bounds` как параметры объекта), а не особая запись в
`map_cells`. `TerrainPatchGeneratorService` переформулируется как
«feature в чертеже + re-materialize» (Todo SM-T7).

**Инвариант связки:** мутация, меняющая связность, обязана отразиться
в topology. Пролом в стене — не «клетки стали пустыми», а `Transition(breach,
origin=runtime)`; pathfinding и LLM-нарратив читают transitions, не клетки.

## 5. Доменные команды, не сырой CRUD

Контракт наружу — доменные структурные операции, внутри = валидация +
каскады + CRUD-примитивы хранения. Сырой `update` позволяет caller'у
сконструировать невалидное состояние.

```text
build_road_segment / degrade_road / remove_road
demolish_building / rebuild / degrade_district
create_transition (breach, excavation success…) / seal / destroy
excavate / collapse / flood
```

Нейтральность к направлению: город растёт, стагнирует, деградирует,
становится руинами — мутации не «development». Разрушенный город — тот
же объект, прошедший трансформацию, где сохраняется причинная идентичность;
не обязательно новая сущность `Ruins`.

**Каскады — часть контракта.** `remove_road` отвечает не только «можно ли»,
но и «что с `transitions`/`connection_nodes` на ребре и с материализованными
кадрами». Политика каскадов фиксируется на доменную операцию (Todo SM-T8).

## 6. LOD и мутации

LOD — другой resolution **тех же механик**, не альтернативные законы мира.
«Далеко от игрока разрешаем бесплатно построить дорогу» — запрещено;
«ту же механику можно посчитать дешевле» — разрешено:

```text
near: конкретные рабочие, материалы, действия, время
far:  workforce × productivity × elapsed × resources → progress
```

**LOD — свойство (процесс, область проявления, время), не сущности.**
Город B далеко строит дорогу к городу A с игроком: source-процесс —
LOW LOD (агрегированные ресурсы/бюджет), строительный фронт у игрока —
HIGH LOD (недостроенная дорога, рабочие, материалы). При уходе игрока —
обратная агрегация.

**Следствия:**

1. У каждой механики — **fold/unfold-функции** (aggregated state ↔
   detailed state) и **единая валюта прогресса**, иначе на шве зон разрыв
   («агрегированная часть построилась быстрее детальной»). Та же проблема,
   что LS-T5 (unfold NPC) — общее требование к механикам.
2. Игрок не видит «трава → тик → готовая дорога»: при входе фронта в
   detailed scope — локальная materialize промежуточного состояния
   (`under_construction`, полу-собранные сегменты).

Зоны near/medium/far и батч-агрегация — [`tz_lazy_simulation.md`](./tz_lazy_simulation.md).

## 7. Журнал и откат

Журнал — первоклассный механизм с тремя потребителями:

| Потребитель | Как использует |
|---|---|
| Текущее состояние | **не использует** — store пишется актуальным состоянием, read-path без реплея |
| Rollback | inverse / scoped re-fold |
| Экспорт | pack + journal — компактнее дампа клеток; реимпорт = один прогон на границе |

**Требования к мутации:** footprint (entity set + bounds), упорядоченность
(патчи не коммутируют), inverse или before-image своего scope.

**Откат:**
- суффикс журнала → применить inverse в обратном порядке;
- выборочный (из середины) → инвалидировать scope патча и пересчитать его
  как base + оставшиеся патчи этого scope. «Пересчёт из базы» существует,
  но bounded — scope патча, не весь мир;
- политика журнала при откате (обрезать суффикс vs писать компенсирующий
  патч) — выбрать один раз (Todo SM-T4).

**Typed mutations:** единая обёртка (mutation_id, scope, origin, причина/
инициатор, ссылка на `world_history`, payload, before-image); `kind`
определяет требования. Structural-подмножество — footprint + каскады;
**simulation state** (`cell_states`, декременты `remaining_ticks`) —
write-through без журнала: текущее условие, не история. Один механизм
записи, политика журнала — по типу.

## 8. Требования к инфраструктуре чертежа

1. **Bounds на каждой materializable-сущности.** Re-materialize работает
   по scope — каждый объект, рендерящийся в клетки, знает свой footprint:
   transition — bounds проёма, здание — AABB, edge — полоса.
2. **Детерминированный re-derive на entity-гранулярности.**
   `rng = f(world_seed, entity_uid)`, никогда от позиции в цикле генерации.
   Пересчёт одного объекта воспроизводим: та же улица, те же соседи, швы
   сходятся. Фундамент — детерминированные uid (DET-1,
   `app/application/worldData/ids/`).
3. **Чертёж выражает всё, что меняется.** Обломки, подпалины,
   полуразрушенная стена — выразимы как feature/state-объекты, иначе эффект
   не переживёт re-derive. Клетки не содержат правды, которой нет в чертеже.

## 9. Экспорт

Два разных режима, не сливать:

- **Checkpoint-экспорт** — instance как есть: чертёж + журнал (или сложенное
  состояние). Реимпорт — мир «продолжаемый с этого места».
- **Clean pack** — база без runtime-истории, для раздачи/редактирования
  мастером; `origin='runtime'` отфильтровывается или промоутится
  в `authored` («включить случившееся в канон»).

Открытый вопрос промоции uid при checkpoint→base (uuid4 → uuid5 и ссылки,
или origin остаётся маркером происхождения) — Todo SM-T5.

## 10. Сводная схема

```text
Politics / Economy / Construction / War / Natural / Player
        ↓
     Mechanics  (законы мира)
        ↓
       LOD      (resolution тех же механик; по области проявления)
        ↓
   DAG-патч     (intent, потребитель объектов)
        ↓
  Mutation layer (единственный commit: footprint, валидация, journal,
                  write-through через persist-делегатов)
        ↓
    Чертёж      (topology + state; authored|generated|runtime)
        ↓  dirty scopes
  Materialization (единственный писатель клеток; читает всегда
                   текущий чертёж)
```
