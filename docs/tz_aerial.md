# ТЗ: Воздушный слой (aerial) — сцены и объекты над поверхностью

**Статус:** seed (семантика утверждена 2026-10-19; impl не начат)  
**Зеркальный домен:** [`tz_terrain_hydrology.md`](./tz_terrain_hydrology.md) § Подводный мир — тот же класс «слой за пределами суши», только над `surface_z` вместо объёма под `z_sea`.

## Назначение

Воздушный слой — домен объектов **выше** `surface_z`: парящие острова, воздушные города, дирижабли/доки, построенные воздушные магистрали. Как и подводный мир — игровая сцена на существующих примитивах, не новый слой мира.

## Концептуальная модель

### Вертикальная модель мира (v1)

| Слой | Что существует |
|---|---|
| `z < surface_z` | solid колонка до `z_min` (`run_column_fill`); cave/underground — carved void |
| `z = surface_z` | surface-клетка: terrain + roles + локации |
| `z > surface_z` | **только z-стеки структур** (этажи зданий). Атмосферных клеток v1 нет — воздух = implicit void, не данные |

**Ключевое отличие от воды:** у океана есть `z_sea` — единый reference-уровень (зеркало) и дно как surface. У воздуха такого уровня нет: объект парит на произвольном z, «верхней границы» нет (см. A1).

### Воздушные объекты — локации, не клетки

| Кейс | Модель |
|---|---|
| Парящий остров (масса) | `location_complex` / `geographic` subtype `floating_island`; твёрдая масса — открытый вопрос A2 (structure-колонка vs terrain-объём) |
| Воздушный город с жителями | `settlement` subtype `aerial_city` (parallel `underwater_city` / `underground_city`) с `is_inhabited` |
| Дирижабль / причал | `structure_type="air_dock"` — уже предполагается узлом `air_route` (см. [`tz_structure_connections.md`](./tz_structure_connections.md) §8) |
| Разбившийся корабль / захваченный левиафан | structure на aerial z или на surface — обычный `location_complex` |

Размещение — declare-якорь мастера (как подводные локации v1); autoresolve aerial placement — v2.

### Поддержка и гравитация (отличие от подводного домена)

Дно океана самонесущее — под ним solid колонка. Воздушный объект **не имеет физической опоры**: нужна семантика anchor.

- v1: anchor — **metadata** (declare-якорь + тип привязки: магия / техника / полёт), не физика.
- Collapse / physics / ballistics — **runtime engine**, не генератор и не этот домен.

### Воздушные связи

| Тип | Что | Статус |
|---|---|---|
| `air_route` | абстрактное мировое ребро, без физических клеток | есть |
| Построенная воздушная магистраль | отдельный `system_connection_type` (напр. `skyway`) — bridge-структура между aerial-объектами или aerial↔surface | открыт; аналог `undersea_tunnel` из подводного домена |
| Вертикальный переход aerial↔surface | staircase / elevator / `portal` / `air_dock` | типы есть; привязка к aerial-объекту — v2 |

### Толща воздуха (граница v1/v2)

- v1: «летать сквозь клетки воздуха» нельзя — aerial-клеток не существует; перемещение по `air_route` = travel между узлами графа.
- v2: если нужен свободный лётный объём — тот же класс решения, что водный столб (`z_floor` + water-column cells): **volumetric non-solid layer**. Единый механизм «объёмных сред» (вода/воздух) vs раздельные — открытый вопрос A4.

## Инварианты

1. Aerial-объект — **локация/структура**, не terrain key; «небо» не красится в `system_terrain`.
2. Климат/погода — per-cell 2D (climate домен); собственный exposure-профиль для aerial-объекта — v2, не дублировать climate field.
3. `air_route` остаётся абстрактным ребром; физические воздушные связи — новые типы, не перегрузка существующего.
4. Нет физики/гравитации в генераторе — anchor это семантика, не симуляция.
5. Мутация aerial-объектов — через общую модель мутаций (patch / worldEdit), как и любой объект мира.

## Антипаттерны

- Aerial-клетки над каждой колонкой в v1 — пустота не нужна как данные (расход хранения).
- `floating_island` как terrain в `terrain_registry` — это локация/масса, не класс покрытия.
- Z-стек структуры как «голые» мировые клетки в небе без локации-владельца.
- Перегружать `air_route` физическими клетками (у него нет контакта — как у `sea_route`).
