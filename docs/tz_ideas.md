## Продуктовая рамка

**Две аудитории:**

| Роль | UX | Движок |
|---|---|---|
| **Игрок** | Загрузить пресет мира → интерактивно создать/выбрать персонажа → играть (чат) | Невидим: sim, validation, DAG, N+1 |
| **Мастер** | JSON import, редактор (будущий), debug, баланс, выпуск пресетов | Полный доступ к реестрам и orchestration |

**Принцип мира:** не сухая таблица и не LLM-хаос, а **творческий живой мир** на базе **simulation + validation first**. LLM — propose (события, сюжет, prose); движок — commit.

**Уникальность платформы (ниша):** geometric procedural substrate (terrain / settlement / structure) + validation-first LLM GM + пресеты миров. Аналогов с полной комбинацией в open source нет; отдельные слои — см. референсы выше.

## ID-1 — Три слоя правды (Facts → Beliefs → Presentation)

**Status:** `open` | **Priority:** P1 | **Layer:** narrative

### Проблема

Есть canonical state (БД, геометрия) и LLM narration. Нет явного слоя **социальной неопределённости**: NPC могут ошибаться, сплетничать, лгать — без мутации фактов.

### Модель

| Слой | Владелец | Пример |
|---|---|---|
| **Facts** | Движок (БД) | Город осаждён; игрок в таверне |
| **Beliefs** | NPC / location aggregate | Трактирщик *думает*, что войск вдвое больше |
| **Presentation** | LLM (narrator) | Prose для игрока из perception + beliefs источника |

```
Facts (engine) → Beliefs (deterministic patches) → Perception filter → Presentation (LLM)
```

### Связь с существующим

- [tz_perception.md](./tz_perception.md) — фильтр **геометрии**; beliefs — фильтр **социальной информации**.
- AI RPG Engine: *presentation channels that can lie*.

### Открыто

- Схема хранения beliefs на NPC (`npc_beliefs` JSON? отдельная таблица?)
- Decay / confidence на belief
- Кто может писать beliefs: только rumor engine + direct observation, не свободный LLM

## ID-2 — Rumor engine (детерминированное распространение слухов)

**Status:** `open` | **Priority:** P1 | **Layer:** narrative

### Принцип

Слух — **структурированное событие**, искажаемое правилами при распространении. LLM только **формулирует** речь NPC, не создаёт факт войны.

```
world_history (fact)
    → rumor_engine (distance, zone noise, faction bias, distortion)
    → belief patches на NPC / location
    → LLM: "ты слышишь, что..."
```

### Параметры искажения (черновик)

| Фактор | Эффект |
|---|---|
| Hops (число передач) | Размытие чисел, имён |
| Zone `noise` / `stability` | Скорость и искажение (см. environment в AI RPG Engine) |
| Faction alignment | Bias toward/against источник |

### Не делать

- LLM-generated rumors без anchor в `world_history` или system event

## ID-3 — Witness graph (кто что видел / слышал)

**Status:** `open` | **Priority:** P0 | **Layer:** narrative

### Принцип

NPC не «знают» off-screen события без цепочки наблюдения. Закрывает классический провал AI-RPG.

### Модель (черновик)

```sql
event_witnesses (
    event_id,           -- FK → world_history или event log
    entity_uid,         -- NPC или player
    observation_quality -- direct | hearsay | rumor
)
```

### Потребители

- Essential NPC background LLM ([tz_lazy_simulation.md](./tz_lazy_simulation.md) § per-event): контекст только по witness-path
- Belief updates (ID-1, ID-2)
- Perception-adjacent: кто был в сцене при событии

### Референс

Project Lunar: witnessed-by filter.

## ID-4 — Scene notebook (volatile state сцены)

**Status:** `open` | **Priority:** P0 | **Layer:** engine

### Проблема

Бой, таймеры, активные эффекты, позиции «прямо сейчас» не должны засорять canonical БД каждым ходом.

### Модель

| Хранилище | Содержимое | TTL |
|---|---|---|
| **Canonical** | `world_history`, `location_states`, `map_cells` | Постоянно |
| **Scene notebook** | Активные эффекты, combat round, временные флаги | Сессия / сцена; сжатие в канон по событию |

### Жизненный цикл

```
Старт сцены / боя → notebook init
Каждый turn → LLM tool / node обновляет notebook (validated)
Конец боя / смена локации → merge релевантного в canonical или discard
```

### Референс

NarrativeEngine-P: Update Scene Notebook; Project Lunar: volatile working memory.

### Связь

- Отдельно от `shared_context` в engine — целевое: typed `SceneContext` ([tz_engine_node_context.md](./tz_engine_node_context.md))

## ID-5 — Plot economy (plot-lock, один активный крючок)

**Status:** `open` | **Priority:** P1 | **Layer:** narrative

### Принцип

Творческий сюжет без хаоса «каждый ход новый квест». Движок **авторизует** активные hooks; LLM предлагает в рамках слота.

| Слот | Лимит |
|---|---|
| **Macro arc** | 1 на кампанию / мир |
| **Micro hook** | 1 активный на игрока |
| Остальное | Очередь или seed pool с cooldown |

### Референс

Project Lunar: PlotGenerator + plot-lock + cooldown.

### TaskType (уже в enum)

`GENERATE_QUEST_RELATED_EVENT`, `GENERATE_LOCAL_EVENT`, `GENERATE_WORLD_EVENT` — wiring в DAG отложен; plot economy — gate **до** LLM event nodes.

```json
  "engine_min": "0.2.0",
  "validation_schema": "0.1",
  "smoke": {
    "start_location_uid": "...",
    "test_character_template": "..."

  "fallback_narration": {
    "scene_blocked": "...",
    "validation_failed": "..."
  }
}
```

### Smoke gate (перед публикацией пресета)

1. `JsonValidationFacade` — bundle OK  
2. Import transaction  
3. Create session + test character  
4. N turns (intent → scene path) — no fatal in engine log

## ID-13 — Event Graph Hash (lazy disclosure сюжетного контекста)

**Status:** `open` | **Priority:** P1 | **Layer:** narrative / engine  
**Происхождение:** инженерное решение автора проекта (с самого начала); prior art в LLM-RPG **не исследовалось** — см. § «Происхождение идеи» ниже.

### Происхождение идеи

Идея возникла **до** survey чужих LLM-проектов: закрыть вопрос «как дать модели длинный сюжет без dump всей `world_history` и без дрейфа». Паттерн (ссылка + краткое описание → дозагрузка) в инженерии старый (event log, content-addressing); **протокол expand в той же engine session** для сюжетного графа — самостоятельная формулировка под этот движок.

**Не цель:** claims на оригинальность в ML; цель — зафиксировать контракт до impl.

### Предусловия (инварианты)

1. **Событие уже в движке.** Узел графа ссылается только на запись, которая **существует** в canonical store (`world_history` и связанный state). Нет записи → нет узла, нет expand. LLM не создаёт «события из головы» для transport-слоя — это вымысел → **невалидно** (propose → validate → persist — отдельный pipeline, не expand).
2. **Событие ≠ лор.** ID-13 — transport **сюжетных событий** (что случилось, с кем, от чего следует). **Лор** (энциклопедия мира, flavor text, glossary) — **другая сущность**, другой канал контекста. Сравнение ID-13 с lore-RAG / `multi_lore_lookup` **не применимо**: разные домены, не конкурирующие алгоритмы.

### Проблема

Передавать LLM полную историю событий (`world_history`, квесты, последствия) — дорого по токенам и шумно. Обрезать «последние N» — теряется причинно-следственная цепочка сюжета.

### Идея (компромисс)

**Сюжетный граф событий** в контексте LLM — в **компактном** виде: узлы = content-hash, рёбра = parent links + participants. Детальное описание события **не** в initial payload; движок отдаёт по **запросу уточнения** в той же conversation/session.

```
Initial context:     compact graph (hashes + titles + parent refs + participants)
LLM needs detail:    expand_request(event_hash) → engine injects full event record
Same session:        messages живы — как repair loop в LLMExecutionEngine
```

### Compact node (wire shape, черновик)

Каждый узел в JSON-графе сюжета:

| Поле | Тип | Назначение |
|---|---|---|
| `hash` | string | Идентификатор события (content-addressed или stable surrogate) |
| `title` | string | Подробный **заголовок** события (display-oriented, для ориентации LLM) |
| `parents` | string[] | 1–3 хэша родительских событий (причинная цепочка / ветвление сюжета) |
| `participants` | object[] | Ссылки на участников: `{ "kind": "npc"\|"player"\|"location"\|"faction", "uid": "..." }` |

```json
{
  "story_event_graph": {
    "anchor": "a3f2…",
    "nodes": [
      {
        "hash": "a3f2…",
        "title": "Осада Stone Ford: первая неделя, провиант на исходе",
        "parents": ["91bc…", "c004…"],
        "participants": [
          { "kind": "location", "uid": "loc_stone_ford" },
          { "kind": "faction", "uid": "fac_northvale" }
        ]
      }
    ]
  }
}
```

**Лимиты (v1):** `parents.length ≤ 3`; participants — по контракту ноды (cap TBD).

### Expanded node (on demand)

По `expand_request` движок возвращает полную запись, связанную с canonical storage:

| Поле | Источник |
|---|---|
| `hash` | тот же ключ |
| `system_event_type` / `display_event_type` | `world_history` / N+1 registry |
| `system_description` / `display_description` | полное описание |
| `system_world_date` / `display_world_date` | время в мире |
| `location_uid` | привязка |
| `effects_summary` | опционально: агрегат последствий (location_states, terrain patch uid) |

LLM **не** придумывает детали — только читает expand из движка.

### Протокол в engine session

1. **Gatherer-нода** (pre_llm): строит `story_event_graph` — подграф вокруг anchor (текущая сцена, active quest, последние k hops по parents).
2. **LLM-нода** (event/plot/narration): получает compact graph в `context_data`.
3. **Expand tool / contract field:** LLM запрашивает `event_hash` из **whitelist** (хэши из выданного графа или разрешённых результатов поиска ID-15). Для NPC граф и expand ограничены его знаниями; наличие события в canonical store само по себе не даёт доступа к объективным деталям.
4. **Engine** (в той же `messages` conversation): append expand payload → LLM продолжает turn.
5. **Validator:** reject expand на неизвестный hash; reject если LLM цитирует детали без prior expand (опционально, v2).

Аналогия: repair loop — тот же session, дозагрузка контекста по запросу.

### Связь с существующим

| Сущность | Роль |
|---|---|
| `world_history` ([tz_locations.md](./tz_locations.md)) | Canonical store; hash = fingerprint canonical JSON row (или `id` + content hash) |
| `npc_llm_triggers` ([tz_lazy_simulation.md](./tz_lazy_simulation.md)) | Триггер по `event_type`; graph — **контекст** для LLM, не замена EventBus |
| ID-3 Witness graph | participants + witness edges могут влиять на subset узлов в подграфе |
| ID-5 Plot economy | `anchor` узла графа = активный macro/micro hook |
| [tz_engine_flow.md](./tz_engine_flow.md) | Expand в фазе `llm`, до commit patches |

### Выигрыш

| Метрика | Эффект |
|---|---|
| Токены | Initial context O(узлы подграфа), не O(вся история мира) |
| Качество | LLM видит **структуру** сюжета (parents) без простыни текста |
| Консистентность | Детали только из expand; hash = audit trail |
| Творчество | LLM выбирает, какие ветки «раскрыть» для narration / нового события |

### Открыто (Todo EV-*)

| ID | Вопрос |
|---|---|
| EV-1 | Hash: content-addressed (canonical JSON → sha256) vs surrogate `world_history.id` |
| EV-2 | Алгоритм выбора подграфа (BFS от anchor? max depth? plot-lock root?) |
| EV-3 | Expand: tool call vs dedicated repair-style user message |
| EV-4 | Кэш expand в `state.node_results` на pass (не re-fetch DB) |
| EV-5 | Новые события от LLM: propose → validate → persist → **новый hash** в ответе |
| EV-6 | Отдельное ТЗ `tz_events.md` при старте impl |

### Не путать

- **Expand и retrieval — разные операции:** ID-13 описывает граф и раскрытие события по hash. Семантический поиск событий может дополнять его через ID-15; lore search остаётся отдельным доменом.
- **Не замена simulation:** compact graph — только **transport** канонических событий в LLM; факты остаются в `world_history` / patches.
- **Не смешивать с лором:** поиск/подгрузка lore — отдельная задача (если понадобится), вне scope ID-13.

### Комментарий: LLM ergonomics (review агента, 2026-07)

Оценка с точки зрения **как модель потребляет контекст** — не вердикт по новизне.

**Почему compact graph удобен модели**

| Элемент | Эффект для LLM |
|---|---|
| `title` | Семантический вес события без простыни; модель решает, нужен ли expand |
| `parents` (1–3) | Причинная структура как outline, не как narrative memory |
| `participants` (uid) | Якоря к сущностям мира; меньше дрейфа имён |
| expand по **whitelist** | Запросы осмысленные; без whitelist — «любопытство» и раздувание контекста |

**Почему идея хорошо стыкуется с simulation-first**

Движок держит факты; модель не обязана «помнить» прошлое в prose — она **запрашивает** канон. Для narration: игрок спрашивает про старое событие → expand одного узла → ответ из фактов, не из додумывания.

**Рекомендации по expanded payload**

- Плотный **структурированный** expand: даты, тип, `effects_summary` (states, accessibility, terrain patch uid).
- Минимум литературной прозы в expand — prose оставить **Narrator**-ноде (ID-9); иначе expand дублирует narration и снова жрёт токены.
- `title` в compact node пишет **движок при persist**, не LLM при создании события — иначе заголовки расплывчатые.

**Риски (на impl)**

| Риск | Митигация |
|---|---|
| Цитирование деталей без expand | Validator v2: детали past events только из expanded nodes |
| Плоский подграф («последние K») | BFS от anchor / plot-lock root, не только timestamp |
| Expand-spam за turn | Лимит 1–3 expand на turn |
| Путаница с RAG | Явный контракт: граф только из БД, детерминированная сборка |

**Первый smoke (когда дойдёт очередь)**

## ID-14 — Производная классификация леса и поля

**Статус: open. Источник: внешнее обсуждение. НЕ ПРОВЕРЕНО:** предложение не валидировано кодом, тестами или архитектурным ревью; не считать реализованным или утверждённым контрактом.

## ID-15 — Поиск событий памяти NPC через API по инициативе LLM

**Status:** `open` | **Priority:** P1 | **Layer:** narrative / engine  
**Происхождение:** обсуждение с автором проекта, 2026-10-11. Концепция для будущей реализации; названия API и формат запросов ниже — черновик, не существующий контракт.

### Принцип

**LLM решает, что ей нужно вспомнить; движок определяет, какие сведения доступны NPC, выполняет поиск и раскрывает их.** Поиск сохраняется как API-вызов внутри LLM session. Не требуется автоматически выполнять retrieval перед каждым обращением к модели или передавать ей всю память для самостоятельного перебора.

ID-13 отвечает за адресацию и lazy disclosure событий по hash. Эта идея дополняет его retrieval-механизмом, когда идентификатор нужного события неизвестен. RAG может использовать такой поиск при подготовке контекста, но не определяет факты мира или знания персонажа.

### Два этапа доступа

| Операция (черновик) | Назначение | Результат |
|---|---|---|
| `search_events(query, filters, limit)` | Найти релевантные события по текстовому запросу и допустимым фильтрам | Ограниченный список: hash, доступный NPC заголовок и краткое содержание |
| `get_event(hash)` / expand ID-13 | Раскрыть выбранное событие | Подробности в пределах знаний NPC |

1. LLM получает текущую сцену, состояние NPC и компактный контекст памяти.
2. При необходимости инициирует `search_events`, например по упоминанию мельницы.
3. Движок ограничивает область поиска памятью текущего NPC и ранжирует доступные записи.
4. LLM получает компактные результаты и при необходимости запрашивает подробности по hash.
5. Движок проверяет доступ повторно и возвращает разрешённое представление события в ту же conversation/session.
6. LLM продолжает диалог на основании полученных воспоминаний.

Если разрешённый hash уже известен из контекста, LLM может сразу запросить раскрытие без поискового этапа. Выданные поиском разрешённые ссылки дополняют whitelist ID-13; найденный hash не означает безусловный доступ ко всей canonical-записи.

### Retrieval в движке

- Поиск может использовать заголовки и текст воспоминаний: полнотекстовый индекс, embeddings или гибридный вариант. Конкретный алгоритм пока не утверждён.
- Поисковая обработка выполняется без дополнительного генеративного LLM-вызова. Embedding-модель при выбранном семантическом поиске — отдельный вычислительный компонент; возможна небольшая локальная модель.
- Embeddings и поисковые индексы — производные данные, которые можно пересчитать. Их не включать в hash события.
- Hash связывает хранилище событий, ссылки памяти NPC и retrieval. Он идентифицирует запись, но сам не кодирует знания и не предоставляет права доступа.
- Лимиты результатов и раскрытий задаются контрактом движка; весь архив памяти не выгружается в контекст.

### Знания и субъективное восприятие

Контекст NPC задаёт движок: LLM не выбирает чужую память через параметр запроса. Ограничение по знаниям применяется до ранжирования; заголовки, краткие результаты, participants, parent links и expanded payload также не должны раскрывать неизвестные персонажу сведения.

Поиск для NPC должен опираться на доступное ему описание восприятия или сообщения, а не на скрытые объективные детали события. Иначе даже ранжирование может выдать неизвестный факт.

Пример: canonical-событие содержит убийство купца игроком; стражник видел лишь фигуру в капюшоне, другой NPC услышал рассказ стражника. Запрос по одному событию возвращает сведения соответствующего наблюдателя. Позднее узнавание игрока обновляет знания стражника, сохраняя объективную историю события.

### Связи и открытые вопросы

- ID-1 — Facts / Beliefs / Presentation; ID-2 — слухи; ID-3 — цепочки наблюдений; ID-13 — компактный граф и expand.
- Строгие JSON/DSL-контракты определяют запрос и ответ API; обработка, поиск и проверка доступа остаются частью движка.
- Требует решения: память ссылается на canonical-событие с отдельным представлением знаний либо на самостоятельную запись восприятия, связанную с canonical-событием. Не считать этот выбор уже утверждённым.
- При реализации определить схему индекса, фильтры, лимиты API и обновление индекса при изменении знаний NPC.

## ID-16 — Источники магической энергии (существо / мир)

**Status:** `open` | **Priority:** TBD | **Layer:** engine

### Принцип

Автор мира через N+1 регистр определяет **источники магической энергии** для описания мира (L0). Рассматриваются два независимых источника:

- **Существо** — магическая энергия возникает у существа.
- **Мир** — магическая энергия возникает в мире.

Поддерживаются четыре комбинации: только существо; только мир; оба источника; ни одного (магическая энергия отсутствует).

```json
{
  "energy_sources": {
    "creature": true,
    "world": true
  }
}
```

Два независимых признака предпочтительнее отдельного enum четырёх комбинаций; конкретный контракт регистра и наследования между описаниями L0 уточнить при проектировании.

### Границы идеи

Здесь фиксируется **только происхождение энергии**. Накопление, передача, расходование, доступность магии и заклинания **не входят** в этот пункт и не должны выводиться из выбора источника автоматически. Лорное объяснение задаётся автором мира, а механические типы источников остаются понятными движку.

## ID-17 — Подключаемые системы причин и универсальная механика облика

**Status:** `open` | **Priority:** TBD | **Layer:** engine  
**Происхождение:** идея автора проекта, 2026-10-11. Концепция; не реализованный и не утверждённый контракт.

### Принцип

Авторский мир может включать или отключать отдельные механические системы (например, магическую энергию или трансформацию облика). Наличие системы и её конфигурация — разные решения: отсутствие магии не равнозначно обязательной системе с нулевой маной. Конкретный способ подключения, зависимости и возможность переключения в ходе существования мира пока не определены.

**Причину изменения отделить от механики облика.** Причины могут принадлежать магии, технологиям, морали, поклонению божествам и другим N+1 конфигурируемым системам. Универсальная механика облика принимает валидированное намерение изменения и применяет его к представлению существа, не реализуя логику конкретной причины.

### Типы изменений

- **Структурные:** добавить, удалить, заменить или изменить часть тела; учитывать существующую модель анатомии и ограничения существа.
- **Описательные:** цвет, свечение, визуальные признаки и описания без обязательного изменения анатомии.
- **Постоянные и временные:** изменение может сохраняться в каноническом состоянии либо быть активным только при условии/действии; временное не обязательно структурное, а постоянное не обязательно структурное.
- **Комбинированные:** один источник может вызывать одновременно структурные и описательные изменения. Игровые способности и эффекты не возникают автоматически из текста описания: их рассчитывают соответствующие механики.

### Примеры

| Причина / условие | Изменение | Характер |
|---|---|---|
| Мораль, проклятие, благословение, биотехнология | Появились рога | Может быть постоянным структурным изменением; разные причины — один результат облика |
| Применение заклинания (cast) | Светятся глаза | Временное описательное изменение на время каста |
| Прицеливание киборга (aim) | Загорается кибернетический глаз | Временное описательное изменение на время действия |
| Магическая трансформация | Крылья и изменение цвета глаз | Комбинированное изменение; полёт — отдельная механика |

### Инварианты и интеграции

1. Одинаковое изменение облика может иметь разные источники. Происхождение сохранять отдельно от результирующего облика для последующей отмены, диагностики и правил мира.
2. Причина определяет условия возникновения, действия и прекращения эффекта; механика облика не должна содержать специальные ветки для магии, технологий, морали или божеств.
3. Не перезаписывать базовую анатомию и постоянное описание при каждом временном эффекте: активные эффекты учитывать при формировании наблюдаемого состояния.
4. Perception получает доступные наблюдателю признаки, а не автоматически знание об их происхождении. Светящиеся глаза не означают улучшенное зрение без отдельной механики.
5. Изменения проходят через контракты и валидацию движка; LLM описывает подтверждённый результат, не создаёт канонические изменения произвольным текстом.
6. Использовать существующую модель частей тела/рас и N+1 регистры; не дублировать анатомию под каждую причину.

### Открытые вопросы

- Формат контракта эффекта, условия активации/деактивации и хранение постоянных и временных эффектов.
- Приоритеты, совмещение, отмена и конфликт нескольких эффектов на одну часть тела.
- Граница между системой облика и более общим механизмом эффектов/изменения состояния.
- Зависимости подключаемых систем и правила их включения/отключения для уже существующего мира.

## ID-18 — Универсальная архитектура статусов и эффектов персонажа

**Status:** `open` | **Priority:** TBD | **Layer:** character state / effects  
**Происхождение:** идея автора проекта, 2026-10-12. Концепция, не реализованный контракт.

### Назначение и состояние

Универсальная система модификаций состояния персонажа без заранее зашитых RPG-статусов или таблиц сочетаний магии, технологий и других причин. Автор мира определяет N+1 свойства, лорные определения, параметры и формулы; LLM отвечает за семантическую интерпретацию, движок — за формальную проверку и расчёт.

Разделять:
- **Base state:** исходные данные персонажа, не перезаписываемые наложенными эффектами.
- **Active effects:** действующие модификации свойств, анатомии, облика, восприятия и иных параметров.
- **Effective state:** актуальное вычисленное состояние как результат наложения активных эффектов на базовое по правилам мира. Допускается производный кэш с инвалидацией при изменении эффектов.

Завершение эффекта не требует обратной мутации базового состояния: актуальное состояние пересчитывается из оставшихся воздействий. Не утверждается, что абсолютно любое изменение персонажа обязательно является эффектом; граница уточняется отдельно.

### Экземпляр эффекта

Предусмотреть идентификатор, цель (персонаж, часть тела, свойство), изменяемые свойства/модификации, источник и событие возникновения, ссылки на лор и регистры авторского мира, зафиксированное семантическое описание конкретного воздействия, механические параметры (включая силу, если она предусмотрена автором), время создания и длительность.

Происхождение и механический результат разделены. Семантика конкретного эффекта формируется LLM при создании с учётом подробного авторского лора, например школы тьмы, и сохраняется, а не генерируется заново при каждом обращении.

**Длительность:**
- `permanent`: действует до успешного снятия; это не «невозможно снять».
- `temporary`: прекращается автоматически через N тиков либо при досрочном снятии.

Сила и длительность независимы. Завершённые эффекты не участвуют в расчёте, но происхождение и история их изменений могут сохраняться в событиях мира.

### Наложение и совмещение

Эффект накладывается поверх базового состояния, не заменяя автоматически другие эффекты. Несколько воздействий могут менять одно свойство; способ их механического совмещения и расчёта задаётся автором мира. Семантическое значение и применимость взаимодействий интерпретирует LLM по конкретному лору и свойствам объектов, без жёстко заданной в ядре матрицы RPG-типов.

### Проверки взаимодействия и снятия

1. **Семантическая проверка (LLM):** получить семантику существующего эффекта, ссылки на его лорное происхождение, свойства применяемого средства и релевантные факты мира. Определить, обосновано ли предполагаемое взаимодействие, и представить результат структурированно для последующей проверки. Высокие числовые характеристики сами по себе не делают бессмысленный способ действенным.
2. **Механическая проверка (движок):** при семантически обоснованном воздействии проверить контракт, условия, ресурсы и вычислить результат по формулам и параметрам автора мира.
3. **Применение:** только подтверждённый результат изменяет набор эффектов; после успешного снятия эффект перестаёт участвовать в вычислении актуального состояния. LLM описывает результат, не подменяя расчёт.

Игрок может пытаться совершить любое действие в рамках мира; отрицательная семантическая оценка предполагаемого результата не запрещает саму попытку и возможные другие последствия.

### Примеры

**Проклятие слепоты:** базовое зрение персонажа сохранено. Проклятие школы тьмы с силой 100 и длительностью `permanent` подавляет зрение в effective state. Биоинженер предлагает средство снятия: LLM проверяет его смысловую применимость по природе проклятия и свойствам средства; затем движок рассчитывает результат. При условной формуле сравнения сил воздействие 80 не снимает эффект 100. При успешном снятии актуальное зрение пересчитывается.

**Гвоздь и проклятие:** высокий навык лечения не позволяет автоматически снять проклятие обычным гвоздём. Но если в лоре конкретного мира железо разрушает тёмные чары либо гвоздь является ритуальным инструментом, семантическая проверка может признать взаимодействие обоснованным, после чего выполняется механический расчёт.

**Биорога:** биотехнологический эффект добавляет рога в effective anatomy без перезаписи базовой. Проклятие может попытаться подавить или изменить их; применимость определяется семантикой эффектов и лором, результат — механическим расчётом. При снятии воздействий актуальная анатомия пересчитывается.

### Хранение и открытые вопросы

- Активные эффекты хранят текущее воздействие; история событий — происхождение, изменение и завершение. Не воспроизводить всю историю для каждого вычисления состояния.
- Уточнить универсальную адресацию свойств и частей тела, контракт модификаций и правила совмещения.
- Уточнить формат структурированного семантического результата, неопределённость лора и ссылки на использованные определения.
- Уточнить инвалидацию кэша и поведение при изменении авторского лора, на который ссылаются существующие эффекты.
- Согласовать с ID-17: прежнее допущение о постоянной мутации канонической анатомии не считать утверждённым; предлагаемая здесь модель сохраняет базовое состояние и вычисляет актуальное через эффекты.

**Связи:** ID-17 (причины и облик), ID-16 (источники магической энергии), [tz_perception.md](./tz_perception.md).

## ID-19 — Lore refs, статусы и свойства локаций

**Status:** `open` | **Priority:** TBD | **Layer:** world state / locations  
**Происхождение:** идея автора проекта, 2026-10-18. Концепция; схема и контракты не утверждены, наличие аналогичных полей в коде требует проверки.

### Назначение

Предусмотреть возможность связывать локацию с записями лора (`lore_refs`) и задавать действующие статусы и свойства локации либо отдельных доменов внутри неё. Лор объясняет происхождение и смысл явления, а механически значимое состояние хранится отдельно и проверяется миром.

Примеры:
- Проклятый лес: статус проклятия на локации, ссылка на объясняющую запись лора.
- Неувядаемая флора: свойство флоры **в пределах конкретной локации**, не меняющее глобально вид растений.

### Принципы (предложения, не утверждённый контракт)

- Не ограничиваться одним `status: enum`: у локации могут одновременно существовать несколько независимых состояний.
- Использовать расширяемые реестры мира для типов статусов и свойств (N+1), без жёстко зашитого перечня проклятий или особенностей.
- Различать `lore_refs` (ссылки на сведения мира), действующие `statuses` (состояния) и `properties` (характеристики). Названия полей предварительные.
- Свойство должно иметь область применения: сама локация, вложенная область либо конкретный домен/объекты внутри неё (например, флора). Не подменять локальным свойством глобальный шаблон вида.
- Механические последствия определяются соответствующими контрактами и проверками мира; LLM не создаёт эффект автоматически из художественного описания.
- Учитывать LOD: существование статуса или свойства не требует немедленной материализации всех объектов локации.

### Открытые вопросы

- Уже существующие поля и модели локаций, лора и эффектов: сначала проверить код, не дублировать контракт.
- Наследование статусов/свойств дочерними локациями и границы пространственного действия.
- Совмещение, приоритеты и конфликты нескольких свойств.
- Постоянные и временные статусы; происхождение, изменение и снятие через события мира.
- Соотношение с ID-18 (эффекты персонажа): переиспользование общего механизма эффектов либо отдельный слой локаций без дублирования логики.

## ID-20 — Контекстная история intent и адаптивный RAG технической Intent-ноды

**Status:** `open` | **Priority:** TBD | **Layer:** DAG / technical intent / context retrieval  
**Происхождение:** идея автора проекта, 2026-10-22. Концепция, не утверждённый контракт.

### Проблема

Один текст текущего сообщения не всегда определяет намерение: «иду в таверну „Когтистый вепрь“» содержит явную цель, а «иду со всеми» зависит от истории диалога, состава участников и актуальных договорённостей. Важны очередность посещений и действий, планы, согласия, отмены, изменения взаимодействий и результаты исполнения. Релевантность события не равна его актуальности.

### Предложение

1. Сохранять структурированную контекстную историю интерпретированных intent и связанных событий/сообщений с привязкой к контексту локаций и доступности участникам. Не считать намерение совершённым действием; фактическое состояние мира остаётся авторитетным.
2. Техническая Intent-нода получает последние доступные события в компактном контексте. Не передавать всю историю на каждом ходе.
3. При необходимости LLM запрашивает поиск более ранних релевантных событий (RAG/retrieval) через существующий механизм валидации и повторного исполнения DAG. Поиск не обязателен для явно заданных действий и целей.
4. Валидатор может принудительно требовать retrieval по политике ноды, например при контекстно зависимом намерении и заявленной уверенности LLM ниже порога. Уверенность LLM — эвристика, не гарантия корректности; структурно валидный intent может быть семантически неверным.
5. Снапшоты — универсальный механизм состояния мира: путешествия во времени и альтернативные ветви, отладка, а также откат ошибок LLM. **Любой откат снапшота значим**, независимо от причины; движок не обязан и не может достоверно классифицировать её. Сам факт отката можно использовать как сигнал для более осторожной политики технической Intent-ноды: при дальнейшем исполнении заранее расширять контекст и ужесточать условия обязательного RAG. Не требовать от игрока объяснения отката и не расходовать отдельный LLM-вызов на выяснение причины. Режим retrieval не является функцией механизма снапшотов: это отдельная политика исполнения DAG.
6. Ограничивать циклы retrieval/repair: повторный запрос не должен бесконечно запускаться, если поиск уже выполнен, но неоднозначность осталась. Конкретные лимиты и режим выхода определить при проектировании.

### Границы и открытые вопросы

- Как хранить историю intent и связи с событиями, диалогами, планами, участниками и локациями; как учитывать доступность контекста после перемещения.
- Как определять актуальность, отмену и порядок намерений, не превращая семантическую историю в физическое состояние мира.
- Как выбирать последние события, порог уверенности, условия обязательного поиска и срок действия усиленного режима после любого отката снапшота, включая путешествие во времени и отладку.
- Как соотнести retrieval технической Intent-ноды с ID-15 (поиск памяти NPC): возможное переиспользование инфраструктуры, но разные области доступа и цели.
- Как обрабатывать события отменённой ветки после rollback: не считать их актуальной историей восстановленного мира.
- Не вводить заранее отдельный LLM-агент или обязательный векторный поиск для каждого действия; алгоритм retrieval (фильтры, полнотекстовый, embeddings, гибрид) выбрать позднее.

**Связи:** ID-13, ID-15, [tz_engine_flow.md](./tz_engine_flow.md), [tz_world_snapshot.md](./tz_world_snapshot.md).
